## 3D

2D is Ollin's default, and most sketches stay 2D. A sketch opts into 3D by setting a **camera**, and once a frame has one, the renderer adds a depth buffer and draws 3D geometry through the camera's view and projection. Set no camera and nothing changes, so the 2D path is untouched and pays nothing.

The 3D geometry is **point clouds** (tens of thousands to millions of points, each drawn as a camera-facing disc, sized in world units so perspective shrinks the far ones and the depth test hides the ones behind), **solid primitives** (box, sphere, cylinder, cone, torus, pyramid, helix, the regular polyhedra, a torus knot, a plane, and the parametric generators), filled meshes drawn through the same camera and depth test, **lit** by a directional/point/spot light model with materials, environments, and shadows, and **meshes loaded from file** (see [Meshes from file](#load)).

<a id="first"></a>
### A first 3D sketch

```swift
import Ollin

@main
final class Cloud: Sketch {
    override func draw() {
        background(.black)

        // Setting a camera makes the frame 3D. `orbiting` swings it around a target.
        camera(.orbiting(target: .zero, radius: 5, azimuth: time * 0.3, elevation: 0.5))

        // Build a cloud of world-space points and draw it.
        var cloud = PointCloud()
        for i in 0..<6000 {
            let a = Double(i) * 0.1, r = Double(i) / 6000 * 2
            cloud.add(Vector3(cos(a) * r, sin(Double(i) * 0.03), sin(a) * r),
                      color: Color(hue: r / 2, saturation: 0.8, brightness: 0.9),
                      size: 0.04)
        }
        drawPointCloud(cloud)
    }
}
```

The camera is **per-frame state**, like the geometry, so it resets each frame and you set it in `draw()`, which is exactly where you'd animate an orbit. A 2D sketch simply never calls `camera`.

<a id="camera"></a>
### The camera

A `Camera3D` is an eye looking at a target, plus how it flattens space onto the canvas (perspective or orthographic). The bare calls set one for the frame:

```swift
// Perspective: nearer is bigger. `fieldOfView` is the vertical angle in radians.
perspective(eye: Vector3(0, 2, 6), target: .zero, fieldOfView: .pi / 3)

// Orthographic: no foreshortening. `height` is the world units framed top-to-bottom.
ortho(eye: Vector3(0, 2, 6), target: .zero, height: 8)

// Or build a Camera3D and pass it, useful to keep and tweak.
camera(.orbiting(target: .zero, radius: 6, azimuth: a, elevation: 0.4))
```

`Camera3D` value-type factories:

- `Camera3D.perspective(eye:target:up:fieldOfView:near:far:)`
- `Camera3D.orthographic(eye:target:up:height:near:far:)`
- `Camera3D.orbiting(target:radius:azimuth:elevation:fieldOfView:near:far:)` places the eye on a sphere around the target, where `azimuth` turns around the up axis (0 looks down +z) and `elevation` tilts above the horizontal, both in radians. It's the easy way to spin a camera around a scene.
- `Camera3D.fromIntrinsics(_:near:far:)` is a **metric** camera built from a depth frame's pinhole `CameraIntrinsics` (an off-axis frustum matching the lens), at the origin looking down −z. It puts a point cloud, a depth feed, and any placed object in one space measured in meters. See [depth compositing](../3D/DepthCompositing.md#metric).

`near`/`far` are the clip distances (geometry outside them is cut away), and `up` defaults to `.unitY`.

<a id="clouds"></a>
### Point clouds

A `PointCloud` is a list of points, each with a world-space position, a color, and a splat diameter in **world units** (so perspective shrinks distant points). Build one up front for a fixed scan, or rebuild it every frame for a live feed, where a ~50k-point cloud rebuilt per frame is comfortable.

```swift
var cloud = PointCloud()
cloud.add(Vector3(x, y, z), color: .white, size: 0.05)   // one at a time
// …or in bulk:
let cloud2 = PointCloud(positions: pts, color: .cyan, size: 0.05)
let cloud3 = PointCloud(positions: pts, colors: cols, size: 0.05)   // per-point colors
drawPointCloud(cloud)
```

Splats composite in draw order and under the active [`blendMode`](../Drawing/Drawing.md#blendMode), so `blendMode(.add)` sums them as light, the glowing-cloud look. Sub-pixel splats fade by area (the same coverage `drawCircle` uses), so a dense cloud of tiny points doesn't flicker.

<a id="primitives"></a>
### Solid primitives

The built-in shapes are filled meshes, drawn through the same camera with depth testing. They cover the closed solids (box, rounded box, sphere, icosphere, cylinder, cone, capsule, torus, the Platonic solids, pyramid, helix, torus knot, plane) and the parametric and profile generators (supershape, superellipsoid, Möbius, Klein, extrude, lathe, tube). Each is centered at the model origin and sized in world units, so you place and orient it with the [3D transform stack](#transforms):

```swift
camera(.orbiting(target: .zero, radius: 8, azimuth: time * 0.2, elevation: 0.4))

withState {
    translate(-2, 0, 0)
    rotateY(time)
    drawBox(size: 1.5)              // a cube
}
drawSphere(radius: 1)              // at the origin
```

The closed solids, all on `Sketch`:

- `drawBox(size:)` / `drawBox(width:height:depth:)`, and `drawRoundedBox(size:radius:)` for filleted edges
- `drawSphere(radius:segments:rings:)` (a UV sphere) and `drawIcosphere(radius:subdivisions:)` (a geodesic sphere with evenly sized triangles and no pole pinching)
- `drawCylinder(radius:height:segments:caps:)`, `drawCone(radius:height:segments:)`, `drawCapsule(radius:height:)`
- `drawTorus(radius:tube:segments:sides:)` and `drawTorusKnot(p:q:radius:tube:…)`
- `drawPyramid(width:depth:height:)`, `drawHelix(radius:tube:turns:height:…)`, `drawPlane(width:depth:)`
- the Platonic solids: `drawTetrahedron(radius:)`, `drawOctahedron(radius:)`, `drawIcosahedron(radius:)`, `drawDodecahedron(radius:)`

And the parametric / profile generators (the [`3D/ShapeFactory`](../../Examples/3D/Geometry/ShapeFactory/) example):

- `drawSupershape(radius:m:n1:n2:n3:…)` is the Gielis superformula, where a few numbers sweep an enormous range of organic, star, and flower forms (good driven by `time`)
- `drawSuperellipsoid(radius:e1:e2:…)` is a sphere that morphs toward a box (`e → 0`) or octahedron (`e → 2`)
- `drawMobius(radius:width:…)` and `drawKlein(scale:…)` are the one-sided surfaces
- `drawExtrude(_ outline: [Vector2], depth:)` / `drawExtrude(_ shape: Shape, depth:)` push a flat 2D shape into 3D, paired with the `Profile` helpers (`Profile.rectangle`/`.ellipse`/`.triangle`/`.polygon`/`.star`)
- `drawLathe(_ silhouette: [Vector2], segments:)` revolves a side profile into a vase or bowl
- `drawTube(_ path: [Vector3], radius:sides:closed:)` sweeps a solid tube down any 3D curve

**A solid takes the current `fill` as its surface color** and is shaded by the [light & material model](#lights) below, and because lighting has an auto-lit default, a solid looks 3D out of the box with no lights to set up. The `fill`'s **alpha** sets opacity (so `fill(Color(white: 1, alpha: 0.5))` makes a translucent solid). Gradient paint isn't supported on the 3D path, so meshes take a solid color.

Under the hood each shape is a `Mesh` value type (positions, normals, a triangle-index list) built by a generator: `Mesh.box(…)`, `.sphere(…)`, `.supershape(…)`, `.extrude(…)`, and so on. **Build a mesh once and draw it every frame** with `drawMesh(_:)`, since the `draw*` calls build it each frame, which is fine for a cube and wasteful for a swept knot or a dense supershape:

```swift
let ball = Mesh.sphere(radius: 1, segments: 48, rings: 32)   // build once
// …each frame:
withState { fill(Color(hex: 0xF5A623)); translate(x, y, z); drawMesh(ball) }
```

You can also hand `drawMesh`/`Mesh(positions:normals:indices:)` your own arrays. Meshes need a camera (like point clouds) and ride the 3D transform stack, not the 2D affine.

A mesh can also carry **per-vertex colors** (`Mesh.colors`, matched to `positions` by index). They *multiply* the current `fill`, the same contract as a texture: with the default white fill the mesh shows its own colors untouched, and `fill` stays a whole-mesh tint. Paint any mesh procedurally with `colored(by:)` (a closure over each vertex's position and normal) or from a point cloud with `colored(from:)` (each vertex takes its nearest sample's color; a reconstructed scan keeps its capture colors this way, see [Surface reconstruction](../Generators/SurfaceReconstruction.md#colors)). A **loaded model brings its own**: glTF's `COLOR_0` and a PLY's per-vertex color both arrive as `colors`, so a vertex-painted export or a colored scan draws in its own colors against a white fill with nothing else to set up. [Subdividing](../Generators/SubdivisionSurfaces.md#result) a painted cage keeps them too. Lighting shades a vertex color exactly as it shades the fill; a wireframe ignores them.

```swift
let globe = Mesh.sphere(radius: 1).colored { p, _ in
    p.y > 0 ? .white : Color(hex: 0x2B6CB0)
}
```

<a id="load"></a>
### Meshes from file

Load a model from a file into a `Mesh` and draw it with `drawMesh`, the same depth-tested, lit path the built-in primitives use. Ollin reads three families:

- **`.obj`** (Wavefront): Ollin's own reader.
- **`.usdz` / `.usdc` / `.usda` / `.usd`**: Ollin's own USD reader, the same one behind [`loadScene`](Scenes.md), merged to one mesh with every part placed by its node transforms.
- **`.gltf` / `.glb`**: Ollin's own reader. glTF 2.0 is what most 3D tools export.
- **`.stl` / `.ply`**: through Apple's Model I/O.

```swift
final class LoadedModel: Sketch {
    var model: Mesh?
    override func setup() {
        model = loadMesh("/path/to/duck.usdz")?.normalized(scale: 3)
    }
    override func draw() {
        camera(.orbiting(radius: 7, azimuth: time * 0.3))
        if let model {
            // Default white fill shows the model's own material; set a fill to tint
            // it (or to color a model that carries no material of its own).
            withState { rotateY(time); drawMesh(model) }
        }
    }
}
```

A loaded model arrives in its author's own coordinates, at whatever scale it was saved (a CAD export might span thousands of units, a game asset fractions of one). **`normalized(scale:)`** recenters it on the origin and uniformly scales it so its longest dimension spans `scale` world units, a drop-in fit, the way the generators are already unit-sized. `bounds`, `center`, and `size` give you the raw extents if you'd rather place it yourself.

The loaders mirror the image and font ones: `loadMesh(path)` / `loadMesh(url)` on `Sketch`, or `Mesh(contentsOf:)`, `Mesh(path:)`, and `Mesh(resource:extension:in:)` for a bundled model (as ever, `in:` has no default, so pass `.module`). Each returns `nil` if the file can't be read.

**Its material, too.** A loaded model brings its own **base-color material**, meaning a base color and an optional texture, mapped through the file's UVs (see [Textured meshes](#textures)). Keep the default white `fill` so it shows true (the `fill` still tints it). A **glTF** reads `baseColorFactor` + `baseColorTexture` + `TEXCOORD_0`, an **OBJ** reads its `.mtl` (`Kd` diffuse color + `map_Kd` texture) and `vt`, a **USD** reads its bound preview surface (diffuse color or a texture from the package) and `primvars:st`, and an **STL/PLY** reads its Model I/O material and texture coordinates. A model with **no** material falls back to shading in your `fill`, so you pick the color. This is the **base color** only for now, and metallic/roughness and normal maps are the later PBR tier. `loadMesh` merges to one mesh, so a multi-material file wears its first material there; to keep every material, load the file as a scene instead ([`loadScene`](./Scenes.md), whose `drawScene` draws each material's slice with its own material).

A model you make yourself is your own work, free to ship. A 3D design tool like Spline exports glTF or USDZ directly, and downloaded sample models often carry non-permissive licenses, so check before bundling one. See the `3D/LoadedMesh` example (drop a `model.usdz`/`.glb`/`.gltf`/`.obj` beside it, or point `OLLIN_MESH` at one).

`loadMesh` deliberately merges: one file, one `Mesh`, placed by you. To keep a file's *structure* instead, the node tree with its names and transforms, plus the cameras and lights the scene was authored with, use [`loadScene`](./Scenes.md).

<a id="lights"></a>
### Lights & materials

A solid is shaded by a Blinn-Phong material whose surface color is the current `fill`. **With no lights set, Ollin applies a sensible default rig automatically**, so `fill(.red); drawSphere()` is a shaded red ball, not a flat circle, with zero setup. Add your own lights to take over the scene:

```swift
camera(.orbiting(target: .zero, radius: 8, elevation: 0.3))

ambientLight(Color(white: 0.15))                                   // flat fill so shadows aren't black
directionalLight(.white, direction: Vector3(-0.5, -0.8, -0.4))    // the sun (parallel rays)
pointLight(Color(hue: 0.5, saturation: 0.8, brightness: 1), at: Vector3(3, 2, 2))   // a bulb at a position
spotLight(Color(hue: 0.85, saturation: 0.7, brightness: 1),
          at: Vector3(0, 5, 0), direction: Vector3(0, -1, 0),
          angle: .pi / 5, penumbra: 0.5)                          // a cone aimed down

fill(.red)
specular(0.6)        // highlight strength (0 = matte, the default)
shininess(64)        // higher = tighter, sharper highlight
drawSphere(radius: 1)
```

The three light kinds:

- **`directionalLight(color, direction:)`** casts parallel rays from a direction (the sun). `direction` is the way the light *travels*, so `Vector3(0, -1, 0)` shines straight down.
- **`pointLight(color, at:)`** is an omnidirectional source at a world position.
- **`spotLight(color, at:direction:angle:penumbra:)`** is a point source narrowed to a cone aimed along `direction`, of full `angle`, with a `penumbra` soft edge (`0` hard … `1` very soft).

Each call takes an `intensity` too (default `1`). `ambientLight(_:)` is a flat term added to every surface, so set it alongside the directional lights and faces turned away aren't pure black. An ambient *alone* gives a flat, unshaded fill of the surface color. `specular(_:)` and `shininess(_:)` set the highlight, and `material(_:)` sets a whole reusable finish at once (matte, glossy, iridescent, …), covered in [Materials](#materials) below. All are drawing state saved by `withState`, so different solids can be matte or glossy in the same frame.

Each light also takes two optional refinements (passed to `directionalLight`/`pointLight`/`spotLight` or the `Light` factories). **`specular:`** tints a light's highlight separately from its diffuse color (default `nil` uses the light's color), so a light can throw a crisp white highlight over a warm key, or a bright rim. **`softness:`** (`0…1`) wraps the light a little past the terminator for a gentler shaded edge (a softbox versus a bare bulb), and the default `0` is hard Lambert shading. The curated [lighting presets](#lights) lean on both.

The convenience calls:

- **`lights()`** installs the default rig explicitly (the same one used automatically). It's handy to restore the default after using your own lights, or to make the intent visible.
- **`noLights()`** turns lighting off for the frame, so solids draw flat in their `fill` color, unlit. `ambientLight(.white)` is the other way to a flat, full-bright look.

#### Area lights

The three kinds above are *punctual*: an infinitesimal point of light. An **area light** is a glowing *surface*, the kind studio lighting uses. A surface has extent, so its highlight is a reflection of the shape itself, shading transitions are gradual, and brightness falls off with distance. Three shapes:

```swift
rectLight(Color(kelvin: 4200), at: Vector3(-3, 2, -2),      // a softbox panel
          direction: Vector3(0.6, -0.5, 0.6),               // the way it faces
          width: 3, height: 2, intensity: 6)
diskLight(.white, at: Vector3(3, 2, -1),                    // a round panel
          direction: Vector3(-0.6, -0.5, 0.4), radius: 1.2)
tubeLight(Color(hue: 0.87, saturation: 0.55, brightness: 1),   // a neon tube
          from: Vector3(-4, 0, 3), to: Vector3(4, 0, 3),
          radius: 0.06, intensity: 30)
```

- **`rectLight(color, at:direction:width:height:)`** is a flat rectangular panel (a softbox, a window) centered at `at`, facing along `direction` like a spot's axis, with an optional `up:` hint orienting its height axis.
- **`diskLight(color, at:direction:radius:)`** is a flat circular panel (a ring light's face, a recessed ceiling can).
- **`tubeLight(color, from:to:radius:)`** is a glowing cylinder between two points (a fluorescent or neon tube), emitting radially all around.

A few things work differently from the punctual kinds:

- **`color` × `intensity` is the surface's *radiance*** (how bright the glowing surface itself is), so a bigger panel casts more light into the scene, and brightness falls off with distance on its own. A thin tube subtends very little sky, so it needs a high intensity: a real neon is a very bright surface.
- **Panels light only the side they face.** Pass `twoSided: true` to a rect or disk to emit from both faces. A tube always emits all around.
- **`softness:` doesn't apply**: an area light's softness *is* its extent (make the panel bigger for softer shading). `specular:` still tints the highlight of the stylized finishes.
- **Panels cast shadows from their real size.** Under [`castShadows()`](#shadows) a rect or disk panel is a caster (after the punctual kinds in the caster order), and its penumbra comes from the panel's extent: a bigger softbox throws a softer shadow, sharp at contact and spreading with distance. A tube never casts (it glows in every direction, so there's no side to render a shadow from). The `3D/Lighting/AreaShadows` example breathes a panel's size to show the link.

Under the physically based material the response follows the GGX model, so low roughness reflects the panel's shape and high roughness spreads it out. The stylized materials take area light too: standard Blinn-Phong maps its `shininess` onto an equivalent roughness, toon quantizes the soft diffuse into its cel bands, and Gooch keys its tone ramp off the panel's direction. The lights themselves are invisible, like every `Light`; draw a matching emissive prop where the source itself belongs in frame (the `3D/Lighting/AreaLights` example does, and shows all three shapes over a glossy floor).

#### Light shaping: IES profiles and cookies

A plain point or spot light throws a featureless pool. A real fixture has a *shape* to its throw: a downlight pools a hot disc with a spill ring, a street lamp throws sideways "batwing" wings so the pole's foot isn't the bright spot, a wallwasher climbs a wall and leaves the room dark. Manufacturers measure that shape and publish it as an **IES file** (the LM-63 photometric format used across the lighting industry), and a light can wear one:

```swift
let downlight = IESProfile(resource: "downlight", in: .module)!   // parse once, in setup()

pointLight(.white, at: Vector3(0, 3, 0), profile: downlight)      // aims straight down
spotLight(.white, at: eye, direction: aim, profile: downlight)    // aims along the cone
```

- **`IESProfile`** parses a file from a `resource:in:`, a URL (`contentsOf:`), `Data`, or a `String`, and is plain data: parse once and keep it. Its intensities are **normalized so the brightest direction is 1**, so the light's `intensity` still sets overall brightness and the punctual no-distance-falloff model is unchanged. `profile.intensity(vertical:horizontal:)` samples it on the CPU (radians, `0` along the beam), for drawing polar diagrams or driving geometry.
- **The profile's 0° aims along the light's axis.** A spot uses its `direction`; a point light takes an `axis:` parameter (straight down by default, the fixture's hanging direction) and `roll:` spins an asymmetric profile around it. Directions outside the file's measured range are dark, as the fixture is, so a downlight file ending at 90° sends nothing upward; tilt the axis at a wall to wash it, the way a real wallwasher aims.
- The parser reads **Type C photometry** (the architectural standard; effectively every published file) across the LM-63 revisions, honoring the format's lateral-symmetry conventions. Type A/B files (automotive/floodlight aiming conventions) fail to parse with a clear message, as does any malformed file; parsing never crashes.

A spot can also project an image through its cone: a **cookie** (the stage term is *gobo*, the metal stencil slid in front of a theater light):

```swift
let gobo = LightCookie(loadImage("blinds.png")!)!    // wrap once, in setup()
spotLight(.white, at: eye, direction: aim, angle: 0.8,
          cookie: gobo, roll: time * 0.1)            // roll spins the projection
```

- **`LightCookie` wraps an `Image` once** (it resamples the pixels into its own fixed-size buffer at init, so build it in `setup()` and keep it). The image's edges land at the spot's **outer cone**: a wider cone projects the same picture larger. Color multiplies the light (black blocks, white passes, color tints like a gel), transparency composites over black, and the projection reads un-mirrored as seen from the light looking along its beam, like a slide in a projector.
- **`roll:` turns profile and cookie together**, the way rotating a real fixture in its yoke does.
- A GPU-backed image (a video frame, a Syphon feed) has no CPU pixels and fails to wrap; `snapshot()` it first. Cookies are spot-only; profiles apply to point and spot lights (a directional light has no position to shape from, and area panels shade by their own geometry).

Shaped lights keep their pattern everywhere the scene shows it: on every material, in the raymarched SDF fields, and in ray-traced reflections. The `3D/Lighting/LightShaping` example pools all three authored profiles and rocks a window gobo across the floor; its `.ies` files ride beside the sketch as bundled resources.

#### Lighting presets

For a good-looking scene without hand-placing lights, hand `lightingPreset(_:)` a ready-made rig:

```swift
lightingPreset(.goldenHour)     // one call relights the whole scene
```

The curated set, each an ambient plus a few lights tuned with color temperatures (`Color(kelvin:)`):

- **`.standard`** is a soft neutral ambient, a key, and a dimmer fill. It's the same rig solids get automatically, so reach for it when you just want the scene to look 3D.
- **`.threePoint`** is the film key, fill, and rim rig: a daylight key from the front-left, a cooler dimmer fill opening the shadows, and a rim light raking from behind for separation.
- **`.goldenHour`** is a warm low sun with a cool sky bounce, and long, warm shadows.
- **`.noir`** is a single hard, near-white key with the shadows crushed nearly to black. It pairs well with `castShadows()`.
- **`.studio`** is bright, soft, even daylight from several directions, low in contrast, so surfaces read clean.
- **`.moonlight`** is cool, dim, blue night light over a deep-blue ambient.

A preset is **per-frame** like the individual light calls (it replaces the auto-lit default), so call it in `draw()`. It's a plain value, so it's also how you extend the set, either building your own or tweaking a copy of a built-in:

```swift
var rig = LightingPreset.noir
rig.ambient = Color(white: 0.06)                       // lift the shadows a touch
rig.lights.append(.point(Color(kelvin: 8000), at: Vector3(2, 3, 1)))
lightingPreset(rig.intensified(by: 0.8))               // and dim the whole rig
```

`LightingPreset(ambient:lights:)` builds one from scratch, and `intensified(by:)` returns a copy with every light's intensity scaled. There's no registry to register with, since a preset is just a value you pass in.

Lighting is **per-frame**, so one setup shades every mesh drawn this frame (like the camera) and you place your lights once at the top of `draw()`. Per-mesh lighting state is a future refinement.

<a id="materials"></a>
### Materials

`material(_:)` gives a 3D shape its surface finish, the way it catches light. Pick one from the library and draw:

```swift
fill(.red)
material(.soapBubble)   // a rainbow sheen that shifts as the sphere turns
drawSphere(radius: 1)
```

The shape's **color** is its `fill`, set separately, so one material works in any color:

```swift
material(.clay)                       // a matte, earthy finish...
fill(.red);  drawSphere(radius: 1)    // ...on a red sphere
fill(.blue); drawSphere(radius: 1)    // ...and a blue one
```

#### The library

| Group | Materials |
|---|---|
| Matte to glossy | `.matte` · `.clay` · `.rubber` · `.plastic` · `.ceramic` · `.glossy` · `.polished` |
| Iridescent (view-angle rainbow) | `.iridescent` · `.soapBubble` · `.oilSlick` · `.beetle` |
| Sparkle (mirror flakes that flash) | `.glitter` (fine dust) · `.sequin` (chunky paillettes) |
| Glowing | `.velvet` (lit edges) · `.jade` · `.wax` (light through the surface) |
| Stylized | `.toon` (cel bands) · `.gooch` (warm-to-cool) |

`material(_:)` is drawing state saved by `withState`, so each shape can have its own material in the same frame.

#### Customizing

A `Material` is a plain value, so copy a built-in and change one thing, or build one from scratch:

```swift
var m = Material.glossy
m.iridescence = 0.4     // the glossy finish, plus a faint pearlescent sheen
material(m)

material(Material(shading: .toon, toonBands: 3, specular: 0.5, shininess: 64))
```

The pieces you can set:

- **shading** is `.standard` (smooth), `.toon` (cel bands), or `.gooch` (warm-to-cool).
- **specular** and **shininess** set the highlight's strength and how tight it is.
- **rim** is a glow around the silhouette.
- **subsurface** is light glowing through thin parts.
- **iridescence** is a rainbow that shifts as the shape or camera moves. Turn up
  **iridescenceFlow** and the sheen becomes a *soap film*: the color comes from a
  film-thickness field that drains downward (broad marbled patches on the body, fine
  stacked interference bands toward the bottom, darkening where the film thins) and
  swirls as you advance **iridescencePhase** (drive it with `time`, so exports
  reproduce; `iridescenceScale` sets how many interference orders the film spans,
  and `iridescenceFlowSize` the marbling's feature size, smaller = finer wisps).
  Compose it with [`.glass()`](#glass) for a real soap bubble; see
  [`Examples/3D/Materials/SoapBubble`](../../Examples/3D/Materials/SoapBubble).
- **sparkle** is tiny mirror flakes that flash as the view, shape, or light moves
  (glitter, metallic car paint, sequins). `sparkleSize` scales the flakes (`1` is a
  fine dust, sized to the camera's framing so it works at any scene scale, and bigger
  reads as sequin paillettes), `sparkleSharpness` sets how rare and hard the flashes
  are, and `sparkleColor` tints them (gold flakes over a dark red `fill` is car paint):

  ```swift
  var m = Material.glitter
  m.sparkleColor = Color(hue: 0.12, saturation: 0.75, brightness: 1.0)
  fill(Color(hue: 0.02, saturation: 0.8, brightness: 0.35))
  material(m)                // gold metal-flake over oxide red
  ```

To nudge just the highlight without rebuilding the material, call `specular(_:)` or `shininess(_:)` after `material(_:)`:

```swift
material(.glossy)
specular(0.4)           // the glossy finish, with a softer highlight
```

#### Physically based (metal and roughness)

For an energy-conserving, physically based finish, set `shading: .physicallyBased` and give it two numbers: **metallic** (`0` a dielectric like plastic or stone, `1` a metal like gold or steel) and **roughness** (`0` mirror-smooth, `1` fully matte). As with every material the surface color is the `fill`, so a metal's reflection is tinted by that color while a dielectric keeps a neutral highlight.

```swift
fill(Color(hue: 0.11, saturation: 0.6, brightness: 0.95))
material(.metal(roughness: 0.2))       // a lightly-brushed gold
drawSphere(radius: 1)

fill(.blue)
material(.dielectric(roughness: 0.6))  // a soft, matte blue plastic
drawSphere(radius: 1)
```

The shortcuts and a few named looks:

| Helper / built-in | What it is |
|---|---|
| `.metal(roughness:)` | a metal of any roughness (its reflection tinted by `fill`) |
| `.dielectric(roughness:)` | a non-metal (plastic, ceramic, stone, paint) |
| `.brushedMetal` · `.polishedMetal` | a satin and a near-mirror metal |
| `.smoothPlastic` · `.roughPlastic` | a clean and a matte dielectric |

Lit by the scene's lights alone, a smooth metal is mostly dark with a few bright hotspots, which is physically what a mirror with nothing to reflect does. The surroundings fill those darks in once you set an [environment](#environment) (image-based lighting).

<a id="glass"></a>
#### Glass (transmission and refraction)

Turn a physically based dielectric see-through with **transmission**: light passes through the surface instead of bouncing back, so the body shows whatever is behind it, tinted by the `fill` and frosted by `roughness`. The `.glass(...)` helper sets it up:

```swift
environment(.studio)                 // something to transmit
fill(.white)
material(.glass(thickness: 1.8))     // a solid clear body (a sphere of radius 0.9)
drawSphere(radius: 0.9)

material(.glass())                   // thickness 0: a thin wall (a pane, a bubble)
material(.frostedGlass)              // rough enough to blur what shows through
```

The knobs, all on `Material`:

| Knob | What it does |
|---|---|
| `transmission` | how much light passes through, `0` opaque … `1` clear glass |
| `ior` | how strongly the body bends the view (`1.33` water, `1.5` glass, `2.42` diamond) |
| `thickness` | `0` a thin wall that tints without bending; `> 0` a solid body (world units; a sphere's diameter is the natural value) |
| `attenuationColor` / `attenuationDistance` | what white light becomes after that distance inside a solid, so thick glass deepens toward bottle green |

Three things to know:

- **Transmission needs an [environment](#environment)** to have something to transmit; without one the material shades as a plain dielectric. On its own it refracts the environment (a solid ball shows the world flipped, the crystal-ball look).
- **`rayTracedReflections()` upgrades the view through the glass to the actual scene** on a ray-tracing GPU: objects behind a pane appear through it, a lens inverts the wall behind it, and a solid's absorption follows the real interior path. Same opt-in as the mirror upgrade, one switch for both.
- **Transmission is not `fill` alpha.** A translucent fill fades the whole surface out of the frame; transmission keeps the surface (and its reflections) and lets the *light* through, bent and tinted. Glass keeps its alpha at 1.

A couple of honest edges: glass still casts an opaque shadow, and glass seen *in a mirror* or through *other* glass reads as a shiny opaque ball (a traced hit doesn't re-enter transmission). See [`Examples/3D/Materials/Glass`](../../Examples/3D/Materials/Glass).

For a **soap bubble**, compose thin glass with the iridescence finish's soap-film mode (`iridescenceFlow`, [above](#materials)): the shell transmits, and a draining, swirling interference film marbles across it. See [`Examples/3D/Materials/SoapBubble`](../../Examples/3D/Materials/SoapBubble).

<a id="clearcoat-sheen"></a>
#### Clearcoat and sheen (layered finishes)

Two more lobes layer over the physically based base, each a real-world surface construction rather than a new material model.

**Clearcoat** is a thin polished lacquer over the base: car paint (a metallic body under a glassy film), piano lacquer, varnished wood. The base keeps its own roughness while the coat carries a second, sharper reflection, and the base dims slightly by exactly the light the film reflects away:

```swift
fill(Color(hue: 0.99, saturation: 0.8, brightness: 0.7))
material(.carPaint(roughness: 0.45))   // a satin red metal under a polished coat
drawSphere(radius: 1)

fill(Color(white: 0.05))
material(.lacquer)                     // piano black: a matte body, a glassy film
```

`clearcoat` (`0…1`) sets the film's intensity and `clearcoatRoughness` its own polish, independent of the base `roughness`. Layer `sparkle` on top of `.carPaint` for the metallic-flake version.

**Sheen** is fabric fuzz: stray fibers catch light at grazing angles, so the silhouette glows softly while the body stays matte, and the body dims to keep the energy honest. `sheen` (`0…1`) sets the strength, `sheenRoughness` how tight the rim band is, and `sheenColor` its tint; a tint away from the `fill` gives the two-tone shot-fabric look:

```swift
fill(Color(hue: 0.62, saturation: 0.65, brightness: 0.45))
material(.felt)                        // a dry, fuzzy blue

var velvet = Material.felt             // a deep red rimmed in orange
velvet.sheenColor = Color(hue: 0.07, saturation: 0.9, brightness: 0.95)
fill(Color(hue: 0.99, saturation: 0.9, brightness: 0.3))
material(velvet)
```

The presets: `.carPaint(roughness:)` and `.lacquer` for the coat, `.satin` and `.felt` for the sheen. Both lobes shade under plain lights, under area-light panels, and from an [environment](#environment); under `rayTracedReflections()` the coat's reflection upgrades to the traced scene along with the base's. One honest edge: a coated or sheened surface seen *in a mirror* shades there without its extra lobes (the same envelope as glass seen in glass). See [`Examples/3D/Materials/CoatAndCloth`](../../Examples/3D/Materials/CoatAndCloth).

<a id="subsurface-scattering"></a>
#### Subsurface scattering (skin, wax, marble)

Real subsurface scattering sends part of a surface's light *into* the body, where it spreads and re-emerges nearby: shadow edges soften, thin lit regions glow into the dark side, and the diffusion carries the material's color with it. It is what separates skin, wax, and marble from painted plastic, and it is distinct from the stylized `subsurface` finish, which fakes a back-glow and can still layer on top:

```swift
fill(Color(red: 0.92, green: 0.72, blue: 0.62))
material(.skin(radius: 0.5))     // radius in world units
drawSphere(radius: 2)

fill(Color(white: 0.88))
material(.marble(radius: 0.4))   // near-neutral stone
```

Three knobs on any `Material` drive it. `scattering` (`0…1`) is how much of the surface's light diffuses; `scatteringRadius` is how far light travels under the surface, **in world units**, the one scene-dependent number (a head-sized form wants roughly 1% of its width; too large reads as wax); `scatteringColor` shapes how far each channel travels relative to that radius. The default `(1, 0.37, 0.3)` lets red run farthest, the warm halo of skin; near-equal channels read as neutral stone, and a green-dominant color makes a jade whose *diffusion itself* is green:

```swift
var jade = Material.dielectric(roughness: 0.3)
jade.scattering = 0.8
jade.scatteringRadius = 0.5
jade.scatteringColor = Color(red: 0.35, green: 1.0, blue: 0.5)
```

With [`castShadows()`](#shadows) on, the same material also **transmits**: light striking the body's far side comes through wherever it is thin, an ear against the sun, a leaf, the wall of a wax candle. The caster's own depth is the thickness gauge (the distance between where the light entered the body and the surface being shaded is exactly how far it traveled inside), so it costs no new setup and no new knobs: what comes through falls out of `scatteringRadius` and `scatteringColor`. A body about a radius thick passes mostly red under the default falloff, the blood-red of a backlit hand; past a few radii nothing comes through. Only the shadow-casting light transmits (it is the one whose depth is known), it works under a directional, spot, or point caster, and an area panel does not transmit.

It rides any shading model (a scattering toon is legal) and needs no other setup: the presence of the material is the opt-in, like glass. Under the hood it is a screen-space diffusion, two small blur passes over the rendered frame masked to the scattering surfaces, so it costs nothing when unused and its result is deterministic (exports reproduce byte for byte). The envelope: it applies to solid and textured meshes on the main canvas; a mesh drawn into a render target and a raymarched SDF field keep their plain shading (each says so once in the console), and a matcap ignores materials entirely. Occlusion is honest: a scattering surface hidden behind something does not blur what hides it. Highlights diffuse along with the body (real wet skin does this a little), which carries one practical limit: a radius far past the guidance above, on a polished surface with a tight bright highlight, can print the blur's individual taps as a faint comb around that highlight. Keep the radius honest and it never shows. See [`Examples/3D/Materials/Subsurface`](../../Examples/3D/Materials/Subsurface).

#### Notes

A material needs lights to show (the auto-lit default counts), and under `noLights()` a surface draws flat in its `fill`. For true *metal* (tinted, mirror-like reflections) use the physically based finish above, which reflects the [environment](#environment) and, on a ray-tracing GPU, the [scene itself](#ray-traced-reflections); for *glass* (see-through, refracting) see [the section above](#glass). See [`Examples/3D/Materials/Materials`](../../Examples/3D/Materials/Materials), [`Examples/3D/Materials/PhysicalMaterials`](../../Examples/3D/Materials/PhysicalMaterials), and [`Examples/3D/Materials/Glass`](../../Examples/3D/Materials/Glass).

<a id="matcap"></a>
### Matcap materials

A **matcap** ("material capture") is a different way to finish a surface, a sphere photographed or baked under fixed lighting and sampled by the **view-space normal**. Because the whole look (the lighting included) is painted into the image, a matcap needs *no* scene lights and costs one texture lookup. `matcap(_:)` wraps subsequent meshes in one:

```swift
matcap(.chrome)
drawSphere(radius: 200)
```

Reach for a built-in by name, bring your own matcap PNG, or generate one:

```swift
matcap(.clay)                                   // a bundled built-in
matcap(loadImage("my-matcap.png"))              // any matcap image
matcap(Matcap.shaded(baseColor: .teal,          // rolled-your-own, no asset
                     metallic: true))
noMatcap()                                      // back to the lit material model
```

A matcap is a **separate axis** from `material(_:)`, so it bypasses the scene lights, `material(_:)`, and `castShadows()` entirely (the lighting is in the texture). The surface is tinted by the current `fill`, so `fill(.white)` shows the matcap as captured and other fills recolor it. It's drawing state, saved by `withState`.

#### The built-in matcaps

The built-ins are real baked studio captures (CC0, derived from the Blender community's matcaps, see [`THIRD-PARTY-NOTICES.md`](../../THIRD-PARTY-NOTICES.md)), grouped by family:

- **Metals**: `.chrome`, `.bronze`, `.carpaint`, `.hardSurfaceGrey`, `.hardSurfaceRed`
- **Clays / earths**: `.clay`, `.terracotta`, `.sage`, `.clayWarm`
- **Whites / ceramics**: `.pearl`, `.ceramic`, `.ceramicDark`
- **Translucent**: `.wax`, `.resin`
- **Neutral studio**: `.studio`, `.basicBright`, `.basicDark`, `.basicSide`
- **Toon / cel**: `.toon`, `.toonDark`
- **Diagnostic** (for inspecting geometry, not material looks): `.checkNormal`, `.checkGradient`, `.checkReflectionHorizontal`, `.checkReflectionVertical`, `.checkRimDark`, `.checkRimLight`

#### `Matcap.shaded(baseColor:metallic:roughness:)`

When you'd rather not bundle an asset, `Matcap.shaded(...)` renders an analytic shaded sphere on the CPU for a quick custom or recolored matcap. `metallic` tints the highlight by the base color (a metal) instead of leaving it white (a dielectric), and `roughness` (`0` mirror-sharp … `1` broad/matte) sets the highlight tightness. It's the same construct-or-reach-for-a-built-in shape as `Material` and `LightingPreset`.

```swift
matcap(Matcap.shaded(baseColor: Color(hex: 0x4488FF)))          // a blue plastic
matcap(Matcap.shaded(baseColor: .gold, metallic: true, roughness: 0.1))
```

Because the look is keyed to the *view*, a matcap shifts as a shape (or the camera) turns, so orbit a matcap'd sphere and the highlights slide, as in [`Examples/3D/Materials/Matcap`](../../Examples/3D/Materials/Matcap). Matcaps shade individual meshes only, and the lit material model, cast shadows, and gradient paint don't apply to them.

<a id="environment"></a>
### Environment lighting

`environment(_:)` lights the scene with an HDRI environment (image-based lighting), so a physically based surface gathers its ambient and reflections from the surroundings. This is what makes a metal read as metal, since a smooth chrome ball reflects the environment instead of going dark.

```swift
environment(.studio)            // a soft photo-studio light
fill(.white)
material(.polishedMetal)
drawSphere(radius: 1)           // a chrome ball reflecting the studio
```

The environment lights the surface *and* shows behind it as a backdrop, so the reflections match what you see. With no other lights set, the environment alone lights the scene, and it also adds to any `directionalLight`/`pointLight`/`spotLight` you place. Raymarched SDF fields shade through the same model, so a merged field and a mesh sharing a material read identically under one environment (see [Combinators ▸ 3D fields](../Drawing/Combinators.md#fields-3d)).

#### The built-in environments

Ollin curates 20 CC0 HDRI environments. Eight ship **bundled at 1K** (instant and offline), and the other twelve **download on first use** from Poly Haven and cache afterward. Pick one as `Environment.<name>`:

| Group | Environments |
|---|---|
| Studios & interiors | `.studio` · `.photoStudio` · `.interior` · `.hall` · `.warehouse` |
| Outdoors & sky | `.courtyard` · `.city` · `.forest` · `.field` · `.day` · `.noon` |
| Golden hour & dusk | `.dawn` · `.sunrise` · `.goldenHour` · `.sunset` · `.dusk` |
| Cool & night | `.snow` · `.cityNight` · `.night` · `.starryNight` |

The eight bundled offline are `.studio`, `.city`, `.courtyard`, `.forest`, `.interior`, `.night`, `.sunrise`, and `.sunset`, and the rest download the first time you use them. They span a wide brightness range, so each is auto-exposed to a consistent level (pair it with `toneMap(.aces)` for a filmic highlight rolloff). `Environment.bundledBuiltins` is the eight offline ones and `Environment.allBuiltins` the full twenty, each with its name, for a gallery that steps through them (see [`Examples/3D/Environments/EnvironmentGallery`](../../Examples/3D/Environments/EnvironmentGallery)).

#### Higher resolution, and your own

The built-ins light from 1K (the lighting never needs more than that). For a sharper *backdrop*, `highRes(_:)` downloads a 2K, 4K, or 8K version on first use and caches it (the 1K shows meanwhile, then it swaps in), and only the skybox gets sharper. You can also load or download any equirectangular HDRI (`.exr` or `.hdr`):

```swift
environment(.sunset.highRes(.fourK))                       // a 4K backdrop, downloaded once
environment(.hdri(path: "/path/to/sky.exr"))               // your own local file
environment(.hdri(downloadURL: "https://…/sky_4k.exr"))    // any HDRI on the web
```

Downloads (and the decoded pixels) cache at `~/Library/Caches/Ollin/Environments/`, overridable with the `OLLIN_ENVIRONMENT_CACHE` environment variable. The download runs in the background, so the live window shows a placeholder (a built-in's bundled 1K, a `placeholder:` you name, or a procedural sky) until it lands, while an export waits so the saved frame is always full resolution. The terminal prints the download's byte/percent progress and then a "decoding" note, so a first-run fetch (and the EXR decode after it) isn't a silent pause. To reclaim the cache later, run `Scripts/clear-caches.sh` (by default it wipes the environment and compiled-model caches, honoring `OLLIN_ENVIRONMENT_CACHE`, and `--environments` clears only the HDRIs while `--all` also clears the fetched `Models/` weights and the `.build/` directory). See [`Examples/3D/Environments/HighResEnvironment`](../../Examples/3D/Environments/HighResEnvironment) and [`Examples/3D/Environments/EnvironmentURL`](../../Examples/3D/Environments/EnvironmentURL).

#### A procedural sky (no asset)

`environment(.sky(...))` synthesizes a physically based daylight sky at runtime (nothing to load or download) and lights the scene with it like any other environment. It's the zero-asset option, and the sun can move:

```swift
environment(.sky(sunElevation: 0.4))                 // a clear midday sky
environment(.sky(turbidity: 6, sunElevation: 0.08))  // a hazy low sun (warm)
environment(.sky(sunElevation: e).rotated(azimuth))  // animate the sun across the sky
```

- **`sunElevation`**: the sun's height above the horizon in radians (`0` at the horizon, `π/2` straight overhead).
- **`turbidity`**: atmospheric haze, `1` (crisp) to `10` (thick), and a low sun reads warmer.
- **`groundAlbedo`**: how much light bounces up from the ground (`0…1`).

The sun's compass direction is fixed, and `rotated(_:)` swings it around the sky. Because rotation is applied at shade time rather than re-baked, **circling the sun costs nothing**, since only a change in elevation, turbidity, or albedo refreshes the lighting, and the sky is light enough to re-bake that every frame, so an animated sun stays smooth. See [`Examples/3D/Environments/ProceduralSky`](../../Examples/3D/Environments/ProceduralSky).

#### Adjustments

```swift
environment(.sunset.intensity(1.5).rotated(time * 0.1))   // brighter, slowly spinning
environment(.studio.lightingOnly())                       // light the objects, keep your background()
environment(.day.backgroundBlur(0.4))                     // a softer backdrop (auto by default)
```

`intensity` scales the lighting and the backdrop together. `rotated(_:)` spins the surroundings to move the key light and the reflections. `lightingOnly()` keeps the environment as light but draws your own `background(_:)` behind the objects. `backgroundBlur(_:)` sets the backdrop's softness, and the default adapts to resolution, a touch of soft focus at 1K and sharp at 4K. See [`Examples/3D/Environments/ImageBasedLighting`](../../Examples/3D/Environments/ImageBasedLighting).

<a id="shadows"></a>
### Shadows

Call **`castShadows()`** and solids ground in their setting, dropping shadows onto a floor and onto one another:

```swift
camera(.orbiting(target: .zero, radius: 12, elevation: 0.4))

directionalLight(.white, direction: Vector3(-0.5, -0.8, -0.4))   // the caster
castShadows()

drawPlane(width: 20, depth: 20)                  // the ground that catches them
withState { translate(0, 2, 0); drawSphere(radius: 1.5) }   // floats, casts a shadow below
```

Shadows are **opt-in** (a sketch that doesn't call `castShadows()` pays nothing) and **per-frame** like the lights and camera, so call it in `draw()`. It needs a camera and a caster: the scene's first **directional** light, or, when there's no directional, its first **spot** light, then its first **point** light, then its first **rect or disk** [area panel](#area-lights). (The auto-lit default's key is directional, so a default-lit scene just works.) With no camera or no caster it's a no-op. `noShadows()` (or `castShadows(false)`) turns it back off.

The shadow frustum **auto-fits** to the scene around the camera target, so there's nothing to size or aim. A directional caster uses an orthographic box and a spot caster a perspective frustum fit to its cone. Both are shadow-mapped, so a pass renders the scene from the light's point of view and each lit surface is darkened where that light can't reach it, with **soft, contact-hardening edges** (see [Soft shadows](#soft-shadows) below) and bias tuned to keep self-shadowing artifacts off.

A **point** caster casts every way at once. On a ray-tracing GPU (Apple silicon) it's **ray-traced**, so each lit pixel traces a few visibility rays straight to the light against a per-frame acceleration structure and the shadow is exact, with no shadow-map bias, acne, or peter-panning. A small area-light disk softens the edge into a contact-hardening penumbra (sharp where an object meets the ground, softer with distance). On a GPU without render-stage ray tracing it falls back to an omnidirectional cube depth map (mid-point shadow mapping, sampled by direction), so point shadows work everywhere. The choice is automatic, and nothing in the sketch changes.

A **rect or disk** area caster shadows from its **real extent**: a bigger softbox throws a proportionally softer shadow, with no knob to set. On a ray-tracing GPU each lit pixel traces visibility rays to points spread over the panel's actual surface, so a wide strip even throws a lopsided penumbra along its long axis; elsewhere the panel renders a spot-style map from its center, aimed at the scene like the directional box auto-fit, with its soft edge sized from the same extent. A tube never casts (it emits radially, so there's no facing side to shadow from). The `3D/Lighting/AreaShadows` example shows the size-to-softness link.

<a id="soft-shadows"></a>
#### Soft shadows

Shadows are **contact-hardening** by default, sharp where an object meets a surface and softening as the shadow falls away, the way real shadows behave. **`shadowSoftness(_:)`** sets how soft, 0…1:

```swift
shadowSoftness(0.7)   // softer penumbrae
shadowSoftness(0)     // hard-edged, the classic look
```

`0` is a hard edge, the `0.5` default is a pleasant contact-hardening soft, and `1` is very soft. **One knob softens every caster kind**: the directional and spot casters (a variable-kernel filter on their shadow maps called *Percentage-Closer Soft Shadows*, which searches for the occluder and widens the blur with the receiver's distance from it) and the ray-traced point caster's area light alike. For a rect/disk area caster the knob scales the panel's physical extent instead: the `0.5` default is the panel's true size, `0` hard, `1` twice as soft. It's persistent, like the other shadow settings, so set it once in `setup()` or `draw()`.

This is the **look** of the shadow's edge, while how *smoothly* that edge is drawn is the quality dial below.

#### Soft-shadow quality

The number of samples that build the penumbra sets how smooth it is, so more samples give a smoother edge for proportionally more GPU. Two knobs control it:

```swift
shadowQuality(.detail)    // a hardware-relative tier (the everyday dial)
shadowSamples(16)         // an exact count (the precise escape)
```

**`shadowQuality(_:)`** takes a `RenderQuality` tier (`.performance`, `.default`, or `.detail`), and the tier **scales with the GPU**, like a game's quality presets, so `.default` is the frame-rate-safe choice on a software-ray-tracing GPU (M1/M2) and a richer one on a hardware-RT GPU (M3 and up). A sketch gets nicer shadows for free on better hardware, and `.detail` means "more detail *for this machine*." Both are persistent (set once, in `setup()` or `draw()`), and `.default` is the default, so you only call them to deviate.

**`shadowSamples(_:)`** sets an exact, hardware-independent count instead, for fine control, pushing past the presets, or a render that should look identical on every machine.

Both apply to **every soft caster**: the directional/spot map's filter taps and the ray-traced point caster's rays. The tiers scale with the GPU for the ray-traced path (better hardware affords more rays), while the directional/spot tap counts are fixed per tier (they're cheap texture reads, so they look the same on any Mac). Exports and the headless image/snapshot path render at the `.detail` tier automatically, so saved frames get the smoothest penumbra. To find the count that holds 60fps on a given GPU, run `Scripts/benchmark-shadows.sh`.

<a id="contact-shadows"></a>
#### Contact shadows

A shadow map has finite resolution, and the bias that keeps its acne off pushes its shadow slightly away from the surfaces that cast it. Both misses land in the same place: the last sliver of contact, so a box resting on a floor can read as hovering a hair above it, especially under a soft, wide penumbra. **`contactShadows()`** closes that seam:

```swift
castShadows()
shadowSoftness(0.8)     // a wide, soft look: the map alone leaves each base loose
contactShadows()        // the short screen-space march that seats it again
```

For each pixel the renderer marches a **short ray toward the casting light through the scene's own depth**, and darkens the pixel where nearby geometry blocks it. The result is the fine dark line that hugs every base and crease, the detail a map can't hold at any resolution. It's a refinement of `castShadows()` (which picks the caster), works with **every caster kind** on **any Metal GPU**, and is per-frame state like the lights. `noContactShadows()` (or `contactShadows(false)`) turns it back off.

```swift
contactShadows(length: 8)   // the ray's reach, in world units
```

`length` is how far the march looks, in world units; leave it out and a short reach derives from the scene scale (2.5% of the camera's eye-to-target distance), so the default seats objects at any scene size. Longer rays darken deeper creases and cost nothing extra (the step count is fixed), but push the technique's envelope harder.

The envelope is the screen: **only what the camera sees can occlude.** Geometry off-screen or hidden behind something else casts no contact shadow, a curved surface can pick up a little extra shading just inside its silhouette (the march can't tell a limb from a wall), and the term dims only the casting light, so ambient and other lights are untouched. These are the technique's own limits, shared by every engine that ships it; the shadow map remains the source of truth for everything past the last few world units. Marched SDF fields and meshes drawn into render targets sit outside the march, and the quality tier follows the frame automatically (exports march at `.detail`).

What participates:

- **Solid and textured meshes** cast and receive shadows.
- **Wireframe meshes** don't (their faces are see-through), and **point clouds** and 2D drawing aren't shadow receivers.
- **Directional**, **spot**, and **point** casters, all with soft, contact-hardening edges (see [Soft shadows](#soft-shadows)).

> Shadows render on the live window and through the headless image/snapshot export. The accumulation surface (`noClear`) and the texture/Syphon hand-off paths draw 3D without shadows for now, the same scope as their existing depth limitation.

The example `3D/Shadows` stands a few turning solids on a floor under a swinging directional key light, `3D/SpotShadow` casts from a sweeping spot light, and `3D/PointShadow` from a central point light whose shadows radiate outward. `3D/Effects/ContactShadows` rests a still life on the floor under a deliberately wide soft shadow and flips the contact march on and off, so the seam under each base is the whole difference.

<a id="ray-traced-reflections"></a>
<a id="rt-reflections"></a>
### Ray-traced reflections

A physically based metal reflects its *environment* (above), and ray-traced reflections make it reflect the **actual scene around it**: the other meshes, the floor, even geometry off the edge of the screen. On a ray-tracing GPU (Apple silicon), each reflective pixel traces a reflection ray into the scene and shades what it hits, so the mirror image is exact.

#### `rayTracedReflections(_ on: Bool = true)`

Turn it on for the frame (per-frame state, like the lights, so call it in `draw()`):

```swift
camera(.orbiting(target: .zero, radius: 8, azimuth: time * 0.1, elevation: 0.3))
environment(.studio)                // lights the metals, and is the reflection's fallback
material(.polishedMetal); fill(.white)
rayTracedReflections()
drawSphere(radius: 1)               // now mirrors the rest of the scene, not just the sky
```

It plugs into the physically based lighting: a metal's environment reflection becomes a reflection of the scene, falling back to the environment where a ray flies off into open sky. So it needs three things:

- a **physically based** material (`material(.physicallyBased)` / `.metal(roughness:)` / `.polishedMetal` …), because a metal is what reflects;
- an **`environment(_:)`**, which lights the metal and is the miss fallback (a ray that leaves the scene shows the surroundings);
- a **ray-tracing GPU** (Apple silicon). On any other GPU it's a no-op and the environment reflection remains, so a sketch stays portable, and reflections just get richer on capable hardware.

Every solid mesh in the frame is reflectable. Roughness still applies, so a smooth metal is a sharp mirror while a rougher one blends the reflection toward the soft environment (a single ray can't blur it). The same holds for the surfaces *inside* a reflection: a matte floor seen in a mirror, or through a pane of glass, reads as matte there rather than turning into a second mirror.

This is the artifact-free counterpart to the screen-space-reflections combine ([`.screenSpaceReflections`](../Drawing/Effects.md#combined)). SSR reflects only what's already on screen and is the tool for a flat reflector *without* a ray-tracing GPU, while ray-traced reflections trace the real geometry, so a curved object's reflection on a near-mirror floor is a clean foreshortened ellipse rather than a smeared contact band. [Combining 3D features](./Combining.md) compares the two systems side by side and maps which geometry appears in each. The example `3D/RayTracedReflections` rings metal spheres around a polished monolith over a near-mirror floor, and holding the space bar drops the reflections to compare, with the mouse free to orbit the scene.

The reflection layer anti-aliases itself by integration, since an edge *inside* a mirror image (a pillar's reflection meeting the floor) is beyond what multisampling can reach. Live, each frame traces a slightly jittered ray per pixel and accumulates the result across frames, so a still or slowly moving view converges to a smooth reflection in a fraction of a second. An export or snapshot instead averages a fixed set of jittered rays within the one frame, so exported art is anti-aliased with no warmup and reproduces exactly.

> **v1 limits.** Two bounces: a metal seen in a mirror shows the scene around it (so a mirror floor's reflection of a chrome sphere carries the room in miniature), and the level beyond that shows the environment. Reflections render at full resolution (a quality dial is a later step). Inside an off-screen render target they keep the single-ray form (the anti-aliased path covers the canvas itself). They draw on the live window and through the headless image/snapshot export, the same scope as shadows.

<a id="global-illumination"></a>
### Global illumination

Direct light only ever explains half a picture. In a real room the sun patch on the floor lights the ceiling from below, a red wall tints the white table beside it, and the shadowed side of a statue is filled by light arriving second-hand. `globalIllumination()` turns that bounce on: light leaves a surface, lands on another, and keeps going.

#### `globalIllumination(_ on: Bool = true, intensity: Double = 1)`

Per-frame state like the lights and camera, so call it in `draw()`, after both:

```swift
camera(.orbiting(target: Vector3(0, 2, 0), radius: 10))
spotLight(.white, at: Vector3(0, 4, 0), direction: Vector3(0, -1, 0), intensity: 3)
castShadows()
globalIllumination()      // the pool on the floor now lights the whole room
```

Under the hood the renderer keeps a grid of **light probes** over the scene, re-traces them every frame against the actual geometry, and every lit surface adds the bounce light its surrounding probes saw. Because the probes are re-traced live, moving lights and moving shapes keep bouncing correctly, and a probe that lands inside a wall walks itself out. Nothing is precomputed, so there's nothing to bake and nothing to invalidate.

A few things follow from how it works:

- **It composes with everything already here.** With an `environment(_:)`, the probes carry the sky into the scene *with occlusion*: an interior lit through a doorway reads right, where the plain environment ambient would light the back room as brightly as the porch. With `castShadows()` on, bounce light respects the same shadow the direct light does, so light can't sneak through a wall on the second hop. Without either it still works from the lights alone. It reaches the whole picture, too: a surface seen *inside* a [ray-traced mirror](#rt-reflections) (or through traced glass) carries the same bounce as its direct view, and a 3D scene drawn into a `withTarget` layer (the depth-of-field recipe) gathers the field like the canvas does.
- **It's diffuse bounce.** Matte and low-gloss surfaces pick it up; a mirror's sharp reflection is [ray-traced reflections](#rt-reflections), the specular sibling, and the two run happily together.
- **`intensity` is the artistic crank.** `1` is physical; higher pours more bounce in for a look, `0` contributes nothing.
- **It needs a ray-tracing GPU** (Apple silicon). Elsewhere it's a no-op and the direct picture remains, so a sketch stays portable.

Live, the probe field converges over a handful of frames and then updates smoothly (a sudden lighting change fades in over a few frames, like your eyes adjusting). An export or snapshot instead converges the field fully within each frame, deterministically, so exported art reproduces exactly and a video can't flicker.

**Vast scenes get a near field automatically.** The probe grid covers the whole scene from a fixed budget, so on a terrain the probes land tens of units apart and the bounce near the camera would smear. When the fitted grid turns that coarse relative to how close the camera is working, the renderer adds up to three finer probe volumes anchored on the camera, each halving the spacing of the last, and every lit point reads the finest volume that covers it (blending smoothly where one hands off to the next). As the camera travels, those volumes glide along with it plane by plane, keeping their interior converged, so walking or flying across a large world keeps room-scale bounce around the camera with no setting to turn on. Room-scale scenes never trigger this and render exactly as before.

#### `globalIlluminationQuality(_ quality: RenderQuality = .default)`

The bounce's quality dial, `shadowQuality`'s GI sibling: how many rays each probe traces per update. `.performance` favors frame rate with a grainier, slower-converging bounce; `.detail` traces more for a smoother one; `.default` is the balanced choice for the GPU, lifted to `.detail` automatically on `--export`/headless (where it also deepens the in-frame convergence). A persistent setting; set it once in `setup()` or `draw()`. The probe grid itself stays the same size on every tier, so the tiers only change how finely the same field is sampled, never where its probes sit.

The example `3D/Lighting/GlobalIllumination` is a Cornell-style room whose only light is one swinging spot pool; the space bar toggles the bounce, which is the clearest way to see what it adds, and the quality tier rides a live segmented `@Param` in the inspector (`RenderQuality` conforms to `ParamOption`, so any of the quality dials can be a knob; see [Parameters](../Helpers/Parameters.md)).

> **v1 limits.** Bounce is gathered by solid meshes and raymarched SDF fields; GPU point clouds and particles don't gather (they barely have surfaces to). The probe grid adapts its shape to the scene, a fixed budget of 512 probes spread per axis by the fitted volume's proportions (a flat tabletop or terrain spends its probes horizontally instead of stacking unused vertical rows), with the camera-anchored volumes above taking over the near field once a scene outgrows that budget. Far-from-camera regions of a vast scene still read the coarse scene-wide grid.

<a id="temporal-antialiasing"></a>
### Temporal anti-aliasing

Every 3D frame already multisamples (8× where the GPU supports it), but MSAA samples each pixel at the *same* fixed positions every frame, so a thin bright rod or a high-contrast silhouette at a shallow angle still quantizes into steps, and those steps crawl as the camera drifts. `temporalAntialiasing()` refines past that: the renderer nudges the camera's projection by a sub-pixel offset that changes every frame and folds the resolved frames into a running average, so over a handful of frames each pixel has effectively been sampled at dozens of positions and the edge settles into a clean gradient.

#### `temporalAntialiasing(_ on: Bool = true)`

Per-frame state like the lights and camera, so call it in `draw()`, after the camera:

```swift
camera(.orbiting(target: .zero, radius: 8, azimuth: time * 0.05, elevation: 0.3))
directionalLight(.white, direction: Vector3(-0.4, -1, -0.5))
temporalAntialiasing()   // edges refine past MSAA as frames accumulate
```

A few things follow from how it works:

- **It also calms the effects that shimmer.** The screen-space and traced systems (ambient occlusion, reflections, global illumination) integrate noisy estimates, and their residual live shimmer is exactly what a temporal average absorbs, so they steady under it.
- **It follows the camera.** History is re-projected by the camera's motion using the scene's own depth, so orbiting and dollying keep the accumulated detail. An object that *itself* moves fast refreshes its history instead (a safeguard against ghost trails), so it briefly reads like plain MSAA until it settles; wrap it in `withMotion` (below) to keep its refinement mid-flight.
- **2D stays crisp.** The jitter applies to the 3D projection only; 2D drawing is already analytically anti-aliased and isn't nudged. Without an active 3D camera the call is a no-op (with a note).
- **It works on any Metal GPU.** No ray tracing involved.

Exports and snapshots stay deterministic: a headless frame renders the scene several times at the same fixed offsets and averages them within the frame, so a single export is anti-aliased with no warmup, a video can't flicker, and two exports of one frame are byte-identical. (`.performance` / `.default` / `.detail` render 4 / 8 / 16 passes; the automatic quality lifts exports to `.detail`.)

The example `3D/Effects/TemporalAA` is a wire trellis of thin tilted rods under a slow camera sway, with the toggle on a live `@Param`; flipping it mid-motion is the clearest way to see both the edge refinement and the crawling stop.

#### `withMotion(_ body:)` / `withMotion(_ name: String, _ body:)`

Camera motion is followed automatically, but a mesh that moves in *world* space (a spun `rotate`, a physics body posed by `withBody`, an animated `drawScene`) leaves no record of where it was last frame, so its history falls back to the conservative blend above. Wrapping its drawing in `withMotion` tells the renderer the block's meshes move together as one thing; Ollin remembers each draw's placement from frame to frame and hands temporal AA its exact screen motion, so the mover's edges keep their accumulated refinement while it moves:

```swift
temporalAntialiasing()
withMotion {
    rotate(time * 0.4, axis: .unitY)
    drawBox(width: 2, height: 0.05, depth: 0.05)   // a thin spinning rod
}
```

The block's identity is its call site (two blocks on one line, as in a loop, are told apart by the order they run in). If the code path that draws a mover changes between frames, give it a name instead: `withMotion("rotor") { … }` keeps one history wherever it's drawn from. It's purely additive: with temporal AA off, for a still mesh, or on a mover's first frame, nothing changes at all. Wireframes, point clouds, and raymarched fields keep the default handling, and a skinned figure is followed by its overall motion (not its per-vertex deformation).

> **v1 limits.** It applies to the main canvas: a `withTarget` layer and the accumulation surface (`noClear()`) keep their plain MSAA. Text or 2D overlays drawn *over* a moving 3D scene can soften a touch while the camera moves (their pixels ride the scene's re-projection); they're untouched when the camera is still. `withMotion` covers meshes; [motion blur](#motion-blur) reads the same declarations, and MetalFX upscaling on the same velocity buffer is a later step.

<a id="motion-blur"></a>
### Motion blur

A real camera's shutter stays open for a slice of each frame, so anything moving smears along its path; a rendered frame is an instantaneous exposure, which is why fast motion reads as a strobe. `motionBlur()` puts the smear back: each pixel streaks along its own screen motion, with a moving object blurring *past* its silhouette, a sharp background staying sharp behind it, and a blurred foreground letting the background it uncovers show through.

#### `motionBlur(shutter: Double = 0.5)`

Per-frame state like the lights and camera, so call it in `draw()`, after the camera:

```swift
camera(.orbiting(target: .zero, radius: 8, azimuth: time * 0.3, elevation: 0.3))
motionBlur()                 // the film-standard 180-degree shutter
withMotion {
    rotate(time * 2.5, axis: .unitY)
    translate(2.5, 1, 0)
    drawSphere(radius: 0.4)  // streaks along its orbit
}
```

`shutter` is the fraction of a frame interval the virtual shutter stays open. The 0.5 default is the film-standard 180-degree shutter (a streak half the frame-to-frame travel); smaller values are crisper and more staccato, 1 smears a full frame of travel, and values past 1 overdrive the streak further than any real shutter could, which is a look of its own. `noMotionBlur()` turns it back off.

Motion comes from two places, and they compose:

- **The camera's own movement** is read from the depth buffer with no declaration at all: pan or orbit past a still scene and the whole frame streaks by exactly how far each surface slid across the screen.
- **An object moving in world space** declares itself with the same [`withMotion { }`](#temporal-antialiasing) blocks temporal AA uses; one wrapper serves both systems. An undeclared mover still gets the camera's blur, just not its own.

A few things follow from how it works:

- **Streak length is capped** at a resolution-relative radius (about 1/36 of the canvas height, the published tile size), so an arbitrarily fast object streaks a bounded distance rather than across the frame.
- **The backdrop holds still by design.** 2D drawing, the clear color, and the environment skybox never smear, so captions and overlays stay crisp under any camera move.
- **First frame excepted.** Motion is read between consecutive frames, so the very first frame has nothing to blur and renders unblurred.
- **It works on any Metal GPU**, and it composes with `temporalAntialiasing()` (the blur reads the stabilized frame, and bloom or a grade reads the streaks).

Exports carry the blur deterministically: exported frame k reads the motion between frames k-1 and k through the same headless drive that already runs every prior frame, so a video export streaks exactly like the live window and two exports of one frame are byte-identical. Point clouds and GPU particles take the camera's blur but not their own per-particle motion; a `withTarget` layer and the accumulation surface stay unblurred (the temporal-AA envelope).

The example `3D/Effects/MotionBlur` orbits three spheres at very different speeds through a still colonnade under a drifting camera, with the toggle and the shutter on live `@Param` knobs.

<a id="textures"></a>
### Textured meshes

A mesh can wear an image on its surface, mapped through per-vertex texture coordinates (UVs) and lit like any solid.

#### `Mesh.textured(_:baseColor:)`

Returns a copy of the mesh wearing `image` as its surface, optionally tinted by `baseColor` (default white). It's a value transform, like `normalized(scale:)`:

```swift
let grid = loadImage("/path/to/texture.png")!
let globe = Mesh.sphere(radius: 200).textured(grid)
drawMesh(globe)
```

The texture maps through the mesh's **`uvs`**, and the built-in `.sphere` and `.plane` generators emit them (the other generators fill in over time). A mesh with no UVs has nothing to map against, so it draws as a flat `baseColor × fill` surface instead, and the texture is simply ignored until the mesh carries UVs.

The surface is the texture **tinted** by `baseColor × fill`, so a white `fill` and white `baseColor` show the image as-is while either one colors it. The textured surface is shaded by the lights exactly like a solid one (the auto-lit default, or your own rig).

For full control, set the material directly, since `MeshMaterial` is a value type (`baseColor` plus an optional `texture`):

```swift
var floor = Mesh.plane(width: 800, depth: 800)
floor.material = MeshMaterial(baseColor: Color(white: 0.7), texture: grid)
```

A diagram of UV space (0,0 at the texture's top-left, matching image coordinates):

```
 (0,0) ───── u ─────▶ (1,0)
   │  ┌───────────────┐
   │  │   the image   │
   v  │   on the mesh │
   │  └───────────────┘
   ▼
 (0,1)               (1,1)
```

A textured `Image` can come from anywhere a normal one does: a loaded file, a frame you authored pixel by pixel, a live feed. The example `3D/TexturedMesh` builds a UV grid in code and wraps it around a sphere and a floor.

> A *loaded model's own* materials and textures are read by the loaders too (so a `.gltf`/`.usdz`/`.obj` arrives looking the way its author made it (see [Meshes from file](#load)). `textured(_:)` is how you give *any* mesh an image yourself. Opaque base-color textures are the supported case, and metallic/roughness and normal maps are the later PBR tier.

<a id="wireframe"></a>
### Wireframe

Draw a mesh as its triangle edges (the mesh "net") instead of filled surfaces.

#### `wireframe(_:)`

This is drawing state, like `fill` and `stroke`, so turn it on and every mesh drawn after it renders as edges, with the faces see-through. It works on any mesh, a built-in primitive or a loaded model.

```swift
wireframe()                      // edges from here on
strokeWeight(1.5)
stroke(Color(hex: 0x53D1FF))     // edge color
drawMesh(.icosphere(radius: 1.5, subdivisions: 2))
wireframe(false)                 // back to solid
```

The edges take the current **`stroke`** color (or the `fill` if there's no stroke) and **`strokeWeight`** for the line thickness. Because the faces are see-through, the back edges show through the front, the classic look for a structure study or a face or scan mesh. It's `withState`-scoped, so you can wireframe one shape and fill the next.

A wireframe doesn't light (there's no surface to shade), and it composes with the camera, depth, and transform stack like any mesh, so a wireframe sphere occludes a solid one along its lines and vice versa.

<a id="transforms"></a>
### Transforms

In a 3D frame, `translate`, `rotateX/Y/Z`, and `scale` move geometry around *inside* the camera, the spatial siblings of the 2D transforms. They build a 4×4 **model matrix**, and `withState { }` saves and restores it, so you can place a body and come back:

```swift
camera(.orbiting(target: .zero, radius: 6, azimuth: time * 0.2, elevation: 0.4))

withState {
    translate(2, 0, 0)        // step along +x
    rotateY(time)             // spin about the world y-axis
    scale(Vector3(0.5, 0.5, 0.5))
    drawPointCloud(blob)      // drawn at (2,0,0), spun and half-size
}
// back to the original frame here, the withState restored it
```

The full set, all on `Sketch` (and the `Drawer`):

- `translate(_ offset: Vector3)` / `translate(_ x:_ y:_ z:)` moves in world units.
- `rotateX(_:)`, `rotateY(_:)`, `rotateZ(_:)` rotate about a world axis (radians, right-handed, so counter-clockwise looking from the positive axis toward the origin).
- `rotate(_ radians:axis:)` rotates about an arbitrary axis.
- `scale(_ x:_ y:_ z:)` / `scale(_ factors: Vector3)` scales per axis. Uniform scale is `scale(Vector3(s, s, s))`.

They **compose by post-multiplication** like the 2D stack, so `translate` then `rotateY` then draw places a point at `T · R · p`. Nesting `withState` is how an orbit rides another orbit, so a moon inherits its planet's position and adds its own circle. The [`3D/Transforms`](../../Examples/3D/Geometry/Transforms/) example is exactly that: a sun, planets orbiting it, and a moon orbiting each planet, every body the same blob placed by a different stack of transforms.

Two things worth knowing:

- **Splat sizes are world units, so `scale` grows a body's dots too.** A body drawn at a small scale needs larger base `size` points to stay visible, since the transform shrinks the splats along with the body.
- **The 3D transforms don't touch 2D drawing.** Shapes, images, and text keep using the 2D transform (`translate(x, y)`, `rotate(angle)`, …), so both stacks stay live in a 3D frame and you can `withBillboard` a 2D label onto a 3D point in the same `draw()`. The 3D `translate(x, y, z)` (three arguments) and the 2D `translate(x, y)` (two) are distinct calls, and the compiler picks by arity and by `Vector3` vs `Vector2`.

### A live depth cloud from a webcam

The Mac has no depth camera, but a neural depth model estimates one from a plain webcam, so a live 3D point cloud of whatever's in front of the camera is a `ModelTracker` plus this point-cloud path. The [`3D/DepthCloud`](../../Examples/3D/Depth/DepthCloud/) example samples the depth map over a grid, lifts each cell into 3D by its depth, colors it from the camera image, and orbits the result. It's the camera-only counterpart to the tethered-iPhone LiDAR clouds in [`3D/Depth/Record3DLiveCloud`](../../Examples/3D/Depth/Record3DLiveCloud/) and [`3D/Phone/PhoneDepthCloud`](../../Examples/3D/Phone/PhoneDepthCloud/), which read real depth off the phone. (It needs the depth model, so run `Scripts/fetch-models.sh` once.)

<a id="space"></a>
### World space

3D world space is **right-handed with y up**: x runs right, y up, and the camera looks down its local −z. Distances are in world units, whatever your geometry uses (meters for a depth cloud, say). This is a different convention from the 2D canvas (top-left origin, y *down*, points), because 3D geometry lives in its own world space and reaches the screen through the camera. So a point cloud rides the camera and the **3D** transform stack ([Transforms](#transforms)), never the *2D* affine (`translate(x, y)` / `rotate(angle)`), which keeps placing 2D shapes, images, and text.

`Vector3` carries 3D positions, giving `Vector2`'s arithmetic with a `z`, plus `cross` (returning a vector), `unitZ`, and `xy` to drop back to the canvas plane. See [Geometry](../Drawing/Geometry.md).

### What's here, what's ahead

Here now: a perspective/orthographic camera, a depth buffer, the 4×4 transform stack ([Transforms](#transforms)), instanced point-cloud splats, the solid primitives ([Solid primitives](#primitives)) over a depth-tested mesh path, [meshes loaded from file](#load) (`.obj`, `.usdz`/`.stl`/`.ply`, `.gltf`/`.glb`) with their own base-color material and texture, the [light & material model](#lights) (directional/point/spot lights with a Blinn-Phong material, auto-lit by default), [lighting presets](#lights) (one-call rigs like `.goldenHour`/`.noir`), the [material library](#materials) (`material(_:)` with stylized finishes (iridescent, sparkle-flake, velvet, jade, toon, gooch), the physically based metallic-roughness tier, [glass](#glass) (transmission and refraction), and the [clearcoat + sheen](#clearcoat-sheen) layered lobes, extensible like the presets), [matcap materials](#matcap) (`matcap(_:)`, a whole look in one view-normal-sampled sphere texture, 26 bundled CC0 looks plus a generator), [cast shadows](#shadows) (`castShadows()`, directional + spot + point + rect/disk area panels), [textured meshes](#textures) (an image on a mesh's surface via UVs), and a [wireframe](#wireframe) mode. That's enough for point clouds (including a live webcam depth cloud) and lit, filled, textured, shadow-casting 3D shapes, and it's the foundation the rest of 3D builds on.

Ahead: scene import (`loadScene`, preserving a file's node hierarchy, cameras, and lights), a live camera environment, 3D rigid-body dynamics, and the deeper realism tier (global illumination, real subsurface scattering, temporal anti-aliasing). See the [roadmap](../../ROADMAP.md#3d-mode). 2D stays the default throughout.

<a id="notes"></a>
### Notes

- **2D is untouched.** With no camera, a frame allocates no depth buffer and renders exactly as before, so the 3D path is entirely opt-in.
- **Depth testing** hides points behind nearer ones (less-equal, depth-writing). 2D overlays drawn in the same frame (a caption, a HUD) composite over the 3D scene in draw order without touching depth, *unless* they opt into a depth with [`depth(at:)`](../3D/DepthCompositing.md), which lets a 2D mark sit inside the scene and be occluded by it.
- **Defocus a 3D scene by its own depth.** Draw the scene into a render target and it captures depth, exposed as `target.depth`, a gray depth layer you can feed straight to the [`.defocus`](../Drawing/Effects.md#depth) depth-of-field combine (or filter/draw to inspect). Set the camera's `near`/`far` to bracket the scene so the focal plane sweeps it. See [`Effects.md`](../Drawing/Effects.md#depth) and the `3D/SceneDefocus` example.
- **Not yet in 3D:** the accumulation surface (`noClear`) and the live texture hand-off (Syphon, the virtual camera) render 3D without depth sorting for now, so keep 3D sketches on the live window and the raster/PNG export paths, which are depth-correct.
