# Ollin design notes

The engineering design intent behind the planned work in [`ROADMAP.md`](ROADMAP.md). The roadmap is the short version (what's planned and how to help); this is the long version (how each piece would be built, the specific APIs involved, and why). A couple of shipped items stay only where their design rationale still guides future maintenance or evolution (extending the examples set, the Swift-idiom track); anything fully done and self-contained lives in its own doc or `CLAUDE.md`, not here.

These notes assume Ollin's two ground rules: it targets Apple platforms only (no cross-platform abstractions), and the bare p5-style API is sugar over a public, typed core, so a feature is built on the core first and given the bare call second. Geometry-emitting calls take a `draw` verb prefix (`drawCircle`, `drawRect`, and so on).

## Swift Playgrounds and iOS (not started)

Worth pursuing. Swift Playgrounds app (Mac and iPad) App Projects (`.swiftpm`) are the closest Swift gets to the p5.js "open the editor and type, see it move" onboarding, and the same work unlocks iPad sketching and embedding in any SwiftUI app. On-brand for the "learn it in an afternoon" goal.

- **The architecture is already most of the way there.** `SketchView` is a SwiftUI-embeddable view, cleanly separated from the macOS-only `OllinApp.run` (the standalone `swift run Example-X` launcher, now a thin SwiftUI `App`, `OllinSketchApp`, hosting `SketchView`, with an AppKit delegate only for activation). Embedding in someone else's SwiftUI `App`, which is what a Playgrounds App Project needs, is exactly that seam.
- **The blocker is iOS support.** Playgrounds App Projects build iOS apps, but Ollin only declares `.macOS("26.0")`. To make it importable: add `.iOS(...)` to `Package.swift`; make `SketchView` conditional (`NSViewRepresentable` and AppKit vs `UIViewRepresentable` and UIKit via `#if canImport(AppKit)` / `#if canImport(UIKit)`); guard `OllinApp.run` behind `#if os(macOS)`. The Metal renderer (`Metal`/`MetalKit`/`simd`) is already portable. A working reference for this exact seam is swifty-creatives, which compiles for macOS, iOS, tvOS, and visionOS from one source using a `ViewRepresentable` typealias (`NSViewRepresentable`/`UIViewRepresentable`) with `#if os(...)`-guarded `makeNSView`/`makeUIView`.
- **Keep shaders Playgrounds-safe.** Swift Playgrounds' support for SwiftPM build-tool plugins is unreliable, so don't go plugin-only for shaders. Keep runtime source compilation as a first-class loader.
- **Onboarding nicety:** ship a ready-made `.swiftpm` starter (Ollin pre-wired plus a `HelloCircle`) so users don't hand-add the package URL.
- **Caveats:** the Playgrounds sandbox restricts file I/O (which matters for the export items, not for drawing); package-dependency UX is finicky; prefer the Swift Playgrounds app's App Projects over the semi-deprecated Xcode Playgrounds. iOS changes need `xcodebuild -destination` with the iOS SDK on a Mac to verify.

## Color additions deliberately kept out

Rationale that still gates future color work:

- **Other color spaces stay out.** Classic Lab/LCH (the 1976 space OKLab was built to fix; interpolating through it bends blues toward purple), CIECAM16/JCh (a full appearance model that needs viewing-condition parameters; OKLab was fitted to give most of that benefit without the machinery), and DIN99/DLCH (an industrial color-difference standard). Any of them can arrive later as a plain conversion if matching an external spec calls for it.
- **Further curated palette collections stay license-gated.** Collections scraped from ColourLovers and similar sites are not license-clean and stay out; anything added must carry a permissive license the way the ColorBrewer data does.

## Supersampled render scale — the crispness dial (not started)

An opt-in render-resolution multiplier (e.g. `renderScale: 2`) — render the frame at N× and downsample — as the explicit performance↔quality dial, off by default for the 60fps path.

- **Why a knob, not the default.** Rendering at N× and downsampling is brute force (N²× the fragment work), the wrong default for a live 60fps sketch but a fine opt-in for a frame off that clock. The thin-line AA it would otherwise be reached for is already handled at native resolution: stroked lines/curves carry their own ~1px coverage fringe (the fringe stroke path), and the analytic SDF shapes (fills, disks, and stroke-band outlines alike) conserve sub-pixel area, so a supersample buys little on those.
- **Where it pays off.** The live view already renders at the display's backing scale (MTKView's default drawable), so on a Retina Mac it's effectively ~2× already; raster `--export`/`image(of:)` is fixed at `canvasSize`. So the knob's first home is export (a gallery-grade still / sequence), with an optional above-Retina multiplier for the live view. It mostly sharpens the *tessellated fill* path (polygon/shape fills, tessellated text) and fine dense detail; the SDF shapes and the fringe-AA strokes are already crisp at native resolution, so the gain there is small. For plotter line art the vector `--export-svg` is already resolution-independent and the better answer.

## Layered effects and compositing (partly shipped)

OPENRNDR-style effects that compose in layers: draw into off-screen layers, run filters over them, composite with blend modes. The off-screen-layer + `Filter` substrate is in (`renderTarget` / `withTarget` / `filtered` / `postProcess`, with Gaussian blur and bloom; see the layered-effects entry under *Current state* in CLAUDE.md). What's ahead is the broader catalog and the composition DSL.

- **The broader filter catalog.** Reach past blur and bloom: color grading and LUTs, chromatic aberration and other distortions, edge and threshold/posterize passes, and **feedback** (the previous frame as a filter input, a ping-pong layer the renderer keeps across frames). The references for *which* effects to offer and *how* they're shaped: AsyncGraphics (its `Graphic` is an `MTLTexture`, effects are functions returning new graphics, plus a blend/stack model; borrow the compositing architecture, not its async call shape) and OPENRNDR's `Filter` (the conceptual model already followed). SwiftUIShaders (MIT) is a catalog menu of forty-odd post-process effects (holographic, kaleidoscope, datamosh, thermal, chromatic split, …): mine the ideas, reimplement against our own pipeline. ofxFX (MIT, Patricio Gonzalez Vivo) is the GL/openFrameworks take: composers (blend, mask, multi-texture), filters (blur, bloom, glow, bokeh, LUT color grading, chroma aberration), generative passes (noise, FBM, Gray-Scott), operations (ripples, flow, edge detect), with **LUT-based color grading** a filter kind worth taking from it. Same stance throughout: study and reimplement, credited in the README's Influences.
- **The `compose { }` composition DSL.** The fluent surface over the substrate, from OPENRNDR's compositor (`compose { layer { draw {…}; post(blur); blend(.screen) } }`), declaring a stack of layers, each with its own post-filters and blend, as one block. The idea worth stealing is the **`aside` helper layer**: a layer drawn only to *feed* another layer's filter (a displacement map, a mask), so a multi-input effect (displace, mask, cross-dissolve) reads as a small graph with the compositor managing the intermediate textures rather than the sketch threading them by hand. Distinct from the per-call `withTarget`/`filtered` substrate it's built on, and the launch pad for the [shader-composition fluent tier](#shader-composition-and-live-coding-not-started).
- **Depth of field belongs in the effect catalog.** A DoF pass is a depth-driven blur filter: a depth input picks the focal plane, blur radius grows with distance from it (bokeh is the dressed-up form). In 3D mode the depth buffer feeds it for free; for 2D sketches the depth input is any gray map the sketch supplies — including a live monocular-depth feed from `ModelTracker` (the DepthRelief example's model), which would make camera-feed DoF work with no 3D scene at all. Prior art in the oF world is ofxDOF (James George, extracted from the RGBDToolkit) — **no license file, so concept only, never source**: the Ollin pass is written from the published technique (scatter-as-gather circle-of-confusion blur).
- **Ambient occlusion is a screen-space pass too (SSAO).** The contact darkening in creases and where surfaces meet — the cheap stand-in for the shadowing the analytic light model can't see. Same screen-space-over-depth shape as the DoF blur: a depth (and normal) prepass feeds a noise-rotated hemisphere-sampling occlusion pass, a small blur hides the sampling pattern, and the result modulates the **ambient** term — so it belongs as much to the [realism tier](#3d-mode-partly-shipped)'s ambient/IBL work as to this catalog. 3D mode already writes a `depth32Float` buffer and the mesh path carries per-vertex normals, so the only new prerequisite is a normal target beside the depth one — a "G-buffer-lite," far short of a full deferred pipeline (the [lighting-architecture note under 3D mode](#3d-mode-partly-shipped) covers why Ollin wouldn't take classic deferred). Written from the published technique (Crytek's original, the HBAO / GTAO refinements); MetalFX and the platform's tile memory are the idiomatic places to hold the intermediate targets.

## Shader composition and live-coding (not started)

Two linked directions on the radar, both about combining and mixing shader-driven visuals fluently, and both distinct from `OllinLive`, which is dev-loop hot-reload, not a performance instrument.

- **A composable shader and effect-mixing API.** What's compelling about Hydra and OPENRNDR: chaining and blending sources and transforms so visuals combine with almost no ceremony (`osc().rotate().modulate(noise())`). This is the call-shape companion to [layered effects and compositing](#layered-effects-and-compositing-partly-shipped): that work is the substrate (render targets, filters, blend modes); this is the fluent surface over it. Study how Hydra and ShaderPark make mixing so fluid and borrow the direction (Hydra is AGPL, so inspiration only; ShaderPark is MIT). The underlying shader functions are written from the published techniques. Keep it sugar over the typed core.
- **A performance live-coding environment.** A separate app from `OllinLive`: a performance instrument where you type expressions live, evaluate them on the fly, and project the output, rather than a file-watcher. The goal is to do natively what's today done by bridging Hydra and openFrameworks, with Hydra as the direct model. It likely builds on the live-reload host, the shader-composition API above, and the parameter-knob work. Apple-only. A working title for it is `OllinLiveCoding`.

## 3D mode (partly shipped)

2D stays the default and most sketches stay 2D, but 3D is a mode in its own right: a sketch opts in by setting a camera and, on the same Metal core, draws depth-tested point clouds and lit solid primitives — with richer shadows and materials as the mode grows. The iPhone point cloud renders through it, and visionOS and AR build on it. openFrameworks and OPENRNDR set the capability bar here, so the target is known. (The camera, depth buffer, the 4×4 transform stack, the instanced point-cloud splat path, the solid-primitive mesh path, meshes loaded from file with their base-color material, textured meshes, the directional/point/spot light & material model, and directional, spot, and point cast shadows are the foundation in place; the rest below builds on them.)

- **Scene import: `loadScene` beside `loadMesh`.** The loaders flatten everything to one merged `Mesh` today (`MeshLoader.swift` / `MeshLoaderGLTF.swift` bake the node hierarchy down and merge primitives), the right thing when a sketch just wants geometry to place itself. The missing complement is *structure-preserving* import, and the distinction isn't "glTF means scene, OBJ means model"; it's two independent axes. **Format capability:** glTF, USD/USDZ, and FBX carry a node graph, per-node transforms, cameras, lights, and animation, where OBJ/STL/PLY carry essentially one blob of geometry. **Caller intent:** even from a scene-capable file a sketch sometimes wants the geometry merged (drop a prop in and place it yourself) and sometimes the structure kept (open on the authored camera, animate one node). So the design is two verbs with non-overlapping contracts: `loadMesh` → `Mesh` (merged, any format; unchanged) and a new `loadScene` → `Scene`. The key is that `Scene`/`Node` are typed value objects that *decompose into the existing core types* rather than a parallel renderer: `scene.camera` is a `Camera3D` passed straight to `camera(...)`, `scene.lights` are `Light`s, each `Node.mesh` is a `Mesh` that also draws standalone, so import is "read the graph, hand back the core objects in place", with `scene.draw()` painting every node at its authored transform and `scene.node("lamp")` reaching one to drive from `draw()`. Two honesty constraints: geometry-only formats stay truthful (`loadScene` on an OBJ yields a degenerate single-node scene with no camera or lights, or the sketch just uses `loadMesh`), and a node's mesh may hold several primitives with different materials, which is the same work as the **per-material submeshes** refinement below, so until that lands `loadScene` inherits the first-material limitation. Scope fidelity to the glTF 2.0 core spec (owned by Khronos; also ISO/IEC 12113:2022) plus the ratified `KHR_` extensions (cameras are core, lights are `KHR_lights_punctual`), with vendor `EXT_`/app-specific extensions as a later tier. It's generic, not Spline-specific: the same `Scene` abstraction serves any glTF exporter (Blender, three.js, Cinema4D) and later a USD reader (Model I/O merges today, exactly as the glTF path does). The motive is the workflow. Composing a 3D scene by code alone is fiddly, so let a design tool place it and bring the layout in, which is what three.js's `GLTFLoader` already does (`gltf.scene` / `gltf.cameras` / `gltf.animations`), and what closes the gap with OPENRNDR's orx-dnk3 while beating p5 (OBJ/STL only) and openFrameworks' flaky Assimp glTF path on ergonomics. Node/TRS keyframe **animation** layers on once the scene graph exists (skinning and morph targets later). The one-way **scene-to-source** alternative (emitting editable Ollin source instead of a live asset) is the lossy scaffold that belongs in the [project generator](#project-generator--sketch-scaffolding-not-started), a complement to this runtime path, not a replacement.
- **Material-from-file refinements.** A loaded model wears its first base-color material (glTF/USD/OBJ-MTL) over the single-material-per-mesh scope. The relaxations: **per-material submeshes** (a `Mesh` carrying index ranges with their own materials, drawn as several batches — a material change already breaks the mesh batch), **REPEAT-wrap samplers** (the shared clamp-to-edge sampler doesn't tile a wrapping texture; a wrap-mode axis on the sampler), and the **metallic/roughness/normal/emissive** channels, which belong with the PBR tier below rather than the analytic Blinn-Phong path. The UV-origin convention for a Model I/O `imageFromTexture` result is unverified and may need a v-flip.
- **Softer shadows and more than one caster at once.** Each light kind casts through a shadow map sampled with a hardware depth-comparison sampler: directional and spot through one 2D map (orthographic / perspective, shared `shadowFactor`), point through an omnidirectional cube (six faces in one layered pass, `shadowFactorCube` reconstructing the per-face depth from the light distance). Two directions extend that base. **Softer shadows** are the quality axis: contact-hardening penumbrae so a shadow sharpens at contact and blurs as it falls away. The point caster gets this from its **ray-traced path** (Metal acceleration structures + inline `intersection_query`, an area-light disk sampled per pixel, true soft penumbrae with no map bias/acne); the directional and spot casters still sample raster 2D maps, so they want either PCSS (a blocker-depth search that widens the PCF kernel with receiver distance) or the same ray-traced path routed through them. The `shadowFactor`/`shadowFactorCube`/`shadowFactorRayTraced` helpers in `Shaders.metal` are the single swap point for whichever technique a caster uses. **More than one caster at once** (e.g. a directional key and a spot together) is the other extension: today only the first eligible light casts (the first directional, else the first spot, else the first point), so it wants a per-light `castsShadow` flag and a small caster array (a `depth2d_array` for the 2D maps, a `depthcube_array` for points) bounded to a small count. Lean on the native Metal feature for each step here rather than hand-rolling a multi-pass equivalent.
- **Many dynamic lights: Forward+ or tile-shading, not classic deferred.** Lighting is forward today — one `OllinLighting` uniform, `OLLIN_MAX_LIGHTS` bounded at 8, every mesh shaded against the same small set — which covers the common low-light-count case. The technique that exists to scale past it is deferred shading (render geometry into a G-buffer, then light in screen space so cost tracks pixels, not geometry×lights), but the textbook multi-pass G-buffer is the wrong fit here: it round-trips the G-buffer through DRAM, breaks the **draw-order compositing** the renderer rests on (2D SDF/triangle/image batches interleaved with 3D meshes under per-batch blend modes — a deferred resolve flattens that and drops transparency ordering), and fights the float-MSAA path (per-sample G-buffer resolve). On Apple-silicon TBDR the idiomatic answers keep forward's strengths: **tile-based forward (Forward+)** culls lights per screen tile and still shades forward (blending and the 2D/3D interleave survive), or Metal's on-chip **imageblock / tile-shading** deferred keeps the G-buffer in tile memory and never spills to DRAM. Either is an in-pass change, not a renderer rewrite, and it's the lever only if the 8-light ceiling actually bites — SSAO's depth/normal prepass (the [layered-effects catalog](#layered-effects-and-compositing-partly-shipped)) is a far smaller step and lands long before any of this.
- **Camera-relative lighting (an opt-in on the world-space default).** A `Light`'s direction is world-space, and that's the right default: the sun stays put as the camera orbits, the intuitive behavior the scene-graph 3D frameworks (openFrameworks' `ofLight`, OPENRNDR, the game engines) all default to. Those frameworks make a light *follow the camera* by parenting it to the camera node. Ollin is immediate-mode with no scene graph to parent into, so the switch has to be an explicit affordance: a `relativeTo: .world / .camera` flag on a light or preset, resolved each frame against the active `Camera3D`'s basis (cheap, since lights are already per-frame state). It earns its keep in two narrow cases: a viewer-following fill so the side facing away never goes fully black (a `headlight` helper is the sugar), and a three-point rig that holds its look under orbit rather than the world-fixed look the shipped `.threePoint` preset has. Sun, sky, and product lighting all want world-space, so add the opt-in only when the headlight or a camera-locked rig actually wants it.
- **Anisotropic specular.** Brushed metal, satin, and hair need a *stretched* highlight that the isotropic Blinn-Phong model can't make — it takes a per-vertex **tangent** direction (the reserved `OllinMeshVertex` pad slot is for exactly that) plus a Ward / Kajiya-Kay specular term keyed to it. It layers over the per-batch `OllinMaterial` uniform like the named finishes — a new finish parameter plus the tangent attribute, no state-machine change. (The matcap path is a sibling "whole look in one texture," but isotropic; anisotropy is the analytic-model gap it doesn't cover.)
  - **Physically-based shading and image-based lighting are the later realism tier.** PBR (an energy-conserving BRDF, roughness/metalness) is what these materials grow into, not the entry bar, and it pairs with **environment-map lighting (IBL)**, which is how modern real-time 3D gets its photographic "nice" look: a prefiltered HDRI, or a procedural studio environment (the no-asset form that fits Ollin's instinct), driving ambient and reflections on PBR surfaces. That's the real gap between Ollin's analytic directional/point/spot model and a photographic one, and the bigger bet — the realism tier above the analytic directional/point/spot model, slotted alongside PBR rather than on the Blinn-Phong path. (Blender's bundled *world* studiolights are CC0 equirectangular HDRIs — Poly Haven / Greg Zaal — a ready prefiltered-environment source when this lands, the same CC0 origin as the bundled matcaps.)
- **Per-mesh lighting (a refinement).** Lighting is per-frame today (one `OllinLighting` shades every mesh in a frame, like the camera), so a frame can't mix lit and unlit meshes or different light sets. Promoting it to per-batch state (break the mesh batch on a lighting change, like blend/depth, and carry the uniform per batch) matches immediate-mode semantics (the light state *at draw time* of each mesh) — do it when a sketch actually needs two lighting setups in one frame; until then per-frame keeps the path simple.
- **Build order.** Softer shadows (and supporting more than one caster at once) are the rendering-heavy step. The tier-one material recipes are pure data over the shipped light/material model with no renderer change, so they land cheaply (the way the lighting presets did) — a `Material` surface beside `specular`/`shininess`. PBR plus image-based lighting is the later realism tier above all of it. Each step is usable on its own.
- **`Vector3` shares most of `Vector2`'s surface — document the common part once.** `length`/`normalized`/`dot`/`distance`/`lerp`/the arithmetic operators/`limited`/`projected`/`with`/the constants are the same idea in one more dimension, so the shared surface lives on a `Vector` protocol (or a SIMD-backed extension): one source of truth in code. A few members diverge and stay per-type — chiefly `cross`, which returns a **scalar** in 2D (the perp-dot, for sidedness/winding/steering) but a **`Vector3`** in 3D (a perpendicular vector, for normals/frames/torque); that scalar-vs-vector split is the headline and wants a prominent call-out. Also 2D-only or reshaped in 3D: `angle` (one direction angle), `perpendicular` (unique only in 2D), the signed `angle(to:)` (3D is unsigned without a reference axis), in-plane `rotated(by:)` (3D needs `rotated(by:axis:)`), and the polar `init(angle:length:)` (3D is spherical). **Docs mirror the code:** one shared "vector basics" section (the schoolbook diagrams are 2D but teach the general idea), then a compact "what's specific" section per type, instead of two near-duplicate pages that drift. The practical-use notes split on the same seam — `dot`/`length`/`lerp` uses are dimension-agnostic (shared), while `cross`/`perpendicular`/signed-`angle` uses stay 2D-specific.
- **visionOS is a different render loop.** Immersive rendering doesn't use `MTKView`/`SketchRunner.draw(in:)`; it uses CompositorServices (`LayerRenderer`) driven by a manual render thread, plus ARKit world tracking. Keep the per-frame loop behind a seam that either an `MTKViewDelegate` or a visionOS layer renderer can drive, rather than assuming `MTKView` everywhere.
- **Reference.** swifty-creatives is the concrete study: it ships both a normal `MTKView` renderer and a visionOS `RendererBase` with a manual `renderLoop()` over `LayerRenderer`, and it's 3D-first (camera, depth, box and 3D text). Borrow the structure (camera plus depth pipeline plus dual render loop) and write our own.
- **Ray tracing is a later tier, and the platform has it native.** Once meshes exist, a fuller ray-traced render path (real reflections, path-traced stills a sketch leaves running, beyond the inline-RT shadow rays the point caster already traces) becomes reachable. Metal has first-class ray tracing (acceleration structures, intersection from compute kernels) on every Apple-silicon Mac, so this is Metal API work, not an engine to vendor. The oF-world prior art is ofxEmbree (Cyril Diagne, Intel Embree inside the oF loop, **no license file, so concept only**): what to mine is its call shape, a creative-coding-friendly "trace this scene" surface rather than a renderer rewrite. Not part of 3D mode's entry bar; it slots behind the camera/mesh/material work as its own pipeline kind.
- **Don't 3D-tax the 2D path.** Most sketches stay 2D, so don't make every draw call pay for a depth buffer or perspective divide. 3D is a mode you opt into, not a cost the 2D core carries.
- **Caveat:** the 3D mode itself builds and verifies on a Mac; visionOS needs the visionOS SDK plus a simulator or device.

## AR mode and templates (eventual; the Meta Spark gap)

Ollin aims to support AR sketches and offer a template-driven AR framework, filling the gap left when Meta Spark was discontinued (January 2025). Apple-only: ARKit plus RealityKit and Metal on iOS and iPadOS, and the visionOS immersive path.

- **It's a mode layered on the iOS and 3D/visionOS work, not a separate engine.** AR needs the iOS target (see [Swift Playgrounds and iOS](#swift-playgrounds-and-ios-not-started)) and the 3D camera and depth pipeline (see [3D mode](#3d-mode-partly-shipped)) in place first.
- **The Spark lesson is templates.** Spark's reach came from ready-made effect templates (face filters, world effects, plane and image tracking) people could start from. The Ollin version: AR-example sketches plus starter templates wired to ARKit anchors (face, world, image tracking), so an AR sketch is "fill in the `draw()`, the tracking is handed to you", the same template-as-on-ramp idea as the examples and `.swiftpm` starters.
- **Caveat:** AR needs ARKit on a device to verify (the simulator has no AR camera).

## Model examples and ModelTracker surfaces (not started)

`ModelTracker` runs any converted Core ML model, so new perception examples are mostly a matter of picking models worth showing — plus, for some, one small new output surface on the tracker. The standing delivery rule for all of them: **weights are never committed** — `Scripts/fetch-models.sh` downloads into the gitignored `Models/`, the example shows the run-the-script notice until they exist, provenance goes in `THIRD-PARTY-NOTICES.md`, and the real-model tests soft-skip where the weights aren't fetched.

Candidates, in rough order of effort:

- **Text-driven knobs — MobileCLIP-class embeddings.** `confidence(of:)` for *any phrase*, not a fixed vocabulary — "how spooky does the camera look" as a `0…1` knob. A real milestone rather than an example: it needs an embedding surface, the text-encoder side, and a tokenizer, and **the license of Apple's MobileCLIP release needs verifying before any fetch script points at it.**

Skip the plain ImageNet classifiers (FastViT, MobileNetV2, ResNet) — redundant with the built-in `ImageClassifier`'s ~1,300-label vocabulary. And the modern Ultralytics YOLOs (v8/26) are AGPL-3.0 — never bundled, never scripted, same tier as p5.js's LGPL.

## iPhone as a sensor array (partly shipped)

A Mac has no depth camera, no inertial sensors, and no spare Neural Engine for live perception. A tethered iPhone has all three, so the idea is to let it act as a sensor and on-device ML co-processor for a sketch that still renders on the Mac. The phone captures and perceives, streams the results over the wire, and the sketch reads them in `draw()` as typed values. The Mac keeps the Metal rendering ceiling; the phone fills the input gap desktop hardware leaves.

The starting want was live RGBD point clouds, the kind an Intel RealSense fed openFrameworks before its Mac drivers were dropped. An iPhone with LiDAR is the same world-facing depth-and-color sensor, except the driver is ARKit and Apple maintains it. Both the *recorded* path and the *live USB* path are in (`OllinRecord3D` reads Record3D `.r3d` clips and its live USB stream — see [`Docs/Record3D.md`](Docs/Record3D.md)): a depth map plus intrinsics unprojects, through the [3D mode](#3d-mode-partly-shipped) point-cloud path, into one splat per depth sample (around 49k for LiDAR's 256×192 map, ~300k for TrueDepth's 640×480). So the renderer, the unprojection, and the live wire are done; the work ahead is *more sensors over that wire*.

**One channel, many typed payloads.** Depth is only the first thing the phone can send. Because both ends are ours and both are Swift, the wire skips the packed-image trick cross-language tools reach for: it is a length-prefixed binary stream of tagged messages, each a typed payload the sketch reads through the same transport-agnostic `FrameSource` abstraction used for the point cloud. The phone app is a configurable sensor hub, so adding a sensor later is a new payload case rather than a new pipeline. A header struct shared verbatim between app and framework carries intrinsics, pose, and a version byte; the rest is raw or LZFSE-compressed channel data.

The phone runs the expensive model on its Neural Engine and ships kilobytes of structured results, so each new sensor is nearly free on the wire:

- **Desktop-impossible.** TrueDepth face mesh and its 52 blendshape coefficients (the Animoji engine: jaw, blink, brow, and smile as 0-to-1 values), 3D body motion capture from a single camera, LiDAR scene mesh with detected planes and real-room light estimation, 6DoF device pose, and the inertial sensors (attitude, gravity, acceleration, rotation rate) a Mac doesn't have at all. The motion stream is the cheapest to build and the most physical: a few floats, no camera, no model.
- **Possible on a Mac, but the phone is the natural host.** Vision runs on macOS too (that's the shipped [`OllinVision` catalog](Docs/Vision.md)), yet the phone holds the camera and the spare Neural Engine: subject segmentation, hand pose, optical flow, saliency, live text, scene and object classification, sound classification, and speech.

Most of those payloads are kilobytes. Only the per-pixel ones (segmentation matte, optical flow field, scene mesh) are heavy, and they arrive as textures, which is what the [layered effects](#layered-effects-and-compositing-partly-shipped) graph already consumes, so a live person-matte becomes a `Filter` input rather than a separate feature. Everything here is Apple-native (ARKit, Vision, Core Motion, Core Location, SoundAnalysis, Speech) with no third-party dependency, and it shares its prerequisites with the [iOS target](#swift-playgrounds-and-ios-not-started) and [AR work](#ar-mode-and-templates-eventual-the-meta-spark-gap).

The transport is the proven live **USB** path (the standard usbmuxd device tunnel) — full-quality LZFSE float32 depth plus camera intrinsics and ARKit pose, RealSense-grade, no extra dependency — and Ollin's own capture app speaks the same length-prefixed-tagged-payload wire, so the sensor catalog isn't capped by what one borrowed app exposes. Record3D's **WiFi** streaming stays deliberately *out*, correcting an earlier assumption that it would be the easy one: it's WebRTC (a heavy dependency, and the `record3d` library doesn't support it at all), gated behind a paid Extension Pack, and its depth is lossy hue-encoded with no pose — the worst option on every axis, and the reason USB is the only streaming mode supported. Device class gates the sensors (TrueDepth for face, Pro-tier LiDAR for rear depth and scene mesh, A12 and later for body tracking), and several heavy models at once will thermal-throttle, so running every sensor together is a practical limit, not an API one.

**The clean-room stance carries forward to our own app.** Both the `.r3d` file reader and the live USB stream are read clean-room from their public structure — the same constraint our own capture app's wire still works under: the `record3d` library is LGPL-2.1, the same copyleft tier as p5.js, so it stays inspiration only — reimplement the wire protocol, never translating its source, exactly as the sourcing rules treat p5.js. Record3D is credited like the other product references, not vendored. New sensor payloads added over the wire follow the same rule.

## Generative geometry (not started)

A tier of classic generative-art algorithms that produce *vector geometry* — points, `Contour`s, `Shape`s — and hand off to the geometry that already exists (the triangulated fill, the stroked path, the shape booleans, hatching, SVG export). They're geometry, not rendering, so they live in the `Ollin` core beside the shape booleans and the `Path` builder rather than in a satellite — none needs a heavy framework, and the split `OllinPhysics` took was about keeping simulation opt-in, not about dependencies. All are driven by the existing seedable `random`/`noise` so a result is reproducible, and each ships with an example; several are the natural implementation behind a [recreation](#examples-folder-maintained-ongoing).

- **Circle and shape packing.** Two flavors: *grow-to-touch* (seed points, grow each radius until it collides — classic circle packing) and *front relaxation* (push overlapping disks apart to equilibrium). The `OllinPhysics` `Packing` example already does the *collision* form via the Verlet world; this is the dependency-free geometry form for the common static case, and generalizes to packing arbitrary `Shape`s by their bounds. Output is `[Circle]`/`[Shape]`.
- **L-systems.** A typed grammar — axiom, production rules, angle, iteration count — interpreted by a turtle that emits a `Path`/polylines, so it rides the transform stack and the curve builder. Stochastic and parametric rules (seeded) give the organic variation; the classic plant/tree/Koch/dragon forms fall out. The recursive-branching ("recursive whispers") direction.
- **Differential growth.** A polyline or closed `Contour` that, each step, inserts nodes where segments stretch and relaxes every node under attraction (to its neighbors), repulsion (from all nearby nodes), and alignment — the organic, brain-coral accretion of the Anders Hoff / inconvergent family. A node-resampling stepper with a spatial hash for the repulsion broad-phase (the `OllinPhysics` collision hash is the precedent); output is the evolving `Contour`. The closest of the four to a simulation, but its product is geometry, so it stays on this side rather than in the physics satellite.

The reproducibility note matters: like the Art Blocks model the [variation galleries](#variation-galleries-and-seed-exploration-not-started) item formalizes, every one of these is a pure function of `seed()` plus parameters, so the same seed always yields the same packing/growth. License stance is the usual one: implement each from the *published technique* (credited in the README's Techniques list). Origin note: these surfaced from mining the `/algorithmic-art` skill's implicit technique vocabulary against what Ollin already ships (Voronoi/Delaunay, the foundational primitive of the tier, was the first to ship — a pure-Swift Bowyer–Watson, no library vendored).

## Variation galleries and seed exploration (not started)

The piece of the Art Blocks / `fxhash` generator model Ollin doesn't have yet. A sketch is already a *generator* in everything but name: `seed()` makes a run deterministic, `@Param` exposes its knobs, and `OllinApp.image(of:)` renders any frame off-screen. What's missing is the first-class notion of a sketch's **variation space** and the tools to explore it.

- **Seed navigation.** In the `OllinLive` inspector (and a sibling of the panel-less stats overlay): show the current seed, with previous/next/random/jump-to controls, persisting across reload the way `@Param` values already do (`LiveSession.syncParams` is the precedent). The host owns it, so the sketch only has to read `seed`.
- **Contact-sheet export.** Render an N×N grid of consecutive (or chosen) seeds into a single image — `OllinApp.contactSheet(of:seeds:)` / a `--export-grid` flag — by looping the existing `renderFrames`/`image(of:)` off-screen driver over seed values and tiling the results. The cheapest high-value piece: it's a loop over machinery that already exists, and it is exactly how a generative artist culls a seed space for the keepers.
- **What it is *not*.** Distinct from the [project generator](#project-generator--sketch-scaffolding-not-started), which scaffolds a *new* sketch folder; this operates on an *existing* sketch's seed/parameter space. The word "generator" is overloaded — keep the two clearly separate in docs.
- **Why it fits Ollin specifically.** Reproducibility is already a load-bearing design value (seeded `random`/`noise`, deterministic export, the snapshot tests). This surfaces that value as a creative tool rather than only a correctness one, and it's the workflow the whole external generative-art world (Art Blocks, fxhash, the p5.js "100 seeds" idiom — and the `/algorithmic-art` skill, whose entire artifact is a seed-navigable explorer) is built around.

## Examples folder (maintained ongoing)

The `Examples/` set is shipped and maintained — small, runnable sketches that double as the "learn it in an afternoon" on-ramp and the compile-tested showroom (current status, the `OllinExamples` gallery, and CI are described in [`CLAUDE.md`](CLAUDE.md)). The design decisions worth keeping, because they guide *extending* the set:

- **Layout organized by topic.** Group by feature so they read as a learning path — basics, color, motion, patterns, text, and so on. Each example is one minimal, focused sketch that shows one idea well. The top `Examples/README.md` indexes only the categories (a table linking to each category folder); each category folder carries its own `README.md` listing its sketches, so the front page stays small as the set grows.
- **Per-example folder, generic `Sketch.swift`.** Each example lives in `Examples/<Category>/<Name>/` and its file is always named `Sketch.swift` rather than `<Name>.swift`, so the example's identity lives in the folder name, not a repeated filename. The per-example folder is also each sketch's home for its own assets (fonts, images, shaders sit alongside `Sketch.swift`), which is the reason not to flatten the layout.
- **The single-file `@main` mechanism.** SwiftPM allows only one entry point per executable target, so each example is its own small executable target (scripted as the set grows, rather than hand-maintained). Adding `static func main()` to `Sketch` on the core (`extension Sketch { static func main() { OllinApp.run(Self()) } }`, which needs a `required init`) makes a file self-contained, so an example is just `@main final class HelloCircle: Sketch { … }` with zero boilerplate. Built once on the core, so any single-file sketch flow (examples, scripting, embedding) can reuse it.
- **A feature isn't done until it has an example.** Each new primitive or capability ships with one. Examples are also a forcing function for API quality: if the example is awkward to write, the API needs work.
- **Snapshot coverage grows with the set.** Compile-testing proves an example builds; render-correctness snapshot tests (`Tests/OllinTests`) prove it still renders the same — a sketch is rendered headlessly through `OllinApp.image(of:)` and its pixels diffed against a committed reference. A new primitive earns a small, deterministic fixture and a recorded reference, so the catalog stays regression-protected as it grows. The reference is GPU-specific — anti-aliasing differs across GPU families — so references are recorded on a developer's machine (`OLLIN_RECORD_SNAPSHOTS=1`) and the comparison stays a local gate, kept out of CI; keep new fixtures flat and pixel-friendly so the mean-difference tolerance has room. A peer Swift and Metal framework does per-primitive snapshot tests the same way (a frame hook gated behind `#if canImport(XCTest)`, using pointfree's swift-snapshot-testing) — a reference if richer image diffing is wanted later.
- **Reuse the samples elsewhere.** Examples can seed the Swift Playgrounds `.swiftpm` starter and serve as starter templates for new sketches. Author once.
- **Recreations grow by artist, and double as a build-it-to-find-the-gap forcing function.** The `Examples/Recreations/` set (organized by artist, homage framing, per-sketch provenance — see its README and the sourcing rules in [`CLAUDE.md`](CLAUDE.md)) ships Vera Molnár, Bridget Riley, and Osamu Sato. Candidate additions, and what each would exercise:
  - **Clean homage tier (historical pioneers).** **Georg Nees** — *Schotter* (1968), a grid of squares sliding from order into rotational and positional disorder: the canonical first generative recreation and a near-trivial fit for the current 2D core, so the obvious next one. **Manfred Mohr** and **Frieder Nake** — early algorithmic line and geometry work in the same tier.
  - **Lineage and concept.** **Casey Reas** — *Process* / agent works, a nod to the Processing lineage Ollin borrows from. **Sol LeWitt** — the *Wall Drawings*, instructions executed deterministically, an homage that doubles as a showcase of seeded reproducibility.
  - **Inspired-by only (living/commercial — credit, never port source).** **Tyler Hobbs** (*Fidenza*, flow fields — which the GPU `Particles`/`CurlField` path already renders at scale), **Anders Hoff / inconvergent** (differential growth), and **Jared Tarbell** (*Substrate*, crack growth — Tarbell has historically shared source under permissive terms, so a *port* may be license-clean if verified per-sketch, unlike the others, which are inspiration-only). These pair with the [generative geometry](#generative-geometry-not-started) tier: Schotter ↔ the grid, Tarbell and Hoff ↔ substrate and differential growth, Hobbs ↔ flow fields. (Candidate list sourced from mining the `/algorithmic-art` skill; it names no artists itself, so these map its technique families to the canonical figures.)

## Developer experience: Swift-idiomatic ergonomics (partly shipped)

A standing track, not a one-time task: keep mining Swift idioms to make the API read better than a literal p5 port would. "Feels like p5" is the shape (bare calls, terse positional args, motion by default), but Swift's type system lets the same call carry more meaning with no extra ceremony, and that's a differentiator worth pressing. The exemplar to extend: `canvasSize` is a `CanvasSize` enum (`.square(n)` / `.size(w, h)` plus named presets like `.uhd4K` / `.vertical1080`, with `.portrait` / `.landscape` to flip orientation, in `CanvasSize.swift`) — it reads as English, is discoverable by dot-completion, carries integer pixels as it should, and beats a bare `createCanvas(3840, 2160)` on both clarity and correctness. More of that. Candidates, in rough order:

- **Keep the presets pattern growing.** The orientation-flip trick (`.portrait` / `.landscape` as computed properties on a value type) generalizes: look for other places a bare tuple or magic number could become a named, dot-completable value with helpers, such as angle units (`.degrees(45)` / `.turns(0.25)` beside raw radians) or named blend modes when they land.
- **More idiom candidates.** Trailing-closure scoping beyond `withState { }` (already the model, and now the `drawShape { p in … }` path builder too); `ExpressibleByArrayLiteral` / `ExpressibleByIntegerLiteral` conformances where they read naturally (a color from a literal, say); `@dynamicMemberLookup` only where it genuinely clarifies. The bar: an idiom earns its place when it makes the call clearer, not just shorter, and never at the cost of the bare-call feel or the typed-core split.
- **Typed `@Param` beyond `Double`.** `@Param` is `Double`-only today — the live host renders one slider per handle. Generalize it to a small typed family so the inspector picks the right native control *from the property's Swift type*: `Color` → a color well with eyedropper, `Bool` → toggle, `Int` → stepper, an `enum` → segmented control or dropdown, with a `Disclosure` group for advanced knobs. For a generative-art tool, live **color** tuning is the headline gap — a sketch can dial quantities but not its palette. This is the natural companion to [variation galleries and seed exploration](#variation-galleries-and-seed-exploration-not-started): a variation space is parameters *plus colors plus seed*, and colors aren't tunable yet. There's a Pixelmator/Photos-hybrid Claude Design mock-up of the exact native control catalog (slider with editable value field, color swatch + eyedropper, segmented, toggle, stepper, dropdown, disclosure, a future per-param keyframe affordance) to build toward — its *parameter-control* surface is the spec; its monitor/clock stats card is superseded by the shipped inspector. Keep it sugar over the typed core; the control follows from the type, so a sketch just writes `@Param var color: Color` and gets the well for free.

## Project generator / sketch scaffolding (not started)

An openFrameworks-style project generator: the on-ramp that turns "I want to start a sketch" into a ready-to-run folder, instead of hand-copying boilerplate. oF ships its `projectGenerator`; the Ollin version asks a few questions and emits a tailored starting point. It's the generative sibling of the maintained [examples](#examples-folder-maintained-ongoing) set and the `.swiftpm` starter: examples are read-only showroom pieces; the generator produces a new, editable sketch.

- **What it asks.** Which capabilities the sketch will use, so the scaffold pre-wires only what's needed and stays minimal otherwise: images, shaders, text, parameters (`@Param` knobs), export, a starting `canvasSize` preset, and orientation. Each "yes" adds the import, a commented stub, and any per-sketch asset folder (fonts, images, shaders beside `Sketch.swift`).
- **What it emits.** A folder with a single-file `@main` `Sketch.swift` (the zero-boilerplate `Sketch.main()` form already on the core) plus, as chosen, an assets dir, a `Shaders.metal` stub, a `@Param` block, and a README. The single-executable-target mechanism is the same one the examples set already scripts; build the target-stanza generation once and share it.
- **Form factor.** Start as a CLI (`swift run OllinNew <name>` with flags or an interactive prompt): cheapest, scriptable, and reuses the runtime targets' patterns. A GUI in the style of oF's projectGenerator is a later nicety; the SwiftUI hosts (`OllinExamples`/`OllinLive`) are a reference if it's wanted. Ties to the `.swiftpm` starter, since one generated form is a Playgrounds App Project.
- **A scene-to-sketch variant.** Beyond a blank scaffold, the generator could emit a sketch *from a 3D scene file* (glTF/USD): the authored camera as a `camera(...)` / `perspective(...)` call, each node as a `withState { translate/rotate/scale; drawMesh(...) }` block, lights as `directionalLight(...)` and friends. This is the one-way, lossy companion to the runtime [`loadScene`](#3d-mode-partly-shipped) import: `loadScene` keeps the file as a live, re-loadable asset, while this hands over editable source the sketch then owns. Same "design tool → code" loop, different end state, so offer both.
- **Why it matters.** It's the same "learn it in an afternoon" lever as the examples and the live host: it removes the blank-page tax, and the questions double as a teaching tour of what Ollin can do.
