# Ollin design notes

The engineering design intent behind the planned work in [`ROADMAP.md`](ROADMAP.md). The roadmap is the short version (what's planned and how to help); this is the long version (how each piece would be built, the specific APIs involved, and why). A couple of shipped items stay only where their design rationale still guides future maintenance or evolution (extending the examples set, the Swift-idiom track); anything fully done and self-contained lives in its own doc or `CLAUDE.md`, not here.

These notes assume Ollin's two ground rules: it targets Apple platforms only (no cross-platform abstractions), and the bare p5-style API is sugar over a public, typed core, so a feature is built on the core first and given the bare call second. Geometry-emitting calls take a `draw` verb prefix (`drawCircle`, `drawRect`, and so on).

## Swift Playgrounds and iOS

The design home for the leg that runs a sketch on the phone and the tablet. The canvas is one view on either window system and `Apps/OllinSketchApp` is the reference project for wrapping a sketch as an iOS app; these notes carry what's ahead: the Swift Playgrounds on-ramp (the closest Swift gets to the p5.js "open the editor and type, see it move" onboarding, on-brand for the "learn it in an afternoon" goal), the tethered edit loop, and the smaller device affordances. The roadmap section is [The sketch on a phone, and Swift Playgrounds](ROADMAP.md#the-sketch-on-a-phone-and-swift-playgrounds).

- **Playgrounds questions, in dependency order.** An App Project (`.swiftpm`) is a Swift package whose manifest declares an `iOSApplication` product through `AppleProductTypes`, built by the Playgrounds app's own build engine and bundled compiler, not the Mac's toolchain. So: (1) the engine is the gate. The shipping app (4.7) will not compile a C, C++, or Objective-C target ("Clang Target Not Supported", which Apple's developer support confirms on the forums) or a `.metal` file ("Metal Files Not Supported"), both strings in its `PlaygroundBuild.framework`. A `.metal` file carried as `.copy`, copied and never compiled, is not refused: it travels into the app and compiles at run time, so the shader segments need no change (they could also travel as text under another extension or as Swift strings). The core links six such targets (libtess2, Clipper2, the shared shader-struct header, the sky model, tangents, spectral data) and ships its shaders as `.metal` segments. A prebuilt core is the way around in principle, and outside the app it works: built with the app's own Swift as a dynamic library with library evolution on, its C imports made `internal`, and its resource bundle inside the framework (where `OllinResources.resolve` already looks), it draws in a Catalyst app. The app does not load it, in any shape. Its project model materializes Swift source targets only. A binary target is dropped whether it sits in the project's own manifest (the XCFramework listed as a folder of code, "cannot find module") or in a package fetched from the web with the framework committed as plain files (the package resolves, then the build stops at "a reference to a missing target"). A static C library in an XCFramework is dropped the same way, and so is a system-library target, a module map over a header with nothing to compile, in the project or in a package. A binary package fetched as a zip stops the app earlier, at a deliberate trap in its package resolver: the resolver's library starts no subprocess on this platform ("subprocess invocations are unavailable"), and unzipping takes one. One more fact shapes a sketch in an App Project: its root target reads its resources from `Bundle.main`, since the build synthesizes no `Bundle.module` for the target that is the app. A prebuilt core also fixes `#if DEBUG` when the framework is built, so the parameters button would need a rule of its own there. After each app update, the check is a project that depends on a binary target, and one with a system-library target, built in the app: the day either target is materialized, the prebuilt route opens; the two refusal strings in its build framework are the cheaper first look. Two smaller facts wait behind that gate. Five public members hand a sketch the shared C structs (`drawParticles` on a GPU buffer, `neighborStep`, `drawMesh(instances:)`, `Camera3D.matrices`, `SpatialHash.gridBuffer`), so a prebuilt core ships `COllinShaders` beside it, as a second binary or as generated Swift, since a header-only module is a system-library target and the app drops those. If the engine never takes C-family code, the other route is a Swift-only edition generated from this tree: the spectral data and the sky model are tables and a few hundred lines, MikkTSpace and the shared header a week or two each (the header's structs generated with their layouts checked against the C), Clipper2 has a Swift port that its upstream project lists, and libtess2 is the long pole at several weeks. And the app bundles Swift 6.2 against the tree's 6.3 floor (its `PlaygroundCompiler.framework` carries the version string, and its own modules are built for `ios-macabi`, the Catalyst preview). That gap is a dozen or so errors across as many files under the app's own SDK, each fixed by naming a result type: an Ollin type writable as a number literal gives 6.2 a second reading of `2 * x`, which 6.3 settles by itself. (2) The dependency arrives by git URL, which the public repository serves, and that is also the only shape a tablet can use. A local `path:` dependency is less of a desk bench than it looks: the Mac app is sandboxed with free access to `/Applications/` and `~/Documents/Playgrounds/` alone, so a checkout anywhere else reads to the user as having no access to the package, and pointing at one means keeping a copy of the tree under that Documents folder. (3) It runs on real GPUs, the Mac's or the tablet's, so the renderer's device tier applies and the simulator wall is irrelevant here; don't chase the simulator to test Playgrounds. The Mac app previews an App Project through Mac Catalyst, so a platform seam there keys on the operating system rather than on whether AppKit imports, and a runtime shader compile names its language version. Prefer the Swift Playgrounds app's App Projects over the semi-deprecated Xcode Playgrounds throughout.
- **The starter is a generator kind, not a hand-kept sample.** `ollin new` writes packages, and an App Project is one, so the Playgrounds starter is a `ProjectKind` beside the others rather than a checked-in sample that rots: the manifest with the `iOSApplication` product, a host file in the reference app's shape (a `SketchView` in a `WindowGroup`, `SwiftUI.Scene` spelled out since the framework has a `Scene` of its own, safe areas ignored), and one small touch-driven sketch, seedable from the examples the way `--from` already seeds. Unlike the `ios-app` kind, it needs no Xcode project and no signing team. The host file can go too, if the framework owns the host: on the Mac `@main` on a sketch already opens its window, and the same entry on iOS would open a full-screen host, so a project is the manifest and one sketch file. Playgrounds gives an app no way to add controls to its own window, so the parameters live in the app: the inspector's `ParametersListView`, which already compiles for iOS, as a side panel on the tablet and the Mac and a sheet on the phone. The host serves Xcode projects and `ollin phone` as well, and it follows the gate above rather than leading it.
- **Keep shaders Playgrounds-safe.** Swift Playgrounds' support for SwiftPM build-tool plugins is unreliable, so don't go plugin-only for shaders. Runtime source compilation stays a first-class loader, and it is also what makes a shader edit instant on a device.
- **Scope inside the sandbox.** Drawing, touch, the parameters, and the shader compile are the Playgrounds surface. The export tier writes files where the sandbox has opinions, so it stays desk work until someone asks; nothing about drawing needs it.
- **Beyond the cable: the sketch on a phone that is not here.** The installed loop needs pairing, which reaches a phone on the cable or the same network and never one across the internet, since an install goes through `devicectl`. The picture stream is the way to a phone anywhere, and what it still needs is a transport past the usbmux tunnel. The sender is handed a connected socket and the phone's listener already accepts on every interface, so the local network is the short step: find the phone by Bonjour and dial it directly. Across the internet the phone has no address a Mac can dial, so it needs a rendezvous both ends reach out to, which Ollin does not run. Any network path also needs pacing the cable never asked for: a bit rate that follows the measured throughput, and a way for the phone to ask for a keyframe after a loss.
- **The tablet keyboard.** UIKit press events (`pressesBegan`/`pressesEnded`) feed the same key path the desk view feeds, so `keyIsPressed` and the key callbacks work with a hardware keyboard on a tablet.
- **Verification:** iOS builds verify on a Mac with `xcodebuild -destination 'generic/platform=iOS'`; anything hands-on needs the device.

## Color additions deliberately kept out

Rationale that still gates future color work:

- **Other color spaces stay out.** Classic Lab/LCH (the 1976 space OKLab was built to fix; interpolating through it bends blues toward purple), CIECAM16/JCh (a full appearance model that needs viewing-condition parameters; OKLab was fitted to give most of that benefit without the machinery), and DIN99/DLCH (an industrial color-difference standard). Any of them can arrive later as a plain conversion if matching an external spec calls for it.
- **Further curated palette collections stay license-gated.** Collections scraped from ColourLovers and similar sites are not license-clean and stay out; anything added must carry a permissive license the way the ColorBrewer data does.

## Layered effects and compositing

OPENRNDR-style effects that compose in layers: draw into off-screen layers, run filters over them, composite with blend modes. The substrate (`renderTarget` / `withTarget` / `filtered` / `combined` / `postProcess` / `generate` / `feedback` and the `compose { }` DSL) is inventoried in `CAPABILITIES.md`; what belongs here is growing the catalog on top of it. The reference menus guide what else to add and how to shape it: AsyncGraphics (its `Graphic` is an `MTLTexture`, effects are functions returning new graphics, plus a blend/stack model; borrow the compositing architecture, not its async call shape), SwiftUIShaders (MIT, a menu of forty-odd post-process effects such as holographic, kaleidoscope, datamosh, and thermal, to mine and reimplement), and ofxFX (MIT, Patricio Gonzalez Vivo: composers, the bokeh/ripple/flow passes still worth taking). More two-input ops (layer-blend variants, chroma keying, wipes and other transitions) slot in as further `Combine` cases. Same stance throughout: study and reimplement, credited in `ATTRIBUTION.md`.

- **What the effect survey found, ranked.** `EffectInvariantTests` pins each of these with its measurement (2026-11-09), so a fix turns its pin green and the pin is then removed. The order is by how likely a sketch is to meet the fault and how wrong the picture is when it does.
  1. **A map read as the gray that was drawn.** `.displace` reads the other layer in linear light (measured), and by reading so do the `.vector` field of `.lineIntegralConvolution` and the luminance of `.mask`, where `.defocus` and `.anaglyph` read the gray a sketch wrote. So `Color(white: 0.5)`, the documented no-shift gray, stores 0.214 and moves the whole layer (5.5 px of a 96-pixel canvas at an amount of 0.1; the `Effects/Aside` example draws its map over exactly that gray), a clear texel of a map reads as the largest shift there is, and a soft-edged map on a clear layer is a hard step. Ruled 2026-11-10: every effect reads a gray as the sketch wrote it, so the map takes the defocus rule (encode on the read), with its alpha as the weight of the shift.
  2. **Sizes in canvas pixels on a scaled layer.** Every pixel-valued argument is in the layer's own texels: on a half-scale layer a Gaussian of radius 4 spreads by 7.98 canvas pixels, an outline of 6 grows a disc by 12, a pixelate of 8 makes 16-pixel cells, and a shadow's offset of 40 lands 80 away (a measured field's distances and an anaglyph's separation follow the texels too, by reading). A supersampled export is already compensated (filters run at canvas size), so the layer's `scale` is the one setting that changes a look, and it is the setting the reference recommends lowering under a blur. Ruled 2026-11-10: a filter's sizes are canvas pixels at any layer scale, so `scale` becomes a pure quality setting. It is one multiplication where a pass's sizes are built, it halves the spread every sketch that filters a half-scale layer has today, and the changelog names it as a breaking change of look.
  3. **Filter arithmetic.** Each a few lines. `dither(levels:)` multiplies by the level count and divides by one less, so a flat 0.5 at two levels is all white. `contour` reads a flat field that sits on a level as on the line (zero distance over a zero pixel step), so flat white comes back black. `gridLines` takes the pixel step of a coordinate that wraps at the cell edge, and where the wrap falls inside one 2 by 2 block two pixels read 0.81; a `weight` of 0 still draws at half. The mirrored fold is one minus the coordinate on the first cell, so `tile(count: 1, mirrored: true)` is the picture turned half round (the kaleidoscope folds through the same line, by reading). `glitch` reads three channels from three places under the green one's alpha, and `crosshatch`, `lineScreen`, and the pattern generators return their colors unmultiplied (`checkers` measured, its five siblings by reading). `grain` adds its seed to the position before the hash, and single precision has no fraction left by a seed of 200,000 (16 values where seed 0 gives 1,605). `motionBlur` steps in the layer's 0 to 1 coordinates with no aspect and always sixteen taps. `levels` clamps before its curve, `lightLeak` adds its dither before the intensity's floor, `vibrance` under -0.5 turns the hue (pure red at -1 reads (0, 0.43, 0.43)), `oilPaint` averages colors already divided by their alpha (a half-clear shape's rim 4% dark), and `colorama` leaves a gray ramp gray.
  4. **The layers' bookkeeping.** Every plain layer is filled before any feedback layer in a frame, so a layer that draws a feedback's image holds the frame before (pinned 2026-11-10). Layers are filled in the order their first block opened, so a layer opened first draws a later layer's image before it exists (the fill order wants the read dependencies, as the filter ops already have). A `background` in a layer's later block clears that block only, and drops what a second layer drew inside it. A handle kept from `setup()` keeps its last clear color. `compose` under an active transform draws its layers under the transform and then the finished layer under it again. A combine whose other layer nothing drew into is skipped to empty, where a mix of 0 should still be the base. Drawing into a filter's result is dropped without a word. `Feedback.previous` on a frame with no block is two frames old. An accumulator's `reset()` after the block zeroes the count the block already took, so the mean reads a tenth, then double, then one pass too many.
  5. **Half floats in a loop.** A half float is stored cut off, never rounded up (of 64 probe values, none above its nearest half), so every write loses half a step on average. One pass hides it; a loop compounds it: a fade at 0.98 holds 0.128 of itself after 100 frames where the gain gives 0.1326, a running mean that keeps 0.98 settles 4.1% dark with an alpha of 0.976, and a Gaussian of radius 8 gives back 99.8% of its light a pass. The candidates, each to be measured for cost: a `Feedback` that defaults to single precision, a half step added back where a persistent layer resolves, or a dithered store.
  6. **A spectrum that keeps its precision.** `.fourier` writes single precision, but its layer carries the picture's precision forward, so a combine over it is half float: on a default 512 square a mask that keeps everything brings white back as 0.376. The transform's result wants `.float32` whatever it read, which is one line where the filter is recorded.
  7. **Tone cuts and the gray a sketch writes.** `threshold`, `levels`, `posterize`, `solarize`, `lumaKey`, the pivot of `colorGrade`, and `invert` work on linear values, where `xdog`, the two-color dither, `filmGrain`, and `lut` work on display values: `threshold(0.5)` cuts at a display gray of 0.735, and a contrast of 0 lands on display 0.735 rather than mid-gray. Ruled 2026-11-10 with item 1: the tone filters read the gray as written too, so `threshold(0.5)` cuts at the gray seen as half, the look of every sketch using these seven changes, and the changelog names each.
  8. **Read and not yet measured.** `Sim.selfWarp` and `.datamosh` under `.float32` blit between two pixel formats, and `.fluid` ignores the precision it is given; a restart that lands on the same frame count is taken for a repeated encode and skips the persistent layers' step; `snapshot()` is nil for the four multi-field sims; a field's direction outlives its reach by about one ladder step (measured: 60 px from a shape under a reach of 32 it still points); the Ising checkerboard is not one across the seam of an odd-sided wrapping field; a seed past about 1e8 collapses a seeded start; `droste` measures in half heights, so a portrait layer smears its sides; `liquidMetal` binds the aspect and never reads it; and four `pow` or `atan2` calls can meet a zero. The reference's wording that these and the measured items contradict (pattern `scale` counts cells down the height, an aside's modifier is `.scaled`, `filmGrain` keeps the mean of the encoded value and lifts the light by 21% at an amount of 0.2, `bubbleWrap` veils the film between its bubbles) is one pass over `Docs/Drawing/Effects.md`, made with the changes items 3 and 8 bring.
- **A user shader that hands back light past white.** A picture shader returns straight sRGB, and the wrapper decodes it with the curve that runs past 1, so a color brighter than white survives the return. The library's `linearToSrgb` stops at 1, so a shader that works in linear light and wants to return more than white writes the inverse curve itself. The encode that runs past 1 wants to be a library function beside `srgbToLinear`; a filter shader may also want to return linear premultiplied color as written, the way a simulation kernel returns its state.
- **A feedback layer as the other side of a combine.** `combined(with:_:)` takes a `RenderTarget` as the layer it combines with, so a `Feedback`'s picture can be a combine's base and never its second input. The way through is a filter over the feedback, whose result can be the second input. A copy does not work: a plain layer that draws the feedback's image is filled before the feedback is in the same frame, so it holds the frame before (measured in a sketch: the copy lagged the newest marks and missed that frame's fade). A feedback wants to be accepted there directly, and a layer that draws a feedback's image wants to be filled after it.
- **A measured field that is exact near the edge.** Within a pixel of an edge, `.distanceField` is the distance to the nearest of a row of discrete seeds, one per crossing found between two pixels, so a pixel lying between two seeds along the edge measures up to about 0.3 pixel long. The layer styles show it (measured 2026-10-08 on a 360-gon's multisampled edge): a one-sided outline under two pixels wide carries up to 0.06 pixel less than its width and a centered one up to 0.125, and the bevel takes its direction from a Sobel stencil two pixels wide because the direction channel turns by up to atan(0.5/d) between neighbors. The canonical answer is the anti-aliased Euclidean distance transform of Stefan Gustavson and Robin Strand (Pattern Recognition Letters, 2011): an edge pixel's distance to the edge estimated from its own coverage and the local gradient, with the offset to the edge carried by the flood. Measure it against the current seeds first, on the zero contour, `cuttingTheFieldGrowsTheShapeByThatMuch`, the outline widths, and the flat light that shares the field, since it moves every consumer of the field.

## 3D mode

2D stays the default and most sketches stay 2D, but 3D is a mode in its own right: a sketch opts in by setting a camera and, on the same Metal core, draws depth-tested point clouds and lit solid primitives, with richer shadows and materials as the mode grows. The iPhone point cloud renders through it, and visionOS and AR build on it. openFrameworks and OPENRNDR set the capability bar here, so the target is known. (The foundation, from the camera, depth buffer, and transform stack through point clouds, meshes, lights, materials, and cast shadows, is inventoried in `CAPABILITIES.md`; the notes below build on it.)

- **The further scene-import legs.** Over the structure-preserving import and animation playback a loaded `Scene` gives (see `Docs/3D/Scenes.md`): vendor `EXT_`/app-specific glTF extensions beyond the ratified `KHR_` set.
- **Material-from-file refinements.** A merged `loadMesh` model uses its first base-color material (glTF/USD/OBJ-MTL). The UV-origin convention for a Model I/O `imageFromTexture` result is unverified and may need a v-flip. A material carries **one** wrap mode for its whole map set, read from the file's first map; a format that gives each map its own sampler (glTF does) would need a wrap per slot to reproduce exactly, which no exporter seen so far asks for. The OBJ reader welds corners by their (v, vt, vn) index triple, so a scan that writes one `vt` per corner (a Polycam export arrives with 141,291 corners over 27,109 positions) comes back with one vertex per corner, which also triples every per-vertex CPU pass over it. Welding by value, the same position and the same uv within a tolerance and the same normal, would fold those back to the positions a chart seam does not split; the tolerance is the design question, since a seam is exactly two corners at one position with different uvs.
- **The light grid's next two steps, if the cost ever asks for them.** The per-tile cull spans the whole depth range, because there is no depth pre-pass to bound a tile by: a **depth-bounds** refinement (min/max the tile's own depth, then cull against that slab, which is the difference between a tile and a cluster) tightens it for a scene with lamps at many depths. And the inline path below `OLLIN_MAX_LIGHTS` culls nothing at all, which is why a measured 16-lamp culled frame beats an 8-lamp inline one; **culling every lit frame** would pick that up, at the cost of the byte-identity the whole 3D reference set rests on, so it is a 1.0-shaped call rather than a free win.
- **A heavy field in bounded passes.** The GPU's hang check is on progress through a pass, tile by tile, and not on a frame's time: a 64-capsule field at 1080 by 1920 draws at 1.42 s a frame, where half a second of work packed into the 135 tiles of a small frame came back as a hang. By a CPU count of the march priced at each run's measured rate, the busiest tile that has drawn clean carried about 8.5 ms of GPU time and the one that hung about 16 ms (`ARCHITECTURE.md`, *A pipeline that traces nothing*). A tile's work is its 1,024 pixels times the steps each marches times the nodes each step reads, so a lower march resolution moves the pixels and leaves the work in a tile where it was, and a field near the 256-node limit under `castShadows()` is past what has drawn clean at any size (about 22 ms in its busiest tile by the same count). Two approaches, which combine. **Stipple passes:** the field drawn into a target of its own in N render passes, each shading one pixel in N of every tile and discarding the rest at once, N chosen from the field's nodes times its steps so that no pass asks a tile for more than what has drawn clean; that bounds the work by construction for any field, and the reduced march's target and its composite are the base. They have to be separate render passes, since a tile is shaded once for every draw of one pass. **Bounds on a field's parts:** a skip instruction ahead of a combine's second operand, which jumps past it when the query point is farther from that operand's box than the first operand's distance plus the blend's reach, where the combine's result is the first operand's exactly; a field of many separate parts then costs what is near the ray. The node count is also a poor measure of work by itself (a fractal leaf iterates, a block scope reads its child up to nine times), so the estimate that picks N weighs each node. The check that closes it is the 126-capsule field under a shadow at 1080 by 1920 on the GPU, at @eaviles's word, since a miss there restarts the GPU.
- **A traced frame's surfaces that do not trace.** A pass with a traced shadow or traced reflections draws every lit kind through the build that carries the traversal, and on a GPU that traces in software that is about eleven times the cost of each lit pixel before a ray is cast. Two questions, measurements first: whether a point or area caster should cast through its map on such a GPU in the live window and trace only in an export (the switch exists, `OLLIN_NO_TRACED_SHADOWS`; the question is the default, and it is @eaviles's ruling), and whether the traced build can be kept to the batches whose material and lights can reach a traced path.
- **The translator's limit note.** The GPU's offline translator prints `Max Unstruct ID ... exceeds supported limit` for every lit fragment compiled with the traversal (870 for the mesh fragment, 871 for the field's; 439 and 440 before one ray query served a fragment) and nothing for a build without it. What passing the limit costs is not known, since the fragments that print it draw correctly. It wants a reduced case, and a report to Apple if @eaviles chooses, and it is the first thing to read if a traced frame misbehaves on that class of GPU.
- **Build order.** Softer shadows (and supporting more than one caster at once) are the rendering-heavy step. The tier-one material recipes are pure data over the existing light/material model with no renderer change, so they land cheaply (the way the lighting presets did): a `Material` surface beside `specular`/`specularSharpness`. Each step is usable on its own.
- **visionOS is a different render loop.** Immersive rendering doesn't use `MTKView`/`SketchRunner.draw(in:)`; it uses CompositorServices (`LayerRenderer`) driven by a manual render thread, plus ARKit world tracking. Keep the per-frame loop behind a seam that either an `MTKViewDelegate` or a visionOS layer renderer can drive, rather than assuming `MTKView` everywhere.
- **Reference.** swifty-creatives is the concrete study: it ships both a normal `MTKView` renderer and a visionOS `RendererBase` with a manual `renderLoop()` over `LayerRenderer`, and it's 3D-first (camera, depth, box and 3D text). Borrow the structure (camera plus depth pipeline plus dual render loop) and write our own.
- **Ray-traced reflection refinements.** The **subsurface diffusion** behind `Material.scattering` does not reach a reflection: its blur runs over the primary view's own buffer, and the transmittance half needs a caster's depth the traced direct light never reads, so a skin or marble body arrives in a mirror with its shading unsoftened. That is bigger than the compact per-geometry finish record the other finishes are stored in, which is what makes it the one left.
- **Richer 3D physics: the solver's own remaining gaps.** The one thing still ahead is **soft-body reach**, and it is upstream's rather than Ollin's: self-collision and cloth-against-cloth are gaps in the solver, so a folded sheet passes through its own layers, and tearing needs a shared vertex split and a rebuilt constraint set mid-simulation, which it cannot do at all. Both stay out until the library grows them. The solver's **volume constraints** (tetrahedra held at their rest volume) stay out for a different reason, a measured one rather than a missing one: built and probed against the shipped `pressure`, they tie on holding a weight, tie on coming back from a dent, and lose on coming back from a hard squash, because their residual is formed from an *unsigned* volume and so reads an inverted tetrahedron as correct, where a gas law's push grows without bound as the space shrinks. The numbers and the two things that would reopen it (a vertex-follows-tetrahedron binding, or a signed volume constraint) are in [`ARCHITECTURE.md`](ARCHITECTURE.md). The solver's neighboring **hair module** stays out for four measured reasons. It accepts no force, so the only way to move a strand is to move the head, where Ollin's cloth and rope examples are driven by `applyForce`. It collides only with `ConvexHullShape`, and Ollin's figures are meshes and capsules. It requires an authored groom and a skinned scalp, where a sketch generates its own geometry. And the rod family already exposed carries 20,000 simulated strands in a 60 fps frame against its 2,500, so the Metal backend it needs (49 shaders cross-compiled and packaged, Objective-C++ admitted into the C bridge's target, a new draw path for a foreign compute buffer) would buy a strand count `Rope3D` already reaches. The measurements and the reopening bar are in [`ARCHITECTURE.md`](ARCHITECTURE.md); if hair is wanted before then, build it as a **multi-strand `Rope3D`** (one soft body holding many rod chains) rather than from that module. When they arrive, the shipped rules still apply: land it as *more capability on the existing surface* (a parameter on `addSoftBody`, a call on `SoftBody3D`), never a parallel system; keep the C bridge flat-POD `extern "C"` with `JPH` never reaching Swift; keep the no-pixel-snapshot policy (determinism is per-binary, so behavioral tests pin each slice) and `unitsPerMeter` as the one scale bridge; and ship an example, tests, a `Docs/Simulation/Physics3D.md` section, and Guide Ch 32 growth together.
- **Lines in 3D, the parts a 2D stroke has and a 3D one does not yet.** A line with 3D points draws whole while a dash, a brush, or a width profile is on, with a note. A dash wants cutting along the projected path, as the 2D stroke cuts it, with each cut point carried back to the 3D point it stands for: a fraction of the way across a projected segment is not the same fraction of the 3D segment, so the cut is mapped through the two ends' clip w (the perspective-correct parameter), and the cut point takes its depth from there. A profile multiplies the per-point half-widths the expander already takes, so it is the smaller of the two. Three outlets leave the line out today and could carry it. A recorded `Batch` has no camera, so its lines would expand at replay against the camera then active, the way a recorded point cloud draws through whatever camera `drawBatch` meets. A spatial export could write USD `BasisCurves` with a width per point, which is a line rather than a surface. And a web page could replay the line's world points and offsets through a WebGL vertex stage that does what `ollin_line_vertex` does, with the frame's camera recorded beside them; a page whose 3D is only lines would then cross without falling back to video.
- **Feature edges on a mesh field, and in call order.** A `MeshField`'s copies draw their faces without their feature edges: the field's GPU cull writes the arguments of the solid draws, and the edges would need the same visible-copy list to write theirs, one more indirect draw per entry. A field that wants edges today draws its copies through `drawMesh(_:instances:)`. Separately, meshes drawn one call at a time put each mesh's edges straight after its faces, so where two solids nearly touch, within the depth pull, the edge of the one drawn first can show through the face of the next; a run of mesh draws could hold its edge batches until the run ends, as an instanced call does by construction. Both wait for a sketch that shows them.
- **Lofting: what is ahead.** A loft matches its sections' contours in order and leaves out a contour some section lacks; a hole that closes on the way (a tube whose bore pinches shut) would want the partnerless contour to shrink to its own center, the way a 2D morph handles it, with the cap at that end filled as if the hole were not there. The blend across unevenly spaced stations reads the sections as evenly spaced (a uniform cubic, the one `Curve3D(curveThrough:)` uses), so the surface's speed along the path changes at a station while its direction does not; a cubic whose knots are the stations themselves would smooth that too. On a closed path the last section joins the first as it was drawn, so a loop whose sections turn progressively twists at the join rather than spreading the turn round, which the path's own frames do for their torsion. Each is a small addition to `Mesh.loft` when a sketch asks for it.
- **Volumes: what is ahead.** The march (`ShaderVolume.metal`) composites after a pass's geometry and reads its resolved depth; the pieces below extend it without changing that shape. **Lighting the medium at a coarser rate, measured and not taken:** lighting every other lit step and interpolating between the two ends of a run, or simply holding the last light, saved nothing on the M2 at 1080² in the saturated harness (interpolated 10.98 → 11.92 ms on the plume example and 10.38 → 11.17 on a dense 64³ cloud; held 10.59 → 10.63 and 9.94 → 9.84), so the march's cost is in its steps and their reads rather than in the light, and every step is lit in full. What is left of the idea is the view-independent part of the light arriving at a point (everything but the phase) worked out once per frame at the grid's lattice, folding the solids' shadow-map tap into the transmittance grid, which turns each lit step into one trilinear read per light in place of a shadow tap, a grid read, and the octaves; it is worth trying only once a measurement says the light is the cost, and its price is a solid's shadow through the medium resolved at the lattice rather than per step, a softer shaft edge on a coarse grid. **The rest of the scene's light:** point (cube) and traced casters do not shadow the medium, and the area kinds scatter nothing. Each is a read the march does not make yet. **The bounce's reach:** the octave sum thins only the medium's own shadow, so light never bends around a solid into its shaft through the cloud, and a diffusion term on the shadow grid (a blurred copy read as the bounced light's even part) is the way to that if a picture asks for it. **Two volumes that pass through each other** order as wholes by their boxes' centers; marching them jointly over their sorted intervals would interleave them. **A glow that follows a ramp:** the classic transfer function, a `Ramp` from the grid's value to the glow's color (fire from a temperature field), would be a 1D lookup beside the grid.
- **Motion for copies placed on the GPU.** A `drawMesh(_:instances:)` list inside `withMotion` keeps last frame's placements on the CPU and the velocity pass reads them per copy. Copies placed by a compute buffer, and a `MeshField`'s, never pass through the CPU, so their last frame would have to be kept on the GPU: for a compute buffer, a copy of the buffer taken before the kernel writes the frame's placements (and kept per buffer, since a sketch may write one twice); for a field, its placements already live on the GPU and stay put unless the field is rebuilt, so a moving field moves through its draw-time matrix, which a field mover would carry as one transform, and the cull's compacted list would map each visible copy back to its id. Separately, at an overdriven shutter (4) on the default tier the streaks read grainy across a fast copy's body: the reconstruction gather's taps are tier-bound (9, 15, 27), and a shutter past 1 stretches the same taps over a longer streak (to the `k` clamp), so `.detail` is the smooth one. Whether an overdrive should raise the count with the streak is the question there.
- **The colonnade's fog.** The `3D/Effects/Atmosphere` example's fog mode (its default; aerial perspective is held under space) reads as a solid layer: below the horizon every pixel is the fog's color and only the column tops above it show, where its poster of 2026-09-26 showed the near columns clear through a mist pooled low. The frame renders pixel-identically at `4c513b60` and after the sky's sun, so the change came between 2026-09-26 and that commit; a bisect over those commits (a release build of the one example each, frame 480 with `--photo --seed 1`) would name it. The example's media shows the current picture meanwhile.
- **Depth of field on the canvas: the parts ahead.** `depthOfField()` runs over the main canvas: a `withTarget` layer and the accumulation surface (`noClear()`) stay sharp, and the pass would need the resolved depth each one keeps. The cost is a full-resolution gather (about 14 ms at 1080 by 1080 on an M2 at `.default` over a frame full of blur); the far field, whose blur is wide and smooth, could gather at half size and be brought back up, as the flare's ghosts are. **The hidden layer reaches the far field only under a veil.** The scene drawn a second time behind the first surface is read under a pixel in front of the focus, where the cover share decides how much of it shows, and under a near veil tap for a pixel behind the focus. A mesh built or loaded by hand carries no word on whether it is closed, so its back face stays out of the layer; the print check's boundary-edge count could answer it once per mesh if a case asks. Just inside the top rim of a near ball against the backdrop the canvas reads darker than the lens (0.02 over a 5 px ring on the lens figure's scene, the cover there within a hundredth): the lens looks over the ball's top from the lower half of the aperture and sees the sphere's own limb, points that face away from the eye's center and so are culled from the hidden layer as back faces; a peel that kept a closed mesh's back faces where they face some point of the aperture would carry them. A one-pixel hole in a near surface (a gap between floor boards) is found by some taps and missed by others, which shows as a faint dotted line where the lens draws a smooth one; the tap count barely moves it (the gap lines' high-frequency error against the lens read 0.0012 at the default tier and 0.0010 at the detail tier on the lens figure's scene, at 288 and 768 taps), so the lever is a read of the color at the tap's own footprint, which has to stay on one surface or it invents a blur a sharp line never had.
- **A traced sequence, cheaper.** What a path-traced sequence could still save beyond the per-pixel stop (`--pt-noise`), the frames carried across it (`--pt-reuse`), and the time budget a frame (`--pt-seconds`), motivated by a sequence of two thousand polished-metal copies under a lighting-only environment at 1080 by 1920, where 128 denoised samples take 12 to 14 s a frame and 256 take 27, so a minute of footage is a night or a day. *A sharper history read:* the carried frame is read through the four texels around where a pixel was, and every frame a surface moves by a fraction of a pixel that read spreads a pixel-wide lamp speck into its neighbors a little, which a file that clips at white shows as a brighter surround (the bead field's mid-tones read 4.5 levels bright against a sharp render while its specks dimmed); the published answers are a Catmull-Rom read of the history (sharper, not sharp: a speck still spreads, more slowly) and a history clamp fed by the frame's spatial neighborhood (the two-sample spread clamp lets the smear through because the smeared history's own spread is wide), and an edge-aware read that takes the nearest texel where the four disagree beyond their errors puts a positional jitter into a panning camera's floor, so it is not the answer either. *A blurred field of movers at different rates:* under a lens a pixel follows the mean motion of the movers inside its circle of confusion, and where those move apart (the far half of a sweep) the mean fits none of them and the carried light smears along the sweep; refusing the history where they disagree by over a pixel refuses most of such a field and gives the gain back, so the next step is a motion per depth layer inside the circle, or the raster's own depth-of-field split, before any threshold. *Reuse that knows a reflection:* the frames carried across a sequence follow each pixel by its surface's motion, and a polished surface's reflection does not move with its surface (a spinning ball's highlight stays put, a mirror's image moves with the eye and at twice the turn), so on such a pixel the facing test drops the history and the pixel falls back to its own frame's count; the published answer is a second motion vector for the reflected point, the hit behind the mirror reprojected as if it stood there (the virtual-position reprojection the real-time denoisers use for specular history), which would let a slowly turning bead field carry its reflections too, and wants the first hit's reflected distance written beside its depth. *Reuse that the stop reads:* the per-pixel stop judges each frame's own samples, so under reuse a pixel whose carried history is already settled still traces the frame's minimum; a stop that read the carried spread would let a still region of a sequence trace a handful of samples a frame, and would want the history's count folded into the convergence check at the round boundary. The stop has one open end: the rare bright path a pixel has not seen when it is checked, which no per-pixel statistic can count. The published answer past a minimum count and a neighbor rule is a hierarchy over blocks (Dammertz and colleagues, 2010) or a reset of a pixel's remaining count when a late sample falls outside its criterion (the RenderMan 2018 paper), either of which would want a scene that shows the gap first. The bound on twice-bounced light (`--pt-clamp`) answers only the caustic kind of firefly, and the scene of two thousand polished beads mirroring a lit studio is not that kind: its grain is one-bounce light, the studio's lamps through each bead's glossy lobe, where the bound takes 7.5 percent of the frame's light at 4 for a tenth of a decibel, and bounding one-bounce light too (the production tracers' *clamp direct*) takes half the frame, since those beads are their reflections. That scene's grain was the pixel's footprint on a curved near-mirror (two thirds of its per-sample variance, measured with the jitter and the lens frozen) and the point light's highlight through a near-delta lobe, and the tracer reads the environment and the lights at that footprint; two levers stay open past it. The table's draw and the continuation read one filtered picture, each at the level the cone reaches along its own direction, while the table that aims the draw is still built from the sharp map, so a draw into a lamp's cell reads the lamp spread over the footprint where the table priced it sharp: a table built per footprint level (a chain of tables, the draw taken from the level the cone asks for) would match the draw's importance to the picture it reads, which is what a polished scene under a lamp-lit studio would want next. And the footprint is isotropic, the mean of the triangle's three edge curvatures, so a surface curved one way (a polished cylinder, a wire) is under-filtered across its flat axis; the published bound takes the largest visible edge curvature instead, at the cost of over-blurring a sphere. Beside it, a light strategy for `.glowing` surfaces, which are credited whole wherever a path lands on them today, so a small hot glowing mesh speckles everything that sees it after one bounce; a mesh light (`MeshMaterial.emissiveColor`) already has one, and the glowing case would join it.
- **Blocks marched cell by cell.** `voxelized` marches as any field does: the child's distance less a block's half diagonal far from the surface, and within the band near it, the eight nearest cells read nearest first and kept along the ray. Measured on an M2 at 1080 square with the GPU saturated in one process, a block field costs about three times its child (a three-leaf melt 15 ms plain, 45 as blocks; an eight-leaf island 51 and 150) whatever the block size, and shadows about double it; the step count near many block edges is what is left. The canonical answer is a grid traversal along the ray once inside the band (Amanatides and Woo, "A Fast Voxel Traversal Algorithm for Ray Tracing", 1987): one read of the child per cell crossed, the hit face from the last axis stepped. It needs the ray in the field walk, which the march has and the walk does not; a block field is recognizable (its last instruction is the voxel scope's end, which the face normal already keys on). What it would cost: the near-miss coverage that antialiases the silhouette reads a distance, which a traversal does not produce, and the soft shadow's penumbra the same. Worth doing when a sketch needs blocks at a live frame rate on a large field.
- **Don't 3D-tax the 2D path.** Most sketches stay 2D, so don't make every draw call pay for a depth buffer or perspective divide. 3D is a mode you opt into, not a cost the 2D core carries.
- **Caveat:** the 3D mode itself builds and verifies on a Mac; visionOS needs the visionOS SDK plus a simulator or device.
- **A view asked for before the camera rig's first frame.** By reading (2026-11-11), not yet in a test: `cameraView(_:)` called before the run's first `cameraControl`, `cameraMove`, or `cameraShowcase` is dropped, since the rig's first frame seeds over the pose the request snapped to. A sketch that wants to open on the top view asks after its first frame. The rig would keep the request until it has been framed once.
- **A radial repeat's axis, in two precisions.** `Sketch.repeatedRadially(count:around:_:)` normalizes its axis in double precision and then narrows it, and `SDF3D.repeatedRadially` normalizes in single, so a skew axis can differ in its last bit between the two spellings of one field. The scope's pair in `CombinatorScopeFormsTests` uses an axis along z for that reason. One of the two wants to call the other.


## Material and scene explorers

The exploring surface is the material explorer example (`Examples/3D/Materials/Explorer`). It puts the curated `Material` library on a preset menu and every finish scalar on a parameter. The stage around the surface switches too: lighting preset, backdrop, fog, shadows, and the preview solid. A caption says when the parameters have left the chosen preset. The rules for anything built on it:

- **A material is source, never a file format.** No JSON and no `.ollinmaterial`: the scene-import rule ("structure becomes source, geometry stays in the file") decides it, since a material is all structure. Live iteration is already `@Param` plus hot reload. Interchange, if ever wanted, means the standard models the loaders already speak (glTF materials, UsdShade), never an invented schema. A preset that bundles surface color and a procedural pattern with the finish (a "marbled" *look*) stays a three-line snippet for the same reason. Only if that want keeps recurring does a value above `Material` earn its own design pass.
- **Reuse before generalizing.** The stage block (lighting, backdrop, fog, shadows) is written per explorer until a third customer proves the shared helper.

## Photorealistic 3D

The realism tier that builds on the physically-based core (PBR metallic-roughness, split-sum IBL from HDRI or the Hosek-Wilkie sky, ray-traced shadows and reflections, SSAO, SSR, raymarched SDF fields) toward the look of a curated product render or film still. Every item is opt-in so 2D and stylized 3D stay untaxed, every one is Metal-native (no engine vendored), and each is implemented from the published technique and credited in `ATTRIBUTION.md`'s Techniques. This is the "anything Metal offers that enriches 3D" tier, after the foundational [3D mode](#3d-mode) buildout: as a new realism technique finds a good fit, it is added to the textured path's twin pipelines (or a gated branch of the surface-mapped fragment, which may branch freely) so non-using materials stay byte-identical.

All Apple-silicon Metal, the realism direction's "build Ollin APIs for anything Metal offers that enriches 3D."

- **What a traced hit still reads flat.** A reflected or refracted hit reads a surface's picture and its normal, metallic-roughness, occlusion, and glow maps at the ray's footprint. Three things stay on the surface itself: a height map's parallax, the tiled detail pair, and decals. A layer's `image` used as a normal, roughness, or occlusion map stays there too, since the traced scene's records are written before the layers draw; the picture's own second route (the table copied with the layer handles filled in, `tracedPictureTable`) is the one that would carry them. The footprint is a pixel's width plus the lobe's, with no curvature term, so a picture seen in a strongly curved mirror is read finer than its image there, and the path tracer's per-triangle curvature (`ollin_pt_curvature`) is the form to carry over. A picture authored pixel by pixel carries no smaller levels, so its read lands on full size whatever the footprint.
- **A shaped lamp's caustic.** Photons leave a spot light through its cone alone: its IES profile and its cookie shape the direct light (`ollin_apply_light_shaping`) and not the photons, so a patterned or profiled lamp throws the caustic of a plain one. The trace would read the same profile and cookie arrays the lit fragments do, at the emission direction, which is also where the cone is read today. Pinned the way the rest of the chain is (`CausticEnergyTests`): a pane under a cookied spot gives back the cookie's own pattern times the pane's transmission.
- **The probe grid's resolution.** A surface reads the probe field from the row of probes nearest it, which sits a third of a cell inside the room, so a ceiling reads the floor's lamp pool from closer than it stands: in the invariant room (8 by 4.4 units, a 512-probe grid) that row is about 0.35 units in, and the converged field reads 1.12 to 1.21 of a 64-deep path trace at the ceiling, the pool's falloff over that distance. The bounce's depth is right (the light room's bounce against the dark room's matches the trace's own ratio within 3%); what remains is the grid. A finer budget shrinks it in proportion to the spacing, and a read that corrected the nearest row by the field's gradient along the normal is the cheaper route; `theBounceMatchesADeepTrace` holds the envelope (0.85 to 1.3) until one lands. Two smaller edges beside it: a glowing surface with an emissive map glows at its factor over its whole face in the bounce (the probe trace reads a surface's material, not its texture; binding the per-geometry texture table the path tracer builds would read it), and a smooth metal's bounce is the cosine-convolved field through its lobe, where its sharp image of the room is the reflection pass's.
- **A bright disc a pixel long under the live resolve.** The history is resampled in linear light, where a pixel a very bright disc covers by any fraction still reads white, so under a turning camera the sky's sun is every pixel its true disc touches: one pixel longer along the turn (1.12 to 1.55 times the plain disc's lit area, 1.16 with the camera still), with its centroid off the true place by half a pixel minus the turn's fraction of one, zero on average, which `theSkyFollowsATurningCameraInTheLiveResolve` holds at eight turn rates. Resampling in the resolve's compressed space is not the answer: four forms of it each place the disc better and wrap it in a soft ring 1.4 to 2.1 times the plain area, and the crisp disc is the one kept (ruled 2026-11-05). What is left to try is a tighter limit on what the history may claim beside a very bright edge: the rectification box around a pixel next to the sun is as wide as the sun, which is what lets the extra pixel stand. The measurements are in `ARCHITECTURE.md` § *Temporal anti-aliasing*.

## AR mode and templates (the Meta Spark gap)

Ollin aims to support AR sketches: a sketch drawn over the camera's picture and held in place by what the device knows about the room, a face, a body, or a printed picture. It aims at the gap left when Meta Spark was discontinued (January 2025). Apple-only: ARKit and Metal on iOS and iPadOS, with the visionOS immersive path after them.

- **It's a mode layered on the phone and 3D/visionOS work, not a separate engine.** AR builds on the phone leg (see [Swift Playgrounds and iOS](#swift-playgrounds-and-ios)), the sensor stream (see [iPhone as a sensor array](#iphone-as-a-sensor-array)), and the 3D camera and depth pipeline (see [3D mode](#3d-mode)).
- **The Spark lesson is templates.** Spark's reach came from ready-made effect templates (face filters, world effects, plane and image tracking) people could start from. The Ollin version: AR-example sketches plus starter templates wired to ARKit anchors (face, world, image tracking), so an AR sketch is "fill in the `draw()`, the tracking is handed to you", the same template-as-on-ramp idea as the examples and `.swiftpm` starters.
- **What of that gap is in reach.** A template-driven AR tool gives people four things: tracking handed to them, templates to start from, a preview at the desk and on the phone, and a place to publish where an audience already is. The first three are in reach, and most of the tracking already crosses the cable. The fourth is out of reach. An effect made with Ollin leaves as a video or as an app built from the sketch, and no feed opens it from a link. A player app that loads other people's effects is out as well, for two reasons: a phone runs no code that was not built into the app, and an effect described as data in place of a sketch would be the document format the framework lane refuses. So the aim is the authoring half, for people who write code, with templates as the way in and no editor of its own.
- **One sketch, three places.** The design rests on one object the sketch reads, `PhoneDevice`, and three places its data can come from: a recording in a file, the phone on the cable, and the phone's own sensors when the sketch runs there. The sketch asks the same questions in all three (the faces, the planes, the camera's place and lens, the picture) and stays the same `.swift` file. Each place has a job. The recording is the desk loop: it replays exactly, needs no phone, and exports at full quality, so it is also how a finished piece is made from footage. The cable is the live loop, with hot reload, since the sketch runs on the Mac. The phone is where an effect ends up. A capability lands in that order where it can, because the first place is the one a test can prove without a device.

**The build order.** Each step is useful without the ones after it.

1. **A recording of the phone's stream.** The capture app writes what it senses to a file, with the camera's video beside it, and the Mac plays it back as if the phone were there. The format and its rules are under [iPhone as a sensor array](#iphone-as-a-sensor-array). With it comes the small sugar an AR sketch opens on: a `Camera3D` built from the frame's pose and lens (today a sketch assembles one from the matrix by hand), and the picture drawn to fill the canvas with the camera cropped to match, where `drawDepthScene` letterboxes.
2. **Drawing on a real surface.** Three pieces. A scope that draws in a plane's own two dimensions, in meters, for a plane the phone found or one fitted through points the sketch names, so a wall is a canvas. Points pinned in the world from a click on one frame (a ray from `cameraRay(through:)` met with the plane), kept in the sketch as values, with a layer drawn into the four of them. And the picture as paint: a mesh colored by the camera's picture as seen from where the camera stood, worked out for each pixel, so a piece of a wall can move and carry its own pixels with it. Beside the paint goes a material that writes depth and no color, for a real thing that should hide a drawn one. The invariant that proves the paint: a mesh painted with the picture and left where it was changes no pixel.
3. **A surface that stays locked.** A tracker's place for the camera is off by a little on every frame, and a drawn thing swims against the picture by that much. For a flat surface the picture itself can correct it: the wall's own texture, flattened through the plane and the pose, is lined up from frame to frame and the pose is nudged to agree. It needs real recordings to measure against, and the measure comes first: how far a pinned point drifts over a walk, before and after. The same registration is the open route to footage filmed without the app, where there is no pose at all and a flat surface is all that can be followed. That part is unmeasured and may not hold.
4. **The camera as a live picture on the cable.** The picture travels today only inside the depth, segmentation, flow, and attention messages, as a small JPEG sized for a point cloud. A video stream from the phone, in the picture coding the Mac already sends the other way, puts the camera behind a sketch in every mode. With `device.show(self)` sending the finished frame back, the phone in the hand is the viewfinder of a sketch that still hot-reloads on the Mac. The round trip's delay has to be measured before it is promised: it suits working on a piece, and the phone's own build is what suits showing one.
5. **Faces.** The front camera's picture with the face mesh the app already sends. A layer drawn in the mesh's own texture coordinates is face paint. The mesh drawn as depth alone lets glasses pass behind a head. A point on the mesh is an anchor for something worn. The expression values become events a sketch can wait on (a blink, an open mouth) beside the numbers it can read.
6. **The phone's own sensors.** The readers that fill the wire live in the capture app. Moved into the library for iOS, they feed the same `PhoneDevice` inside one process, so a sketch that reads a recording at the desk runs unchanged as an app on the phone, the camera behind it. Open questions for that step: whether the satellite builds for iOS as it stands (its cable transport has no meaning there), how the picture and the lens follow the screen's shape and the way the phone is held, and what an install on every save does to a tracking session that starts over each time.
7. **Capture and share on the phone.** The effect's own output recorded with sound into the photo library, and a still, through the frame hook a recorder already uses, since a video is the form an effect is shared in.
8. **Templates.** The generator's AR kind, with a starter for each tracker (a face, a surface, a printed picture, a body, hands). Each starter is a worked sketch that reads a small sample recording, so it runs at the desk the moment it is generated and on the phone once built.

- **A recording made on the Mac is the test.** The format's writer compiles on both ends, so a test renders a known scene through a moving camera, writes it as a recording, and reads it back. Anything drawn at a known point in that scene must land on its picture within a pixel on every frame, and a dropped frame planted in the file must be caught. This holds every step that reads a recording to a number without a device.
- **Further out.** A place that is remembered between launches, so an effect stays in a room. People passing in front of a recording, cut out on the Mac by the trackers it already has. The visionOS path.
- **Caveat:** what the phone does needs the phone (the simulator has no AR camera). The app's side builds at the desk for a generic device, and its behavior is checked by hand with the device in the room.

## iPhone as a sensor array

A Mac has no depth camera, no inertial sensors, and no spare Neural Engine for live perception. A tethered iPhone has all three, so the idea is to let it act as a sensor and on-device ML co-processor for a sketch that still renders on the Mac. The phone captures and perceives, streams the results over the wire, and the sketch reads them in `draw()` as typed values. The Mac keeps the Metal rendering ceiling; the phone fills the input gap desktop hardware leaves.

The starting want was live RGBD point clouds, the kind an Intel RealSense fed openFrameworks before its Mac drivers were dropped. An iPhone with LiDAR is the same world-facing depth-and-color sensor, except the driver is ARKit and Apple maintains it. Both the *recorded* path and the *live USB* path exist (`OllinRecord3D` reads Record3D `.r3d` clips and its live USB stream; see [`Docs/3D/Record3D.md`](Docs/3D/Record3D.md)): a depth map plus intrinsics unprojects, through the [3D mode](#3d-mode) point-cloud path, into one splat per depth sample (around 49k for LiDAR's 256×192 map, ~300k for TrueDepth's 640×480). The renderer, the unprojection, and the live wire need no new work; what's ahead is *more sensors over that wire*.

**One channel, many typed payloads.** Depth is only the first thing the phone can send. Because both ends are ours and both are Swift, the wire skips the packed-image trick cross-language tools reach for: it is a length-prefixed binary stream of tagged messages, each a typed payload the sketch reads through the same transport-agnostic `FrameSource` abstraction used for the point cloud. The phone app is a configurable sensor hub, so adding a sensor later is a new payload case rather than a new pipeline. A header struct shared verbatim between app and framework carries intrinsics, pose, and a version byte; the rest is raw or LZFSE-compressed channel data.

The phone runs the expensive model on its Neural Engine and ships kilobytes of structured results, so each new sensor is nearly free on the wire:

- **Desktop-impossible.** TrueDepth face mesh and its 52 blendshape coefficients (the Animoji engine: jaw, blink, brow, and smile as 0-to-1 values), 3D body motion capture from a single camera, 6DoF device pose, and the inertial sensors (attitude, gravity, acceleration, rotation rate) a Mac doesn't have at all. The motion stream is the cheapest to build and the most physical: a few floats, no camera, no model.
- **Possible on a Mac, but the phone is the natural host.** Vision runs on macOS too (that's the [`OllinVision` catalog](Docs/Vision/Vision.md)), yet the phone holds the camera and the spare Neural Engine: subject segmentation, scene and object classification, and speech.

Most of those payloads are kilobytes. Only the per-pixel ones (segmentation matte, optical flow field) are heavy, and they arrive as textures, which is what the [layered effects](#layered-effects-and-compositing) graph already consumes, so a live person-matte becomes a `Filter` input rather than a separate feature. Everything here is Apple-native (ARKit, Vision, Core Motion, Core Location, SoundAnalysis, Speech) with no third-party dependency, and it shares its prerequisites with the [phone leg](#swift-playgrounds-and-ios) and [AR work](#ar-mode-and-templates-the-meta-spark-gap).

The transport is the proven live **USB** path (the standard usbmuxd device tunnel): full-quality LZFSE float32 depth plus camera intrinsics and ARKit pose, RealSense-grade, no extra dependency. Ollin's own capture app speaks the same length-prefixed-tagged-payload wire, so the sensor catalog isn't capped by what one borrowed app exposes. Record3D's **WiFi** streaming stays deliberately *out*, correcting an earlier assumption that it would be the easy one: it's WebRTC (a heavy dependency, and the `record3d` library doesn't support it at all), gated behind a paid Extension Pack, and its depth is lossy hue-encoded with no pose: the worst option on every axis, and the reason USB is the only streaming mode supported. Device class gates the sensors (TrueDepth for face, Pro-tier LiDAR for rear depth and scene mesh, A12 and later for body tracking), and several heavy models at once will thermal-throttle, so running every sensor together is a practical limit, not an API one.

**The stream, written down.** The phone sends the Mac everything it senses and keeps none of it, so nothing can be captured away from the desk and nothing can be replayed. A recording is that same stream written to a file on the phone, with no cable, in any mode. It is a folder holding three things. The first is the wire's own framed messages, each stamped with its capture time, so the Mac decodes a recording through the path the cable uses and every payload the wire gains is recorded without new work. The second is the camera's picture as a video file, at the best format the tracking session offers, with the microphone's sound. It replaces the small JPEG a depth message carries. The third is a short description (the mode, the way the phone was held, the format's version). One rule keeps the picture and the data together: a frame is written to both files or to neither, so picture `k` and camera record `k` are always the same instant, and a writer that falls behind drops whole frames. On the Mac the recording is a source for `PhoneDevice`, played on the sketch's clock and exact frame for frame under an export, with access by frame index for a sketch that wants to scrub. Its name and shape are not settled: the working name is `PhoneRecording`, beside `Record3DRecording`, since a `Take` is already a sketch's own recorded run. Because the device object does not change, every phone example can run from a recording, which is also how the phone pages' figures and tests can stop needing a phone. A satellite cannot depend on another, so the reader decodes its own video. The folder sits in the app's documents, where the Files app and Finder already reach it. This is the first step of the [AR work](#ar-mode-and-templates-the-meta-spark-gap), and the tracker's limits travel with it: depth reaches a few meters on a coarse grid, and the camera's place drifts a little over a long walk.

**The clean-room stance carries forward to our own app.** Both the `.r3d` file reader and the live USB stream are read clean-room from their public structure, the same constraint our own capture app's wire still works under: the `record3d` library is LGPL-2.1, the same copyleft tier as p5.js, so it stays inspiration only (reimplement the wire protocol, never translating its source, exactly as the sourcing rules treat p5.js). Record3D is credited like the other product references, not vendored. New sensor payloads added over the wire follow the same rule.

## Generative geometry

A tier of classic generative-art algorithms that produce *vector geometry* (points, `Contour`s, `Shape`s) and hand off to the geometry that already exists (the triangulated fill, the stroked path, the shape booleans, hatching, SVG export). They're geometry, not rendering, so they live in the `Ollin` core beside the shape booleans and the `Path` builder rather than in a satellite: none needs a heavy framework, and the split `OllinPhysics` took was about keeping simulation opt-in, not about dependencies. All are driven by the existing seedable `random`/`noise` so a result is reproducible, and each ships with an example; several are the natural implementation behind a [recreation](#examples-folder).

The reproducibility note matters: every one of these is a pure function of `seed()` plus parameters, so the same seed always yields the same packing/growth. License stance is the usual one: implement each from the *published technique* (credited in `ATTRIBUTION.md`'s Techniques list). Origin note: these surfaced from mining the `/algorithmic-art` skill's implicit technique vocabulary against what Ollin already ships (Voronoi/Delaunay, the foundational primitive of the tier, is a pure-Swift Bowyer–Watson, no library vendored).


## Technique and algorithm helpers

This is the umbrella the [generative-geometry](#generative-geometry) tier is one wing of: a standing catalog of the creative-coding algorithm vocabulary, added as helpers over time the way the SDF-shape catalog, the `Filter` catalog, and the color family grew. The organizing rule is to route each technique to the seam it naturally belongs on rather than invent a parallel system:

- **A looping noise made for motion.** The noise is stretched to fill its range and clipped at the ends, so about 6 samples in 100 of the looping forms sit exactly at an end (the gain's own comment in `Noise.swift` measures it), and a position driven by the signed looping noise, or by `sway` in its wander shape, rests there for a stretch. The Noise page gives the two-read mean as the workaround. The helper is a soft-limited form: the mean of two decorrelated reads passed through an error-function limiter (`erf(1.75 n)` spreads it evenly over the range, measured on 80,000 reads), under a name that says it is for motion, with `sway`'s wander reading it.
- **Geometry emitters** produce points, `Contour`s, or `Shape`s and feed the existing draw, shape-boolean, hatching, and SVG paths, exactly like the generative-geometry builders. The most plotter-friendly and the cheapest to add.
- **Field techniques** that read per-pixel (a new noise basis, an interference field) land as a GPU `Generator` (a no-input `ollin_gen_*` fragment) or a user shader, reusing the layered-effects substrate rather than the CPU geometry path.
- **Simulations** (iterated function systems accumulated on the GPU) run on the compute and `SimField` paths already in place: persistent ping-pong buffers or textures stepped each frame, drawn through the instanced or image path.

The rest of the catalog follows the same shape: a canonical algorithm implemented from the published source, credited in `ATTRIBUTION.md`'s Techniques list, seeded for reproducibility, and shipped with an example, several of which pair naturally with a [recreation](#examples-folder) (an attractor plot, a flow field, a substrate).

The catalog is also a *Nature of Code* coverage map, so it reads as a familiar curriculum to anyone arriving from that world.

For any animated per-pixel `Generator`, three implementation notes hold (their map is fluid, enonforetsam/fluid, MIT, a single-file WebGL background studio read the LYGIA way: a catalog of which looks matter, implemented from the canonical sources rather than its code): spread a noise-family field's contrast around its midpoint so a palette reaches its end stops (fbm piles up near 0.5 and otherwise hides them); animate by small bounded sways at non-commensurate frequencies so the field churns in place instead of panning as a rigid sheet (which also keeps the time argument precision-safe over long sessions); and normalize field coordinates by the canvas's geometric mean so a portrait crop reveals more field rather than zooming in.

- **A disk pass whose cost holds when sizes vary, and removing many particles at once.** `solveCollisions` buckets every disk into a `[Cell: [Int]]` dictionary rebuilt on each relaxation pass, with the cell twice the *largest* radius, and tests each disk against its own bucket and the eight around it. A stand-in copy of the pass, compiled `-O` on the M2 with 9,000 disks over 1080 by 1920 at four passes, measured on 2026-10-25: with every disk 8 px, 30 ms a step (0.8 µs a disk a pass), 60% of it the dictionary's build and lookups; with radii from 5 to 80 px, most of them small, 430 ms (12 µs a disk a pass), 386 pair tests a disk, the dictionary 3%. Through the framework itself, a settled packing of 3,650 disks (largest radius 32 px, median about 10, so a 64 px cell over mostly 8 to 12 px disks) measured 22 ms a step at four passes, 1.5 µs a disk a pass. So a packing pays for the cell size first and the hash second. The changes, in order: (1) cells sized to the typical disk rather than the largest, a disk wider than a cell entered in every cell its box overlaps (or a second, coarser grid for the large ones alone), and each pair resolved once, owned by the one cell holding the lower corner of the two boxes' overlap; (2) the table flat, after Teschner, Heidelberger, Müller, Pomeranets and Gross, "Optimized Spatial Hashing for Collision Detection of Deformable Objects" (VMV 2003): each disk's cell computed once a pass, then counted, prefix-summed, and filled into one contiguous index array, a counting sort with no allocation per cell; (3) positions, radii, and weights gathered into arrays for the pass and written back after it, which takes the retain, release, and exclusivity check on every pair test out of the inner loop (springs and soft bodies relax between the passes, so the gather is per pass, not per step). The determinism rule holds: disks are walked in index order with a fixed cell scan, so a seeded pile settles the same on every run, but any change to which pairs are tested in what order moves a settled pile once. No test pins a colliding pile's settled positions today (`PhysicsTests` checks that two disks separate), so the change wants one first, a seeded pile settled twice in one process and compared, and then re-renders the Guide's Chapter 11 pile figure and the `Physics/Packing` example's media with it. Removal is the other half: `remove(_ particle:)` scans `springs` and `particles` once a call (a hundred removals at 9,000 took 4.3 ms in the stand-in against 0.25 ms as one scan, and a sketch removing about 750 a frame from 9,000 measured 25 to 33 ms), so a batch form takes them all in one scan through a set of identities. Its name wants a ruling: `remove(_ particles: [Particle])` beside the single form, or `removeParticles(where:)`; a bare `removeAll(where:)` would misread, since `World.removeAll()` empties the whole world.
- **Noise read without the clamp.** Every Perlin form scales its raw field by a contrast gain (2.0 in one to three dimensions, about 1.9 in the looping four and five) and clamps the overshoot, so about 4% of a 2D field sits flat on its ends (1.9% at 0 and 2.0% at 1 over 800,000 samples, 2 to 3.5% at each end in the looping forms, measured 2026-10-16); a curve read straight from it runs flat there. A form that hands back the field before the clamp (the raw value with its own range said, or a contrast the sketch chooses with a soft knee in place of the clamp) is the ask, from a port whose source read an unclamped noise; name not settled. The field's 256-unit period on each axis, the table's size, is documented rather than changed.
- **Points spread evenly over a sphere.** The Fibonacci lattice: point i of n at height `1 − (2i + 1) / n` and longitude `i` times the golden angle, π(3 − √5), which gives every point close to the same area with no seam and no pole cluster (Álvaro González, "Measurement of Areas on a Sphere Using Fibonacci and Latitude–Longitude Lattices", *Mathematical Geosciences* 2010, the half-step offset included). It belongs beside `surfacePoints(on:count:)`, returning `[Vector3]` on a unit sphere a sketch scales, with a hemisphere form for a dome; the even count is exact, which a Poisson scatter is not. A test reads the spread as the ratio of the largest to the smallest nearest-neighbor distance against the lattice's known bound.

Origin note, the same as the generative-geometry tier: this catalog is the broader read of the `/algorithmic-art` skill's technique vocabulary against what Ollin already ships. This section is the standing list of what's left.

## Expressive brushes and strokes

The fringe expander carries a half-width per path vertex, `StrokeProfile` shapes it by position along the path, a recorded `StrokeMark` drives it from the hand, and a `Brush` stamps a shape along the path instead of expanding it. The tier builds out from there:

- **Painterly simulation stays separate.** Watercolor-style marks built from layered, deformed translucent geometry are a [technique-catalog](#technique-and-algorithm-helpers) recipe over the shape and accumulation machinery, not a brush engine; keeping the two distinct keeps the stroke renderer lean.
- **A wet stroke over a kept canvas on the web page.** On a canvas that keeps its paint (`noClear`), the Mac's ground pass starts from the pile so far, and the page refuses the stroke by name. The page's ground would load the canvas's resolved texture first (a full-screen copy into the pooled ground surface, since WebGL2 forbids a blit between two multisampled buffers) and then draw the frame's other items over it.

## Sound, synthesis, and spatial audio

`OllinAudio` covers both directions: `AudioAnalyzer` (FFT, bands, beat detection) over `AudioInput` / `AudioPlayer` / `Tone` / `Soundtrack` on the listening side, and a polyphonic `Synth` (voices over anti-aliased oscillators, ADSR envelopes, a resonant state-variable filter, delay and reverb) on the playing side, with a clock-free composition tier deciding what it plays. Both sides are routing as a value now, so what is left is depth rather than shape: more of what a voice can be made of.

- **The render-thread rule holds.** Anything the audio callback touches is built non-isolated and allocated before the first note, and parameters reach it through the lock-free event ring rather than a lock. A new voice type inherits that constraint; it is not a per-feature decision.
- **Keep the renderer pure.** The samples are made by a renderer that knows nothing about the audio engine: events in, buffer out, no clock. That is what makes the sound testable at all (a test renders and measures) and what a sound-carrying export would be built on, so a feature that reaches for the engine from inside the renderer is going the wrong way.

- **A curve run above the chain's rate.** The distortion's curves run at the rate the chain runs at, so a high note driven hard makes harmonics past what that rate holds and they fold back as tones outside the note. Running the curve at twice the rate between two half-band filters is the standard remedy; it wants measuring first (the folded power of a soft clip and an overdrive at MIDI 84 and 96 against the note's own), since the filters cost a few samples of delay the characters do not have today.
- **A ring at a frequency a sketch names.** The ring multiplies by a sine fixed at 300 Hz, and the squeeze's band sits at 1,200 Hz. `Distortion.Character` is a plain list of names, so a carrier or a band a sketch sets wants either a field on `Distortion` that only one character reads or an effect of its own (`.ring(Ring(frequency:))`), which is the cleaner of the two.
- **A loop that holds.** An echo's feedback stops at 0.95, so a phrase in a long echo fades by half in about fourteen passes. A looper that holds a phrase until told to let go wants a feedback of 1 with the input shut while it holds, which is a state (recording, holding, overdubbing) rather than a setting, and a level that cannot grow.
- **A bowed string's loop.** The bowed string's loop carries a one-zero loss and a tuning allpass, whose delay differs between a note and its harmonics, and it reads up to four cents sharp from MIDI 69 up. The blown tube's loop (three symmetric taps and a read between samples) is the pattern to follow, and it wants the same measurement first: the pitch at every bow pressure, at both rates.
- **Measured and left as they are.** The three tube presets share one steady spectrum at pressure 0.6 (an odd-harmonic series at 1/n, as the reference says of the clarinet), the reedy one thinning only at 0.8; the bowed loudness dips 4 dB at pressure 0.5 inside its 5 to 10 dB range, and below 0.15 the cello drops an octave; `.ponticello` jumps to its second or third mode below MIDI 69, and its pitch wanders by up to 8 cents from note to note, a heavy bow near the bridge being a chaotic regime. A bow whose pressure glides to 0 slows on the string before it lifts, which takes 7 to 12 dB of the ring in the first 60 ms where a stepped lift takes 2. The plucked and struck sources scale their level by the velocity squared where the wave and the driven ones scale linearly (a half-velocity steel string plays at 0.38, a sine at 0.51), a ruling rather than a defect, since nothing promises either.
- **The soundtrack path, what is still open.** By reading only: an instrument's shared `pressure` is set on the live renderer and never written down, so a bowed or blown voice in an export plays at the pressure the export's own renderer starts with, whatever the sketch did to it frame by frame (a note pressed on its own, `press`, is an event and is carried). It wants the grain scrub's treatment, a value recorded against the export clock and applied at the block. Measured and documented rather than pinned: the mixed soundtrack bends anything above 0.7, which a single loud instrument meets too (3,898 of 88,200 samples of a five-note pad chord moved). By reading only: a note inside `draw()` is recorded once per settle draw when `OllinApp.exportSettle` is above 1. The offline pan is the system's equal-power algorithm, which puts a source 30 degrees off axis in one ear alone and one directly to the side 18% in the far ear (a 15 degree sweep from 0 to 180 reads 1.00/1.00, 0.49/1.33, 0.00/1.41, 0.06/1.41, 0.13/1.41, 0.19/1.40, 0.25/1.39 and back to 1.00/1.00 behind), constant power throughout; not Ollin's to change, worth a sentence on the page when a moving source is taught.

## Live rigs: physical computing, lighting, and network video

The hardware-and-network interop tier, extending the app-to-app integrations (Syphon, OSC, MIDI, the virtual camera) to the physical rig around the machine. Same posture throughout: play in the existing rig, implement published protocols from the spec, vendor nothing incompatible.

- **NDI.** Network video between machines, the cross-machine sibling of Syphon and the standard of the VJ and broadcast rig. It is the one integration in this tier with no published protocol: the SDK license (the November 2024 NDI SDK License Agreement) forbids reverse engineering the SDK "or any protocols used by the SDK", so unlike OSC, Art-Net, sACN, and MIDI it cannot be written from a specification, and the only path is the vendor's own library. That license shapes how the library can be reached, and three of its terms decide the design:
  - *The headers are MIT; the library is not.* The SDK documentation licenses the header files to open-source projects under the MIT license (each file carries the notice that the MIT terms apply to that file only), so the C declarations can be vendored under `External/` like any permissive component, with their notices intact and an entry in `THIRD-PARTY-NOTICES.md`. The compiled library is under the SDK license alone: redistributable "solely as used by" a product, and only under an end-user license that carries NDI's own list of terms (section 3d: no modification of the SDK, no reverse engineering, NDI's copyright notice, a flow-down asking every third-party developer who builds on the product to accept the same list). A pure-MIT repository cannot carry that list, and a framework cannot pass it on to every sketch, so **Ollin ships no NDI object code, ever**: no library in the repository, none in a release, none in a generated project.
  - *Load the runtime the user installed.* The SDK's own dynamic-load entry point exists for exactly this: `NDIlib_v6_load()` in `Processing.NDI.DynamicLoad.h` returns a table of function pointers, so the satellite opens the runtime that NDI's free installer put on the machine (the folder `NDI_RUNTIME_DIR_V6` names, then the header's redistributable folder), looks up that one symbol, and calls through the table. This is the pattern code completion already uses over sourcekitd (a C interface of our own, nothing linked), with the headers vendored instead of hand-written. Without the runtime the satellite says so once, with the link to ndi.video the license asks for, and does nothing else; the sketch keeps running. The user accepts NDI's terms when they install the runtime, which is where those terms belong. Loading at run time is also what sidesteps two obligations a small project cannot credibly keep, that a product release "must use a version of the SDK that is less than thirty (30) days old" and that a product "must maintain current and complete NDI compatibility at all times": the runtime is whatever NDI's own installer keeps current, and the satellite pins only the load table's version.
  - *The name and the mark.* NDI is a registered trademark of Vizrt NDI AB. NDI asks that a product wanting NDI in its name ask first, that the registered mark travel with the first use in a document beside the statement "NDI® is a registered trademark of Vizrt NDI AB", and that a link to ndi.video sit near wherever NDI is used or selected. So the satellite is named for what it does, `OllinNetworkVideo` with `NetworkVideoSender` and `NetworkVideoClient` (as DistroAV, the OBS plugin, keeps NDI out of its name), the Docs page names NDI® with the notice and the link, and the hosts' about panels carry the statement.

  The practice in open source matches this reading: DistroAV and the openFrameworks addon both carry the MIT headers in their trees and require the runtime installed separately. One caution from the same record: the FFmpeg project removed its NDI device in 2019 over a license dispute with the vendor, so the satellite stays small, isolated, and optional, one a release could drop without touching anything else.

  What it ships, in order: **send first**, the Syphon parallel (`publishNetworkVideo(name:)` over the `frameRendered(_:texture:)` hook, a blit into a shared buffer, and the SDK's video send in BGRA; its asynchronous variant needs the buffer alive until the next call), so a sketch is a source in Resolume, OBS, or vMix on another machine; then **receive**, `NetworkVideoClient(named:)` with `frame` as an `Image(texture:)` and a `FrameSource` conformance so the vision trackers read a camera on another Mac; then audio on the same connection, which pairs with the sound tier. iOS stays out: the SDK for iOS is a static library, which cannot be loaded at run time and would have to be linked into the app, exactly the distribution the terms above refuse. Verification without hardware is a self-loop (send, find, receive in one process, the SyphonLoopback shape) beside the NDI Tools' own monitor, both of which need the runtime installed, and installing it means accepting the EULA, which is @eaviles's to accept, not a session's.

- **A pen plotter, driven live.** Two published command sets reach it. The EiBotBoard firmware in AxiDraw-family plotters publishes a command set for stepper moves and the pen servo over USB serial. GRBL-family machines take G-code a line at a time, with the character-counting flow control GRBL documents, and the program `Toolpath` writes is what streams. Satellites cannot depend on each other, so the driver lives in `OllinSerial` or the port moves into a shared seam in the core. The EiBotBoard moves at the speed it is told, so the driver plans acceleration itself. Pause, resume, and pen height are live controls, and a plotter on the desk is the only proof.
- **Art-Net discovery.** Art-Net 4 finds nodes with two packets. A controller broadcasts ArtPoll, and every node replies with ArtPollReply: its address and port, a short and a long name, the universes each of its ports listens on or sends, and two identity codes, an OEM code issued by Artistic Licence and an ESTA manufacturer code. A node also sends the reply unsolicited when it starts and when its configuration changes. `OllinDMX` sends and decodes ArtDmx only, so today a sketch is reached by a unicast address typed into the console. Both halves are small over the existing `Network.framework` listener and sender:
  - *Being found.* `DMXReceiver(.artNet)` answers each ArtPoll on port 6454 with one reply per group of four input ports, carrying a name the sketch sets (its type name by default), the Mac's address, and the universes `start(universes:)` asked for or the ones heard so far. It sends the same reply once at `start()` and whenever that list changes. The specification has a node wait a short random time before replying, so a network of nodes does not answer at once, and answer the poll's sender rather than the whole subnet where the poll asks for that; both are rules the spec sets.
  - *Finding others.* `DMXSender` gains `availableNodes()`, the house name for a listing that asks the outside world. It broadcasts one ArtPoll, collects the replies for the wait the spec allows, and returns each node's name, address, and universes, so `DMXSender(artNet:)` can be given a node picked from that list rather than an address copied from a console's menu. The reply's decode is total and golden-byte-pinned against the spec's table like `ArtDmxPacket`, and a reply that fails to decode is dropped, never trapped on (the wire harness's rule).
  - *The codes.* The reply cannot go out under someone else's identity. Until Ollin holds an OEM code of its own, the reply carries the placeholder the specification reserves for products in development, and a release never ships it that way: applying to Artistic Licence for the code is the gate, and the ESTA manufacturer code (assigned by ESTA) goes with it. The Art-Net credit line the documentation already carries covers the protocol; the code covers the product.
  - *Proof.* A loopback in one process, a receiver answering a sender's poll, pins the packets. A console or a node on the network is the only proof of the listing and of the sketch appearing in a console's node list, so the item needs a rig on the desk, as the plotter does.

All output paths are real-time side effects of `draw()`, so they follow the render-thread rule (non-isolated closures) and the background-producer handoff pattern the receivers already use.

## New input sources

Each conforms to the core `FrameSource` (so the vision trackers and effect graph consume it) or reads as a simple value in `draw()`.

- **Apple Pencil.** Tilt, azimuth, force, and hover, on the iOS leg where a Pencil exists. Force joins the `pressure` `Sketch` already reads rather than arriving as a second thing, so a sketch written against trackpad pressure carries over unchanged and tilt, azimuth, and hover are the additions; each reads as a plain value in `draw()` beside the mouse and keyboard.
- **Body data, and where the Mac is.** HealthKit (heart rate from a paired Apple Watch) for biofeedback, and Core Location so a `Weather` can follow the machine. Each needs its entitlement and consent prompt, the same "keep the easy things easy, make the prompt explicit" concern as screen capture. Location has a gate the weather reader (`Docs/Helpers/Weather.md`) does not: macOS 14 and later show the Location Services prompt only to an executable carrying an `Info.plist`. A bare `swift run` binary is not even listed under Location Services, and the reference command-line tool had to link a plist into its executable (`-sectcreate __TEXT __info_plist`) to get the prompt back. A plist embedded in the hosts carries a bundle identifier, which may change how TCC attributes their camera, microphone, and screen grants, all of which land on the launching terminal today. So the location reader ships behind a backend seam a test can fake (the Bluetooth satellite's shape), with the plist embedded only in the executables that ask for it, and its first run is a desk check of both the prompt and the other grants. WeatherKit stays out: it needs a paid developer entitlement and a signed app, and the keyless service the weather reads is enough for a sketch. Niche but distinctive and impossible in a browser.
- **Pinch and turn on the phone itself.** The installed sketch's canvas (`OllinMTKView`) turns multi-touch off so a second finger never moves the pointer, and whether a pinch recognizer still sees that second finger is a question only a device answers. So the touch twin turns multi-touch on, keeps the pointer on the first touch by its identity, and reads the pinch and rotation recognizers beside it, each event's change handed to `handlePinch(by:)` and `handleTurn(by:)` the way the Mac's view hands its own. Its first run is a desk check on a phone, since a broken one-finger pointer is the cost of getting it wrong.
- **Typed text on the phone itself.** The iOS canvas view would adopt `UITextInput` and feed the same `typedText()` and `composingText` the Mac's input client fills. The difference is the keyboard: on a phone, becoming first responder raises the on-screen keyboard over the canvas, where a Mac's canvas holds the keys silently. So the canvas cannot claim the keyboard on its own, and a sketch asks for it (a call that raises it and one that puts it away), with a hardware keyboard on an iPad typing without the on-screen one appearing.

## New output surfaces

Ways a sketch leaves the window, beside the flat image / video / GIF / SVG / web-page exporters already in place.

- **Rumble on a game controller.** The motors in a pad are the same kind of output as the shipped haptics tier, reached through `GCDeviceHaptics` and its localities rather than through the trackpad performer, so the pattern layer carries over and only the destination changes. Adaptive triggers and the light bar sit beside it on the same hardware. All of it needs a pad on the desk, since a synthetic controller reports no haptics.
- **The rest of the sketch on the web page.** The platform stance rules out a second renderer, so what crosses is an artifact: the recorded page (`Docs/Output/Web.md`), whose recorder writes down what the renderer received each frame and whose WebGL2 player replays it with the framework's own shaders carried to GLSL ES 3.00 by the shader lexer the GLSL import shares, the import's function table inverted. The core changes by that one recorder and no renderer seam, and every door below keeps it so. The one player part that is not a shader is the stroke and fill expander, the framework's own `OllinExpander` module compiled to WebAssembly and committed as a resource, which is what lets a stroke travel as its points; a door that needs more of the framework on the page takes the same shape (a shared module the Mac draws with, built by a script, its provenance checked by a test), never a second implementation in JavaScript. *The effects that stay with video:* the passes that are a solve or a ladder on the Mac (the diffusion, the summed-area table, the Fourier transform, the alpha-shape design filters, the seamless clone, the depth combines, the flat light) and the simulations with pipelines of their own (the fluid, the watercolor, the self-warp, the multi-scale Turing field); each could cross as a recorded sequence of fragment passes with the intermediate formats the page can hold, a door of its own if a sketch asks for it. *What goes to video:* lit meshes and the rest of the 3D path beyond the raymarched field (a 3D door is a recorded thought, not a plan: a scene export played by a third-party WebGL scene library such as Three.js, its lights and materials mapped onto that library's own, at look-alike rather than exact fidelity and marked so; @eaviles accepts the fidelity cost for the sake of getting 3D sketches out at all, and it stays apart from the exact 2D player), ray-traced reflections, global illumination, caustics, the path tracer, temporal upscaling, mesh fields, compute work such as the particles and the fluids, wide gamut and HDR output, and a sketch whose input is a picture every frame (the camera, a video); the exporter refuses those with the name of the first call rather than drawing a partial picture. *Target:* WebGL2 first, because reach is the point and an iPhone below iOS 26 has no WebGPU, GLSL ES shares Metal's C grammar, the picture is the same, and nothing here needs compute; a WGSL back end comes only when a pass needs compute or WebGPU reach passes WebGL2, sharing the page and the plumbing so it is a second shader target, not a second exporter. *Verification without eyes:* every translated unit compiles in headless Chrome (WebGL compiles synchronously, so a DOM dump reports it), the page played to a fixed frame diffs against the same frame from `OllinApp.image(of:frame:)` under the snapshot tolerance, and the inline fragment inside a bare page diffs against the standalone file. *Parked:* the sketch's own `draw()` compiled through Swift's WebAssembly SDK against a small browser host; it would add a second sketch surface to maintain, and the recorded page with the triangle door covers more sketches. *Boundaries to hold:* this is an export like SVG or video; the `.swift` sketch stays the artifact; the page is generated and never hand-edited and shows no source; there is no share command, no hosting, and no live editor; and no renderer seam enters the core. A browser build of the drawing core is declined, since it would put the Mac-only work at risk, and the bar for it stays where it was.
- **A see-through canvas background on the web page.** The page's canvas is opaque, and a background's alpha reaches nothing there, so `background(Color(white: 0.9, alpha: 0.1))` shows light gray on the page where the Mac's window shows it over black. The page wants the alpha as a recorded fact of its own beside the clear's color, multiplied in as the page clears (the way a layer's clear is), so the background's color and its alpha each stay a straight line in the parameter that drives them and a color well for the paper gains its opacity.
- **A page carries the shaders' comments.** The page's fragment shaders are the framework's own Metal, cut by section and translated, and the translation keeps every comment line: in a page of thin strokes measured on 2026-11-12, 41 KB of 110 KB of shader text was whole-line comments, about a tenth of a 389 KB page. Dropping them at assembly (GLSL has no strings for a `//` to hide in) is a few lines in `WebShaderLibrary`; what it costs is a readable shader in the page's source, which nobody is promised, and every recorded page's bytes move once, the front page's ring among them.
- **Shadows in a layer.** A layer's pass is handed no shadow map, no cube, and no structure to trace against, so a solid drawn into a layer is lit and unshadowed whichever camera the layer looks through, and a second window shows a stage without the shadows the first one has (`LayerCameraTests.aMeshInALayerReceivesNoCastShadowYet` pins it as a known issue). The shape: hand the layer's pass what the frame already built, all of it in world space. A point caster's cube and a traced caster reach any view whole. A directional or spot map is fitted around the frame's camera, so a layer looking elsewhere is shadowed only where that fit reaches, and a second fit per camera is the step after. Two things to settle first. The lighting a layer packs fits its casters to the layer's own camera (`Drawer.withPassCamera` answers every camera question with the layer's for the length of its pass), and the caster block has to come from the camera the maps were rendered around, while the eye and the fog stay the layer's. And a pass handed a structure draws through the traced build of the lit fragments (`PipelineKey.untraced`), about eleven times the cost a pixel on a GPU that traces in software, so a layer takes the structure only in a frame where a caster traces. The contact shadows, the deferred reflection, and the caustics are passes over the canvas's own view and stay the canvas's.
- **One field of copies in two views.** A `MeshField` keeps one visible set a frame (its cull results live on the field), so it is drawn once a frame, culled through the view of the pass it is drawn in, and a second view of the same copies takes a second field holding them again. The shape: a visible set per view, with the count, the compacted indices, and the draw arguments keyed by the pass, or, cheaper, the field drawn whole in a frame where its draws disagree. The shadow set, the structure's instances, and the motion vectors each walk every field draw of the frame, and each would count a field drawn twice as two.
- **The overlay's two limits.** One pane on the main display (a pane per display, as the wallpaper has, wants the hit test and the pointer per pane), and the coverage read back on the CPU every other frame (a one-pixel read from the frame's own texture would cost nothing).
- **The framework commit a frame's recipe names.** A recipe carries the framework's commit, read by asking git in the checkout the binary was compiled from, when the process starts (`ExportMetadata.frameworkHash`). A binary built at one commit and run after the checkout has moved on writes the later commit, with nothing to say the two differ. The commit wanted is the one the binary was built from: written in at build time, or the newest commit not newer than the executable, with both recorded when they differ. An archive that keeps the recipe beside each picture is what reads it.

## Rendering and color frontier

Deeper use of the Metal core and Apple displays, every item opt-in so the 2D path stays untaxed.


- **Dolby Vision.** The static HDR10 metadata an extended sketch exports describes the whole file; Dolby Vision carries per-scene metadata instead, which a generative piece could drive from what it knows it just drew. It needs the licensed encoder path rather than AVFoundation's plain HDR writer, so it is a licensing question first and an API question second.
- **The layered lobes in a traced frame.** The clearcoat, the fabric sheen, the anisotropic streak, and the scattering under a surface trace as their metallic-roughness base. Each is a real lobe rather than a look, so each wants a sampled form in the kernel's own estimator and its pairing: the coat a second specular lobe over the base with the base dimmed by the coat's Fresnel, the sheen its own distribution with the base scaled by the sheen's directional albedo, the streak the anisotropic visible-normal sampler, and the scattering a walk under the surface or a diffusion profile at the hit.
- **What a look leaves out of a traced frame.** A look is drawn by the lit fragment's formula at every vertex the camera sees (`ollin_pt_direct`, `ollin_pt_look_layers`), and each limit below is a deliberate match to the window that a physically based finish answers today. The standard finishes' highlight answers the light list alone and never mirrors the room or the environment. The hologram's rainbow answers the punctual lights alone. A light's `softness` wrap is not read by the tracer at all, where a traced shadow stands in for it, so a terminator wrapped in the window is a hard one in the export. And a cel band or a highlight under a panel is the window's whole-panel value times the share of the panel one ray per sample sees, an unweighted share, which reads a little bright where the hidden part of the panel is the part nearest the surface (the weighted form is the ratio estimator the raster's traced panel shadow uses).
- **The stroke band's thin end and its footprint.** An outline thinner than its ramp lays 5.4% more ink than its width: each edge's smoothstep runs a pixel each side of the band's floored half-width, and where the two edges overlap at the centerline the band is cut at zero distance rather than summed, so the inner halves are counted once at full height; the exact form sums the two edges' ramps or narrows the ramp to the band. And the band's footprint is `fwidth`, the L1 pixel step, which overshoots by up to the square root of two on a diagonal, so a thin outline there is spread wider and reads lighter: its darkest pixel is 0.84 of the axes' at 0.5 and at 1 px (the sectors' total ink agrees). A plain stroke takes the exact share of each pixel its band covers (`ollin_edge_share`), read from the screen steps of its two edge distances, and the outline band wants the same: the share between its two edges, in place of two smoothsteps over `fwidth`. A disk's own outline still reads its footprint as `fwidth` of the *distance*, which collapses where the 2x2 derivative block straddles a small disk's center, so a stroked circle under a pixel or two across loses its outline at some places on the grid; the band's footprint wants the coordinate's own screen step, as the disk's fill takes it. Pinned (`anOutlinesInkIsItsLengthTimesItsWidth` at 0.3 to 1, `aThinOutlineIsAsDarkAtEveryAngle`).
- **What a stroke's exact coverage leaves.** A stroke's fragment reads how far inside each of its two edges the pixel sits and takes the exact share of the pixel between them, so its ink is its width at any angle and anywhere on the grid. Five things around that are approximate still. *A flat end.* A butt or square end fades over one pixel wholly past the end line, so it lays half a pixel more than its length at each end (a 3 px dash reads 4); the fade sits there because two strokes drawn end to end then meet with no seam between them, the way two fills do, and a fade that straddles the end wants that seam answered first (the second stroke would need to know the first). The end's two corners are one diagonal ramp where the true corner is two edges, which wants a third number on the vertex. *A stretched transform.* The expander's fringe is one number (the transform's mean scale), and the rim past the edge and the hairline's one-pixel floor are sized by it: the coverage itself is exact under any transform, but under `scale(2, 0.5)` the rim is short along the squeezed axis, where the multisample mask can cut a pixel that carries coverage, and a hairline's footprint is a pixel on average only. A fringe per segment, from the transform and the segment's direction, closes both. *A retained batch replayed smaller.* The rim was laid out at record time and scales with the replay, so below about seven tenths the mask clips again; the replay's vertex stage could push the rim out by the replay's scale. *A ribbon.* A stroke under a medium or a shader paint has room on its vertex for one of the two edge distances and rebuilds the other in the fragment from the ribbon's place across (`ollin_ribbon_coverage`); past a flat end it reads one edge at full thinness, so a hairline's end under a medium is a pixel short, and a hairline's join subtracts a far edge a round join does not have. The second slot of a ribbon's vertex pair repeats the position, which is room for the second number once symmetry's replication stops folding that slot. *The page's disk quad.* The Mac sizes a solid disk's covering quad by a pixel and a half where that is more than two of the shape's own units, so a dot held at a pixel's footprint is whole on a canvas zoomed far out or in a coarse layer; the page's vertex stage still adds two units, and wants the surface's texels per point to do the same. *A line through the camera in a coarse layer.* A 3D line's fringe is one canvas pixel whatever it is drawn into, where a 2D stroke's follows the layer's texels.
- **What a dot's exact coverage still costs.** Three things a profile would look at first. *The shape fragment carries the walk.* A disk drawn through the analytic-shape fragment can take any of the three forms of the share, and the walk round a parallelogram pixel is compiled in for every one of them though only an ellipse turned off the axes, or a sheared transform, reaches it; on the particles' fragment the same walk, never taken, measured 1.8 ms on a million marks (2026-11-12), which is why the particles' own entry (`squareDotCoverage`) leaves it out. The shapes' fragment wants the same split: a second build chosen by a function constant, the way the lit fragments are built with and without the tracer, picked per batch when no instance in it is a turned ellipse. *A light disc works its pixel out per fragment.* The pixel's size in the disc's units is the same for every fragment of a particle, and the vertex stage could hand it over flat with one over the radius; each fragment takes two screen derivatives, a division, and a square root before it can say it is inside, which is most of what a large disc's interior pays over the old ramp. *A thin line's ribbon is four pixels wide.* The rim runs a pixel and a half past each edge so that every pixel carrying coverage is whole under the multisample mask; by the sample pattern (no sample sits more than 7/16 of a pixel from a pixel's center on either axis) 1.33 would do, a twelfth fewer fragments on a one-pixel line, and it wants the rim test's plants run again before it is believed.
- **A point cloud's splat under a pixel.** By reading, unmeasured: a 3D point's quad is its radius and three tenths more (`ollin_point_vertex`), while a splat under a pixel across is drawn at a pixel's footprint with its coverage scaled by its area, which reaches a full pixel from its center. The quad of a far splat is then smaller than its footprint and the multisample mask keeps only the samples the quad reaches, so a distant cloud should fade faster than its points' areas. The margin wants a pixel and a half in view units at the splat's depth, as the analytic shapes' quad takes it on the canvas; the measurement is a row of splats receding, each one's light against its projected area.
- **A curve flattened by flatness, not by chord.** `CurveSampling` flattens a cubic or quadratic to chords of about 8 points, so the chord sits 8 over the radius pixels inside the curve: 0.2 px at a 40-radius circle, 0.4 px at 20, visible facets on a small imported circle and on a `drawShape { }` curve, and an SVG round trip whose every rim pixel reads past 32 levels against the analytic shape (1.7% of the frame). A flatness tolerance (a sagitta under about 0.1 px at the current transform's scale, the segment count from the curve's second derivative) makes a curve's facets invisible at every size and spends fewer points on a large gentle one. Pinned (`anExportedDrawingReimportsToTheSamePixels`).
- **Two halos at a seam's end.** The inside-biased fill ramp is what lets abutting fills tile without a seam, and it holds to the byte along the seam; where a seam meets the tiled region's outer edge the two fills' halos overlap on the one pixel outside the corner and that pixel takes a second coat, up to 67 levels darker than the whole rectangle's (one pixel per seam end, a notch along the boundary of a tiled region on a background). Pinned (`twoHalfRectanglesAreOneRectangle`, `aGridOfAbuttingTilesIsOneSolid`). Small: the wash's dry end picks the ground up into the paint and its glaze does not, so the first quarter of water darkens a black wash over white by 0.5% before the glaze thins (`aWashesDarkeningIsMonotoneInItsWater`). By reading: `drawPolygon` fills as a fan from its first point and says so, so a concave outline fills wrong with no error; a convexity check costs one pass over the points and would route a concave one to the triangulator `drawShape` uses.

## Authoring and editor tooling

Editing experiences the live-reload core makes possible, and the place Ollin states its line on AI.

- **The boundary, stated first because it is load-bearing and public.** The README promises it ("It's a tool for making art ... Ollin is not a generative-art model"), and it extends to any AI *feature*: AI helped build the framework and plays no part in the work made with it. Not as an author of a sketch, and not at the controls either. The tidier line, operate the framework but never author the work, does not survive contact with generative art: the parameters are the work (a palette, a density, a speed chosen by hand is the hand), so a model moving them toward a phrase is a model making the piece; it cannot tell a development nudge from an aesthetic choice; and the exception it forces into the README's promise costs more than any such feature is worth. Ruled 2026-09-07 over a working slice (`dbb93dbc`, the on-device model moving `@Param`s toward a phrase, reverted the same day; it also moved parameters the words never named). What stays: models that read the world (the perception tier, depth, listening) are input the way a camera is, credited in `THIRD-PARTY-NOTICES.md`, and never draw. A proposal that puts a model between the artist and a value, a color, or a picture is out by this ruling, not parked.
- **No node editor.** The effect graph (`compose` / `Filter` / `Combine`), the SDF combinators (`SDF` / `SDF3D`), and the `Visual` chains are graphs written as code, which makes a node surface look cheap: a presentation of a structure that already exists, round-tripping to Swift. In practice it needs an interface of its own (selecting a node, editing its settings, wiring it), and once the work can be done in boxes it moves out of the sketch, which is the node-graph studio the scope rule turns away. The graphs stay code, and `@Param` already gives their values a control. A code-less, node-based Ollin could come one day as a separate app built on the framework, taken on for real demand and never as a core feature.
- **The rest of a package in the live window.** A sketch file in a package target compiles with the target's other files (`SketchLoader.Scope.target`, `SketchTarget`), and the compile reaches the framework and its libraries because the host carries them; anything else the package resolves does not compile live. *Other targets of the package:* build them first with `swift build --target <dep>` against the package's own `.build` (the read already knows the dependency names from `dump-package`), then compile the sketch with `-I` on the built modules and load the dependency's object code beside it, either linked into the sketch's dylib or as a dylib of its own loaded first. Two questions decide the shape: a dependency built as a static archive drags its own copy of anything it links (Ollin above all, the two-copies failure the host's `-undefined dynamic_lookup` exists to avoid), so the dependency's link must leave Ollin unresolved too; and a save to the dependency's own files has to rebuild it, so the watch covers its folder. *Other packages:* the same, after `swift package resolve`, with the build's lock now in play, since the dependency build has to happen in the package's `.build` or a copy of it (the manifest read's private scratch folder avoids the lock only because it builds nothing). Measure the first compile and a save before choosing: a dependency rebuilt on every save would cost a live session its reason. *The phone route* (`PhoneProject`) references the one sketch file and its assets; a target's other `.swift` files would join the spec's sources the way the assets do, read through the same `SketchTarget`, and the tether's watch would follow the target's folder. *Completion in the live-coding editor* hands the service the buffer alone, so a helper's names do not complete; `completionArguments(sourceFile:)` would add the target's other files, from the manifest cache only, so a cold read never holds the editor up. *A shape drag in a helper file* is refused by name (the drag host owns one file, `ShapeDragHost.sourceName`); a host that answered for every file of the target, by the site's file name, would let it write the helper.
- **The doc comment above a `@Param` as its description.** `help:` is the description the framework carries: the parameter owns it, so it reaches the listing, an exported page, and a host someone else writes. A sketch that already explains every parameter in a `///` comment above the line would rather not say it twice, and a property wrapper cannot read the comment above its own declaration (an attached macro could; `@Param` is not one, and making it one is a larger change than the comment is worth). What can read it is a host: OllinLive and OllinLiveCoding already read the sketch's source by the byte (the save button walks forward from each `@Param` attribute to its `var`; a drag rewrites a call's arguments), so a scanner that gathers the `///` lines directly above each attribute, keyed by the property's name, could hand the inspector a description for every parameter whose `help:` is absent, with `help:` winning where both exist. The seam is `SketchSession`, which holds the source every compile reads, to the shared `ParametersListView`, as a lookup beside the handles (a `ParamHandle` is the parameter's own and knows nothing of the file). Open: whether a sentence written for the code's reader is the one the tuner wants; and that the sketch as an app, the gallery's listing, and `--list-params` have no source at hand, so the two routes would not be one feature, and a sketch that wants its description everywhere still writes `help:`.
- **Undo in the inspector, what is still open.** The window's Undo covers a parameter turned by hand in the parameters list, one gesture a step. Four things are outside it. *A value moved from elsewhere* (a fader, an OSC message, the remote surface, a cue) is not a step, so Undo after a fader move goes to the last hand edit before it. *A smoothed parameter* reads as its gliding value, so a second edit made while it is still gliding undoes to a point on the glide rather than to the value the first edit asked for; the step wants the parameter's target, which `AnyParam` does not hand out. *On a phone or a tablet* there is no button to hold, so a drag paused for longer than the quiet time is two steps. *The timeline's keys and the inspector's values are two lists*: Undo with the panel in front takes back a key and with the window in front a value, so a hand edit that also re-keyed a track is undone in two places.
- **More menus to fold.** A `ParamChoices` roster that declares `paramChoiceGroups` gets a menu of submenus, and `Easing` declares one. `Material`'s thirty-one built-ins are still one list, and want a grouping that reads as the materials page reads (the plain finishes, the stylized, the iridescent, the soft, the metals, the glasses) before the menu takes it. A `ParamOption` enum has no way to declare groups; the same optional list would give it one. The exported page's controls, the remote surface, and the phone's list all read `options` flat, and each would read `groups` the way the inspector does.

## Opening the repository

Everything a private repository never had to answer for arrives at once when it opens. This section covers how Ollin presents itself to somebody who has not seen it before, which is a different question from what it can do. The observations below came from reading the public face of vgpu (credited under Directions ahead in [`ATTRIBUTION.md`](ATTRIBUTION.md)) against ours, so the sizes and ratios are measured rather than guessed.

- **The README does three jobs, and the split between them is what a presentation pass protects.** It pitches the project, states positions (Apple-only, the AI posture, licensing), and points at the catalog, which lives at the top of the reference index because an index is where an enumeration reads well and a front door is not. The pitch stays above the fold, and the position statements are load-bearing enough to keep but not to lead with. The opening as it stands (title, one line, a nav row, the facts list, the status callout) is the part that already works, so the pass named under Toward 1.0 should protect it rather than rewrite it, and anything that grows the file past a pitch should ask which of the three jobs it is doing. Applying that question once (2026-09-19) found two sections doing a fourth: *Live reload* and *Export* had grown into a manual, with flag-level and option-level detail the pages they link already carry, so the claims stayed and the usage went back to those pages. Four headings are load-bearing beyond the README itself, because the website's front page names them (`SiteHome.rows`: *Hello, circle*, *Run it* and *Install* side by side, *What's in it*), and the run command under *Run it* is the one the site rewrites per sketch, so neither can be renamed casually. The remaining question for the pass at the tag is *Documentation*'s nine-item starting list, which is a curated route into the reference and reads as one, but sits under a paragraph that has just called `Docs/README.md` the annotated index.
- **The inward and outward tiers are wildly out of proportion, on purpose, and worth watching anyway.** `CAPABILITIES.md`, `ARCHITECTURE.md`, `CLAUDE.md`, and this file come to roughly 1.3 MB of contributor and agent-facing prose, against a 47 KB README. About 28 to 1. Each of those files earns its size (`CAPABILITIES.md` exists because `CLAUDE.md` outgrew the context budget it has to fit in every turn), so this is not a cleanup task. It is a reminder for the release pass that the 40 KB is the part anybody outside will actually read, and that `ATTRIBUTION.md`, unusually thorough for a project this size, is one of the better arguments Ollin can make for itself.
- **The agent-facing question, stated so it can be decided rather than drifted into.** What is left of it is one convention: the reference served over a tool protocol, from the same pages the CLI prints and the site writes as an index. What is not settled is whether Ollin wants it, and the reason to decide deliberately is that the project has a public position on AI which this touches. The distinction that seems to hold: serving accurate reference to an assistant so a person writes their own sketch is the same act as serving it to a search engine, while anything that produces sketches is the thing the boundary refuses. The practical argument for is that an assistant working from guesses invents API and the person blames the framework, and it is stronger here than for an established framework, because no model has read an API this new. The argument against is that the gesture reads as endorsement whatever the README says. The fact that keeps the question cheap to leave open: a general-purpose documentation server already reads an index of the shape the site writes, so a server of Ollin's own buys a search and fewer round trips rather than access to the reference at all. Both arguments are real, so this stays a question with @eaviles's name on it.

## A third-party extension ecosystem

The contributed-addon ecosystems are a large part of why p5.js, openFrameworks (`ofxAddons`, the `ofx*` convention), and OPENRNDR (`orx-*`) have the reach they do, and it's the one incumbent advantage no Ollin *feature* closes. SwiftPM makes the mechanics free: a third-party Swift package that declares `Ollin` as a dependency and adds types or `SketchExtension`s is already a working extension, installed by URL like any Swift package. So the work is not plumbing, it is **convention and discoverability**, and what remains is the discoverability half:

- **A curated list.** An awesome-list-style index so extensions are findable without a registry of our own. It needs published extensions to list, so it follows the repository going public rather than leading it.
- **Ollin's own front door.** The listing on the Swift Package Index. It is a pull request against the index's own package list, which is the one step that cannot be taken from inside this repository, and it is worth taking deliberately: the listing carries a compatibility matrix, and the rows for the platforms this package does not support read as red rather than as absent, which is correct and still worth expecting.

Two facts about the surface constrain anything built on this tier, and both are easy to assume the other way round. `Drawer` is internal, not public, so an extension extends `Sketch` and the public value types rather than the renderer's recorder. `Filter` / `Generator` / `Sim` / `Combine` are structs with no public initializer, so the effect catalogs take no new cases and the way into the render graph is a `Shader` through the `.shader(_:)` factories. Opening either would be a deliberate API decision, not a small one. The current seams are cataloged in [`Docs/Tools/Extensions.md`](Docs/Tools/Extensions.md).

License hygiene carries over: a third-party extension is the author's own package under their own license, not bundled, so it sidesteps the vendoring rules entirely.

## Testing

What the coverage reads (2026-10-10 and 2026-11-11, `Scripts/test.sh coverage`; `Tests/README.md` § *Coverage, and the hosts' own gates*) leave without a test, by class, with why. At the second read 84.1% of 205,899 lines ran; of the 32,724 that did not, these are the classes, largest first.

- **SwiftUI views** (the inspector, the timeline panel, the host windows, the cues card, the axis widget, the generator's stages). A view test needs a driver, and the one there is drives the parameters list: `OllinLive --inspectortest` posts clicks, keys, and a drag to a window built in the process, finds the controls SwiftUI draws itself through the accessibility tree, and sends undo down the responder chain (`Tests/README.md` says how). What it has not been pointed at: the curve and bars rows, the palette strip, and the XY pad, whose elements in the tree are unread; a menu opened by a click, since opening one starts a tracking loop a posted event does not end, so the grouped menu is read and chosen from without opening it and the flat menu and the segmented control are not driven at all; and the timeline panel and the cues card, which are windows and cards of their own with no gate. The same three moves (a view by class, an element by role, an action by selector) would carry each.
- **Device and network backends** (Core Bluetooth, the phone and Record3D devices, the room's local-network transport, the laser DAC's live socket, the WebSocket push transport; about 1,500 lines). Each is tested through a stand-in at its seam; the live half needs the device. A transport that speaks to a server on the loopback is the exception that has a test (the web socket feed, the MQTT client, the laser DAC's stream); the ping a web socket sends every twenty seconds is the part of that transport no test waits for.
- **The command fronts** (`ollin docs`, `ollin new`, the tether, the snippet and figure tools; about 3,800 lines). Scripts drive them (`check-snippets.sh`, `guide-figures.sh`, `preflight.sh`), so they run on every relevant commit without a test reading their lines.
- **Live-only paths**: the live window's own half of `SketchView.swift` (1,930 lines: the window modes, AppKit's events, the display link), `startRecording(to:audio:)` (the live loop's take), the environment downloads (the network), the Vision and sound models' live runs (a camera, a model); their failure sentences are now held by `VisionStatusTests`.
- **A path the desk never takes**: the raster point-light shadow (`encodePointShadowPass`) runs only without ray tracing, so a desk read reports it unreached while the CI runner takes it every run.
- **Public forwarders the pair tables leave out.** Six tables pair a bare call with its core (`SwitchFormsTests`, `QualityFormsTests`, `CameraRigFormsTests`, `CombinatorScopeFormsTests`, `TextMetricFormsTests`, `SimFactoryFormsTests`, beside `BareFormsTests` and `BareForms3DTests`). Outside them: the switches whose feature shows only over several frames or only in a live window (`noMotionBlur`, `noTemporalUpscaling`, `noFrameInterpolation`) and the two that need a GPU that traces to show at all (`noCaustics`, `noGlobalIllumination`), which are read on the setting they clear and not on a picture; the `quality:` arguments of the export calls and of `Filter` and `Combine`, which are not setters on a sketch; and `makeLineSpray`, which has no initializer beside it to pair with.
- **The gallery's cycle and an example whose `setup()` is heavy.** `OllinExamples --cycletest`, which `Scripts/host-gates.sh --all` runs, stops at `Patterns/GatherIntoLetters` in a debug build: the watchdog reads the main thread as stuck past its 90 s and exits (measured 2026-11-11, in a plain debug build and under coverage alike). The thread is working, not waiting. The example's `setup()` pairs 1,600 dots six times with `Matching.optimal`, and one pairing of 1,600 random points takes 9.6 s in a debug build of the framework, most of it in the solver's own loops (a `for` over a range is a generic iterator call a step when nothing is optimized). The sketch itself is compiled optimized by the gallery; the solver is the framework's and is not. Three ways out, to be measured against each other: the solver made inlinable, so the sketch's optimized compile carries it as it carries a parameter's read; the solver's inner loops over unsafe buffers with `while`, which is what a debug build can run fast; or the example pairing one leg a frame behind a first picture. Until then the cycle is red on this example and the read of the gallery's own lines stops there: the process exits without writing its profile, so the second read counts the inspector at 2,045 of 4,530 lines without the forty-odd inspectors the cycle hosts.

## Examples folder

The `Examples/` set is maintained: small, runnable sketches that double as the "learn it in an afternoon" on-ramp and the compile-tested showroom (current status, the `OllinExamples` gallery, and CI are described in [`CLAUDE.md`](CLAUDE.md)). The design decisions worth keeping, because they guide *extending* the set:

- **Layout organized by topic.** Group by feature so they read as a learning path: basics, color, motion, patterns, text, and so on. Each example is one minimal, focused sketch that shows one idea well. The top `Examples/README.md` indexes only the categories (a table linking to each category folder); each category folder carries its own `README.md` listing its sketches, so the front page stays small as the set grows.
- **Per-example folder, generic `Sketch.swift`.** Each example lives in `Examples/<Category>/<Name>/` and its file is always named `Sketch.swift` rather than `<Name>.swift`, so the example's identity lives in the folder name, not a repeated filename. The per-example folder is also each sketch's home for its own assets (fonts, images, shaders sit alongside `Sketch.swift`), which is the reason not to flatten the layout.
- **The single-file `@main` mechanism.** SwiftPM allows only one entry point per executable target, so each example is its own small executable target (scripted as the set grows, rather than hand-maintained). Adding `static func main()` to `Sketch` on the core (`extension Sketch { static func main() { OllinApp.run(Self()) } }`, which needs a `required init`) makes a file self-contained, so an example is just `@main final class HelloCircle: Sketch { … }` with zero boilerplate. Built once on the core, so any single-file sketch flow (examples, scripting, embedding) can reuse it.
- **A feature isn't done until it has an example.** Each new primitive or capability ships with one. Examples are also a forcing function for API quality: if the example is awkward to write, the API needs work.
- **Snapshot coverage grows with the set.** Compile-testing proves an example builds; render-correctness snapshot tests (`Tests/OllinTests`) prove it still renders the same: a sketch is rendered headlessly through `OllinApp.image(of:)` and its pixels diffed against a committed reference. A new primitive earns a small, deterministic fixture and a recorded reference, so the catalog stays regression-protected as it grows. The reference is GPU-specific (anti-aliasing differs across GPU families), so references are recorded on a developer's machine (`OLLIN_RECORD_SNAPSHOTS=1`) and the comparison stays a local gate, kept out of CI; keep new fixtures flat and pixel-friendly so the mean-difference tolerance has room. A peer Swift and Metal framework does per-primitive snapshot tests the same way (a frame hook gated behind `#if canImport(XCTest)`, using pointfree's swift-snapshot-testing), a reference if richer image diffing is wanted later.
- **Reuse the samples elsewhere.** Examples can seed the Swift Playgrounds `.swiftpm` starter and serve as starter templates for new sketches. Author once.
- **A candidate list read off a peer gallery.** The vgpu example gallery (MIT, Vercel Labs; credited under Directions ahead in [`ATTRIBUTION.md`](ATTRIBUTION.md)) was read the way the shader catalogs are read, for which pieces are worth having rather than for code, since it is WGSL against WebGPU and nothing in it transfers as source. Most of it maps onto capabilities Ollin already ships (a fluid solver, instanced draws in the hundreds of thousands, a recorded batch, an environment map lighting a scene, an SDF clip through a mesh, depth estimation and classification through Core ML, a hand-tracked canvas), so those are covered and want nothing new. One is the natural first reader of a shipped capability, a **light-painting scene** over the light a flat sketch works out for itself, and three wait on the tiers above: an **ocean surface** for the [2D transform](#technique-and-algorithm-helpers), a **glass object standing in a drawn scene** now that it has something to stand in, and **one scene shown through each anti-aliasing path at once** for the [post-process pass](#rendering-and-color-frontier), which teaches the four-way split better than prose does. Two of the gallery's pieces are its own and a sibling product's branding, so they stay out. The license permits redistribution, but a rewrite in Metal from the same published techniques is what will actually happen, so each one carries the per-example header naming the gallery entry as inspiration alongside the technique's canonical source, per the sourcing rules in [`CLAUDE.md`](CLAUDE.md).
- **Recreations grow by artist, and double as a build-it-to-find-the-gap forcing function.** The `Examples/Recreations/` set (organized by artist, homage framing, per-sketch provenance; see its README and the sourcing rules in [`CLAUDE.md`](CLAUDE.md)) includes Vera Molnár, Georg Nees, Frieder Nake, Bridget Riley, Osamu Sato, Nick Cave, Jared Tarbell, Manuel Felguérez, Manfred Mohr, Josef Albers, John Whitney, Sol LeWitt, Casey Reas, Vicente Rojo, Ryszard Winiarski, Hassan Sharif, Owen Schuh, Monir Shahroudy Farmanfarmaian, Gego, and Vladimir Bonačić. ## Developer experience: Swift-idiomatic ergonomics

A standing track, not a one-time task: keep mining Swift idioms to make the API read better than a literal p5 port would. "Feels like p5" is the shape (bare calls, terse positional args, motion by default), but Swift's type system lets the same call carry more meaning with no extra ceremony, and that's a differentiator worth pressing. The exemplar to extend: `canvasSize` is a `CanvasSize` enum (`.square(n)` / `.size(w, h)` plus named presets like `.uhd4K` / `.vertical1080`, with `.portrait` / `.landscape` to flip orientation, in `CanvasSize.swift`): it reads as English, is discoverable by dot-completion, carries integer pixels as it should, and beats a bare `createCanvas(3840, 2160)` on both clarity and correctness. More of that. Candidates, in rough order:

- **What the second API meaning pass found and left (read 2026-09-19, per satellite), after the two passes that acted on it.** The renames it made are in the changelog; the rule it settled, one shape per kind of failure, is in [`CLAUDE.md`](CLAUDE.md), and the failures it found are one shape each now. Three rulings came out of the work and are worth keeping: a start a sketch calls itself throws for what it can see, as `Camera.start()` and `AudioInput.start()` do, while a start the first note makes for the sketch (`Synth`, and `Tone.play()` / `AudioPlayer.play()` beside it) writes `unavailableReason`, since the note has nobody to throw to; a tracker's `detect` throws `VisionError.unavailable` with the same sentence its `unavailableReason` holds, because a call in hand can throw where a frame drawn without one can only read, and that is two moments rather than two shapes; and a server that fails to bind keeps the property and says the sentence once on stderr too, the way the vision status does, since the terminal is where the person who typed the port is looking. **Two words for one answer:** `unavailableReason` (the Bluetooth, haptics, controller, vision, camera, audio, Syphon, Link and server types) is a present state and clears when the thing works, where `lastError` (MQTT, the laser, the serial port) is the last thing that went wrong and is cleared by the next success; they are two answers and stay two words. **Left in place, with the reason:** `Collider3D.capsule(height:radius:)` takes its two numbers in the opposite order from `drawCapsule(radius:height:)`, and so do `cylinder`, `cone`, `taperedCapsule` and `taperedCylinder`, which makes the standing colliders one height-first family; matching the draw call would mean flipping five cases and thirty-three positional pattern matches, several of which bind two `Double`s that would swap in silence, for one label order, and the family's own consistency is worth more than agreement with the draw call. `PhoneDevice.isRunning` and `Record3DDevice.isRunning` report the socket rather than the retry loop, which is a behavior question before it is a naming one; `PhoneTouches.isReporting` only ever rises; `Hit3D.body` is typed `any Colliding3D` where `Contact3D` calls the same value a thing; `SoftBody3D.density` moves nothing but buoyancy while `Body3D.density` sets mass; and `Character3D` carries three velocities of which two are intents.
- **Keep the presets pattern growing.** The orientation-flip trick (`.portrait` / `.landscape` as computed properties on a value type) generalizes: look for other places a bare tuple or magic number could become a named, dot-completable value with helpers.
- **What the long-run pass left (read 2026-09-26, beside what it fixed).** *A frame's image batch whose texture never builds* is left out of `FrameProfile`'s counts by design, and no test draws one. *The widget run answers a renderer that will not start with an empty run*: `widgetFrames` is what the system surface asks, and an empty timeline is the one answer it can show, so the failure is silent there (the `--export-widget` path throws on an empty run); a reading the widget's own host could show is not built.
- **What the test audit left (read 2026-09-26, reread 2026-10-06).** Three things stay open. *About sixty files read a frame inside a helper of their own* that reads and then computes (a luminance sum, a histogram, a peak); each could call the shared `pixels(of:)` for its first half (`Tests/README.md` § *What the suites share*), one file at a time as it is touched, and none is worth a sweep. *Three skips are judgment-shaped*, named in their comments: the two listening tests that read what the classifier made of a synthesized tone, and the one where an empty transcript is a recognizer with no on-device model; a probe for those would be the test itself, so they keep their early return. *The web families' sanity tests* (a page against the wrong frame must read as different) keep a browser launch each, six in all, since each proves its own family's gate can fail; they could join their family's batched launch only by giving up that independence. One item the audit named is not ahead: the GPU simulation probes stay at the default canvas, because the attractor flow, fluid, soft body, drift, particle life, and spatial-hash suites take 6.2 s together at 1080 square (measured 2026-10-06), so a smaller canvas has nothing to cut.
- **What planting the wildfire left (read 2026-09-29, beside the forest fire's inject).** *Two rims make a mark*: the snapped injects ignore coverage under three quarters, and two one-texel SDF rects beside one gap composite to exactly that, so a dense grid stamped a rect a cell fills its gaps. A stamp drawn into a state field without the analytic halo would let a sketch plant cell by cell; today the answer is an outline or a polygon, whose coverage is geometric.
- **What the same-seed pass left (read 2026-09-26, beside what it fixed).** *A reflection ray on a tie*: a ray that meets two surfaces at one distance, a cylinder's base cap lying on the floor's top face, gets whichever the intersector reaches first, and that follows the acceleration structure the driver built for that process, so one pixel of a same-seed export came back half a percent different about one run in three, and no other pixel moved (found in the Upscaling example by float exports, which see a difference the 8-bit picture hides unless it crosses a level; it went with `rayTracedReflections()` and vanished with the bases lifted a thousandth). The rule that settles a tie is `ollin_rt_query_ordered` (every candidate reported, the strictly nearer kept, a tie to the back face and then the lower instance, geometry, and primitive), which the probe traces use; the reflection and refraction walks keep the opaque query, since the ordered one costs a candidate call per triangle a ray meets and they trace a ray or more for every pixel. Moving them over waits for a scene that shows the tie at more than a pixel and a measurement of that cost on it; the example stands its geometry a hair above the floor instead, and says why. The milestone of 2026-09-30 found a second instance in the Convertible recreation, mirror and painted-glass plates on a plaster kite under `rayTracedReflections()`: one pixel two levels apart at (616, 699), one run in three, the rest of the picture the same. *A detector that is not exact*: Vision's trajectory request fits its arcs a few millionths differently from run to run, on identical frames with identical timestamps (measured on a fixed synthetic throw, and in `TrajectoryTracking`, where two of five exports at frame 900 detected a different set of arcs). The export clock makes every input repeat, so the rest is inside the request; a trajectory detector of Ollin's own would be exact, and waits for a sketch that needs one. *A detector answering an input during a replay*: an export analyzes every frame its sources offer on its own clock, but a detector a sketch calls from an input hook (a `PointSegmenter` pick on a click, a `Task` awaiting `detect(in:)` on a finished stroke) answers on a background task, so a replayed take that clicks has the answer land on whichever frame the machine reached. Under an export such a call could wait for its answer on the thread driving it, as the trackers do. No example records a take like that, so the change waits for the first one that does. A tracker made in a property initializer, before the export begins, can also read a frame the still feed's thread published during a slow `setup()`; it shows only for a tracker whose answers carry from frame to frame, and every example makes its trackers lazily or in `setup()`, where they never see one.
- **More idiom candidates.** Trailing-closure scoping beyond `withState { }` (already the model, as is the `drawShape { p in … }` path builder); `@dynamicMemberLookup` only where it genuinely clarifies. The richest seam so far has been **conforming Ollin's types to the protocols the standard library already understands**, since that hands a sketch the whole library rather than one new call: a type that is a sequence of things says so, and a type that generates randomness is reachable wherever `using:` is asked for. Look for the rest of that shape (an ordered set of values that still hides behind a stored array, a value with a natural stride or ordering) before inventing spellings. Two literal conformances were weighed and left out on the bar below: `ExpressibleByArrayLiteral` on `Palette` loses the type name that `Palette(.red, .white)` already carries, and `ExpressibleByIntegerLiteral` on `Color` would let any stray integer become a color, which is shorter and less clear. Four collection candidates went the same way, and the reasons generalize to the next one: `Path` keeps pen *commands*, not points, so the element a collection would hand back has to be sampled and a subscript would re-sample the whole curve to answer for one point; `Rhythm` would arrive with `count` saying exactly what its own `length` says, over a run of `Bool`s nobody walks, while `onsets` is the read people actually want; `Ramp` has a `reversed` *property* returning another ramp, which a `reversed()` method returning a list of stops would sit one pair of parentheses away from, meaning something else; and a document carrying several parallel lists (`Automation`, `MIDIFile`, `Timeline`) has no single list that is "the" content, so picking one to be the elements is a coin toss the reader has to remember. Two shapes to watch for on the way in: a conformance that quietly redefines an existing call (a geometric `contains` becoming a membership test), and `Sequence` shadowing the global two-argument `min`/`max` inside the type's own extensions, which is a compile error at every bare call site. The bar: an idiom earns its place when it makes the call clearer, not just shorter, and never at the cost of the bare-call feel or the typed-core split.
