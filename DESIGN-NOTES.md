# Ollin design notes

The engineering design intent behind the planned work in [`ROADMAP.md`](ROADMAP.md). The roadmap is the short version (what's planned and how to help); this is the long version (how each piece would be built, the specific APIs involved, and why). A couple of shipped items stay only where their design rationale still guides future maintenance or evolution (extending the examples set, the Swift-idiom track); anything fully done and self-contained lives in its own doc or `CLAUDE.md`, not here.

These notes assume Ollin's two ground rules: it targets Apple platforms only (no cross-platform abstractions), and the bare p5-style API is sugar over a public, typed core, so a feature is built on the core first and given the bare call second. Geometry-emitting calls take a `draw` verb prefix (`drawCircle`, `drawRect`, and so on).

## Swift Playgrounds and iOS

Worth pursuing. Swift Playgrounds app (Mac and iPad) App Projects (`.swiftpm`) are the closest Swift gets to the p5.js "open the editor and type, see it move" onboarding, and the same work unlocks iPad sketching and embedding in any SwiftUI app. On-brand for the "learn it in an afternoon" goal.

- **The architecture is already most of the way there.** `SketchView` is a SwiftUI-embeddable view, cleanly separated from the macOS-only `OllinApp.run` (the standalone `swift run` launcher, now a thin SwiftUI `App`, `OllinSketchApp`, hosting `SketchView`, with an AppKit delegate only for activation). Embedding in someone else's SwiftUI `App`, which is what a Playgrounds App Project needs, is exactly that seam.
- **The blocker is iOS support.** Playgrounds App Projects build iOS apps, but Ollin only declares `.macOS("26.0")`. To make it importable: add `.iOS(...)` to `Package.swift`; make `SketchView` conditional (`NSViewRepresentable` and AppKit vs `UIViewRepresentable` and UIKit via `#if canImport(AppKit)` / `#if canImport(UIKit)`); guard `OllinApp.run` behind `#if os(macOS)`. The Metal renderer (`Metal`/`MetalKit`/`simd`) is already portable. A working reference for this exact seam is swifty-creatives, which compiles for macOS, iOS, tvOS, and visionOS from one source using a `ViewRepresentable` typealias (`NSViewRepresentable`/`UIViewRepresentable`) with `#if os(...)`-guarded `makeNSView`/`makeUIView`.
- **Keep shaders Playgrounds-safe.** Swift Playgrounds' support for SwiftPM build-tool plugins is unreliable, so don't go plugin-only for shaders. Keep runtime source compilation as a first-class loader.
- **Onboarding nicety:** ship a ready-made `.swiftpm` starter (Ollin pre-wired plus a `HelloCircle`) so users don't hand-add the package URL.
- **Caveats:** the Playgrounds sandbox restricts file I/O (which matters for the export items, not for drawing); package-dependency UX is finicky; prefer the Swift Playgrounds app's App Projects over the semi-deprecated Xcode Playgrounds. iOS changes need `xcodebuild -destination` with the iOS SDK on a Mac to verify.

## Color additions deliberately kept out

Rationale that still gates future color work:

- **Other color spaces stay out.** Classic Lab/LCH (the 1976 space OKLab was built to fix; interpolating through it bends blues toward purple), CIECAM16/JCh (a full appearance model that needs viewing-condition parameters; OKLab was fitted to give most of that benefit without the machinery), and DIN99/DLCH (an industrial color-difference standard). Any of them can arrive later as a plain conversion if matching an external spec calls for it.
- **Further curated palette collections stay license-gated.** Collections scraped from ColourLovers and similar sites are not license-clean and stay out; anything added must carry a permissive license the way the ColorBrewer data does.

## Supersampled render scale (the crispness dial)

An opt-in render-resolution multiplier (e.g. `renderScale: 2`), rendering the frame at N× and downsampling, as the explicit performance↔quality dial, off by default for the 60fps path.

- **Why a knob, not the default.** Rendering at N× and downsampling is brute force (N²× the fragment work), the wrong default for a live 60fps sketch but a fine opt-in for a frame off that clock. The thin-line AA it would otherwise be reached for is already handled at native resolution: stroked lines/curves carry their own ~1px coverage fringe (the fringe stroke path), and the analytic SDF shapes (fills, disks, and stroke-band outlines alike) conserve sub-pixel area, so a supersample buys little on those.
- **Where it pays off.** The live view already renders at the display's backing scale (MTKView's default drawable), so on a Retina Mac it's effectively ~2× already; raster `--export`/`image(of:)` is fixed at `canvasSize`. So the knob's first home is export (a gallery-grade still / sequence), with an optional above-Retina multiplier for the live view. It mostly sharpens the *tessellated fill* path (polygon/shape fills, tessellated text) and fine dense detail; the SDF shapes and the fringe-AA strokes are already crisp at native resolution, so the gain there is small. For plotter line art the vector `--export-svg` is already resolution-independent and the better answer.

## Layered effects and compositing

OPENRNDR-style effects that compose in layers: draw into off-screen layers, run filters over them, composite with blend modes. The substrate (`renderTarget` / `withTarget` / `filtered` / `combined` / `postProcess` / `generate` / `feedback` and the `compose { }` DSL) is inventoried under *Current state* in CLAUDE.md; what belongs here is growing the catalog on top of it. The reference menus guide what else to add and how to shape it: AsyncGraphics (its `Graphic` is an `MTLTexture`, effects are functions returning new graphics, plus a blend/stack model; borrow the compositing architecture, not its async call shape), SwiftUIShaders (MIT, a menu of forty-odd post-process effects such as holographic, kaleidoscope, datamosh, and thermal, to mine and reimplement), and ofxFX (MIT, Patricio Gonzalez Vivo: composers, the bokeh/ripple/flow passes still worth taking). More two-input ops (layer-blend variants, chroma keying, wipes and other transitions) slot in as further `Combine` cases. Same stance throughout: study and reimplement, credited in `ATTRIBUTION.md`.

## 3D mode

2D stays the default and most sketches stay 2D, but 3D is a mode in its own right: a sketch opts in by setting a camera and, on the same Metal core, draws depth-tested point clouds and lit solid primitives, with richer shadows and materials as the mode grows. The iPhone point cloud renders through it, and visionOS and AR build on it. openFrameworks and OPENRNDR set the capability bar here, so the target is known. (The foundation, from the camera, depth buffer, and transform stack through point clouds, meshes, lights, materials, and cast shadows, is inventoried under *Current state* in CLAUDE.md; the notes below build on it.)

- **The further scene-import legs.** Over the structure-preserving import and animation playback a loaded `Scene` gives (see `Docs/3D/Scenes.md`): vendor `EXT_`/app-specific glTF extensions beyond the ratified `KHR_` set. The one-way **scene-to-source** alternative (emitting editable Ollin source instead of a live asset) is the lossy scaffold that belongs in the [project generator](#project-generator--sketch-scaffolding), a complement to the runtime path, not a replacement.
- **Material-from-file refinements.** A merged `loadMesh` model wears its first base-color material (glTF/USD/OBJ-MTL). The relaxation ahead: **REPEAT-wrap samplers** (the shared clamp-to-edge sampler doesn't tile a wrapping texture; a wrap-mode axis on the sampler). The UV-origin convention for a Model I/O `imageFromTexture` result is unverified and may need a v-flip.
- **More than one caster at once.** Each light kind casts through a shadow map sampled with a hardware depth-comparison sampler: directional and spot through one 2D map (orthographic / perspective, shared `shadowFactor`), point through an omnidirectional cube (six faces in one layered pass, `shadowFactorCube` reconstructing the per-face depth from the light distance). Today only the first eligible light casts (e.g. a directional key and a spot together can't both cast: the first directional, else the first spot, else the first point), so it wants a per-light `castsShadow` flag and a small caster array (a `depth2d_array` for the 2D maps, a `depthcube_array` for points) bounded to a small count. Lean on the native Metal feature here rather than hand-rolling a multi-pass equivalent.
- **Many dynamic lights: Forward+ or tile-shading, not classic deferred.** Lighting is forward today: one `OllinLighting` uniform, `OLLIN_MAX_LIGHTS` bounded at 8, every mesh shaded against the same small set, which covers the common low-light-count case. The technique that exists to scale past it is deferred shading (render geometry into a G-buffer, then light in screen space so cost tracks pixels, not geometry×lights), but the textbook multi-pass G-buffer is the wrong fit here: it round-trips the G-buffer through DRAM, breaks the **draw-order compositing** the renderer rests on (2D SDF/triangle/image batches interleaved with 3D meshes under per-batch blend modes, a deferred resolve flattens that and drops transparency ordering), and fights the float-MSAA path (per-sample G-buffer resolve). On Apple-silicon TBDR the idiomatic answers keep forward's strengths: **tile-based forward (Forward+)** culls lights per screen tile and still shades forward (blending and the 2D/3D interleave survive), or Metal's on-chip **imageblock / tile-shading** deferred keeps the G-buffer in tile memory and never spills to DRAM. Either is an in-pass change, not a renderer rewrite, and it's the lever only if the 8-light ceiling actually bites.
- **Camera-relative lighting (an opt-in on the world-space default).** A `Light`'s direction is world-space, and that's the right default: the sun stays put as the camera orbits, the intuitive behavior the scene-graph 3D frameworks (openFrameworks' `ofLight`, OPENRNDR, the game engines) all default to. Those frameworks make a light *follow the camera* by parenting it to the camera node. Ollin is immediate-mode with no scene graph to parent into, so the switch has to be an explicit affordance: a `relativeTo: .world / .camera` flag on a light or preset, resolved each frame against the active `Camera3D`'s basis (cheap, since lights are already per-frame state). It earns its keep in two narrow cases: a viewer-following fill so the side facing away never goes fully black (a `headlight` helper is the sugar), and a three-point rig that holds its look under orbit rather than the world-fixed look the `.threePoint` preset has. Sun, sky, and product lighting all want world-space, so add the opt-in only when the headlight or a camera-locked rig actually wants it.
- **Anisotropic specular.** Brushed metal, satin, and hair need a *stretched* highlight that the isotropic Blinn-Phong model can't make: it takes a per-vertex **tangent** direction (the reserved `OllinMeshVertex` pad slot is for exactly that) plus a Ward / Kajiya-Kay specular term keyed to it. It layers over the per-batch `OllinMaterial` uniform like the named finishes: a new finish parameter plus the tangent attribute, no state-machine change. (The matcap path is a sibling "whole look in one texture," but isotropic; anisotropy is the analytic-model gap it doesn't cover.)
- **Per-mesh lighting (a refinement).** Lighting is per-frame today (one `OllinLighting` shades every mesh in a frame, like the camera), so a frame can't mix lit and unlit meshes or different light sets. Promoting it to per-batch state (break the mesh batch on a lighting change, like blend/depth, and carry the uniform per batch) matches immediate-mode semantics (the light state *at draw time* of each mesh); do it when a sketch actually needs two lighting setups in one frame; until then per-frame keeps the path simple.
- **Build order.** Softer shadows (and supporting more than one caster at once) are the rendering-heavy step. The tier-one material recipes are pure data over the existing light/material model with no renderer change, so they land cheaply (the way the lighting presets did): a `Material` surface beside `specular`/`shininess`. Each step is usable on its own.
- **`Vector3` shares most of `Vector2`'s surface: document the common part once.** `length`/`normalized`/`dot`/`distance`/`lerp`/the arithmetic operators/`limited`/`projected`/`with`/the constants are the same idea in one more dimension, so the shared surface lives on a `Vector` protocol (or a SIMD-backed extension): one source of truth in code. A few members diverge and stay per-type, chiefly `cross`, which returns a **scalar** in 2D (the perp-dot, for sidedness/winding/steering) but a **`Vector3`** in 3D (a perpendicular vector, for normals/frames/torque); that scalar-vs-vector split is the headline and wants a prominent call-out. Also 2D-only or reshaped in 3D: `angle` (one direction angle), `perpendicular` (unique only in 2D), the signed `angle(to:)` (3D is unsigned without a reference axis), in-plane `rotated(by:)` (3D needs `rotated(by:axis:)`), and the polar `init(angle:length:)` (3D is spherical). **Docs mirror the code:** one shared "vector basics" section (the schoolbook diagrams are 2D but teach the general idea), then a compact "what's specific" section per type, instead of two near-duplicate pages that drift. The practical-use notes split on the same seam: `dot`/`length`/`lerp` uses are dimension-agnostic (shared), while `cross`/`perpendicular`/signed-`angle` uses stay 2D-specific.
- **visionOS is a different render loop.** Immersive rendering doesn't use `MTKView`/`SketchRunner.draw(in:)`; it uses CompositorServices (`LayerRenderer`) driven by a manual render thread, plus ARKit world tracking. Keep the per-frame loop behind a seam that either an `MTKViewDelegate` or a visionOS layer renderer can drive, rather than assuming `MTKView` everywhere.
- **Reference.** swifty-creatives is the concrete study: it ships both a normal `MTKView` renderer and a visionOS `RendererBase` with a manual `renderLoop()` over `LayerRenderer`, and it's 3D-first (camera, depth, box and 3D text). Borrow the structure (camera plus depth pipeline plus dual render loop) and write our own.
- **Ray tracing is a later tier, and the platform has it native.** A fuller ray-traced render path (path-traced stills a sketch leaves running, global illumination, beyond the inline-RT shadow rays the point caster traces and the inline-RT reflection rays a physically-based metal traces) is reachable. Metal has first-class ray tracing (acceleration structures, intersection from compute kernels) on every Apple-silicon Mac, so this is Metal API work, not an engine to vendor. Quality and performance refinements to the ray-traced reflections live here too: multi-bounce (a reflected metal recursively mirroring the scene, not just the environment), reflected non-PBR stylized finishes (a reflection shades a metallic-roughness surface correctly from its baked per-vertex metalness, but a toon or gooch surface reflects as plain diffuse), a half-resolution `RenderQuality` tier (the raymarch/SSR half-res pattern is the template), and a dedicated all-mesh reflection acceleration structure (the reflections reuse the shadow-caster one today). The oF-world prior art is ofxEmbree (Cyril Diagne, Intel Embree inside the oF loop, **no license file, so concept only**): what to mine is its call shape, a creative-coding-friendly "trace this scene" surface rather than a renderer rewrite. Not part of 3D mode's entry bar; it slots behind the camera/mesh/material work as its own pipeline kind.
- **Richer 3D physics: the solver's own remaining gaps.** The one thing still ahead is **soft-body reach**, and it is upstream's rather than Ollin's: self-collision and cloth-against-cloth are gaps in the solver, so a folded sheet passes through its own layers, and tearing needs a shared vertex split and a rebuilt constraint set mid-simulation, which it cannot do at all. Both stay out until the library grows them. The solver's **volume constraints** (tetrahedra held at their rest volume) stay out for a different reason, a measured one rather than a missing one: built and probed against the shipped `pressure`, they tie on holding a weight, tie on coming back from a dent, and lose on coming back from a hard squash, because their residual is formed from an *unsigned* volume and so reads an inverted tetrahedron as correct, where a gas law's push grows without bound as the space shrinks. The numbers and the two things that would reopen it (a vertex-follows-tetrahedron binding, or a signed volume constraint) are in [`ARCHITECTURE.md`](ARCHITECTURE.md). The solver's neighbouring **hair module** stays out for four measured reasons. It accepts no force, so the only way to move a strand is to move the head, where Ollin's cloth and rope examples are driven by `applyForce`. It collides only with `ConvexHullShape`, and Ollin's figures are meshes and capsules. It requires an authored groom and a skinned scalp, where a sketch generates its own geometry. And the rod family already exposed carries 20,000 simulated strands in a 60 fps frame against its 2,500, so the Metal backend it needs (49 shaders cross-compiled and packaged, Objective-C++ admitted into the C bridge's target, a new draw path for a foreign compute buffer) would buy a strand count `Rope3D` already reaches. The measurements and the reopening bar are in [`ARCHITECTURE.md`](ARCHITECTURE.md); if hair is wanted before then, build it as a **multi-strand `Rope3D`** (one soft body holding many rod chains) rather than from that module. When they arrive, the shipped rules still apply: land it as *more capability on the existing surface* (a parameter on `addSoftBody`, a call on `SoftBody3D`), never a parallel system; keep the C bridge flat-POD `extern "C"` with `JPH` never reaching Swift; keep the no-pixel-snapshot policy (determinism is per-binary, so behavioral tests pin each slice) and `unitsPerMeter` as the one scale bridge; and ship an example, tests, a `Docs/Simulation/Physics3D.md` section, and Guide Ch 17 growth together.
- **Don't 3D-tax the 2D path.** Most sketches stay 2D, so don't make every draw call pay for a depth buffer or perspective divide. 3D is a mode you opt into, not a cost the 2D core carries.
- **Caveat:** the 3D mode itself builds and verifies on a Mac; visionOS needs the visionOS SDK plus a simulator or device.

## Photorealistic 3D

The realism tier that builds on the physically-based core (PBR metallic-roughness, split-sum IBL from HDRI or the Hosek-Wilkie sky, ray-traced shadows and reflections, SSAO, SSR, raymarched SDF fields) toward the look of a curated product render or film still. Every item is opt-in so 2D and stylized 3D stay untaxed, every one is Metal-native (no engine vendored), and each is implemented from the published technique and credited in `ATTRIBUTION.md`'s Techniques. This is the "anything Metal offers that enriches 3D" tier, after the foundational [3D mode](#3d-mode) buildout: as a new realism technique finds a good fit, it rides the textured path's twin pipelines (or a gated branch of the surface-mapped fragment, which may branch freely) so non-using materials stay byte-identical.

All Apple-silicon Metal, the realism direction's "build Ollin APIs for anything Metal offers that enriches 3D."

## AR mode and templates (the Meta Spark gap)

Ollin aims to support AR sketches and offer a template-driven AR framework, filling the gap left when Meta Spark was discontinued (January 2025). Apple-only: ARKit plus RealityKit and Metal on iOS and iPadOS, and the visionOS immersive path.

- **It's a mode layered on the iOS and 3D/visionOS work, not a separate engine.** AR needs the iOS target (see [Swift Playgrounds and iOS](#swift-playgrounds-and-ios)) and the 3D camera and depth pipeline (see [3D mode](#3d-mode)) in place first.
- **The Spark lesson is templates.** Spark's reach came from ready-made effect templates (face filters, world effects, plane and image tracking) people could start from. The Ollin version: AR-example sketches plus starter templates wired to ARKit anchors (face, world, image tracking), so an AR sketch is "fill in the `draw()`, the tracking is handed to you", the same template-as-on-ramp idea as the examples and `.swiftpm` starters.
- **Caveat:** AR needs ARKit on a device to verify (the simulator has no AR camera).

## Model examples and ModelTracker surfaces

`ModelTracker` runs any converted Core ML model, so new perception examples are mostly a matter of picking models worth showing, plus, for some, one small new output surface on the tracker. The standing delivery rule for all of them: **weights are never committed**. `Scripts/fetch-models.sh` downloads into the gitignored `Models/`, the example shows the run-the-script notice until they exist, provenance goes in `THIRD-PARTY-NOTICES.md`, and the real-model tests soft-skip where the weights aren't fetched.

Candidates, in rough order of effort:

- **Text-driven knobs (MobileCLIP-class embeddings).** `confidence(of:)` for *any phrase*, not a fixed vocabulary: "how spooky does the camera look" as a `0…1` knob. A real milestone rather than an example: it needs an embedding surface, the text-encoder side, and a tokenizer, and **the license of Apple's MobileCLIP release needs verifying before any fetch script points at it.**

Skip the plain ImageNet classifiers (FastViT, MobileNetV2, ResNet), redundant with the built-in `ImageClassifier`'s ~1,300-label vocabulary. And the modern Ultralytics YOLOs (v8/26) are AGPL-3.0: never bundled, never scripted, same tier as p5.js's LGPL.

## iPhone as a sensor array

A Mac has no depth camera, no inertial sensors, and no spare Neural Engine for live perception. A tethered iPhone has all three, so the idea is to let it act as a sensor and on-device ML co-processor for a sketch that still renders on the Mac. The phone captures and perceives, streams the results over the wire, and the sketch reads them in `draw()` as typed values. The Mac keeps the Metal rendering ceiling; the phone fills the input gap desktop hardware leaves.

The starting want was live RGBD point clouds, the kind an Intel RealSense fed openFrameworks before its Mac drivers were dropped. An iPhone with LiDAR is the same world-facing depth-and-color sensor, except the driver is ARKit and Apple maintains it. Both the *recorded* path and the *live USB* path exist (`OllinRecord3D` reads Record3D `.r3d` clips and its live USB stream; see [`Docs/3D/Record3D.md`](Docs/3D/Record3D.md)): a depth map plus intrinsics unprojects, through the [3D mode](#3d-mode) point-cloud path, into one splat per depth sample (around 49k for LiDAR's 256×192 map, ~300k for TrueDepth's 640×480). The renderer, the unprojection, and the live wire need no new work; what's ahead is *more sensors over that wire*.

**One channel, many typed payloads.** Depth is only the first thing the phone can send. Because both ends are ours and both are Swift, the wire skips the packed-image trick cross-language tools reach for: it is a length-prefixed binary stream of tagged messages, each a typed payload the sketch reads through the same transport-agnostic `FrameSource` abstraction used for the point cloud. The phone app is a configurable sensor hub, so adding a sensor later is a new payload case rather than a new pipeline. A header struct shared verbatim between app and framework carries intrinsics, pose, and a version byte; the rest is raw or LZFSE-compressed channel data.

The phone runs the expensive model on its Neural Engine and ships kilobytes of structured results, so each new sensor is nearly free on the wire:

- **Desktop-impossible.** TrueDepth face mesh and its 52 blendshape coefficients (the Animoji engine: jaw, blink, brow, and smile as 0-to-1 values), 3D body motion capture from a single camera, LiDAR scene mesh with detected planes and real-room light estimation, 6DoF device pose, and the inertial sensors (attitude, gravity, acceleration, rotation rate) a Mac doesn't have at all. The motion stream is the cheapest to build and the most physical: a few floats, no camera, no model.
- **Possible on a Mac, but the phone is the natural host.** Vision runs on macOS too (that's the [`OllinVision` catalog](Docs/Vision/Vision.md)), yet the phone holds the camera and the spare Neural Engine: subject segmentation, hand pose, optical flow, saliency, live text, scene and object classification, sound classification, and speech.

Most of those payloads are kilobytes. Only the per-pixel ones (segmentation matte, optical flow field, scene mesh) are heavy, and they arrive as textures, which is what the [layered effects](#layered-effects-and-compositing) graph already consumes, so a live person-matte becomes a `Filter` input rather than a separate feature. Everything here is Apple-native (ARKit, Vision, Core Motion, Core Location, SoundAnalysis, Speech) with no third-party dependency, and it shares its prerequisites with the [iOS target](#swift-playgrounds-and-ios) and [AR work](#ar-mode-and-templates-the-meta-spark-gap).

The transport is the proven live **USB** path (the standard usbmuxd device tunnel): full-quality LZFSE float32 depth plus camera intrinsics and ARKit pose, RealSense-grade, no extra dependency. Ollin's own capture app speaks the same length-prefixed-tagged-payload wire, so the sensor catalog isn't capped by what one borrowed app exposes. Record3D's **WiFi** streaming stays deliberately *out*, correcting an earlier assumption that it would be the easy one: it's WebRTC (a heavy dependency, and the `record3d` library doesn't support it at all), gated behind a paid Extension Pack, and its depth is lossy hue-encoded with no pose: the worst option on every axis, and the reason USB is the only streaming mode supported. Device class gates the sensors (TrueDepth for face, Pro-tier LiDAR for rear depth and scene mesh, A12 and later for body tracking), and several heavy models at once will thermal-throttle, so running every sensor together is a practical limit, not an API one.

**The clean-room stance carries forward to our own app.** Both the `.r3d` file reader and the live USB stream are read clean-room from their public structure, the same constraint our own capture app's wire still works under: the `record3d` library is LGPL-2.1, the same copyleft tier as p5.js, so it stays inspiration only (reimplement the wire protocol, never translating its source, exactly as the sourcing rules treat p5.js). Record3D is credited like the other product references, not vendored. New sensor payloads added over the wire follow the same rule.

## Generative geometry

A tier of classic generative-art algorithms that produce *vector geometry* (points, `Contour`s, `Shape`s) and hand off to the geometry that already exists (the triangulated fill, the stroked path, the shape booleans, hatching, SVG export). They're geometry, not rendering, so they live in the `Ollin` core beside the shape booleans and the `Path` builder rather than in a satellite: none needs a heavy framework, and the split `OllinPhysics` took was about keeping simulation opt-in, not about dependencies. All are driven by the existing seedable `random`/`noise` so a result is reproducible, and each ships with an example; several are the natural implementation behind a [recreation](#examples-folder).

- **Parametric L-systems.** The L-systems in place interpret deterministic and stochastic rules through a turtle into `[Contour]` line-work. The remaining extension is *parametric* rules: symbols carrying numeric parameters (`F(3)` = forward 3) with arithmetic in the productions, for the continuous length/angle/width variation the plain symbolic grammar can't express (the ABOP parametric-L-system chapter). It rides the same turtle, so the work is the parameter syntax and the expansion evaluator.

The reproducibility note matters: every one of these is a pure function of `seed()` plus parameters, so the same seed always yields the same packing/growth. License stance is the usual one: implement each from the *published technique* (credited in `ATTRIBUTION.md`'s Techniques list). Origin note: these surfaced from mining the `/algorithmic-art` skill's implicit technique vocabulary against what Ollin already ships (Voronoi/Delaunay, the foundational primitive of the tier, is a pure-Swift Bowyer–Watson, no library vendored).

## Technique and algorithm helpers

This is the umbrella the [generative-geometry](#generative-geometry) tier is one wing of: a standing catalog of the creative-coding algorithm vocabulary, added as helpers over time the way the SDF-shape catalog, the `Filter` catalog, and the color family grew. The organizing rule is to route each technique to the seam it naturally belongs on rather than invent a parallel system:

- **Geometry emitters** produce points, `Contour`s, or `Shape`s and feed the existing draw, shape-boolean, hatching, and SVG paths, exactly like the generative-geometry builders. The most plotter-friendly and the cheapest to add.
- **Field techniques** that read per-pixel (a new noise basis, an interference field) land as a GPU `Generator` (a no-input `ollin_gen_*` fragment) or a user shader, reusing the layered-effects substrate rather than the CPU geometry path.
- **Simulations** (iterated function systems accumulated on the GPU) run on the compute and `SimField` paths already in place: persistent ping-pong buffers or textures stepped each frame, drawn through the instanced or image path.

The rest of the catalog follows the same shape: a canonical algorithm implemented from the published source, credited in `ATTRIBUTION.md`'s Techniques list, seeded for reproducibility, and shipped with an example, several of which pair naturally with a [recreation](#examples-folder) (an attractor plot, a flow field, a substrate).

The catalog is also a *Nature of Code* coverage map, so it reads as a familiar curriculum to anyone arriving from that world.

For any animated per-pixel `Generator`, three implementation notes hold (their map is fluid, enonforetsam/fluid, MIT, a single-file WebGL background studio read the LYGIA way: a catalog of which looks matter, implemented from the canonical sources rather than its code): spread a noise-family field's contrast around its midpoint so a palette reaches its end stops (fbm piles up near 0.5 and otherwise hides them); animate by small bounded sways at non-commensurate frequencies so the field churns in place instead of panning as a rigid sheet (which also keeps the time argument precision-safe over long sessions); and normalize field coordinates by the canvas's geometric mean so a portrait crop reveals more field rather than zooming in.

Origin note, the same as the generative-geometry tier: this catalog is the broader read of the `/algorithmic-art` skill's technique vocabulary against what Ollin already ships, and this section is the standing list of what's left.

## Expressive brushes and strokes

The fringe expander carries a half-width per path vertex, `StrokeProfile` shapes it by position along the path, a recorded `StrokeMark` drives it from the hand, and a `Brush` stamps a shape along the path instead of expanding it. The tier builds out from there:

- **Painterly simulation stays separate.** Watercolor-style marks built from layered, deformed translucent geometry are a [technique-catalog](#technique-and-algorithm-helpers) recipe over the shape and accumulation machinery, not a brush engine; keeping the two distinct keeps the stroke renderer lean.

## Sound, synthesis, and spatial audio

`OllinAudio` covers both directions: `AudioAnalyzer` (FFT, bands, beat detection) over `AudioInput` / `AudioPlayer` / `Tone` / `Soundtrack` on the listening side, and a polyphonic `Synth` (voices over anti-aliased oscillators, ADSR envelopes, a resonant state-variable filter, delay and reverb) on the playing side, with a clock-free composition tier deciding what it plays. Both sides are routing as a value now, so what is left is depth rather than shape: more of what a voice can be made of, and a seam for an effect a sketch wrote itself.

- **The render-thread rule holds.** Anything the audio callback touches is built non-isolated and allocated before the first note, and parameters reach it through the lock-free event ring rather than a lock. A new voice type inherits that constraint; it is not a per-feature decision.
- **Keep the renderer pure.** The samples are made by a renderer that knows nothing about the audio engine: events in, buffer out, no clock. That is what makes the sound testable at all (a test renders and measures) and what a sound-carrying export would be built on, so a feature that reaches for the engine from inside the renderer is going the wrong way.

## Tempo sync

Locking a sketch's clock to external musical time, for live performance and installation. The wire tier is `OllinMIDI`'s `TempoClock` (MIDI clock in, beat/phase/BPM out); the tier ahead is the network:

- **Ableton Link.** Link is the de-facto standard for tempo-and-phase sync across apps and machines on a local network (Ableton Live and most modern music apps speak it). It would let an Ollin sketch share a session's tempo and downbeat with a whole rig with no manual setup. The catch is licensing: Ableton's Link SDK is GPLv2 (or a paid commercial license), incompatible with Ollin shipping as MIT, so it stays the inspiration-only tier alongside Hydra's AGPL: the protocol is documented, so reimplement the wire and clock-sync from the spec rather than vendoring the SDK, exactly the clean-room stance the Record3D and OSC work already take. It's real work (a networked clock-consensus protocol), not a quick pickup. The read surface should land on the `TempoClock` shape (`tempo` / `beats` / `phase` / `progress(over:)`), so a sketch written against the wire tier moves to a Link session unchanged.
- **Why it fits.** Ollin's audience includes VJs and live performers (the Syphon, OSC, MIDI, and virtual-camera work is all for them), and motion-by-default is the whole premise, so making that motion lock to a beat is squarely on-brand. It complements the [audio synthesis](#sound-synthesis-and-spatial-audio) work on the output side: a sketch can both make sound and move in time with the room.

## Live rigs: physical computing, lighting, and network video

The hardware-and-network interop tier, extending the app-to-app integrations (Syphon, OSC, MIDI, the virtual camera) to the physical rig around the machine. Same posture throughout: play in the existing rig, implement published protocols from the spec, vendor nothing incompatible.

- **Serial.** USB microcontrollers enumerate as serial devices on macOS (IOKit discovery over POSIX termios, no dependency needed), so a small `SerialPort` covers the classic physical-computing loop: sensor lines read in `draw()`, bytes written out to drive servos and LEDs. Read surfaces mirror OSC/MIDI: a latest-value cache, a line/message drain, `@Param` binding. Framing stays at lines and bytes; higher protocols (Firmata and friends) are extension territory, not core.
- **Bluetooth LE.** CoreBluetooth central reads from BLE peripherals (buttons, environmental sensors; heart-rate straps overlap the HealthKit item under [new input sources](#new-input-sources)), the same value-cache surface. Needs its entitlement and consent prompt, the "make the permission explicit" concern screen capture set.
- **Laser projection.** Show lasers draw vectors: the galvos trace a stream of points, which is what a `Contour` resampled by arc length already is, so the geometry core supplies the material (even `resampled(spacing:)`, and path ordering to minimize dead travel is the `singleLine` tour problem again). Consumer DACs speak published protocols (Ether Dream documents its wire protocol; Helios ships an open SDK), so the wire layer repeats the written-from-spec recipe; the mature laser libraries in the creative-coding lineage are studied as references, never ported, credited in `ATTRIBUTION.md` when studied. The real work is the optimizer between shapes and beam: corner dwell, blanking between paths, a per-frame point budget traded against flicker, brightness versus scan speed. Safety is a first-class API concern, not a footnote: no output without an explicit arm step, and conservative defaults for scan speed and dwell.
- **NDI.** Network video send/receive between machines, the cross-machine sibling of Syphon. The SDK is a binary-only distribution under NDI's own license, which doesn't fit the source-vendored tier (Syphon, Box2D, Clipper2 all ship as permissively-licensed source); a satellite that links a user-installed NDI runtime may fit instead. The licensing review is the gate before any code, and its outcome decides send-only, both directions, or staying out.

All output paths are real-time side effects of `draw()`, so they follow the render-thread rule (non-isolated closures) and the background-producer handoff pattern the receivers already use.

## New input sources

Each conforms to the core `FrameSource` (so the vision trackers and effect graph consume it) or reads as a simple value in `draw()`.

- **Apple Pencil.** Tilt, azimuth, force, and hover, on the iOS leg where a Pencil exists. Force joins the `pressure` `Sketch` already reads rather than arriving as a second thing, so a sketch written against trackpad pressure carries over unchanged and tilt, azimuth, and hover are the additions; each reads as a plain value in `draw()` beside the mouse and keyboard.
- **Body and world data.** HealthKit (heart rate from a paired Apple Watch) for biofeedback, WeatherKit and Core Location for slow ambient input. Each needs its entitlement and consent prompt, the same "keep the easy things easy, make the prompt explicit" concern as screen capture. Niche but distinctive (native Apple-sensor-sourced live data) and impossible in a browser.

## New output surfaces

Ways a sketch leaves the window, beside the flat image / video / GIF / SVG exporters already in place.

- **Haptics.** Core Haptics (`CHHapticEngine`) on the Force Touch trackpad and on the phone, a felt pattern emitted from `draw()` alongside the frame, so touch joins pixels and sound as an output. A pattern per frame or a short event timeline, synced to the visuals. The constraint is that good haptics are designed, not auto-derived, so the API should make a felt pattern as composable as a stroke.
- **The OS as a canvas.** Wrap a sketch as a macOS screen saver (a `.saver` bundle hosting the renderer), a dynamic wallpaper, a desktop widget (WidgetKit, with its timeline-refresh limits), or a menu-bar piece, so output lives in the system rather than a window. The wrapper-emitting work is the natural home of the [project generator](#project-generator--sketch-scaffolding), so this leans on that. High delight-and-share value, and uniquely low-friction on Apple where these wrapper formats are first-class.
- **Performance capture.** The offline exporters re-render deterministically on a fixed clock, which is exactly wrong for capturing an improvised live run (input, params, and audio happen in real time). ScreenCaptureKit records the live window with system or mic audio; the GPU-texture frame hook (`wantsRenderedTexture`) is the higher-fidelity capture point for the canvas itself, muxed with an audio tap through AVAssetWriter's real-time mode. The OllinLiveCoding performance host and VJ sets are the customers; record-and-replay in the [authoring tier](#authoring-and-editor-tooling) is the deterministic sibling (replay the inputs), and the two compose: replay a captured run and export it offline at full quality.

## Rendering and color frontier

Deeper use of the Metal core and Apple displays, every item opt-in so the 2D path stays untaxed.

- **Wide-gamut and HDR.** The pipeline already composites in a linear `rgba16Float` intermediate and tone-maps to an sRGB drawable, so the wide-gamut float data exists and is narrowed only at the end. Presenting through a Display P3 (or Rec. 2020) drawable over an extended-linear working space widens the gamut on Apple panels; exporting HDR video (HDR10 / Dolby Vision via AVFoundation's HDR-capable writer) preserves the float as HDR rather than tone-mapping it down. Both are present-pass and pixel-format changes on built machinery, not a new renderer, and they pair into one "deeper than 8-bit sRGB" story. The default SDR look is unchanged.
- **GPU-driven rendering.** Instancing (the lever already in place) draws many copies of one mesh cheaply; the tiers above it are indirect command buffers (encode draw calls on the GPU, so the CPU leaves the per-object loop and the scene can hold far more *distinct* objects) and mesh shaders (generate geometry on the GPU: grass, hair, shells with no CPU vertex buffer). Both are Metal-native, slot in as new pipeline kinds behind the `PipelineKey` cache, and are the answer when CPU tessellation or encoding is the bottleneck rather than the GPU.
- **Film-quality export.** An offline path-traced render path (global illumination, soft shadows, depth of field) a sketch switches to for stills and sequences, spending seconds per frame on a look the live raster path can't reach, from the *same* scene description. Metal has first-class ray tracing on every Apple-silicon Mac (acceleration structures, intersection from compute), so this is API work, not an engine to vendor, and it extends the ray-tracing tier already sketched under [3D mode](#3d-mode) (which covers the existing inline-RT shadow and reflection rays). "Tune it live, render it gorgeous" is the workflow.
- **Exploratory.** Spectral rendering (composite in spectra, not RGB, for physically-correct subtractive mixing, thin-film iridescence, diffraction); AI frame interpolation (render at a lower frame rate, ship smooth slow-motion via an on-device model); optical-flow self-warp (feed the sketch's own motion field, from the existing Vision optical flow, back into its history for flow and glitch looks); print color management (CMYK process separation through real ICC profiles, with ColorSync doing the transforms so there is no color engine to write, plus a soft-proof `Filter` that renders the canvas as a chosen output profile reproduces it, with an out-of-gamut highlight mode: the offset-print sibling of the spot-ink `printInks` separations). Each is a stretch, listed so the direction is on record.

## Authoring and editor tooling

Editing experiences the live-reload core makes possible, and the place Ollin states its line on AI.

- **The boundary, stated first because it is load-bearing and public.** The README already promises it ("It's a tool for making art ... Ollin is not a generative-art model"), and that extends to any AI *feature*: AI is a tool for *operating* the framework, not an author of sketches. Assisting at the controls is in scope; generating a sketch or its imagery from a prompt is out, because that is exactly the use the creative-coding community has good reason to distrust. Every AI-touching item here is scoped to that line, and where the line sits is @eaviles's call to make explicit if such a feature ships.
- **Visual node editor.** The effect graph (`compose` / `Filter` / `Combine`), the SDF combinators (`SDF` / `SDF3D`), and the `Visual` chains are already graphs expressed as code, so a node-graph surface in the live host that round-trips to Swift is a presentation of an existing structure, not a parallel runtime. It pairs with the typed `@Param` registry (a node's parameters are `@Param`s) and the OllinLiveCoding live host.
- **Deeper live-coding evaluation.** Refinements to the OllinLiveCoding host's evaluate loop: per-block evaluation (evaluate just the edited region on its own keystroke), sub-second turnaround on small edits (finer-grained or partially-interpreted evaluation over the compile-and-swap baseline), and MIDI/OSC mapping of the host's own performance surface (evaluate, code visibility, backdrop) beside the sketch-level `@Param` bindings that already reach MIDI and OSC.
- **Direct manipulation.** The live-reload core hot-swaps the sketch dylib already; the addition is bidirectional editing, where dragging a shape in the running window writes the new coordinates back into the source (the SwiftUI-preview model). It needs a source-location map from a draw call to its `.swift` site (the `#filePath` / `#line` capture the user-shader error path already uses is the same machinery) plus a careful write-back, so it is a larger piece that builds on smaller ones.
- **Record and replay.** The host already owns the input and `@Param` timeline (it syncs params across reloads); capturing that timeline plus the seed and replaying or scrubbing it backward is a rewind for a generative run, useful for finding a moment and for debugging. Deterministic, since `seed()` and the fixed-timestep clock already make a run reproducible.
- **AI at the controls.** Within the boundary above, an assistant that moves knobs toward a described look, wires and parameterizes a generator, or suggests a filter, all as operations on the typed `@Param` registry and the effect graph (the surfaces the node editor and variation tools also use), never emitting a sketch from scratch, on-device where the model allows (Foundation Models / Core ML). The auto-tuning idea (search the `@Param` and seed space toward a target image) is the same shape: a tool turning the knobs, the artist owning the sketch.
- **On-device ML as a material.** Apple-silicon models a sketch invokes deliberately, the way it calls `noise()`: semantic parameter control (map a phrase onto the `@Param` set via a text-embedding model), neural style transfer as a `Filter`, segmentation-driven generators. Text-to-image generation (on-device diffusion) is the one to weigh hardest against the boundary, since it sits closest to the contested use; if it ever ships it is an optional material the artist composes with, gated and clearly labelled, never the framework making the piece.

## Collaboration and multi-device

Apple-native, low-ceremony ways several machines share one piece.

- **Multipeer room canvas.** Multipeer Connectivity (`MCSession`) for zero-config local networking: several Macs and iPhones on one network forming a shared or split canvas with no server, ideal for room-scale installations. Sketches exchange typed messages under the same length-prefixed-tagged-payload discipline the [phone wire](#iphone-as-a-sensor-array) uses.
- **iPhone as a 6DoF wand.** The phone already streams CoreMotion attitude and the sensor link is in place, so exposing the phone as a spatial input device (its pose driving a cursor or tool in a Mac sketch) is a small addition over the shipped transport, not new plumbing.
- **SharePlay co-creation.** GroupActivities so two people tune one sketch together over a FaceTime call. The most speculative, listed for the direction, and Apple-unique.

## Installation mode

The needs of a piece running unattended for days in a gallery, which none of the desktop creative-coding frameworks treat as first-class: checkpoint and restore of generative state (a relaunch resumes rather than restarts), restart on failure (a watchdog), scheduled evolution (behavior by time of day), and graceful display sleep, wake, and resolution-change handling. Reproducibility (seeded `random` / `noise`, the deterministic clock) is the foundation a checkpoint rides on. Mostly a robustness-and-lifecycle track over the existing loop rather than new rendering, and the natural companion to the installation audience the framework keeps drawing.

The output side of the same audience is **projection mapping and multi-display**: a corner-pin / homography warp applied to the presented frame (a small matrix or mesh warp in the present pass, where tone-mapping already runs, so exports stay unwarped), edge blending with gamma-aware feathering for multi-projector spans, and fullscreen output across several displays (one canvas spanning them, or one sketch driving per-display regions). Warp calibration is host chrome in the OllinLive spirit (drag the corners live, persist per setup), not sketch code; Syphon already covers the case where a dedicated mapping app owns the wall.

## A third-party extension ecosystem

The contributed-addon ecosystems are a large part of why p5.js, openFrameworks (`ofxAddons`, the `ofx*` convention), and OPENRNDR (`orx-*`) have the reach they do, and it's the one incumbent advantage no Ollin *feature* closes. SwiftPM makes the mechanics free: a third-party Swift package that declares `Ollin` as a dependency and adds types or `SketchExtension`s is already a working extension, installed by URL like any Swift package. So the work is not plumbing, it is **convention and discoverability**:

- **A naming convention.** An `ollinx-*` prefix (the `ofx*` / `orx-*` lineage) so extensions are recognizable and searchable.
- **Documented, stable extension points.** Name what an extension hangs off: the `extend(...)` / `SketchExtension` lifecycle seam, custom `Filter` / `Generator` / `Sim` / `Shader` / `Combine` cases, the `FrameSource` protocol (a new capture source), `Material` / `Light`, and the satellite-package pattern the first-party `OllinAudio` / `OllinVision` packages already follow. These are the public surface a third party builds on, so they carry an implied stability promise (ties to the pre-1.0 deprecation discipline).
- **A starter template plus a curated list.** A `swift package` template for a new extension (the [project generator](#project-generator--sketch-scaffolding) can emit it), and a curated, awesome-list-style index so extensions are findable without a registry of our own.
- **Ollin's own front door.** The discovery story includes the framework itself: a DocC catalog generated from the source (hosted through the Swift Package Index's documentation support or GitHub Pages) and a Swift Package Index listing, the places Swift developers look first. The hand-written `Docs/` stays the curated reference; DocC is the API-completeness net under it.

Deciding the conventions now, while the surface is small, keeps the ecosystem coherent later. License hygiene carries over: a third-party extension is the author's own package under their own license, not bundled, so it sidesteps the vendoring rules entirely.

## Performance profiling and GPU debugging

Ollin's pitch is the GPU rendering ceiling, but a sketch author has no view into *their own* sketch's cost beyond the FPS and stats overlay (`FrameStats`: fps, CPU frame time, vertex and SDF draw counts). The gap is a real profiler. The renderer's performance model (recorded in `CLAUDE.md`) is that CPU tessellation is the first bottleneck, not the GPU, so the author needs to *see* where the frame goes:

- **A per-frame cost breakdown:** draw calls, vertices, and tessellation cost split by batch kind (SDF vs triangle vs fringe vs image vs glyph vs 3D), so a hot loop is attributable to a primitive.
- **An honest CPU-versus-GPU frame-time split.** The FPS overlay already learned that timing across the present semaphore measures vsync, not work, so the split times `performDraw()` apart from the GPU submit.
- **A Metal frame-capture hook** for the deep cases, handing the author off to Xcode's GPU frame debugger on the actual render.

It builds on the `FrameStats` and extension-seam machinery (the overlay is the first reader of the same data), so it's a richer reader plus more counters, not new infrastructure. The audience is anyone whose sketch dropped below 60, which on an immediate-mode GPU framework is a when, not an if.

## Accessibility and inclusive text

Inclusivity on the platform's native support, split by who it serves.

- **For authors (color and motion).** Colorblind-safe palette helpers (palettes that stay distinguishable under the common color-vision deficiencies, beside the existing ColorBrewer and harmony builders) and a color-vision **simulation** `Filter` (preview a sketch as it reads under deuteranopia, protanopia, tritanopia, the standard transform, a sibling of the existing stylize filters). Plus reduced-motion awareness: motion is the default, so honor the system Reduce Motion setting (a readable flag a sketch can check, and a sensible default for built-in animation).
- **For viewers (describable output).** The native counterpart to p5.js's `textOutput()` / `gridOutput()`: a way to attach an accessible text description to a sketch (and, where it can be derived, to the drawn structure), so a generative piece is not opaque to a screen reader. The hardest and most valuable part; scope it to author-provided descriptions first, derived ones later.
- **Robust complex-script text.** The text system rides Core Text, which shapes CJK, Arabic and other right-to-left scripts, Indic scripts, emoji, and combining marks correctly, but that path needs verifying and surfacing (bidi handling, cluster-aware `textToShapes`, font fallback for missing glyphs) so a global audience is served, not just Latin. Pairs with the existing text system.

## Examples folder

The `Examples/` set is maintained: small, runnable sketches that double as the "learn it in an afternoon" on-ramp and the compile-tested showroom (current status, the `OllinExamples` gallery, and CI are described in [`CLAUDE.md`](CLAUDE.md)). The design decisions worth keeping, because they guide *extending* the set:

- **Layout organized by topic.** Group by feature so they read as a learning path: basics, color, motion, patterns, text, and so on. Each example is one minimal, focused sketch that shows one idea well. The top `Examples/README.md` indexes only the categories (a table linking to each category folder); each category folder carries its own `README.md` listing its sketches, so the front page stays small as the set grows.
- **Per-example folder, generic `Sketch.swift`.** Each example lives in `Examples/<Category>/<Name>/` and its file is always named `Sketch.swift` rather than `<Name>.swift`, so the example's identity lives in the folder name, not a repeated filename. The per-example folder is also each sketch's home for its own assets (fonts, images, shaders sit alongside `Sketch.swift`), which is the reason not to flatten the layout.
- **The single-file `@main` mechanism.** SwiftPM allows only one entry point per executable target, so each example is its own small executable target (scripted as the set grows, rather than hand-maintained). Adding `static func main()` to `Sketch` on the core (`extension Sketch { static func main() { OllinApp.run(Self()) } }`, which needs a `required init`) makes a file self-contained, so an example is just `@main final class HelloCircle: Sketch { … }` with zero boilerplate. Built once on the core, so any single-file sketch flow (examples, scripting, embedding) can reuse it.
- **A feature isn't done until it has an example.** Each new primitive or capability ships with one. Examples are also a forcing function for API quality: if the example is awkward to write, the API needs work.
- **Snapshot coverage grows with the set.** Compile-testing proves an example builds; render-correctness snapshot tests (`Tests/OllinTests`) prove it still renders the same: a sketch is rendered headlessly through `OllinApp.image(of:)` and its pixels diffed against a committed reference. A new primitive earns a small, deterministic fixture and a recorded reference, so the catalog stays regression-protected as it grows. The reference is GPU-specific (anti-aliasing differs across GPU families), so references are recorded on a developer's machine (`OLLIN_RECORD_SNAPSHOTS=1`) and the comparison stays a local gate, kept out of CI; keep new fixtures flat and pixel-friendly so the mean-difference tolerance has room. A peer Swift and Metal framework does per-primitive snapshot tests the same way (a frame hook gated behind `#if canImport(XCTest)`, using pointfree's swift-snapshot-testing), a reference if richer image diffing is wanted later.
- **Reuse the samples elsewhere.** Examples can seed the Swift Playgrounds `.swiftpm` starter and serve as starter templates for new sketches. Author once.
- **Recreations grow by artist, and double as a build-it-to-find-the-gap forcing function.** The `Examples/Recreations/` set (organized by artist, homage framing, per-sketch provenance; see its README and the sourcing rules in [`CLAUDE.md`](CLAUDE.md)) includes Vera Molnár, Bridget Riley, and Osamu Sato. Candidate additions, and what each would exercise:
  - **Clean homage tier (historical pioneers).** **Georg Nees**: *Schotter* (1968), a grid of squares sliding from order into rotational and positional disorder: the canonical first generative recreation and a near-trivial fit for the current 2D core, so the obvious next one. **Manfred Mohr** and **Frieder Nake**: early algorithmic line and geometry work in the same tier.
  - **Lineage and concept.** **Casey Reas**: *Process* / agent works, a nod to the Processing lineage Ollin borrows from. **Sol LeWitt**: the *Wall Drawings*, instructions executed deterministically, an homage that doubles as a showcase of seeded reproducibility.
  - **Inspired-by only (living/commercial: credit, never port source).** **Tyler Hobbs** (*Fidenza*, flow fields, which the GPU `Particles`/`CurlField` path already renders at scale), **Anders Hoff / inconvergent** (differential growth), and **Jared Tarbell** (*Substrate*, crack growth; Tarbell has historically shared source under permissive terms, so a *port* may be license-clean if verified per-sketch, unlike the others, which are inspiration-only). These pair with the [generative geometry](#generative-geometry) tier: Schotter ↔ the grid, Tarbell and Hoff ↔ substrate and differential growth, Hobbs ↔ flow fields. (Candidate list sourced from mining the `/algorithmic-art` skill; it names no artists itself, so these map its technique families to the canonical figures.)

## Developer experience: Swift-idiomatic ergonomics

A standing track, not a one-time task: keep mining Swift idioms to make the API read better than a literal p5 port would. "Feels like p5" is the shape (bare calls, terse positional args, motion by default), but Swift's type system lets the same call carry more meaning with no extra ceremony, and that's a differentiator worth pressing. The exemplar to extend: `canvasSize` is a `CanvasSize` enum (`.square(n)` / `.size(w, h)` plus named presets like `.uhd4K` / `.vertical1080`, with `.portrait` / `.landscape` to flip orientation, in `CanvasSize.swift`): it reads as English, is discoverable by dot-completion, carries integer pixels as it should, and beats a bare `createCanvas(3840, 2160)` on both clarity and correctness. More of that. Candidates, in rough order:

- **Keep the presets pattern growing.** The orientation-flip trick (`.portrait` / `.landscape` as computed properties on a value type) generalizes: look for other places a bare tuple or magic number could become a named, dot-completable value with helpers, such as angle units (`.degrees(45)` / `.turns(0.25)` beside raw radians).
- **More idiom candidates.** Trailing-closure scoping beyond `withState { }` (already the model, as is the `drawShape { p in … }` path builder); `ExpressibleByArrayLiteral` / `ExpressibleByIntegerLiteral` conformances where they read naturally (a color from a literal, say); `@dynamicMemberLookup` only where it genuinely clarifies. The bar: an idiom earns its place when it makes the call clearer, not just shorter, and never at the cost of the bare-call feel or the typed-core split.
- **`@Param` disclosure groups.** The inspector's parameter group cards are flat; a sketch with many knobs wants an advanced tier folded behind a disclosure row (collapsed by default, remembered per sketch), so the everyday knobs stay one glance. Rides the existing group metadata; the per-param keyframe affordance belongs to the record-and-replay direction below.
- **More `@Param` value kinds.** Two catalog types still sit outside the menu tier because `ParamChoices` needs `Equatable` to find the current selection: `Easing` (a closure wrapper with no equality; joining would take a named-curve identity, say a case-backed wrapper over the closure) and the `Material` finishes (parameterized builders, so a curated subset would have to freeze representative values). A `Palette`/`Ramp` knob is a different shape entirely, a swatch-strip row rather than a menu. Each rides the existing `ParamValue`/`ParamControl` seam when it comes.

## Project generator / sketch scaffolding

An openFrameworks-style project generator: the on-ramp that turns "I want to start a sketch" into a ready-to-run folder, instead of hand-copying boilerplate. oF ships its `projectGenerator`; the Ollin version asks a few questions and emits a tailored starting point. It's the generative sibling of the maintained [examples](#examples-folder) set and the `.swiftpm` starter: examples are read-only showroom pieces; the generator produces a new, editable sketch.

- **What it asks.** Which capabilities the sketch will use, so the scaffold pre-wires only what's needed and stays minimal otherwise: images, shaders, text, parameters (`@Param` knobs), export, a starting `canvasSize` preset, and orientation. Each "yes" adds the import, a commented stub, and any per-sketch asset folder (fonts, images, shaders beside `Sketch.swift`).
- **What it emits.** A folder with a single-file `@main` `Sketch.swift` (the zero-boilerplate `Sketch.main()` form already on the core) plus, as chosen, an assets dir, a `Shaders.metal` stub, a `@Param` block, and a README. The single-executable-target mechanism is the same one the examples set already scripts; build the target-stanza generation once and share it.
- **Form factor.** Start as a CLI (`swift run OllinNew <name>` with flags or an interactive prompt): cheapest, scriptable, and reuses the runtime targets' patterns. A GUI in the style of oF's projectGenerator is a later nicety; the SwiftUI hosts (`OllinExamples`/`OllinLive`) are a reference if it's wanted. Ties to the `.swiftpm` starter, since one generated form is a Playgrounds App Project.
- **A scene-to-sketch variant.** Beyond a blank scaffold, the generator could emit a sketch *from a 3D scene file* (glTF/USD): the authored camera as a `camera(...)` / `perspective(...)` call, each node as a `withState { translate/rotate/scale; drawMesh(...) }` block, lights as `directionalLight(...)` and friends. This is the one-way, lossy companion to the runtime `loadScene` import (`Docs/3D/Scenes.md`): `loadScene` keeps the file as a live, re-loadable asset, while this hands over editable source the sketch then owns. Same "design tool → code" loop, different end state, so offer both.
- **A Shadertoy-to-sketch variant.** The same import shape, for a fragment shader: paste a Shadertoy URL (or its GLSL source) and emit a ready-to-run sketch wired to the user-supplied shader path, the shader running through the effect graph as a `generate(.shader(...))` (or a `.metal` resource beside `Sketch.swift`). The on-ramp is huge (a vast public corpus of fragment shaders), so it's a strong teaching lever, but the load-bearing work is honest GLSL-to-MSL translation: rename the `mainImage(out fragColor, in fragCoord)` contract to Ollin's `shade(uv, info)`, map the `iTime`/`iResolution`/`iMouse`/`iFrame` uniforms onto `ShaderInfo`, flip the bottom-left `fragCoord` to top-left `uv`, translate `vec`/`mix`/`fract`/`mod`/texture-sampling spellings to MSL, and surface what couldn't be auto-translated (multi-buffer passes, channel inputs, GLSL-only intrinsics) as commented TODOs rather than silently dropping them. License hygiene matters too: a fetched shader carries its author's terms (much of Shadertoy is CC-BY-NC or all-rights-reserved), so the emitter records provenance in the file header and leans on it being the *user's own* paste, never a bundled corpus.
- **Why it matters.** It's the same "learn it in an afternoon" lever as the examples and the live host: it removes the blank-page tax, and the questions double as a teaching tour of what Ollin can do.
