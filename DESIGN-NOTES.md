# Ollin design notes

The engineering design intent behind the planned work in [`ROADMAP.md`](ROADMAP.md). The roadmap is the short version (what's planned and how to help); this is the long version (how each piece would be built, the specific APIs involved, and why). A couple of shipped items stay only where their design rationale still guides future maintenance or evolution (extending the examples set, the Swift-idiom track); anything fully done and self-contained lives in its own doc or `CLAUDE.md`, not here.

These notes assume Ollin's two ground rules: it targets Apple platforms only (no cross-platform abstractions), and the bare p5-style API is sugar over a public, typed core, so a feature is built on the core first and given the bare call second. Geometry-emitting calls take a `draw` verb prefix (`drawCircle`, `drawRect`, and so on).

## Swift Playgrounds and iOS

The design home for the leg that runs a sketch on the phone and the tablet. The canvas is one view on either window system and `Apps/OllinSketchApp` is the reference project for wrapping a sketch as an iOS app; these notes carry what's ahead: the Swift Playgrounds on-ramp (the closest Swift gets to the p5.js "open the editor and type, see it move" onboarding, on-brand for the "learn it in an afternoon" goal), the tethered edit loop, and the smaller device affordances. The roadmap section is [The sketch on a phone, and Swift Playgrounds](ROADMAP.md#the-sketch-on-a-phone-and-swift-playgrounds).

- **Playgrounds questions, in dependency order.** An App Project (`.swiftpm`) is a Swift package whose manifest declares an `iOSApplication` product through `AppleProductTypes`, built by the Playgrounds app's own bundled toolchain, not the Mac's installed one. So: (1) confirm that toolchain builds the framework's platform floor (`.iOS("26.0")`, current Swift) before scaffolding anything; if it lags, that is the gate and everything else waits on an app update, not on work here. (2) The dependency arrives by git URL, so the tablet waits on the repository being public; an App Project's manifest is editable text, so verify on the Mac Playgrounds app whether a local `path:` dependency resolves, which would make the desk the verification bench in the meantime. (3) It runs on real GPUs, the Mac's or the tablet's, so the renderer's device tier applies and the simulator wall is irrelevant here; don't chase the simulator to test Playgrounds. Prefer the Swift Playgrounds app's App Projects over the semi-deprecated Xcode Playgrounds throughout.
- **The starter is a generator kind, not a hand-kept sample.** `ollin new` writes packages, and an App Project is one, so the Playgrounds starter is a `ProjectKind` beside the others rather than a checked-in sample that rots: the manifest with the `iOSApplication` product, a host file in the reference app's shape (a `SketchView` in a `WindowGroup`, `SwiftUI.Scene` spelled out since the framework has a `Scene` of its own, safe areas ignored), and one small touch-driven sketch, seedable from the examples the way `--from` already seeds. Unlike the gated `ios-app` kind, no Xcode project and no signing team stands in the way, so this kind can be `available` from the start.
- **Keep shaders Playgrounds-safe.** Swift Playgrounds' support for SwiftPM build-tool plugins is unreliable, so don't go plugin-only for shaders. Runtime source compilation stays a first-class loader, and it is also what makes a shader edit instant on a device.
- **Scope inside the sandbox.** Drawing, touch, the parameters, and the shader compile are the Playgrounds surface. The export tier writes files where the sandbox has opinions, so it stays desk work until someone asks; nothing about drawing needs it.
- **Beyond the cable: the sketch on a phone that is not here.** The installed loop needs pairing, which reaches a phone on the cable or the same network and never one across the internet, since an install goes through `devicectl`. The way to a phone anywhere is the one thing a phone can always do: show a picture and send its touches. The Mac runs the sketch under its own hot reload and streams the frames (HEVC through VideoToolbox from an IOSurface-backed texture, over the usbmux tunnel or any network), with touch, pressure, and motion flowing back as the sketch's input, the way the phone's sensors already reach a Mac sketch through `OllinPhone`. It answers "does it look and feel right on the phone" at once and from anywhere, and not "does it hold 120 fps on the phone's GPU", which the installed loop answers; the two are complements. The `frameRendered` seam is the hook for the encoder, and its CPU readback is the part a streaming tier replaces first.
- **The tablet keyboard.** UIKit press events (`pressesBegan`/`pressesEnded`) feed the same key path the desk view feeds, so `keyIsPressed` and the key callbacks work with a hardware keyboard on a tablet.
- **Verification:** iOS builds verify on a Mac with `xcodebuild -destination 'generic/platform=iOS'`; anything hands-on needs the device.

## Color additions deliberately kept out

Rationale that still gates future color work:

- **Other color spaces stay out.** Classic Lab/LCH (the 1976 space OKLab was built to fix; interpolating through it bends blues toward purple), CIECAM16/JCh (a full appearance model that needs viewing-condition parameters; OKLab was fitted to give most of that benefit without the machinery), and DIN99/DLCH (an industrial color-difference standard). Any of them can arrive later as a plain conversion if matching an external spec calls for it.
- **Further curated palette collections stay license-gated.** Collections scraped from ColourLovers and similar sites are not license-clean and stay out; anything added must carry a permissive license the way the ColorBrewer data does.

## Layered effects and compositing

OPENRNDR-style effects that compose in layers: draw into off-screen layers, run filters over them, composite with blend modes. The substrate (`renderTarget` / `withTarget` / `filtered` / `combined` / `postProcess` / `generate` / `feedback` and the `compose { }` DSL) is inventoried in `CAPABILITIES.md`; what belongs here is growing the catalog on top of it. The reference menus guide what else to add and how to shape it: AsyncGraphics (its `Graphic` is an `MTLTexture`, effects are functions returning new graphics, plus a blend/stack model; borrow the compositing architecture, not its async call shape), SwiftUIShaders (MIT, a menu of forty-odd post-process effects such as holographic, kaleidoscope, datamosh, and thermal, to mine and reimplement), and ofxFX (MIT, Patricio Gonzalez Vivo: composers, the bokeh/ripple/flow passes still worth taking). More two-input ops (layer-blend variants, chroma keying, wipes and other transitions) slot in as further `Combine` cases. Same stance throughout: study and reimplement, credited in `ATTRIBUTION.md`.

## 3D mode

2D stays the default and most sketches stay 2D, but 3D is a mode in its own right: a sketch opts in by setting a camera and, on the same Metal core, draws depth-tested point clouds and lit solid primitives, with richer shadows and materials as the mode grows. The iPhone point cloud renders through it, and visionOS and AR build on it. openFrameworks and OPENRNDR set the capability bar here, so the target is known. (The foundation, from the camera, depth buffer, and transform stack through point clouds, meshes, lights, materials, and cast shadows, is inventoried in `CAPABILITIES.md`; the notes below build on it.)

- **The further scene-import legs.** Over the structure-preserving import and animation playback a loaded `Scene` gives (see `Docs/3D/Scenes.md`): vendor `EXT_`/app-specific glTF extensions beyond the ratified `KHR_` set.
- **Material-from-file refinements.** A merged `loadMesh` model wears its first base-color material (glTF/USD/OBJ-MTL). The UV-origin convention for a Model I/O `imageFromTexture` result is unverified and may need a v-flip. A material carries **one** wrap mode for its whole map set, read from the file's first map; a format that gives each map its own sampler (glTF does) would need a wrap per slot to reproduce exactly, which no exporter seen so far asks for.
- **Many dynamic lights: Forward+ or tile-shading, not classic deferred.** Lighting is forward today: one `OllinLighting` uniform, `OLLIN_MAX_LIGHTS` bounded at 8, every mesh shaded against the same small set, which covers the common low-light-count case. The technique that exists to scale past it is deferred shading (render geometry into a G-buffer, then light in screen space so cost tracks pixels, not geometry×lights), but the textbook multi-pass G-buffer is the wrong fit here: it round-trips the G-buffer through DRAM, breaks the **draw-order compositing** the renderer rests on (2D SDF/triangle/image batches interleaved with 3D meshes under per-batch blend modes, a deferred resolve flattens that and drops transparency ordering), and fights the float-MSAA path (per-sample G-buffer resolve). On Apple-silicon TBDR the idiomatic answers keep forward's strengths: **tile-based forward (Forward+)** culls lights per screen tile and still shades forward (blending and the 2D/3D interleave survive), or Metal's on-chip **imageblock / tile-shading** deferred keeps the G-buffer in tile memory and never spills to DRAM. Either is an in-pass change, not a renderer rewrite, and it's the lever only if the 8-light ceiling actually bites.
- **Camera-relative lighting (an opt-in on the world-space default).** A `Light`'s direction is world-space, and that's the right default: the sun stays put as the camera orbits, the intuitive behavior the scene-graph 3D frameworks (openFrameworks' `ofLight`, OPENRNDR, the game engines) all default to. Those frameworks make a light *follow the camera* by parenting it to the camera node. Ollin is immediate-mode with no scene graph to parent into, so the switch has to be an explicit affordance: a `relativeTo: .world / .camera` flag on a light or preset, resolved each frame against the active `Camera3D`'s basis (cheap, since lights are already per-frame state). It earns its keep in two narrow cases: a viewer-following fill so the side facing away never goes fully black (a `headlight` helper is the sugar), and a three-point rig that holds its look under orbit rather than the world-fixed look the `.threePoint` preset has. Sun, sky, and product lighting all want world-space, so add the opt-in only when the headlight or a camera-locked rig actually wants it.
- **Per-mesh lighting (a refinement).** Lighting is per-frame today (one `OllinLighting` shades every mesh in a frame, like the camera), so a frame can't mix lit and unlit meshes or different light sets. Promoting it to per-batch state (break the mesh batch on a lighting change, like blend/depth, and carry the uniform per batch) matches immediate-mode semantics (the light state *at draw time* of each mesh); do it when a sketch actually needs two lighting setups in one frame; until then per-frame keeps the path simple.
- **Build order.** Softer shadows (and supporting more than one caster at once) are the rendering-heavy step. The tier-one material recipes are pure data over the existing light/material model with no renderer change, so they land cheaply (the way the lighting presets did): a `Material` surface beside `specular`/`specularSharpness`. Each step is usable on its own.
- **`Vector3` shares most of `Vector2`'s surface: document the common part once.** `length`/`normalized`/`dot`/`distance`/`lerp`/the arithmetic operators/`limited`/`projected`/`with`/the constants are the same idea in one more dimension, so the shared surface lives on a `Vector` protocol (or a SIMD-backed extension): one source of truth in code. A few members diverge and stay per-type, chiefly `cross`, which returns a **scalar** in 2D (the perp-dot, for sidedness/winding/steering) but a **`Vector3`** in 3D (a perpendicular vector, for normals/frames/torque); that scalar-vs-vector split is the headline and wants a prominent call-out. Also 2D-only or reshaped in 3D: `angle` (one direction angle), `perpendicular` (unique only in 2D), the signed `angle(to:)` (3D is unsigned without a reference axis), in-plane `rotated(by:)` (3D needs `rotated(by:axis:)`), and the polar `init(angle:length:)` (3D is spherical). **Docs mirror the code:** one shared "vector basics" section (the schoolbook diagrams are 2D but teach the general idea), then a compact "what's specific" section per type, instead of two near-duplicate pages that drift. The practical-use notes split on the same seam: `dot`/`length`/`lerp` uses are dimension-agnostic (shared), while `cross`/`perpendicular`/signed-`angle` uses stay 2D-specific.
- **visionOS is a different render loop.** Immersive rendering doesn't use `MTKView`/`SketchRunner.draw(in:)`; it uses CompositorServices (`LayerRenderer`) driven by a manual render thread, plus ARKit world tracking. Keep the per-frame loop behind a seam that either an `MTKViewDelegate` or a visionOS layer renderer can drive, rather than assuming `MTKView` everywhere.
- **Reference.** swifty-creatives is the concrete study: it ships both a normal `MTKView` renderer and a visionOS `RendererBase` with a manual `renderLoop()` over `LayerRenderer`, and it's 3D-first (camera, depth, box and 3D text). Borrow the structure (camera plus depth pipeline plus dual render loop) and write our own.
- **Ray-traced reflection refinements.** The **subsurface diffusion** behind `Material.scattering` does not reach a reflection: its blur runs over the primary view's own buffer, and the transmittance half needs a caster's depth the traced direct light never reads, so a skin or marble body arrives in a mirror with its shading unsoftened. That is bigger than the compact per-geometry finish record the other finishes ride, which is what makes it the one left.
- **Richer 3D physics: the solver's own remaining gaps.** The one thing still ahead is **soft-body reach**, and it is upstream's rather than Ollin's: self-collision and cloth-against-cloth are gaps in the solver, so a folded sheet passes through its own layers, and tearing needs a shared vertex split and a rebuilt constraint set mid-simulation, which it cannot do at all. Both stay out until the library grows them. The solver's **volume constraints** (tetrahedra held at their rest volume) stay out for a different reason, a measured one rather than a missing one: built and probed against the shipped `pressure`, they tie on holding a weight, tie on coming back from a dent, and lose on coming back from a hard squash, because their residual is formed from an *unsigned* volume and so reads an inverted tetrahedron as correct, where a gas law's push grows without bound as the space shrinks. The numbers and the two things that would reopen it (a vertex-follows-tetrahedron binding, or a signed volume constraint) are in [`ARCHITECTURE.md`](ARCHITECTURE.md). The solver's neighboring **hair module** stays out for four measured reasons. It accepts no force, so the only way to move a strand is to move the head, where Ollin's cloth and rope examples are driven by `applyForce`. It collides only with `ConvexHullShape`, and Ollin's figures are meshes and capsules. It requires an authored groom and a skinned scalp, where a sketch generates its own geometry. And the rod family already exposed carries 20,000 simulated strands in a 60 fps frame against its 2,500, so the Metal backend it needs (49 shaders cross-compiled and packaged, Objective-C++ admitted into the C bridge's target, a new draw path for a foreign compute buffer) would buy a strand count `Rope3D` already reaches. The measurements and the reopening bar are in [`ARCHITECTURE.md`](ARCHITECTURE.md); if hair is wanted before then, build it as a **multi-strand `Rope3D`** (one soft body holding many rod chains) rather than from that module. When they arrive, the shipped rules still apply: land it as *more capability on the existing surface* (a parameter on `addSoftBody`, a call on `SoftBody3D`), never a parallel system; keep the C bridge flat-POD `extern "C"` with `JPH` never reaching Swift; keep the no-pixel-snapshot policy (determinism is per-binary, so behavioral tests pin each slice) and `unitsPerMeter` as the one scale bridge; and ship an example, tests, a `Docs/Simulation/Physics3D.md` section, and Guide Ch 21 growth together.
- **Don't 3D-tax the 2D path.** Most sketches stay 2D, so don't make every draw call pay for a depth buffer or perspective divide. 3D is a mode you opt into, not a cost the 2D core carries.
- **Caveat:** the 3D mode itself builds and verifies on a Mac; visionOS needs the visionOS SDK plus a simulator or device.

## Material and scene explorers

The exploring surface is the material explorer example (`Examples/3D/Materials/Explorer`). It puts the curated `Material` library on a preset menu and every finish scalar on a parameter. The stage around the surface switches too: lighting preset, backdrop, fog, shadows, and the preview solid. A caption says when the parameters have left the chosen preset. The rules for anything built on it:

- **A material is source, never a file format.** No JSON and no `.ollinmaterial`: the scene-import rule ("structure becomes source, geometry stays in the file") decides it, since a material is all structure. Live iteration is already `@Param` plus hot reload. Interchange, if ever wanted, means the standard models the loaders already speak (glTF materials, UsdShade), never an invented schema. A preset that bundles surface color and a procedural pattern with the finish (a "marbled" *look*) stays a three-line snippet for the same reason. Only if that want keeps recurring does a value above `Material` earn its own design pass.
- **Reuse before generalizing.** The stage block (lighting, backdrop, fog, shadows) is written per explorer until a third customer proves the shared helper.

## Photorealistic 3D

The realism tier that builds on the physically-based core (PBR metallic-roughness, split-sum IBL from HDRI or the Hosek-Wilkie sky, ray-traced shadows and reflections, SSAO, SSR, raymarched SDF fields) toward the look of a curated product render or film still. Every item is opt-in so 2D and stylized 3D stay untaxed, every one is Metal-native (no engine vendored), and each is implemented from the published technique and credited in `ATTRIBUTION.md`'s Techniques. This is the "anything Metal offers that enriches 3D" tier, after the foundational [3D mode](#3d-mode) buildout: as a new realism technique finds a good fit, it rides the textured path's twin pipelines (or a gated branch of the surface-mapped fragment, which may branch freely) so non-using materials stay byte-identical.

All Apple-silicon Metal, the realism direction's "build Ollin APIs for anything Metal offers that enriches 3D."


## AR mode and templates (the Meta Spark gap)

Ollin aims to support AR sketches and offer a template-driven AR framework, filling the gap left when Meta Spark was discontinued (January 2025). Apple-only: ARKit plus RealityKit and Metal on iOS and iPadOS, and the visionOS immersive path.

- **It's a mode layered on the phone and 3D/visionOS work, not a separate engine.** AR builds on the phone leg (see [Swift Playgrounds and iOS](#swift-playgrounds-and-ios)) and the 3D camera and depth pipeline (see [3D mode](#3d-mode)).
- **The Spark lesson is templates.** Spark's reach came from ready-made effect templates (face filters, world effects, plane and image tracking) people could start from. The Ollin version: AR-example sketches plus starter templates wired to ARKit anchors (face, world, image tracking), so an AR sketch is "fill in the `draw()`, the tracking is handed to you", the same template-as-on-ramp idea as the examples and `.swiftpm` starters.
- **Caveat:** AR needs ARKit on a device to verify (the simulator has no AR camera).

## iPhone as a sensor array

A Mac has no depth camera, no inertial sensors, and no spare Neural Engine for live perception. A tethered iPhone has all three, so the idea is to let it act as a sensor and on-device ML co-processor for a sketch that still renders on the Mac. The phone captures and perceives, streams the results over the wire, and the sketch reads them in `draw()` as typed values. The Mac keeps the Metal rendering ceiling; the phone fills the input gap desktop hardware leaves.

The starting want was live RGBD point clouds, the kind an Intel RealSense fed openFrameworks before its Mac drivers were dropped. An iPhone with LiDAR is the same world-facing depth-and-color sensor, except the driver is ARKit and Apple maintains it. Both the *recorded* path and the *live USB* path exist (`OllinRecord3D` reads Record3D `.r3d` clips and its live USB stream; see [`Docs/3D/Record3D.md`](Docs/3D/Record3D.md)): a depth map plus intrinsics unprojects, through the [3D mode](#3d-mode) point-cloud path, into one splat per depth sample (around 49k for LiDAR's 256×192 map, ~300k for TrueDepth's 640×480). The renderer, the unprojection, and the live wire need no new work; what's ahead is *more sensors over that wire*.

**One channel, many typed payloads.** Depth is only the first thing the phone can send. Because both ends are ours and both are Swift, the wire skips the packed-image trick cross-language tools reach for: it is a length-prefixed binary stream of tagged messages, each a typed payload the sketch reads through the same transport-agnostic `FrameSource` abstraction used for the point cloud. The phone app is a configurable sensor hub, so adding a sensor later is a new payload case rather than a new pipeline. A header struct shared verbatim between app and framework carries intrinsics, pose, and a version byte; the rest is raw or LZFSE-compressed channel data.

The phone runs the expensive model on its Neural Engine and ships kilobytes of structured results, so each new sensor is nearly free on the wire:

- **Desktop-impossible.** TrueDepth face mesh and its 52 blendshape coefficients (the Animoji engine: jaw, blink, brow, and smile as 0-to-1 values), 3D body motion capture from a single camera, 6DoF device pose, and the inertial sensors (attitude, gravity, acceleration, rotation rate) a Mac doesn't have at all. The motion stream is the cheapest to build and the most physical: a few floats, no camera, no model.
- **Possible on a Mac, but the phone is the natural host.** Vision runs on macOS too (that's the [`OllinVision` catalog](Docs/Vision/Vision.md)), yet the phone holds the camera and the spare Neural Engine: subject segmentation, optical flow, scene and object classification, sound classification, and speech.

Most of those payloads are kilobytes. Only the per-pixel ones (segmentation matte, optical flow field) are heavy, and they arrive as textures, which is what the [layered effects](#layered-effects-and-compositing) graph already consumes, so a live person-matte becomes a `Filter` input rather than a separate feature. Everything here is Apple-native (ARKit, Vision, Core Motion, Core Location, SoundAnalysis, Speech) with no third-party dependency, and it shares its prerequisites with the [phone leg](#swift-playgrounds-and-ios) and [AR work](#ar-mode-and-templates-the-meta-spark-gap).

The transport is the proven live **USB** path (the standard usbmuxd device tunnel): full-quality LZFSE float32 depth plus camera intrinsics and ARKit pose, RealSense-grade, no extra dependency. Ollin's own capture app speaks the same length-prefixed-tagged-payload wire, so the sensor catalog isn't capped by what one borrowed app exposes. Record3D's **WiFi** streaming stays deliberately *out*, correcting an earlier assumption that it would be the easy one: it's WebRTC (a heavy dependency, and the `record3d` library doesn't support it at all), gated behind a paid Extension Pack, and its depth is lossy hue-encoded with no pose: the worst option on every axis, and the reason USB is the only streaming mode supported. Device class gates the sensors (TrueDepth for face, Pro-tier LiDAR for rear depth and scene mesh, A12 and later for body tracking), and several heavy models at once will thermal-throttle, so running every sensor together is a practical limit, not an API one.

**Saying what to look for, from the sketch.** The phone recognizes a picture by holding a library of reference files in its own folder, because the wire is a one-way push (the app broadcasts, the Mac never writes back) and a scanned object file has to live on the phone in any case. The alternative is a second direction: the sketch declares a picture and the width it was printed at, the Mac sends it down the same tunnel, and the phone rebuilds its library from what arrived. That is the better fit for a project whose rule is that the `.swift` file is the whole artifact, and it is also the first time anything would travel up the cable, so it deserves its own decision rather than riding along with a payload.

**The clean-room stance carries forward to our own app.** Both the `.r3d` file reader and the live USB stream are read clean-room from their public structure, the same constraint our own capture app's wire still works under: the `record3d` library is LGPL-2.1, the same copyleft tier as p5.js, so it stays inspiration only (reimplement the wire protocol, never translating its source, exactly as the sourcing rules treat p5.js). Record3D is credited like the other product references, not vendored. New sensor payloads added over the wire follow the same rule.

## Generative geometry

A tier of classic generative-art algorithms that produce *vector geometry* (points, `Contour`s, `Shape`s) and hand off to the geometry that already exists (the triangulated fill, the stroked path, the shape booleans, hatching, SVG export). They're geometry, not rendering, so they live in the `Ollin` core beside the shape booleans and the `Path` builder rather than in a satellite: none needs a heavy framework, and the split `OllinPhysics` took was about keeping simulation opt-in, not about dependencies. All are driven by the existing seedable `random`/`noise` so a result is reproducible, and each ships with an example; several are the natural implementation behind a [recreation](#examples-folder).

The reproducibility note matters: every one of these is a pure function of `seed()` plus parameters, so the same seed always yields the same packing/growth. License stance is the usual one: implement each from the *published technique* (credited in `ATTRIBUTION.md`'s Techniques list). Origin note: these surfaced from mining the `/algorithmic-art` skill's implicit technique vocabulary against what Ollin already ships (Voronoi/Delaunay, the foundational primitive of the tier, is a pure-Swift Bowyer–Watson, no library vendored).

## Technique and algorithm helpers

This is the umbrella the [generative-geometry](#generative-geometry) tier is one wing of: a standing catalog of the creative-coding algorithm vocabulary, added as helpers over time the way the SDF-shape catalog, the `Filter` catalog, and the color family grew. The organizing rule is to route each technique to the seam it naturally belongs on rather than invent a parallel system:

- **Geometry emitters** produce points, `Contour`s, or `Shape`s and feed the existing draw, shape-boolean, hatching, and SVG paths, exactly like the generative-geometry builders. The most plotter-friendly and the cheapest to add.
- **Field techniques** that read per-pixel (a new noise basis, an interference field) land as a GPU `Generator` (a no-input `ollin_gen_*` fragment) or a user shader, reusing the layered-effects substrate rather than the CPU geometry path.
- **Simulations** (iterated function systems accumulated on the GPU) run on the compute and `SimField` paths already in place: persistent ping-pong buffers or textures stepped each frame, drawn through the instanced or image path.

The rest of the catalog follows the same shape: a canonical algorithm implemented from the published source, credited in `ATTRIBUTION.md`'s Techniques list, seeded for reproducibility, and shipped with an example, several of which pair naturally with a [recreation](#examples-folder) (an attractor plot, a flow field, a substrate).

The catalog is also a *Nature of Code* coverage map, so it reads as a familiar curriculum to anyone arriving from that world.

For any animated per-pixel `Generator`, three implementation notes hold (their map is fluid, enonforetsam/fluid, MIT, a single-file WebGL background studio read the LYGIA way: a catalog of which looks matter, implemented from the canonical sources rather than its code): spread a noise-family field's contrast around its midpoint so a palette reaches its end stops (fbm piles up near 0.5 and otherwise hides them); animate by small bounded sways at non-commensurate frequencies so the field churns in place instead of panning as a rigid sheet (which also keeps the time argument precision-safe over long sessions); and normalize field coordinates by the canvas's geometric mean so a portrait crop reveals more field rather than zooming in.

Origin note, the same as the generative-geometry tier: this catalog is the broader read of the `/algorithmic-art` skill's technique vocabulary against what Ollin already ships, and this section is the standing list of what's left. A second read against OPENRNDR's own extension set (orx) contributed the G-code output surface, the keyframing and expression tier, and the small sketch-level conveniences noted under developer experience.

## Expressive brushes and strokes

The fringe expander carries a half-width per path vertex, `StrokeProfile` shapes it by position along the path, a recorded `StrokeMark` drives it from the hand, and a `Brush` stamps a shape along the path instead of expanding it. The tier builds out from there:

- **Painterly simulation stays separate.** Watercolor-style marks built from layered, deformed translucent geometry are a [technique-catalog](#technique-and-algorithm-helpers) recipe over the shape and accumulation machinery, not a brush engine; keeping the two distinct keeps the stroke renderer lean.

## Sound, synthesis, and spatial audio

`OllinAudio` covers both directions: `AudioAnalyzer` (FFT, bands, beat detection) over `AudioInput` / `AudioPlayer` / `Tone` / `Soundtrack` on the listening side, and a polyphonic `Synth` (voices over anti-aliased oscillators, ADSR envelopes, a resonant state-variable filter, delay and reverb) on the playing side, with a clock-free composition tier deciding what it plays. Both sides are routing as a value now, so what is left is depth rather than shape: more of what a voice can be made of.

- **The render-thread rule holds.** Anything the audio callback touches is built non-isolated and allocated before the first note, and parameters reach it through the lock-free event ring rather than a lock. A new voice type inherits that constraint; it is not a per-feature decision.
- **Keep the renderer pure.** The samples are made by a renderer that knows nothing about the audio engine: events in, buffer out, no clock. That is what makes the sound testable at all (a test renders and measures) and what a sound-carrying export would be built on, so a feature that reaches for the engine from inside the renderer is going the wrong way.

## Live rigs: physical computing, lighting, and network video

The hardware-and-network interop tier, extending the app-to-app integrations (Syphon, OSC, MIDI, the virtual camera) to the physical rig around the machine. Same posture throughout: play in the existing rig, implement published protocols from the spec, vendor nothing incompatible.

- **NDI.** Network video send/receive between machines, the cross-machine sibling of Syphon. The SDK is a binary-only distribution under NDI's own license, which doesn't fit the source-vendored tier (Syphon, Box2D, Clipper2 all ship as permissively-licensed source); a satellite that links a user-installed NDI runtime may fit instead. The licensing review is the gate before any code, and its outcome decides send-only, both directions, or staying out.

All output paths are real-time side effects of `draw()`, so they follow the render-thread rule (non-isolated closures) and the background-producer handoff pattern the receivers already use.

## New input sources

Each conforms to the core `FrameSource` (so the vision trackers and effect graph consume it) or reads as a simple value in `draw()`.

- **Apple Pencil.** Tilt, azimuth, force, and hover, on the iOS leg where a Pencil exists. Force joins the `pressure` `Sketch` already reads rather than arriving as a second thing, so a sketch written against trackpad pressure carries over unchanged and tilt, azimuth, and hover are the additions; each reads as a plain value in `draw()` beside the mouse and keyboard.
- **Body and world data.** HealthKit (heart rate from a paired Apple Watch) for biofeedback, WeatherKit and Core Location for slow ambient input. Each needs its entitlement and consent prompt, the same "keep the easy things easy, make the prompt explicit" concern as screen capture. Niche but distinctive (native Apple-sensor-sourced live data) and impossible in a browser.

## New output surfaces

Ways a sketch leaves the window, beside the flat image / video / GIF / SVG / web-page exporters already in place.

- **Rumble on a game controller.** The motors in a pad are the same kind of output as the shipped haptics tier, reached through `GCDeviceHaptics` and its localities rather than through the trackpad performer, so the pattern layer carries over and only the destination changes. Adaptive triggers and the light bar sit beside it on the same hardware. All of it needs a pad on the desk, since a synthetic controller reports no haptics.
- **A desktop widget.** Wrap a sketch as a widget (WidgetKit, with its timeline-refresh limits), so output lives in the system rather than a window: a new kind on the project generator's kind axis (`Docs/Tools/ProjectGenerator.md`) plus whatever host class the format asks for. The widget needs real thought rather than wrapping: its timeline refresh is measured in minutes, so a piece there is a still that changes rather than a sketch that moves, and what a `draw()` means under that constraint is the design question. High delight-and-share value, and uniquely low-friction on Apple where the wrapper format is first-class.
- **The rest of the sketch on the web page.** The platform stance rules out a second renderer, so what crosses is an artifact: the recorded page (`Docs/Output/Web.md`), whose recorder writes down what the renderer received each frame and whose WebGL2 player replays it with the framework's own shaders carried to GLSL ES 3.00 by the shader lexer the GLSL import shares, the import's function table inverted. The core changes by that one recorder and no renderer seam, and every door below keeps it so. *The doors, in order, each with its gate:* (1) the weight budget: a page past its budget refused with the video pointer, and, since a drawing's strokes are where a page gets heavy (a segment is a few dozen vertices where the call was two points and a style), one option to measure against the budget: record the draw calls as points and styles and ship the fringe expander and the tessellator compiled to WebAssembly as a player part, the same source, pixel parity, a player component rather than the framework running; (2) the site's front page drawn from the inline form of `Examples/Web/BreathingRing`. *The effects that stay with video:* the passes that are a solve or a ladder on the Mac (the diffusion, the measured distance field, the summed-area table, the Fourier transform, the alpha-shape design filters, the seamless clone, the depth combines, the flat light) and the simulations with pipelines of their own (the fluid, the watercolor, the self-warp, the multi-scale Turing field); each could cross as a recorded sequence of fragment passes with the intermediate formats the page can hold, a door of its own if a sketch asks for it. *What goes to video:* lit meshes and the rest of the 3D path beyond the raymarched field (a 3D door is a recorded thought, not a plan: a scene export played by a third-party WebGL scene library such as Three.js, its lights and materials mapped onto that library's own, at look-alike rather than exact fidelity and marked so; @eaviles accepts the fidelity cost for the sake of getting 3D sketches out at all, and it stays apart from the exact 2D player), ray-traced reflections, global illumination, caustics, the path tracer, temporal upscaling, mesh fields, compute work such as the particles and the fluids, wide gamut and HDR output, and a sketch whose input is a picture every frame (the camera, a video); the exporter refuses those with the name of the first call rather than drawing a partial picture. *Target:* WebGL2 first, because reach is the point and an iPhone below iOS 26 has no WebGPU, GLSL ES shares Metal's C grammar, the picture is the same, and nothing here needs compute; a WGSL back end comes only when a pass needs compute or WebGPU reach passes WebGL2, sharing the page and the plumbing so it is a second shader target, not a second exporter. *Verification without eyes:* every translated unit compiles in headless Chrome (WebGL compiles synchronously, so a DOM dump reports it), the page played to a fixed frame diffs against the same frame from `OllinApp.image(of:frame:)` under the snapshot tolerance, and the inline fragment inside a bare page diffs against the standalone file. *Parked:* the sketch's own `draw()` compiled through Swift's WebAssembly SDK against a small browser host; it would add a second sketch surface to maintain, and the recorded page with the triangle door covers more sketches. *Boundaries to hold:* this is an export like SVG or video; the `.swift` sketch stays the artifact; the page is generated and never hand-edited and shows no source; there is no share command, no hosting, and no live editor; and no renderer seam enters the core. A browser build of the drawing core is declined, since it would put the Mac-only work at risk, and the bar for it stays where it was.

## Rendering and color frontier

Deeper use of the Metal core and Apple displays, every item opt-in so the 2D path stays untaxed.

- **Dolby Vision.** The static HDR10 metadata an extended sketch exports describes the whole file; Dolby Vision carries per-scene metadata instead, which a generative piece could drive from what it knows it just drew. It needs the licensed encoder path rather than AVFoundation's plain HDR writer, so it is a licensing question first and an API question second.

## Authoring and editor tooling

Editing experiences the live-reload core makes possible, and the place Ollin states its line on AI.

- **The boundary, stated first because it is load-bearing and public.** The README already promises it ("It's a tool for making art ... Ollin is not a generative-art model"), and that extends to any AI *feature*: AI is a tool for *operating* the framework, not an author of sketches. Assisting at the controls is in scope; generating a sketch or its imagery from a prompt is out, because that is exactly the use the creative-coding community has good reason to distrust. Every AI-touching item here is scoped to that line, and where the line sits is @eaviles's call to make explicit if such a feature ships.
- **Visual node editor.** The effect graph (`compose` / `Filter` / `Combine`), the SDF combinators (`SDF` / `SDF3D`), and the `Visual` chains are already graphs expressed as code, so a node-graph surface in the live host that round-trips to Swift is a presentation of an existing structure, not a parallel runtime. It pairs with the typed `@Param` registry (a node's parameters are `@Param`s) and the OllinLiveCoding live host.
- **Deeper live-coding evaluation.** Refinements to the OllinLiveCoding host's evaluate loop: per-block evaluation (evaluate just the edited region on its own keystroke), sub-second turnaround on small edits (finer-grained or partially-interpreted evaluation over the compile-and-swap baseline), and MIDI/OSC mapping of the host's own performance surface (evaluate, code visibility, backdrop) beside the sketch-level `@Param` bindings that already reach MIDI and OSC.
- **The drag on the performance stage.** The performance host's editor buffer is a second place the same edit could go (`EditorController.replaceBuffer` already carries the parameter write-back), and the letterboxed stage already maps the pointer, so what it waits on is deciding whether a drag on a stage that is also a performance surface is wanted at all.
- **AI at the controls.** Within the boundary above, an assistant that moves parameters toward a described look, wires and parameterizes a generator, or suggests a filter, all as operations on the typed `@Param` registry and the effect graph (the surfaces the node editor and variation tools also use), never emitting a sketch from scratch, on-device where the model allows (Foundation Models / Core ML). The auto-tuning idea (search the `@Param` and seed space toward a target image) is the same shape: a tool adjusting the parameters, the artist owning the sketch.
- **On-device ML as a material.** Apple-silicon models a sketch invokes deliberately, the way it calls `noise()`: semantic parameter control (map a phrase onto the `@Param` set via a text-embedding model), neural style transfer as a `Filter`, segmentation-driven generators. Text-to-image generation (on-device diffusion) is the one to weigh hardest against the boundary, since it sits closest to the contested use; if it ever ships it is an optional material the artist composes with, gated and clearly labeled, never the framework making the piece.

## Collaboration and multi-device

Apple-native, low-ceremony ways several machines share one piece.

- **SharePlay co-creation.** Not a feature but a transport: the room's session logic (membership, the shared clock, last-writer-wins parameters) is transport-independent behind `RoomTransport`, so the whole idea is a GroupActivities-backed transport plus the app entitlement. The constraints that shape it: the `com.apple.developer.group-session` entitlement applies to apps only (macOS 12+), so it reaches a sketch bundled as an app and never a terminal-launched one; the session context is system-owned (two Apple IDs on a live FaceTime call) and both Macs need the same app installed, so parameter, seed, and clock sync work while co-editing the code cannot (an edit is a rebuild and a redistribution); `GroupSessionMessenger` is a small-payload channel (reliable and best-effort modes), which fits the room's wire and nothing heavier; and a proof needs two Macs, two Apple IDs, and a real call, so no CI holds it. One check to run before any code: whether the entitlement rides Developer ID signing outside the App Store. Gated on a public repository, a verified real-signing run for the app kind, and demand.

## Opening the repository

Everything a private repository never had to answer for arrives at once when it opens. This section covers how Ollin presents itself to somebody who has not seen it before, which is a different question from what it can do. The observations below came from reading the public face of vgpu (credited under Directions ahead in [`ATTRIBUTION.md`](ATTRIBUTION.md)) against ours, so the sizes and ratios are measured rather than guessed.

- **The README does three jobs, and only one of them has to stay there.** It pitches the project, catalogs the surface, and states positions (Apple-only, the AI posture, licensing). That is 315 lines and about 6,200 words, which is long for the first thing a person reads, and the length is honest rather than padded, since on GitHub the README is the front door. The presentation pass named under Toward 1.0 is where this gets decided, and the split to decide it on is which job each section does: the pitch has to stay above the fold, the catalog is what the website's reference index does better, and the position statements are load-bearing enough to keep but not to lead with. The opening as it stands (title, one line, a nav row, the facts list, the status callout) is the part that already works, so a pass should protect it rather than rewrite it.
- **The inward and outward tiers are wildly out of proportion, on purpose, and worth watching anyway.** `CAPABILITIES.md`, `ARCHITECTURE.md`, `CLAUDE.md`, and this file come to roughly 1.3 MB of contributor and agent-facing prose, against a 47 KB README. About 28 to 1. Each of those files earns its size (`CAPABILITIES.md` exists because `CLAUDE.md` outgrew the context budget it has to fit in every turn), so this is not a cleanup task. It is a reminder for the release pass that the 40 KB is the part anybody outside will actually read, and that `ATTRIBUTION.md`, unusually thorough for a project this size, is one of the better arguments Ollin can make for itself.
- **The agent-facing question, stated so it can be decided rather than drifted into.** The conventions are settled enough to adopt in an afternoon (a machine-readable index of the reference, docs and examples served offline by the CLI, the same over a tool protocol). What is not settled is whether Ollin wants them, and the reason to decide deliberately is that the project has a public position on AI which this touches. The distinction that seems to hold: serving accurate reference to an assistant so a person writes their own sketch is the same act as serving it to a search engine, while anything that produces sketches is the thing the boundary refuses. The practical argument for is that an assistant working from guesses invents API and the person blames the framework. The argument against is that the gesture reads as endorsement whatever the README says. Both are real, so this stays a question with @eaviles's name on it.
- **One of the three conventions is separable from that question.** Of the three, docs and examples served offline by the CLI is the only one with a reader who has no assistant in it: somebody on a plane, or anybody who would rather stay in the terminal. It is also the layer the index and the tool protocol would both read, so building it first tests the shape while the question stays open, and a command that prints a documentation page states no position on AI. The two that do state one, the machine-readable index and the tool protocol, are the two that wait.

## A third-party extension ecosystem

The contributed-addon ecosystems are a large part of why p5.js, openFrameworks (`ofxAddons`, the `ofx*` convention), and OPENRNDR (`orx-*`) have the reach they do, and it's the one incumbent advantage no Ollin *feature* closes. SwiftPM makes the mechanics free: a third-party Swift package that declares `Ollin` as a dependency and adds types or `SketchExtension`s is already a working extension, installed by URL like any Swift package. So the work is not plumbing, it is **convention and discoverability**, and what remains is the discoverability half:

- **A curated list.** An awesome-list-style index so extensions are findable without a registry of our own. It needs published extensions to list, so it follows the repository going public rather than leading it.
- **Ollin's own front door.** A DocC catalog generated from the source (hosted through the Swift Package Index's documentation support or GitHub Pages) and a Swift Package Index listing. Both require a public repository. When the DocC leg lands, keep the plugin out of the default dependency graph (a conditional `dependencies` entry behind an environment check), since every generated project resolves what the framework declares.

Two facts about the surface constrain anything built on this tier, and both are easy to assume the other way round. `Drawer` is internal, not public, so an extension extends `Sketch` and the public value types rather than the renderer's recorder. `Filter` / `Generator` / `Sim` / `Combine` are structs with no public initializer, so the effect catalogs take no new cases and the way into the render graph is a `Shader` through the `.shader(_:)` factories. Opening either would be a deliberate API decision, not a small one. The current seams are cataloged in [`Docs/Tools/Extensions.md`](Docs/Tools/Extensions.md).

License hygiene carries over: a third-party extension is the author's own package under their own license, not bundled, so it sidesteps the vendoring rules entirely.

## Accessibility and inclusive text

Inclusivity on the platform's native support. What ships is in [`Docs/Helpers/Accessibility.md`](Docs/Helpers/Accessibility.md); one decision from it carries forward, which is that nothing is applied on a sketch's behalf, since only the sketch knows which of its movements, distinctions or shapes is load-bearing. One idea is on record as deliberately out, and the reasoning is what guides the next person who proposes it:

- **Descriptions Ollin could derive.** A sketch writes its own words today. The vector recorder holds one frame as typed commands (`SVGCommand`). Shape kinds, positions, sizes and colors are all there, so that is the seam a derived summary would be built on. It stays out for now: a list of what was drawn is not a description of what it means.

## Examples folder

The `Examples/` set is maintained: small, runnable sketches that double as the "learn it in an afternoon" on-ramp and the compile-tested showroom (current status, the `OllinExamples` gallery, and CI are described in [`CLAUDE.md`](CLAUDE.md)). The design decisions worth keeping, because they guide *extending* the set:

- **Layout organized by topic.** Group by feature so they read as a learning path: basics, color, motion, patterns, text, and so on. Each example is one minimal, focused sketch that shows one idea well. The top `Examples/README.md` indexes only the categories (a table linking to each category folder); each category folder carries its own `README.md` listing its sketches, so the front page stays small as the set grows.
- **Per-example folder, generic `Sketch.swift`.** Each example lives in `Examples/<Category>/<Name>/` and its file is always named `Sketch.swift` rather than `<Name>.swift`, so the example's identity lives in the folder name, not a repeated filename. The per-example folder is also each sketch's home for its own assets (fonts, images, shaders sit alongside `Sketch.swift`), which is the reason not to flatten the layout.
- **The single-file `@main` mechanism.** SwiftPM allows only one entry point per executable target, so each example is its own small executable target (scripted as the set grows, rather than hand-maintained). Adding `static func main()` to `Sketch` on the core (`extension Sketch { static func main() { OllinApp.run(Self()) } }`, which needs a `required init`) makes a file self-contained, so an example is just `@main final class HelloCircle: Sketch { … }` with zero boilerplate. Built once on the core, so any single-file sketch flow (examples, scripting, embedding) can reuse it.
- **A feature isn't done until it has an example.** Each new primitive or capability ships with one. Examples are also a forcing function for API quality: if the example is awkward to write, the API needs work.
- **Snapshot coverage grows with the set.** Compile-testing proves an example builds; render-correctness snapshot tests (`Tests/OllinTests`) prove it still renders the same: a sketch is rendered headlessly through `OllinApp.image(of:)` and its pixels diffed against a committed reference. A new primitive earns a small, deterministic fixture and a recorded reference, so the catalog stays regression-protected as it grows. The reference is GPU-specific (anti-aliasing differs across GPU families), so references are recorded on a developer's machine (`OLLIN_RECORD_SNAPSHOTS=1`) and the comparison stays a local gate, kept out of CI; keep new fixtures flat and pixel-friendly so the mean-difference tolerance has room. A peer Swift and Metal framework does per-primitive snapshot tests the same way (a frame hook gated behind `#if canImport(XCTest)`, using pointfree's swift-snapshot-testing), a reference if richer image diffing is wanted later.
- **Reuse the samples elsewhere.** Examples can seed the Swift Playgrounds `.swiftpm` starter and serve as starter templates for new sketches. Author once.
- **A candidate list read off a peer gallery.** The vgpu example gallery (MIT, Vercel Labs; credited under Directions ahead in [`ATTRIBUTION.md`](ATTRIBUTION.md)) was read the way the shader catalogs are read, for which pieces are worth having rather than for code, since it is WGSL against WebGPU and nothing in it transfers as source. Most of it maps onto capabilities Ollin already ships (a fluid solver, instanced draws in the hundreds of thousands, a recorded batch, an environment map lighting a scene, an SDF clip through a mesh, depth estimation and classification through Core ML, a hand-tracked canvas), so those are covered and want nothing new. One is worth building on what is already here, and it leans on the user-shader seam harder than any current example does: **gravitational lensing**, where a raymarcher bends starlight along null geodesics around an event horizon and an orbiting disk is beamed brighter on the side turning toward the camera. One more is the natural first reader of a shipped capability, a **light-painting scene** over the light a flat sketch works out for itself, and three wait on the tiers above: an **ocean surface** for the [2D transform](#technique-and-algorithm-helpers), a **glass object standing in a drawn scene** now that it has something to stand in, and **one scene shown through each anti-aliasing path at once** for the [post-process pass](#rendering-and-color-frontier), which teaches the four-way split better than prose does. Two of the gallery's pieces are its own and a sibling product's branding, so they stay out. The license permits redistribution, but a rewrite in Metal from the same published techniques is what will actually happen, so each one carries the per-example header naming the gallery entry as inspiration alongside the technique's canonical source, per the sourcing rules in [`CLAUDE.md`](CLAUDE.md).
- **Recreations grow by artist, and double as a build-it-to-find-the-gap forcing function.** The `Examples/Recreations/` set (organized by artist, homage framing, per-sketch provenance; see its README and the sourcing rules in [`CLAUDE.md`](CLAUDE.md)) includes Vera Molnár, Georg Nees, Bridget Riley, Osamu Sato, Nick Cave, Jared Tarbell, Manuel Felguérez, and Manfred Mohr. Candidate additions, and what each would exercise:
  - **Clean homage tier (historical pioneers).** **Frieder Nake**: early algorithmic line and geometry work, a near-trivial fit for the current 2D core.
  - **Lineage and concept.** **Casey Reas**: *Process* / agent works, a nod to the Processing lineage Ollin borrows from. **Sol LeWitt**: the *Wall Drawings*, instructions executed deterministically, an homage that doubles as a showcase of seeded reproducibility.
  - **Inspired-by only (living/commercial: credit, never port source).** **Tyler Hobbs** (*Fidenza*, flow fields, which the GPU `Particles`/`CurlField` path already renders at scale) and **Anders Hoff / inconvergent** (differential growth). These pair with the [generative geometry](#generative-geometry) tier: Hoff to differential growth, Hobbs to flow fields. (Candidate list sourced from mining the `/algorithmic-art` skill; it names no artists itself, so these map its technique families to the canonical figures.)

## Developer experience: Swift-idiomatic ergonomics

A standing track, not a one-time task: keep mining Swift idioms to make the API read better than a literal p5 port would. "Feels like p5" is the shape (bare calls, terse positional args, motion by default), but Swift's type system lets the same call carry more meaning with no extra ceremony, and that's a differentiator worth pressing. The exemplar to extend: `canvasSize` is a `CanvasSize` enum (`.square(n)` / `.size(w, h)` plus named presets like `.uhd4K` / `.vertical1080`, with `.portrait` / `.landscape` to flip orientation, in `CanvasSize.swift`): it reads as English, is discoverable by dot-completion, carries integer pixels as it should, and beats a bare `createCanvas(3840, 2160)` on both clarity and correctness. More of that. Candidates, in rough order:

- **Keep the presets pattern growing.** The orientation-flip trick (`.portrait` / `.landscape` as computed properties on a value type) generalizes: look for other places a bare tuple or magic number could become a named, dot-completable value with helpers.
- **More idiom candidates.** Trailing-closure scoping beyond `withState { }` (already the model, as is the `drawShape { p in … }` path builder); `ExpressibleByArrayLiteral` / `ExpressibleByIntegerLiteral` conformances where they read naturally (a color from a literal, say); `@dynamicMemberLookup` only where it genuinely clarifies. The bar: an idiom earns its place when it makes the call clearer, not just shorter, and never at the cost of the bare-call feel or the typed-core split.
