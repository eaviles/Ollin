# Ollin design notes

The engineering design intent behind the planned work in [`ROADMAP.md`](ROADMAP.md). The roadmap is the short version (what's planned and how to help); this is the long version (how each piece would be built, the specific APIs involved, and why). A couple of shipped items stay only where their design rationale still guides future maintenance or evolution (extending the examples set, the Swift-idiom track); anything fully done and self-contained lives in its own doc or `CLAUDE.md`, not here.

These notes assume Ollin's two ground rules: it targets Apple platforms only (no cross-platform abstractions), and the bare p5-style API is sugar over a public, typed core, so a feature is built on the core first and given the bare call second. Geometry-emitting calls take a `draw` verb prefix (`drawCircle`, `drawRect`, and so on).

## Swift Playgrounds and iOS (not started)

Worth pursuing. Swift Playgrounds app (Mac and iPad) App Projects (`.swiftpm`) are the closest Swift gets to the p5.js "open the editor and type, see it move" onboarding, and the same work unlocks iPad sketching and embedding in any SwiftUI app. On-brand for the "learn it in an afternoon" goal.

- **The architecture is already most of the way there.** `SketchView` is a SwiftUI-embeddable view, cleanly separated from the macOS-only `OllinApp.run` (the standalone `swift run Example-X` launcher, now a thin SwiftUI `App`, `OllinSketchApp`, hosting `SketchView`, with an AppKit delegate only for activation). Embedding in someone else's SwiftUI `App`, which is what a Playgrounds App Project needs, is exactly that seam.
- **The blocker is iOS support.** Playgrounds App Projects build iOS apps, but Ollin only declares `.macOS("26.0")`. To make it importable: add `.iOS(...)` to `Package.swift`; make `SketchView` conditional (`NSViewRepresentable` and AppKit vs `UIViewRepresentable` and UIKit via `#if canImport(AppKit)` / `#if canImport(UIKit)`); guard `OllinApp.run` behind `#if os(macOS)`. The Metal renderer (`Metal`/`MetalKit`/`simd`) is already portable. A working reference for this exact seam is swifty-creatives, which compiles for macOS, iOS, tvOS, and visionOS from one source using a `ViewRepresentable` typealias (`NSViewRepresentable`/`UIViewRepresentable`) with `#if os(...)`-guarded `makeNSView`/`makeUIView`.
- **Keep shaders Playgrounds-safe.** Swift Playgrounds' support for SwiftPM build-tool plugins is unreliable, so don't go plugin-only for shaders. Keep runtime source compilation as a first-class loader.
- **Onboarding nicety:** ship a ready-made `.swiftpm` starter (Ollin pre-wired plus a `HelloCircle`) so users don't hand-add the package URL.
- **Caveats:** the Playgrounds sandbox restricts file I/O (which matters for the export items, not for drawing); package-dependency UX is finicky; prefer the Swift Playgrounds app's App Projects over the semi-deprecated Xcode Playgrounds. iOS changes need `xcodebuild -destination` with the iOS SDK on a Mac to verify.

## Rendering precision (HDR/float pipeline) (not started)

A 16-bit float linear render target as the compositing substrate, with a final pass that tone-maps and encodes to the 8-bit screen drawable.

- **Why float.** A fixed 8-bit target bands on smooth gradients and clamps every value to [0, 1]. A `rgba16Float` linear intermediate removes both limits: the precision kills banding outright, and values above 1.0 survive, which is the prerequisite for bloom/glow and any HDR-style effect.
- **The shape.** Draw the frame into an off-screen `rgba16Float` color target, then a single fullscreen pass reads it, applies a tone-map, and writes the sRGB-encoded drawable. The existing pipelines render into the float target unchanged; only the final present pass is new.
- **Substrate for layered effects.** This is the same off-screen-target capability [layered effects and compositing](#layered-effects-and-compositing-not-started) needs — a texture a sketch draws into and samples — so build the float target first and let the effect graph compose over it.
- **Cost note.** MSAA tile memory grows fast at float precision (8 samples × 8 bytes per pixel of color), so the MSAA sample count is a real decision at this precision in a way it isn't at 8-bit.

## Supersampled render scale — the crispness dial (not started)

An opt-in render-resolution multiplier (e.g. `renderScale: 2`) — render the frame at N× and downsample — as the explicit performance↔quality dial, off by default for the 60fps path.

- **Why this and not better shading.** The thin-mark issue (a diagonal 1px line reading faint/"beaded") is a *display* problem, fixed by the perceptual-coverage remap and the L2 footprint on the analytic AA path (see the linear-light bullet in [CLAUDE.md](CLAUDE.md)). What that *cannot* fix is the residual softness of a 1px diagonal versus a crisp axis-aligned one: a 1px line can't align to the pixel grid at any angle, so its ink spreads across the staircase. Measured directly — 4× SSAA barely beats the analytic single-sample path — so the shader is near its ceiling and the only remaining lever for that softness is *more pixels per mark*, i.e. resolution.
- **Where it pays off.** The live view already renders at the display's backing scale (MTKView's default drawable), so on a Retina Mac it's effectively ~2× already; raster `--export`/`image(of:)` is fixed at `canvasSize`. So the knob's first home is export (a gallery-grade still / sequence), with an optional above-Retina multiplier for the live view. It mostly sharpens the *tessellated* path (polygon/curve outlines, tessellated text) and fine dense detail; for 1px SDF lines the gain is small (the measurement above). For plotter line art the vector `--export-svg` is already resolution-independent and the better answer.
- **Related gap to close at the same time.** Region-shape *outlines* (rect/star/triangle stroke bands via `regionCoverage`) get the perceptual remap but lack the sub-pixel *area conservation* the capsule/disk have (`hwE = max(hw, ½·footprint)` + width scaling), so an outline thinner than ~1px thins/vanishes instead of fading by area. Giving the region stroke band the same area-conserving floor would make *every* outline honor 0→n, matching lines and dots.

## Layered effects and compositing (not started)

A planned direction: OPENRNDR-style effects that compose in layers. Draw into off-screen targets, run filters (blur, bloom, feedback, color grades) over them, and composite the results with blend modes. This is the natural home for post-processing, and it fits the extension seam (effects are after-draw passes) and user-supplied shaders (each effect is a fragment shader over a texture).

- **The plumbing is partly here.** The `--export` path already renders off-screen into a texture (MSAA, then resolve). A render target a sketch can draw into and then sample is the same capability surfaced as API, so it's the seam to build on, not a new substrate.
- **Shape to aim for.** A render-target/layer value type (a texture you draw into), a `Filter` notion (a fragment shader from one texture to another, with parameters), and composite-with-blend-mode. Blend mode wants to be a pipeline parameter in the `Hashable` pipeline descriptor, not a renderer subclass.
- **Swift and Metal reference.** AsyncGraphics is the concrete study here: its `Graphic` is an `MTLTexture`, effects are functions returning new graphics, and it ships blend modes plus a stack/layout layer model. The API paradigm (async, immutable) differs from Ollin's immediate-mode loop, so borrow the compositing/effects architecture, not the call shape. OPENRNDR's `Filter` / `compose {}` / `RenderTarget` is the conceptual model. SwiftUIShaders (MIT) is a second study, but for the effect *catalog* rather than the architecture: forty-odd post-process effects (holographic, kaleidoscope, datamosh, thermal, chromatic split, and so on) as a menu of what to offer. It rides SwiftUI's `.layerEffect`/`.colorEffect` over a rasterized view, a different mechanism than Ollin's renderer, so mine the effect ideas and reimplement them against our own off-screen-target pipeline. MIT permits more, but the stance stays study-and-reimplement, credited in the README's Influences.
- **Bigger than a primitive.** This touches the renderer (multiple render passes, target management) and the extension seam at once. Design it deliberately when the seam lands; don't bolt it on.

## Shader composition and live-coding (not started)

Two linked directions on the radar, both about combining and mixing shader-driven visuals fluently, and both distinct from `OllinLive`, which is dev-loop hot-reload, not a performance instrument.

- **A composable shader and effect-mixing API.** What's compelling about Hydra and OPENRNDR: chaining and blending sources and transforms so visuals combine with almost no ceremony (`osc().rotate().modulate(noise())`). This is the call-shape companion to [layered effects and compositing](#layered-effects-and-compositing-not-started): that work is the substrate (render targets, filters, blend modes); this is the fluent surface over it. Study how Hydra and ShaderPark make mixing so fluid and borrow the direction (Hydra is AGPL, so inspiration only; ShaderPark is MIT). The underlying shader functions are written from the published techniques. Keep it sugar over the typed core.
- **A performance live-coding environment.** A separate app from `OllinLive`: a performance instrument where you type expressions live, evaluate them on the fly, and project the output, rather than a file-watcher. The goal is to do natively what's today done by bridging Hydra and openFrameworks, with Hydra as the direct model. It likely builds on the live-reload host, the shader-composition API above, and the parameter-knob work. Apple-only. A working title for it is `OllinLiveCoding`.

## 3D mode and visionOS (eventual; 2D stays primary)

2D is the focus now and stays the default; Ollin is a 2D creative-coding framework first. A 3D mode is planned eventually, with visionOS support, so the back end is kept from foreclosing it.

- **What 3D needs.** A camera (perspective or ortho) feeding view and projection matrices; a depth buffer (`depth32Float[_stencil8]`) plus depth-stencil state in the pipeline; the transform stack generalized from 2D affine to `f4x4`; a `Vector3` and 3D primitives (box, sphere, mesh/`.obj`). The `Hashable` pipeline descriptor already anticipates this; it carries a depth axis, so a depth-tested pipeline is a new descriptor, not a new renderer.
- **`Vector3` shares most of `Vector2`'s surface — document the common part once.** `length`/`normalized`/`dot`/`distance`/`lerp`/the arithmetic operators/`limited`/`projected`/`with`/the constants are the same idea in one more dimension, so the shared surface lives on a `Vector` protocol (or a SIMD-backed extension): one source of truth in code. A few members diverge and stay per-type — chiefly `cross`, which returns a **scalar** in 2D (the perp-dot, for sidedness/winding/steering) but a **`Vector3`** in 3D (a perpendicular vector, for normals/frames/torque); that scalar-vs-vector split is the headline and wants a prominent call-out. Also 2D-only or reshaped in 3D: `angle` (one direction angle), `perpendicular` (unique only in 2D), the signed `angle(to:)` (3D is unsigned without a reference axis), in-plane `rotated(by:)` (3D needs `rotated(by:axis:)`), and the polar `init(angle:length:)` (3D is spherical). **Docs mirror the code:** one shared "vector basics" section (the schoolbook diagrams are 2D but teach the general idea), then a compact "what's specific" section per type, instead of two near-duplicate pages that drift. The practical-use notes split on the same seam — `dot`/`length`/`lerp` uses are dimension-agnostic (shared), while `cross`/`perpendicular`/signed-`angle` uses stay 2D-specific.
- **visionOS is a different render loop.** Immersive rendering doesn't use `MTKView`/`SketchRunner.draw(in:)`; it uses CompositorServices (`LayerRenderer`) driven by a manual render thread, plus ARKit world tracking. Keep the per-frame loop behind a seam that either an `MTKViewDelegate` or a visionOS layer renderer can drive, rather than assuming `MTKView` everywhere.
- **Reference.** swifty-creatives is the concrete study: it ships both a normal `MTKView` renderer and a visionOS `RendererBase` with a manual `renderLoop()` over `LayerRenderer`, and it's 3D-first (camera, depth, box and 3D text). Borrow the structure (camera plus depth pipeline plus dual render loop) and write our own.
- **Don't 3D-tax the 2D path.** Most sketches stay 2D, so don't make every draw call pay for a depth buffer or perspective divide. 3D is a mode you opt into, not a cost the 2D core carries.
- **Caveat:** visionOS needs the visionOS SDK plus a simulator or device to verify.

## AR mode and templates (eventual; the Meta Spark gap)

Ollin aims to support AR sketches and offer a template-driven AR framework, filling the gap left when Meta Spark was discontinued (January 2025). Apple-only: ARKit plus RealityKit and Metal on iOS and iPadOS, and the visionOS immersive path.

- **It's a mode layered on the iOS and 3D/visionOS work, not a separate engine.** AR needs the iOS target (see [Swift Playgrounds and iOS](#swift-playgrounds-and-ios-not-started)) and the 3D camera and depth pipeline (see [3D mode and visionOS](#3d-mode-and-visionos-eventual-2d-stays-primary)) in place first.
- **The Spark lesson is templates.** Spark's reach came from ready-made effect templates (face filters, world effects, plane and image tracking) people could start from. The Ollin version: AR-example sketches plus starter templates wired to ARKit anchors (face, world, image tracking), so an AR sketch is "fill in the `draw()`, the tracking is handed to you", the same template-as-on-ramp idea as the examples and `.swiftpm` starters.
- **Caveat:** AR needs ARKit on a device to verify (the simulator has no AR camera).

## Computer vision (in progress)

Image understanding as a first-class Mac capability, not something that requires the phone. Apple ships the whole computer-vision stack on macOS, hardware-accelerated on the M-series Neural Engine, so a sketch can grab the Mac's own webcam (or a Continuity Camera) and run real perception locally. Over the camera frame source and the composable-tracker spine, the capabilities still to add:

- **Vision** for hand and body pose (2D and 3D from a single camera), person and subject segmentation, optical flow, contour and rectangle detection, text recognition (OCR), barcodes, image classification, trajectory tracking, and saliency.
- **Core ML** to run any converted model, **Core Image** for filters and the legacy `CIDetector`, **vImage and Accelerate** for fast low-level pixel work, and **Create ML** for training custom models.
- **AVFoundation** for capture: the built-in camera, an external webcam, or a Continuity Camera iPhone used purely as a webcam.

The shape each tracker follows: a request run per frame (or throttled to a slower cadence) over the camera's frames, and the results exposed as typed values a sketch reads in `draw()`, such as hand joints, a segmentation matte as a texture, a flow field, or detected rectangles. It stays sugar over the typed core, and the heavier per-pixel results (mattes, flow fields) arrive as textures, which is what the [layered effects](#layered-effects-and-compositing-not-started) graph already consumes.

**The Mac and iPhone split, drawn explicitly.** The Mac does image understanding natively: anything that takes a 2D camera frame and infers from it runs on the Mac with no phone. What the Mac cannot do is depth and AR sensing; there is no LiDAR, no TrueDepth front sensor, and no ARKit world or anchor tracking on a Mac. Those need the iPhone, which is the [iPhone as a sensor array](#iphone-as-a-sensor-array-not-started) section. So computer vision is available two ways: standalone on the Mac for image understanding, and as the depth-and-AR superset over the phone link. The phone can run these same Vision and Core ML models on its own Neural Engine too, but the reason to reach for it is the sensors the Mac lacks, not the understanding the Mac already does. References: oF `ofxCv`.

## iPhone as a sensor array (not started)

A Mac has no depth camera, no inertial sensors, and no spare Neural Engine for live perception. A tethered iPhone has all three, so the idea is to let it act as a sensor and on-device ML co-processor for a sketch that still renders on the Mac. The phone captures and perceives, streams the results over the wire, and the sketch reads them in `draw()` as typed values. The Mac keeps the Metal rendering ceiling; the phone fills the input gap desktop hardware leaves.

The starting want was live RGBD point clouds, the kind an Intel RealSense fed openFrameworks before its Mac drivers were dropped. An iPhone with LiDAR is the same world-facing depth-and-color sensor, except the driver is ARKit and Apple maintains it. That point cloud is the first slice, and it doubles as a forcing function for [3D mode](#3d-mode-and-visionos-eventual-2d-stays-primary): it needs `Vector3`, a camera, and a depth buffer, and it exercises the planned instanced-draw path at one splat per depth sample (around 49k points for LiDAR's 256x192 depth map).

**One channel, many typed payloads.** Depth is only the first thing the phone can send. Because both ends are ours and both are Swift, the wire skips the packed-image trick cross-language tools reach for: it is a length-prefixed binary stream of tagged messages, each a typed payload the sketch reads through the same transport-agnostic `FrameSource` abstraction used for the point cloud. The phone app is a configurable sensor hub, so adding a sensor later is a new payload case rather than a new pipeline. A header struct shared verbatim between app and framework carries intrinsics, pose, and a version byte; the rest is raw or LZFSE-compressed channel data.

The phone runs the expensive model on its Neural Engine and ships kilobytes of structured results, so each new sensor is nearly free on the wire:

- **Desktop-impossible.** TrueDepth face mesh and its 52 blendshape coefficients (the Animoji engine: jaw, blink, brow, and smile as 0-to-1 values), 3D body motion capture from a single camera, LiDAR scene mesh with detected planes and real-room light estimation, 6DoF device pose, and the inertial sensors (attitude, gravity, acceleration, rotation rate) a Mac doesn't have at all. The motion stream is the cheapest to build and the most physical: a few floats, no camera, no model.
- **Possible on a Mac, but the phone is the natural host.** Vision runs on macOS too (that's the [computer vision](#computer-vision-not-started) section), yet the phone holds the camera and the spare Neural Engine: person and subject segmentation, hand pose, optical flow, saliency, live text, scene and object classification, sound classification, and speech.

Most of those payloads are kilobytes. Only the per-pixel ones (segmentation matte, optical flow field, scene mesh) are heavy, and they arrive as textures, which is what the [layered effects](#layered-effects-and-compositing-not-started) graph already consumes, so a live person-matte becomes a `Filter` input rather than a separate feature. Everything here is Apple-native (ARKit, Vision, Core Motion, Core Location, SoundAnalysis, Speech) with no third-party dependency, and it shares its prerequisites with the [iOS target](#swift-playgrounds-and-ios-not-started) and [AR work](#ar-mode-and-templates-eventual-the-meta-spark-gap).

A natural build order: a recorded RGBD file to a point cloud first (deterministic, no networking, proving the 3D math), then a live WiFi stream over `Network.framework`, then our own iPhone capture app so the chain is ours end to end. USB, for RealSense-grade tethered reliability, comes after WiFi, since a custom-app USB tunnel is more work to stand up. Device class gates the sensors (TrueDepth for face, Pro-tier LiDAR for rear depth and scene mesh, A12 and later for body tracking), and several heavy models at once will thermal-throttle, so running every sensor together is a practical limit, not an API one.

**Reusing an existing capture app.** Record3D is a shipping iOS app that already captures RGBD with ARKit and streams it over USB and WiFi, with a `record3d` Python library on the receiving end. A `FrameSource` that speaks its protocol, or reads its exported files, would give anyone who owns it a live cloud into Ollin before our own app exists, so it is worth supporting as an extra source behind the same abstraction. The catch is that the library is LGPL-2.1, the same copyleft tier as p5.js, so it stays inspiration only: we reimplement the wire protocol clean-room and write our own decoder, never translating its source, exactly as the sourcing rules treat p5.js. Credited like the other product references, not vendored.

## Examples folder (maintained ongoing)

The `Examples/` set is shipped and maintained — small, runnable sketches that double as the "learn it in an afternoon" on-ramp and the compile-tested showroom (current status, the `OllinExamples` gallery, and CI are described in [`CLAUDE.md`](CLAUDE.md)). The design decisions worth keeping, because they guide *extending* the set:

- **Layout organized by topic.** Group by feature so they read as a learning path (`hello`, `primitives`, `color`, `motion-and-time`, `transforms`, `shapes-contours`, `shaders`, `export`). Each example is one minimal, focused sketch that shows one idea well. The top `Examples/README.md` indexes only the categories (a table linking to each category folder); each category folder carries its own `README.md` listing its sketches, so the front page stays small as the set grows.
- **Per-example folder, generic `Sketch.swift`.** Each example lives in `Examples/<Category>/<Name>/` and its file is always named `Sketch.swift` rather than `<Name>.swift`, so the example's identity lives in the folder name, not a repeated filename. The per-example folder is also each sketch's home for its own assets (fonts, images, shaders sit alongside `Sketch.swift`), which is the reason not to flatten the layout.
- **The single-file `@main` mechanism.** SwiftPM allows only one entry point per executable target, so each example is its own small executable target (scripted as the set grows, rather than hand-maintained). Adding `static func main()` to `Sketch` on the core (`extension Sketch { static func main() { OllinApp.run(Self()) } }`, which needs a `required init`) makes a file self-contained, so an example is just `@main final class HelloCircle: Sketch { … }` with zero boilerplate. Built once on the core, so any single-file sketch flow (examples, scripting, embedding) can reuse it.
- **A feature isn't done until it has an example.** Each new primitive or capability ships with one. Examples are also a forcing function for API quality: if the example is awkward to write, the API needs work.
- **Snapshot coverage grows with the set.** Compile-testing proves an example builds; render-correctness snapshot tests (`Tests/OllinTests`) prove it still renders the same — a sketch is rendered headlessly through `OllinApp.image(of:)` and its pixels diffed against a committed reference. A new primitive earns a small, deterministic fixture and a recorded reference, so the catalog stays regression-protected as it grows. The reference is GPU-specific — anti-aliasing differs across GPU families — so references are recorded on a developer's machine (`OLLIN_RECORD_SNAPSHOTS=1`) and the comparison stays a local gate, kept out of CI; keep new fixtures flat and pixel-friendly so the mean-difference tolerance has room. A peer Swift and Metal framework does per-primitive snapshot tests the same way (a frame hook gated behind `#if canImport(XCTest)`, using pointfree's swift-snapshot-testing) — a reference if richer image diffing is wanted later.
- **Reuse the samples elsewhere.** Examples can seed the Swift Playgrounds `.swiftpm` starter and serve as starter templates for new sketches. Author once.

## Developer experience: Swift-idiomatic ergonomics (partly shipped)

A standing track, not a one-time task: keep mining Swift idioms to make the API read better than a literal p5 port would. "Feels like p5" is the shape (bare calls, terse positional args, motion by default), but Swift's type system lets the same call carry more meaning with no extra ceremony, and that's a differentiator worth pressing. The exemplar to extend: `canvasSize` is a `CanvasSize` enum (`.square(n)` / `.size(w, h)` plus named presets like `.uhd4K` / `.vertical1080`, with `.portrait` / `.landscape` to flip orientation, in `CanvasSize.swift`) — it reads as English, is discoverable by dot-completion, carries integer pixels as it should, and beats a bare `createCanvas(3840, 2160)` on both clarity and correctness. More of that. Candidates, in rough order:

- **Keep the presets pattern growing.** The orientation-flip trick (`.portrait` / `.landscape` as computed properties on a value type) generalizes: look for other places a bare tuple or magic number could become a named, dot-completable value with helpers, such as angle units (`.degrees(45)` / `.turns(0.25)` beside raw radians) or named blend modes when they land.
- **More idiom candidates.** Trailing-closure scoping beyond `withState { }` (already the model, and now the `drawShape { p in … }` path builder too); `ExpressibleByArrayLiteral` / `ExpressibleByIntegerLiteral` conformances where they read naturally (a color from a literal, say); `@dynamicMemberLookup` only where it genuinely clarifies. The bar: an idiom earns its place when it makes the call clearer, not just shorter, and never at the cost of the bare-call feel or the typed-core split.

## Project generator / sketch scaffolding (not started)

An openFrameworks-style project generator: the on-ramp that turns "I want to start a sketch" into a ready-to-run folder, instead of hand-copying boilerplate. oF ships its `projectGenerator`; the Ollin version asks a few questions and emits a tailored starting point. It's the generative sibling of the maintained [examples](#examples-folder-maintained-ongoing) set and the `.swiftpm` starter: examples are read-only showroom pieces; the generator produces a new, editable sketch.

- **What it asks.** Which capabilities the sketch will use, so the scaffold pre-wires only what's needed and stays minimal otherwise: images, shaders, text, parameters (`@Param` knobs), export, a starting `canvasSize` preset, and orientation. Each "yes" adds the import, a commented stub, and any per-sketch asset folder (fonts, images, shaders beside `Sketch.swift`).
- **What it emits.** A folder with a single-file `@main` `Sketch.swift` (the zero-boilerplate `Sketch.main()` form already on the core) plus, as chosen, an assets dir, a `Shaders.metal` stub, a `@Param` block, and a README. The single-executable-target mechanism is the same one the examples set already scripts; build the target-stanza generation once and share it.
- **Form factor.** Start as a CLI (`swift run OllinNew <name>` with flags or an interactive prompt): cheapest, scriptable, and reuses the runtime targets' patterns. A GUI in the style of oF's projectGenerator is a later nicety; the SwiftUI hosts (`OllinExamples`/`OllinLive`) are a reference if it's wanted. Ties to the `.swiftpm` starter, since one generated form is a Playgrounds App Project.
- **Why it matters.** It's the same "learn it in an afternoon" lever as the examples and the live host: it removes the blank-page tax, and the questions double as a teaching tour of what Ollin can do.
