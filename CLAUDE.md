# Ollin — guidance for development

Ollin is a creative-coding framework for Swift + Metal (macOS). This file captures the design intent so work here stays coherent across sessions.

## Vision

**p5.js ergonomics on an OPENRNDR-grade core, with motion as the default.**

- The API people *type* should feel like p5: `setup()`/`draw()`, bare calls like `background(.white)`, `stroke(.black)`, `drawCircle(x, y, radius)`. That familiarity is the point — don't sacrifice it.
- The architecture they *grow into* should feel like OPENRNDR: typed value objects, an explicit `Drawer`, and composable geometry.
- `draw()` runs continuously at the display refresh rate. Animation is not opt-in — `radius: 120 + sin(time) * 40` just moves. `noLoop()` is the rare still-image escape hatch.

## Platform scope

Apple platforms only, by design. macOS is the focus today; iOS, tvOS, and visionOS are in scope as *future* targets (see the Swift Playgrounds / iOS follow-up and the 3D & visionOS follow-up). Linux and Windows are explicitly out of scope — not now, not later — so don't add cross-platform abstractions for them: lean on Metal, AppKit/UIKit, and SwiftUI freely. "No Linux/Windows" is not "macOS-only"; keep Apple-platform portability in mind (the `#if canImport(AppKit)`/`#if canImport(UIKit)` seams) so the iOS/visionOS work later isn't a retrofit.

## The architecture rule (load-bearing)

**The bare p5-style API is sugar over a public, typed core. Never make the facade the only path to a feature.**

- `Sketch`'s bare methods forward to an internal `Drawer` (see `Sources/Ollin/Core/Sketch.swift`). Keep that split. Anything `drawCircle(...)` can do, the `Drawer` should also do — with more control.
- The day a capability is reachable *only* through the bare API, the ceiling is capped. Build the feature on the core first, then add the sugar.

## Conventions

- **Typed value objects early.** Geometry and color are data you pass around, transform, and compose — not just immediate draw calls. Prefer adding `Vector2`, `Rectangle`, and a vector `Shape`/`Contour` type *before* the call sites multiply; retrofitting `x:y:` doubles into `Vector2` later is expensive.
- **Swift-idiomatic, not a literal p5 port.** Enums for modes (not `"CENTER"` strings), trailing-closure scoping (`withState { }`) over leaky global state, value types, overloads. Borrow p5's feel, not its warts.
- **Build on the extension seam.** OPENRNDR's `extend(...)` is shipped: register a `SketchExtension` (`Sketch.extend`) for `setup`/`beforeDraw`/`afterDraw` (in-frame, before the render — can draw into the canvas), `afterFrame` (post-render, with `FrameInfo` timing), and `frameRendered` (post-render, with the rendered `CGImage`) hooks. New cross-cutting features — overlays, guides, recorders, the FPS stats (already the seam's first customer) — bolt on as extensions instead of bloating the core. Extensions are per-instance, so the runner re-attaches built-ins like the stats observer across live-reload swaps. The **frame-grab** hook is the seam's latest customer: `frameRendered(_:_:)` hands an extension the rendered frame, *opt-in* via `wantsRenderedFrame` (read live each frame, so a recorder can arm/disarm) so only something recording pays the GPU→CPU readback; on the live path it's served by an off-screen re-render (pixel-identical to export, keeps it off the present path — an async drawable readback is a later optimization). The same capture without a window is the public headless `OllinApp.image(of:frame:)` (returns a `CGImage`; `OllinApp.export` is the PNG wrapper over it), which is what the render-correctness snapshot tests diff against committed references.
- Drawing methods live on `Sketch` (scoped to the instance), not true globals — keep it that way.
- **Draw verbs, not nouns.** Geometry-emitting calls are imperative verb phrases with a `draw` prefix — `drawCircle`, `drawRect`, `drawLine`, `drawPolygon`, `drawPolyline`, never bare nouns (`circle`). They read as the side-effecting immediate-mode commands they are (what the Swift API Design Guidelines want), and the prefix gives a clean rule: `draw*` emits geometry; state (`fill`/`stroke`/`background`) and transforms (`translate`/`rotate`/`scale`) keep their own names. "Feels like p5" is the *shape* of the API — bare top-level calls, terse positional args, motion by default — not p5's literal spelling, so the prefix keeps the feel and stays a good Swift citizen. New primitives take it too (`drawEllipse`, `drawTriangle`, …). (oF landed here too: `ofCircle` → `ofDrawCircle`.)
- **Consistent point arguments.** A primitive that takes a point offers a *positional* scalar form and a *role-labeled* `Vector2` form: `drawCircle(x, y, radius)` beside `drawCircle(center:radius:)`, `drawRect(x, y, width, height)` beside `drawRect(corner:…)`/`drawRect(center:…)`, `drawLine(x1, y1, x2, y2)` beside `drawLine(_:_:)`, `translate(x, y)` beside `translate(_ offset: Vector2)`. The rule: bare scalars go positional — everyone knows the `x, y, radius` order, and labels on them are pure stutter once call sites pass `x`/`y` variables (`drawCircle(x: x, y: y, …)`). The label is reserved for the value-object overload, where it names the *anchor* (`center:` vs `corner:`) and carries real information. New point-taking primitives (`drawEllipse`, `drawPoint`, `drawTriangle`, …) follow the same split. (Unlike Kotlin/OPENRNDR, Swift can't make one declaration callable both ways, so don't double the overloads to fake "both" — pick positional for the scalar form.)
- **State stack reads as Swift.** The drawing-state stack is `pushState()` / `popState()` — the combined transform+style snapshot, mirroring Core Graphics' `saveGState`/`restoreGState` — with `withState { }` as the scoped, exception-safe primary form (the `with…{ }` idiom of `withAnimation`/`withTaskGroup`). Reach for `withState { }`; the bare pair is the escape hatch. Combined (not split into transform vs style) by design; a split push/pop can come later as `Drawer`-level methods.
- **Deprecation path is a 1.0 gate.** Pre-1.0 the public API churns freely with no shims (the README disclaims stability) — no external sketches to protect yet, so renames like the noun→verb (`circle`→`drawCircle`) and `push`/`pop`/`isolated`→`pushState`/`popState`/`withState` ship unshimmed. *Before* 1.0, stand up the migration discipline that holds from 1.0 on: every public rename/removal ships an `@available(*, deprecated, renamed: "…")` shim that forwards to the new API, so Xcode offers a one-click fix-it. Gotchas: use the *full selector* in `renamed:` when labels or arity differ (`@available(*, deprecated, renamed: "drawCircle(_:_:_:)")`, not just `"drawCircle"`); keep deprecated members together (a `Deprecations.swift`) so they're easy to audit and drop after a grace cycle; have the shim *forward* to the new API, not duplicate it. A must-do gate, not a nice-to-have — the 1.0 stabilization pass is where the pre-1.0 renames get their shims.

## Sourcing & attribution (load-bearing — it's the public face)

This project is built with AI and says so openly (README's "Built with AI" and "Influences & attribution" sections). Getting attribution and license-compatibility right earns the creative-coding community's trust — treat it as first priority, not a side chore.

The framework is *inspired by* p5.js (LGPL-2.1), OPENRNDR (BSD-2-Clause), and openFrameworks (MIT): borrow their ideas and API vocabulary, write the implementation independently. **Never translate their source line-by-line** — a port of source is a derivative work that carries the original's license, and p5.js's LGPL is incompatible with Ollin shipping wholesale as MIT. "Inspired by" keeps Ollin MIT-clean; "ported from source" does not.

**One sanctioned exception: bundled third-party source (a distinct tier).** A library may be *vendored* — shipped as actual source — when it's a self-contained, permissively-licensed component wasteful to reimplement, wrapped behind Ollin's own API so it stays swappable and off the public surface. This is the opposite of inspired-by (it *is* their code), so it carries license obligations: keep the upstream LICENSE + per-file headers **intact** in the vendored dir (the one exception to "no framework names in code" — they're the library's own headers, and stripping them breaks the license); record provenance (upstream URL, commit, date); list it in the repo-root `THIRD-PARTY-NOTICES.md`; add a *Bundled third-party code* line to the README's Influences section; keep the root `LICENSE` pure MIT so GitHub's root-only license detection holds the "MIT" badge. Vendor under `External/`, not `Sources/`. The first and only instance is **libtess2** (`External/CLibtess2`, SGI-B), the triangulator behind `Shape`/`Contour`. This tier is *not* a license to vendor copyleft (LGPL/AGPL/GPL) code, which stays inspired-by-only.

For ported *example sketches* (the iterate-by-porting workflow), provenance is per-sketch and must be honored:

- **Only port sketches whose license permits redistribution under MIT** — MIT, BSD, Apache-2.0, CC0/public domain, or CC-BY (with credit). For GPL/LGPL, CC-BY-NC, or CC-BY-SA sources, either get permission or rewrite the sketch as original work using the source only as inspiration (credit it as "inspired by").
- **Name the source in the file header** — the specific sketch, its author, a URL, and its license. Template lives in `Examples/README.md`.
- When unsure of a sketch's origin or license, **ask before committing it.** A trivial sketch (a plain dot grid) may fall below the copyright-originality bar, but crediting the inspiration is still the default.
- **Recreations** (`Examples/Recreations/`, organized by artist) credit the artist, framed as a homage *after* them (not a reproduction, not endorsed), plus the SFPC "Recreating the Past" class that inspired the section. Some are *ported* from a source sketch, so they also carry the code-lineage header (e.g. the Molnár ones, via the p5 repo); others are *original* Ollin interpretations built directly from the artwork, with no code lineage (e.g. the Riley one). Either way, name the artist and work and keep the homage framing. See `Examples/Recreations/README.md`.
- **Keep framework names — and product/lineage comparisons — out of code.** The influence story (p5.js / OPENRNDR / openFrameworks) lives in this file, the README, and commit messages — *not* in `.swift` comments. This is not limited to those three: it covers any *external product* reference (e.g. **Record3D** the capture app, SinkCam, Hydra) **and** *lineage/marketing comparison framing*. Don't write `// p5 default`, `/// like oF's ofNoise`, `// the own-app successor to borrowing Record3D's feed`, `// Ollin's own-app answer to X`, `// the way X does, but ours` — keep the information, drop the name *and* the comparison. (Ollin's *own* type/example names — `Record3DDevice`, `Camera`, `PhoneBodyPose` — are fine as plain internal cross-references, and Apple-framework API names actually in use — ARKit, Vision, usbmuxd — are fine; the prohibition is *external* product/framework names and *comparison framing*, not internal documentation.) Apply this *at authoring time*, not as a later cleanup, and when sweeping a file check *pre-existing* comments too — these have slipped into committed code before. The one *exception* is the per-example attribution header, which credits the actual source lineage. Source littered with running comparisons reads like a port and undercuts the "independent implementation, inspired-by not copied" stance.

There's a second tier of influence worth distinguishing from the conceptual one. Where p5.js / OPENRNDR / openFrameworks shaped the *API and ideas*, two peer Swift+Metal frameworks were read for *engineering approach* on the same platform: **swifty-creatives** (Apache-2.0, Processing-style immediate-mode) and **AsyncGraphics** (MIT, GPU image/video compositing). They were studied, not ported — specific lessons are noted inline through this file (shader build, pipeline cache, SDF circle, iOS seam, easing, snapshot testing). Same rules apply: credit them in the README and commits, never in `.swift` comments, and write our own implementation. The public credit lives in the README's Influences & attribution. (PixelKit is AsyncGraphics's older node-graph predecessor; cite AsyncGraphics instead.)

A third tier names influences for *capabilities still ahead* — shader-function collections, shader-composition / livecoding APIs, and AR. **These are inspirations, not dependencies:** *study how they work and reimplement our own*, never vendor or depend on them. It's especially clean for the shader-function collections — mostly implementations of *known, published techniques* (SDFs, noise, blends, color-space math, domain repetition): peek at the approach, then write Ollin's own, preferring the canonical source of a technique over any one collection's expression. Licenses still drive the no-line-by-line-copy rule:

- **LYGIA** (github.com/patriciogonzalezvivo/lygia, Patricio Gonzalez Vivo, who also created The Book of Shaders) — a large, multi-language catalog of shader functions (GLSL/HLSL/WGSL/CUDA plus an *experimental, partial* MSL/Metal port: `sdf`, `sampler`, `blend`, parts of `distort`/`generative`/`math` done; `lighting`/`geometry`/`palette` not yet). The best *map* of which techniques exist and how they're commonly approached. Licensed **Prosperity Public License 3.0.0** (noncommercial) — since we reimplement rather than ship its code, that's not a bundling problem; it's the reason to never translate a LYGIA file line-by-line and to implement from the underlying technique instead.
- **Hydra** (github.com/ojack/hydra, Olivia Jack) — a web livecoding environment with a chainable, analog-video-synth shader API (`osc().rotate().modulate(noise())…`). The thing to mine is *how it makes combining and mixing visuals so fluid* — borrow that ergonomic direction. Licensed **AGPL-3.0** (strong network copyleft) → **inspiration only**, never ported or vendored, exactly like p5.js's LGPL.
- **ShaderPark** (github.com/shader-park — `shader-park-core`, `shader-park-examples`, `shader-park-live-coding`, all **MIT**) — a JS→shader SDF "sculpting" library with composable combine/blend functions and its own livecoding environment; another reference for *how to compose and mix* shader-driven shapes. MIT, so it can be studied freely — still: write our own, credit it.
- **ofxFX** (github.com/patriciogonzalezvivo/ofxFX, Patricio Gonzalez Vivo again, **MIT**) — the openFrameworks effects addon behind his *Efecto Mariposa*: each effect is a ping-pong-FBO object chained/mixed with a `<<` operator, organized as composers (blend/mask/multi-texture), filters (blur, gaussian, bloom, glow, bokeh, **LUT color grading**, chroma aberration, old-TV), generative (noise, FBM, fire, Gray-Scott), and operations (ripples, flow, edge detect, normals). The reference for the [layered-effects](DESIGN-NOTES.md#layered-effects-and-compositing-partly-shipped) *effect-object architecture and catalog* — blending fx shaders and LUTs — from the GL/oF generation, beside AsyncGraphics' Metal-native take. MIT, study freely — still: write our own, credit it.
- **Meta Spark** (Meta's discontinued AR studio, shut down Jan 2025 — no public source) — the *product* reference for an AR direction: its template-driven AR-effect authoring is the void @eaviles wants Ollin to fill on Apple platforms. Conceptual/product influence only; there's nothing to port. (Used in Zach Lieberman's AR class — keep that personal detail out of public files, see the AR follow-up.)

Same rules as every tier: credit in the README's Influences & attribution and in commits, never in `.swift` comments, own implementation.

## Shaders & the Metal back end

The shader set is split across several `.metal` segments (`Renderer/Shader*.metal`), concatenated and compiled as one library at runtime (see *The shader set is multiple segments* below). Decisions that are cheap now and expensive to retrofit:

- **One source of truth for CPU↔GPU structs — defined once in a shared C header.** The three structs shared between Swift and MSL (`OllinVertex`, `Uniforms`, and `SDFInstance` — the last a stride-144 *tagged union* that keeps growing) live in `Sources/Ollin/Renderer/OllinShaderTypes.h`, so a field can't drift between the two sides and silently corrupt memory. Swift imports them through the thin `COllinShaders` C target (whose umbrella header re-includes the canonical file by relative path, since SwiftPM won't let a resource escape its target or two targets' dirs overlap); `ShaderCore.metal` (the first segment) `#include`s the same header. The one wrinkle the header note predicted: runtime `makeLibrary(source:)` has no include path, so `MetalRenderer.composeShaderSource` splices the header's text in for the `#include` directive before compiling — which is why the header ships *beside* the segments as a `.copy` resource. The fields are spelled in the `simd_*` names the Swift importer maps to `SIMD2<Float>`/etc.; a `__METAL_VERSION__` guard aliases those onto Metal's `float2`/`float3x3`. **A new shared struct (or a wider `SDFInstance`) goes in that header — never re-declared in two places.**
- **Runtime source compilation is a feature, keep it.** `loadLibrary` concatenates the `.metal` segments and compiles them from source at runtime (`makeLibrary(source:)`). For a creative-coding framework that's the seam for shader hot-reload and user-supplied shaders later — don't rip it out. Its costs are startup time and *no build-time error checking*.
- **Add a precompiled `default.metallib` when those costs bite, don't replace.** Build-time validation and zero startup cost need the built-in shaders compiled ahead of time. `loadLibrary` prefers a precompiled `Bundle.module` metallib *before* the source path **on a non-ray-tracing device** (an RT device source-compiles, to splice in the device-conditional `OLLIN_RT_SHADOWS` define), so a precompiled lib slots in with no API change; runtime compilation stays for dynamic shaders. Two facts settle *how* to produce it (both verified on this toolchain — Swift 6.3, macOS):
    - **Ship `.metal` as `.copy` (raw source) — `.process` now precompiles a metallib.** Ollin compiles its shaders from source at runtime, the seam the shader hot-reload, user shaders, *and the device-conditional `OLLIN_RT_SHADOWS` ray-traced-shadow path* all rely on — so the raw `.metal` must reach `Bundle.module`. **On current SwiftPM toolchains, `.process` on a `.metal` precompiles a single `default.metallib`** (and stops copying the raw source), so `makeDefaultLibrary(bundle: .module)` then succeeds — convenient for a fixed shader set, but a metallib holds only one compile, so it *can't* carry a device-conditional variant. That's why the `Shader*.metal` segments are **`.copy`** resources and `loadLibrary` source-compiles on a ray-tracing device (preferring the metallib only on non-RT GPUs). (Historically `swift run` did *not* auto-compile loose `.metal` — that was Xcode-build-system-only — but the toolchain caught up; don't assume `.process` leaves the source uncompiled.)
    - **A precompiled `default.metallib` shipped as a `.copy` resource loads fine.** `xcrun metal` + `xcrun metallib` produce a `default.metallib`; `.copy`-listed in the target, it's found by `makeDefaultLibrary(bundle: .module)`. So under `swift run` the path is a SwiftPM build-tool plugin that runs that compile and emits the metallib as a resource. (Playgrounds plugin support is unreliable — see the iOS follow-up — so keep runtime source compilation too; never go plugin-*only*.)
- **A user-supplied shader-library seam is cheap.** Resolve the active library as `customMetalLibrary ?? defaultMetalLibrary` so a user can drop in their own compiled library without touching the built-ins; pairs with the runtime-source loader for hot-reload. (Both peer Swift+Metal frameworks expose exactly this.)
- **Built-in shader functions are our own, written from the technique — not a vendored library.** As the shader set grows past drawing (noise, SDF primitives, blends, color-space conversions, domain repetition), implement each from the *published technique*, then credit that source in the README's Techniques list (as the cosine `CosinePalette` and `curlNoise` already do). The canonical sources to reach for, baked in here so we go straight to them: **Inigo Quilez** for signed-distance functions (2D `iquilezles.org/articles/distfunctions2d`, 3D `/distfunctions`) and smooth-minimum, and the cosine palette (already used); **hg_sdf** (`mercury.sexy/hg_sdf`) for domain operators — axis rotation, mirror, and linear/polar repetition; **The Book of Shaders** for hashing and value noise. LYGIA is a broad *catalog/map* of which techniques exist and how they're approached — read it to discover, implement from the underlying technique, never translate its files (Prosperity; see [Sourcing & attribution](#sourcing--attribution-load-bearing--its-the-public-face)). (Distinct from the user-supplied seam above, which is for a *user's* own shaders, not for vendoring someone else's library into Ollin.)
- **Cache pipelines; don't grow `init`.** `MetalRenderer.init` builds one `MTLRenderPipelineState` inline. A new pipeline (textured quads, a new blend mode, compute) should be a cache lookup, not more code in the constructor. Key the cache on a `Hashable` descriptor struct (shader, blend mode, MSAA sample count, pixel format), not a flat enum: pipeline variants are *combinations* of those axes, and a struct key captures the product without an enum case per combination. Folding blend mode into that descriptor also keeps it a pipeline *parameter* — one pipeline factory — rather than a whole renderer subclass per blend mode (the trap a peer framework fell into).
- **The shader set is multiple `.metal` segments, concatenated at load.** It outgrew a single file at ~2,000 lines and split into `Renderer/Shader*.metal`: `ShaderCore` (preamble + shared color/dither/hash helpers), `ShaderShapes` (SDF primitives + the shared `ollin_sdf_distance`), `ShaderCombinator` (the SDF-combinator node VM — must follow `ShaderShapes`, it reuses `ollin_sdf_distance` + the coverage tail), `Shader3D` (particles/cloud/mesh/matcap/wireframe), `ShaderEffects` (present + filters + generators). `loadLibrary` reads them from `Bundle.module` in the fixed order `MetalRenderer.shaderSourceNames` and concatenates into one compile unit, because runtime `makeLibrary(source:)` has no include path (so an `#include` umbrella can't work). **Order is load-bearing:** `ShaderCore` is first because Metal needs a declaration before use and the later segments rely on its helpers; no segment is compilable alone, and the header `#include` lives once in `ShaderCore` for `composeShaderSource` to splice. Live shader reload (`SketchRunner.reloadShaderLibrary(fromDirectory:)`, used by OllinLive) concatenates the same segments from the repo filesystem via `MetalRenderer.concatenatedShaderSource(fromDirectory:)`. Adding a segment: create the file, add it to `shaderSourceNames` (in dependency order) and to the `Package.swift` `.copy` resources.

## Rendering performance (roadmap)

The drawing model is *immediate-mode GPU*: every frame `Drawer` tessellates each primitive into one flat triangle array on the CPU, the renderer uploads it to a **triple-buffered, semaphore-gated vertex-buffer ring**, and issues a single `drawPrimitives`. (That ring is load-bearing — never collapse it back to one shared buffer: writing a buffer the GPU is still reading for an in-flight frame tears the geometry on screen, e.g. gaps in a stroked ring. That was a real bug, fixed by the `maxFramesInFlight` ring + `frameBoundary` semaphore in `MetalRenderer`.) This is the right shape — it's what NanoVG, Dear ImGui, and Processing's GL renderer do — so the "low-level" look is the cost of a Metal core, not accidental complexity. Don't trade it for Core Graphics / SwiftUI `Canvas` / SpriteKit: those are CPU rasterizers or retained-mode scene graphs, and adopting one as the substrate throws away the GPU + shader ceiling the whole vision rests on.

Where it caps out, and the levers — in priority order, all *iterations on this pipeline, not rewrites*:

- **CPU tessellation is the first bottleneck, not the GPU.** Re-tessellating thousands of primitives every frame on the draw thread stalls long before the GPU breaks a sweat. Everything below attacks that cost.
- **Instancing is the biggest lever.** Upload one unit-circle mesh once and draw it N times with a per-instance buffer (center, radius, color) via `drawPrimitives(instanceCount:)`. CPU work per circle drops to a struct write; this is the "10,000 circles at 60fps" path. It's a new `Pipeline` case (`.instancedCircle`) plus a per-instance buffer — the cache seam already exists for exactly this.
- **SDF analytic primitives (point, circle, ellipse, rect, oriented box, line, circular arc, triangle, general 3-point triangle, quadratic Bézier, regular polygon, star, rhombus, vesica, oriented vesica, moon, cross, ring, trapezoid, parallelogram, egg, heart, cut disk, uneven capsule, horseshoe, parabola, rounded X, blobby cross, tunnel, stairs, cool S) — *shipped*.** `drawPoint`/`drawCircle`/`drawEllipse`/`drawRect`, circular `drawArc`, `drawTriangle` (equilateral + isosceles), and `drawNgon`/`drawStar` are no longer tessellated: each is one instanced quad (`SDFInstance`, the `.sdf` `Pipeline` case). (`drawLine`/`drawBezier` were SDF too, but moved to the **fringe stroke path** — see the *Strokes render through the fringe expander* paragraph below; their `.capsule`/`.bezier` shader cases are retained-but-unemitted.) `SDFInstance` is a *tagged union* — a `shape` tag plus generic `size`/`param0`/`param1`/`param2`/`extra` slots — and `ollin_sdf_fragment` switches on it to evaluate the matching SDF, then runs a shared fill + stroke + anti-aliasing tail (iq's 2D distance functions, written from the technique). Per-shape CPU cost is one struct write — `Myriad` draws 8,100 circles at ~1,100 fps CPU ceiling. Each instance carries its own CTM (`float3x3`), so the fragment evaluates the SDF in local space and AA stays ~1px under any transform (`fwidth`); the quad covers `size` + ½ stroke + a small margin. (Circle approach studied from AsyncGraphics's circle shader, MIT — written independently.) The per-shape encodings — which param slot carries what and the `sd*` each calls (`drawPoint`'s round/square/diamond/cross/x markers, `drawNgon`/`drawStar` sharing one `sdStar`, the egg/heart/tunnel/stairs Y-flips, the three-point `drawTriangle` and `drawBezier` reading their free points from `param0`/`param1`/`param2`, and the rest) — live in `SDFShape` + `ShaderShapes.metal`; all evaluate iq's distance functions and all region shapes use `regionCoverage`. One rule there is *not* safely discoverable from the code, so it stays: the four roundable shapes (rhombus/vesica/moon/cross) take a footprint-preserving `cornerRadius`, and vesica/moon must `opRound` off a *full-footprint* SDF — insetting the vesica's waist toward zero sends its derived circle radius/offset to ~1e7 and the shader's `sqrt(r²−d²)` loses all precision (a real glitch, fixed by the full-footprint form). **Coverage is split by whether a shape tiles, and it's load-bearing.** `box`, `pie`, `chord`, `triangle`, `star`/n-gon, and the non-round point `marker`s use an **inside-biased** ramp (`regionCoverage`: full to the geometric edge, AA halo only outside) so abutting fills — tiled grids, gradient bands, the rotated wedges that tile a cell in `LifeQuilt` — leave no seam; never move them onto the centered ramp or the seams return. The **disk (ellipse/circle/round point)** and **capsule/line** instead use **area-conserving** coverage (`diskCoverage` and the capsule case): a centered AA ramp, but any mark smaller than ~½px on screen keeps a ~1px footprint while its alpha scales by the true/clamped **area** (disk) or **width** (line). That makes sizes run from 0…n — tiny dots, small circles, and thin lines fade by area instead of popping in, snapping to a 1px floor, or flickering as they move — and it's safe because disks and lines never tile edge-to-edge, so they don't need the inside bias. **Stroke *bands* conserve ink the same way:** a shared `strokeBandCoverage` (used by both `regionCoverage` for region-shape outlines and `diskCoverage` for disk outlines) holds a band thinner than ~1px at a ~1px footprint and scales its alpha by the width ratio — the capsule's trick — so an outline thinner than a pixel fades by ink to nothing instead of plateauing at a fixed hairline (the old smoothstep band floored at ~half coverage as `hw→0`, so a 0.4px and a 0.05px outline read alike); a band ≥~1px reduces to the plain smoothstep edge it always was (byte-identical, snapshot-safe), so only sub-pixel outlines change. (These area-conserving paths and every stroke band then run their coverage through `perceptualCoverage`, and the capsule/bézier footprint is the L2 gradient length rather than `fwidth` — both detailed in the linear-light bullet below.) **The other load-bearing piece is draw-order preservation:** `Drawer` records geometry into call-ordered `GeometryBatch`es (a run is `.triangles` or `.sdf`), so SDF shapes and tessellated triangles composite front-to-back as the sketch drew them — never collapse that into two unordered passes (it breaks occlusion, e.g. EllipseField's black-fill ropes). Still on the triangle path by nature: arbitrary `drawPolygon`/`drawPolyline`, and *elliptical* + full-turn arcs (`drawArc` runtime-branches `rx == ry` and sweep `< τ` to SDF, else tessellates). **Hollow/band mode** generalizes the ring's `opOnion` to every region shape: `hollow(_:)` / `solid()` set a per-instance `bandWidth`, and `regionFill` onions the shape's SDF (`abs(d) − bandWidth/2`) before `regionCoverage`, so the `fill` paints a constant-width band hugging the outline and an active `stroke` borders *both* edges (the framed-ring look stroke alone can't make). The band straddles the edge, so the covering quad grows by `bandWidth/2`; the `bandWidth` field fit the `SDFInstance` *tail padding*, so it forced no widening (the struct only grew later, to 144, for the three-point shapes' `param2`). Region shapes opt in via `SDFShape.honorsHollow`; points, lines, and the ring (already a band) opt out, and the round-dot point opts out by hand since it shares the `.ellipse` tag (a solid disk's area-conserving `diskCoverage` is bypassed for `regionFill` only when banding). **Stroke alignment** (`strokeAlign(_:)` → `.center`/`.inside`/`.outside`) rides the same coverage tail: `regionCoverage`/`diskCoverage` take a `strokeBias` (`0` / `−hw` / `+hw`) that shifts the stroke band off the edge (`abs(d − strokeBias) < hw`) while the fill still stops at `d = 0`, so the inset/outset is an exact SDF offset; `.center` (bias 0) is byte-identical to before. The 3-state align rides in **bits 8-9 of the `shape` tag** (the tag is < 256), so the vertex shader masks (`shape & 0xFF`) before the switch and align costs the instance no room; `.outside` grows the covering quad by another ½ stroke. Hollow forces the bias to 0 (a band already has two edges); lines/points/open-arc never compute a stroke band, so they stay centered.
- **More SDF primitives — the cheap catalog expansion (roadmap).** The tagged union has a *scalar budget* — `size`(2) + `param0`(2) + `param1`(2) + `param2`(2) + `extra`(1) on top of the per-instance CTM/center/colors/stroke — so any shape that's a *canonical form parameterized by a size + a ratio or two* drops in as the same four touch-points (an `SDFShape` case, a `Drawer.draw*` builder, an `sd*` function, a fragment `case`) with **no renderer/pipeline change**; position/rotation/scale come free from the CTM. One constraint: `size` is *not* a free slot — the vertex shader uses it as the covering quad's AABB half-extent, so it carries the bounding extent and can't double as a geometry point. All from iq's 2D distance functions, implemented from the technique and credited in the README's Techniques list (canonical-source and no-copy rules under *Built-in shader functions* above; **hg_sdf** is the source for the *operator* track below). More canonical iq forms drop in the same four touch-points whenever one's wanted. The two shapes that need **three free points** beside `size`-as-AABB — the **general 3-point triangle** and the **quadratic Bézier** stroke (`sdBezier`, the *fast* path for curved contours, exact AA, no tessellation) — forced the one widening so far: a `param2` (2) slot added to `SDFInstance` in the shared C header (one definition for both sides — see *One source of truth for CPU↔GPU structs* below), taking the stride 128 → 144; the 8 bytes of tail padding that left have since been claimed by the gradient-paint row fields, so the struct is *full* at 144 — the next field is a real widening. Two things stay *off* this list by nature: arbitrary polygon/polyline (variable vertex count — they stay on the triangle path / libtess2), and SDF *operators* (smooth-min, union/subtract, hg_sdf domain repetition) which *combine* fields and so live on the **SDF-combinator path** (the `SDF` value type + `ShaderCombinator.metal`'s node VM — see *SDF combinators* under *Current state*), not the one-shape-per-instance primitive path.
- **MSAA is 8× where the device supports it** (else 4×), and only for the *triangle* path. The SDF primitives already bypass it (analytic coverage); the remaining triangle-path shapes (polygon/polyline, elliptical/full arcs) are where thin strokes or large zoom can still reveal that limit. The sample count is chosen once via `ollinPreferredSampleCount(_:)` (`SketchView.swift`) and shared by the live view and the export paths.
- **Rendering is gamma-correct (linear-light).** Geometry composites into a **linear `rgba16Float` intermediate** (`linearFormat`; the sRGB `.bgra8Unorm_srgb` `ollinColorPixelFormat` is now the *drawable*/present-target format, not the geometry target — see *HDR / float pipeline* under *Current state*), so the hardware blends and resolves MSAA in linear space — anti-aliased edges and translucent stacks composite physically, not with the too-dark fringes of a gamma-space blend, and the float precision means many overlapping translucent layers don't band as an 8-bit intermediate would. Three load-bearing pieces keep tones from shifting: (1) the shaders **linearize** their sRGB `Color` inputs before compositing and output linear into the float target (the *present pass* re-encodes to sRGB, not the geometry store); (2) the **background/clear color** is *also* linearized (`Color.srgbToLinear` in `mtlClearColor`) so the clear value lands in the float target as linear, matching the shaded geometry — miss this and the background washes out lighter (the clear bypasses the shader); (3) image textures load `.SRGB: true` so each sample decodes to linear, matching the linearized solid colors beside them. A triangular-PDF **dither** (a pure function of pixel position, so renders stay reproducible) is applied in `finalizeColor` — which now runs **in the present pass** (the single 8-bit quantization point, after tone-mapping the resolved float frame) — just before the 8-bit quantization to break the banding smooth gradients otherwise show. The image fragment still skips the dither (its source pixels are premultiplied; it outputs premultiplied linear straight into the float target). **One deliberate carve-out from pure linear light: stroke and disk/dot AA *coverage* is remapped to perceptual alpha** (`perceptualCoverage`, `1 − srgbToLinear(1 − c)`) before compositing. Linear blending makes a partially-covered dark mark read lighter than its coverage (a 50%-covered black pixel → sRGB ~0.74), so a thin diagonal line's correctly-conserved ink splits across the pixel staircase and reads faint/"beaded" — the bug that made the Molnár *Interruptions* field look chopped after the linear-light switch. The remap lands each covered pixel at the gamma-space darkness its coverage implies, so a 1px stroke is evenly dark at *any* angle and a sub-pixel mark still fades 0…n. It touches **only partial coverage** (`perceptualCoverage(1)=1`, `(0)=0`) and never a shape's own fill/stroke *alpha*, so solid interiors and translucent/overlap blending stay linear-light (solids still merge correctly). It's applied to the capsule/`drawBezier` strokes, `diskCoverage` (fill + outline), and `regionCoverage`'s **stroke** band — but **not** the region *fill* ramp, which stays plain linear so abutting fills tile seamlessly. Paired with this, the capsule/bézier footprint uses the **L2 gradient length**, not `fwidth`: a unit-gradient distance field's L1 norm overshoots √2× at 45°, which had been fading diagonal 1px lines as if sub-pixel. (Verified near-optimal for the raster path: 4× SSAA barely beats it — a 1px diagonal's residual softness is fundamental to native-resolution rasterization, see [`DESIGN-NOTES.md`](DESIGN-NOTES.md).)

Seam in place and now exercised: `MetalRenderer` builds pipelines through an enum-keyed cache (`Pipeline` + `makePipeline(_:)`) — `.solid` and `.sdf` today — so further pipelines slot in as new cases instead of more `init` code. Once variants multiply across blend mode × MSAA × pixel format, migrate that enum key to a `Hashable` descriptor struct (see *Cache pipelines* above) rather than enumerating the product by hand. (The CPU↔GPU structs feeding these pipelines live in the shared C header — see *One source of truth for CPU↔GPU structs* under *Shaders & the Metal back end*.)

Triangulator — *shipped, not hand-rolled.* The vector `Shape`/`Contour` type (concave polygons, holes) fills via **vendored libtess2** (the GLU tessellator lineage Processing/p5 descend from), wrapped in `Shape.triangulatedFill()` (`ShapeTriangulator.swift`, `import CLibtess2`) and drawn by `drawShape` on the triangle path. The fill rule is a per-`Shape` `winding: FillWinding` (`.evenOdd` default — nested contours become holes, a contour's direction doesn't matter — or `.nonZero`); `triangulatedFill()` maps it to `TESS_WINDING_ODD`/`TESS_WINDING_NONZERO`. **Font glyphs must be `.nonZero`** (the rule outlines are authored for): even-odd drops the region where a glyph's outline self-overlaps — e.g. the terminal of an `e`/`a`/`g`/`s` rendered as a flat *cut* (a real bug, fixed by giving glyph `Shape`s `.nonZero`), while simple glyphs (`o`, `l`) look the same either way. So `OutlineFont` builds glyph shapes `.nonZero`, and `Shape.mapPoints(_:)` (the point-transform helper used to place/warp glyphs — in `drawText(along:)`, `shifted`, the `OutlineText` warp) *preserves* `winding`; rebuilding a glyph via `Shape(contours:)` would silently reset it to even-odd and re-break the `e`. **A second glyph gotcha, distinct from winding: some system faces (San Francisco) build a glyph from *overlapping* sub-contours.** Even with `.nonZero`, the overlaps leave a faint hairline seam in the triangulated *fill* (visible inside the counters of `a`/`e`/`g`) and doubled edges in the *outline* (so a stroke, or dots sampled along the outline, double up where sub-contours cross). `OutlineFont.geometry(for:)` cleans each glyph with a Clipper2 union (`Shape.union` with an empty shape, normalizing it under nonzero) before triangulating, and feeds the **cleaned contours to both the fill and the returned outline** (so stroke/`textToShapes`/dots are clean too). Two load-bearing details: the union only merges cleanly when the curves are finely flattened, and **flatten density tracks the render size** (`CurveSampling`), so at small sizes the overlap stays coarse and the seam survives — so clean at a large **reference scale (1024)**, then scale the result to the render size; and that reference-scale flatten leaves the contours ~40× denser than the render size needs, which the per-frame stroke tessellation + fill bake then pay for *every frame* (a real 12→ fps regression), so **simplify** the cleaned contours back to a sub-pixel tolerance (Ramer–Douglas–Peucker, `OutlineFont.simplifyClosed`) before returning. All cached per `(glyph, size)`. (The niche `glyphRun` text-on-path/per-glyph path still flattens raw — a known follow-up.) libtess2 is bundled, not reimplemented — see the bundled-third-party-source tier in [Sourcing & attribution](#sourcing--attribution-load-bearing--its-the-public-face) (`External/CLibtess2`, SGI-B). Convex shapes (circle, rect, ellipse) and convex `drawPolygon` stay on the current fan/strip math; don't route them through the triangulator. **Strokes render through the AGG/NanoVG-style fringe expander** (`appendFringeStroke`, written from the technique — no SDF, no MSAA/SSAA). Every stroked path — `drawLine`, `drawBezier`, `drawPolyline`, the `drawPolygon` outline, and `drawShape` contours — is edge-expanded CPU-side into per-segment butt quads plus a **~1px screen-space anti-aliasing fringe** (`fw = 1/ctmScale`; coverage ramps 1→0 across it, GPU-interpolated so the edge stays smooth at *any* angle at native resolution — the staircase the SDF capsule's single-sample `fwidth` left on shallow diagonals). It rides its own `.fringe` `GeometryKind`/pipeline (`ollin_fringe_vertex`/`ollin_fringe_fragment`) but **reuses the triangle vertex buffer**: the coverage rides in an `aa` field tucked into `OllinVertex`'s existing float2→float4 alignment padding (stride stays 32, the triangle path byte-identical), with the stroke's rgb + paint alpha in `color`. The fragment remaps **only the coverage** through `perceptualCoverage` (thin lines stay dark in linear light) and keeps the **paint alpha linear** (translucent strokes composite at their true opacity — the two channels kept separate is *why* the `aa` field was needed). Solid, translucent, and gradient paint all take this path — gradient samples per path vertex like the tessellated path (`vertexPaint`: along-path reads arc length; long segments split first so the baked LUT tracks). The fringe **straddles** the true edge so perceived width = `strokeWidth` — geometry stays within snapshot tolerance of the old SDF/tessellated output, so **no snapshot re-record was needed**. **Joins/caps are honored** via per-join outer-gap fillers (`strokeJoin` `.miter` — beveling past the limit — / `.bevel` / `.round`; `strokeCap` `.butt`/`.round`/`.square` on open ends), so `drawLine` (single segment, cap-only — now default **butt**, not the old always-round capsule) and `drawBezier` (flattened → cap + joins) honor them too. `appendStrokedPath` (the old tessellated `appendSegment`/`appendArcFan` join-filler path) is **retained for text glyph stroking only**. **Fills stay on libtess2 + 8× MSAA, byte-identical** — the empirical call (native-res A/B): MSAA fill edges are already smooth, and a fill fringe would reintroduce abutting-fill seams (Voronoi/LifeQuilt) or fatten, so the fringe is **strokes-only**. Curved outlines (quadratic/cubic Bézier + Catmull-Rom `curve`) **sample to points** via the public `Path` builder (`Path.swift` — `move`/`line`/`curve`/`quadCurve`/`cubicCurve`/`close`, plus `Contour`/`Shape(curveThrough:)`), surfaced as the closure sugar `drawShape { p in … }` and the top-level `drawCurve(_:closed:)`. They feed the same triangulated fill + stroked path, so a curve never touches the SDF/renderer side — the `Contour`/`Shape` data stays polygonal, the `Path` just flattens curves into it.

## Build, run, verify

```sh
swift run Example-Basic-HelloCircle   # opens a window running an example
```

The canvas is `1080×1080` by default (`canvasSize`, the typed `CanvasSize` enum — `.square(n)` / `.size(w, h)` + named presets, integer pixels); the preview window is sized from the sketch's `windowMode` (`.auto` fits the screen, `.fixed`, or `.resizable`) — the window is a scaled view of the canvas, not the canvas itself.

- **Requires macOS 26+ and a Metal-capable GPU.**
- **`swift build --target Example-X` does not relink the executable.** It compiles the module and reports success, but `.build/debug/Example-X` stays the *old* binary — a tuning loop against it silently re-runs stale code (a real hour lost: three "tuning" rounds of VideoTrace all ran the first build). Rebuild runnable examples with `swift build --product Example-X` or just `swift run Example-X`; reserve `--target` for compile-checking libraries.
- **Check the environment before claiming you can't build.** Ollin needs the Swift toolchain and Metal, which exist on a Mac but *not* in the Linux web/iPhone container. These two run on different machines, so don't assume: if `swift --version` and `xcrun --find metal` succeed, you're on a Mac with the toolchain — **build, run, and verify directly** (`swift build`, `swift run <Example>`), and don't add caveats about being unable to compile. Only when that toolchain is genuinely absent (the Linux container) are changes unverifiable on this machine — say so then, and not before. Either way, the things that truly need a simulator or device (iOS/visionOS/AR) stay unverifiable here regardless.

## Current state & roadmap

Per-feature depth lives in the `Docs/` page named in each bullet; this section is the capability inventory plus the cross-cutting gotchas. Architecture and policy that span features stay in their own sections above (*Shaders & the Metal back end*, *Rendering performance*, *Sourcing & attribution*, *Conventions*). When work ships it lands here — see the ship checklist under *Roadmap & design notes*.

A few load-bearing rules recur across the satellites, so they're stated once here instead of per-bullet:

- **Render-thread closures must be built non-isolated.** Any closure an audio / MIDI / Vision / capture render thread calls, if formed in a `@MainActor` context, inherits main-actor isolation and Swift injects an executor assertion that *SIGILLs* the instant that thread runs it — build it in a free function or a non-`@MainActor` type.
- **`resource:in:` can't default `in:` to `.module`** — a default arg resolves to *Ollin's* bundle, not the caller's; every font / image / mesh / model loader makes `in:` explicit.
- **Never replace a GPU texture in place** — an in-flight frame may still be reading the old one; allocate a fresh texture when the bytes change.
- **Satellites can't depend on each other** — a shared seam (`RGBDFrame`, `SegmentationImages`, `FrameSource`, the `OllinUSBMux` tunnel) lives in the `Ollin` core, often `package`-access.
- **Background-producer → main-reader handoff** is uniformly an `@unchecked Sendable` producer with an `OSAllocatedUnfairLock` handoff (audio analyzer, OSC/MIDI receivers, Vision analyzer, phone readers all share this shape).

**Today** (the shipped surface):

- **Lifecycle & input.** `Sketch` base class; temporal state (`frameCount` / `time` / `deltaTime` / `frameRate`); mouse (`mouseX` / `mouseY`, `mouseIsPressed`, `mousePressed()` / `mouseReleased()`) and keyboard (`key` / `keyCode` / `keyIsPressed`, `keyPressed()` / `keyReleased()`, `isKeyDown(_:)`, typed `KeyCode`). The held-flag + release-hook pair makes drag-to-paint a `draw()` poll. `Docs/Core/Sketch.md`, `Docs/Helpers/Input.md`.

- **Rendering.** `Drawer` + Metal renderer over several pipelines recorded into **call-ordered batches** (so SDF / triangle / fringe / image / glyph / 3D geometry composite front-to-back as drawn — never collapse into unordered passes): a tessellated-triangle path (libtess2 fills + 8×/4× MSAA), an instanced-SDF path, a fringe-stroke path (the high-quality stroke renderer), a textured-quad image path, and a glyph-atlas path. Gamma-correct **linear-light** compositing in a `rgba16Float` intermediate that a final present pass tone-maps + dithers to the sRGB drawable. **`blendMode(_:)`** (`.normal` / `.add` / `.subtract` / `.multiply` / `.screen` / `.lightest` / `.darkest`) is stack state carried as a `Pipeline` cache-key parameter, not a renderer-per-mode. **HDR / tone-map** — `toneMap(_:exposure:)` (`.clamp` default / `.reinhard` / `.aces`), a frame-wide mode over the float pipeline (`Docs/Drawing/HDR.md`). **Accumulation surface** — `noClear()` / `clearEachFrame()`, a persistent float canvas drawing piles onto; `background(_:)` is the in-mode wipe (`Docs/Drawing/Accumulation.md`). The **SDF path** covers a broad analytic-shape catalog (`drawPoint` / `drawCircle` / `drawEllipse` / `drawRect` / `drawOrientedBox` / circular `drawArc` / `drawTriangle` / `drawNgon` / `drawStar` / `drawRing` / `drawHeart` / `drawMoon` / … + `hollow(_:)` band mode, `strokeAlign(_:)`, area-conserving disk + outline coverage); the **fringe path** covers every stroke (`drawLine` / `drawBezier` / `drawPolyline` + polygon/shape outlines, honoring `strokeJoin` / `strokeCap`, translucent + gradient paint); the **triangle path** covers convex/concave/holed fills (`drawPolygon` / `drawShape`, curved via the `Path` builder + `drawCurve`) and elliptical/full arcs. Collection sugar: `drawCircles` / `drawPoints` / `drawRects`. The load-bearing renderer rules (the vertex-buffer ring, the SDF tagged union, coverage models, the present/float pipeline) live in *Shaders & the Metal back end* + *Rendering performance* above. `Docs/Drawing/Drawing.md`.

- **SDF combinators** (`Sources/Ollin/Drawing/SDF.swift` + `Renderer/ShaderCombinator.metal`). Compose signed-distance *fields* so 2D shapes **merge** instead of stack — the geometry analogue of the layered-effects `Filter`/`Combine` catalog (and the field-combining axis the per-instance SDF primitive path can't express). The typed **`SDF`** value type (leaf shapes — circle/ellipse/rect/square/ngon/star/rhombus/ring/triangle — plus `.union`/`.smoothUnion(_:k:)`/`.subtract`/`.smoothSubtract`/`.intersect`/`.smoothIntersect`/`.morph(_:amount:)`/`.rounded`/`.onion`/`.at`/`.rotated`/`.scaled`/`.colored`/`.mirrored`/`.repeated`/`.repeatedRadially`) is the core; `drawSDF(_:)` draws it honoring the current fill/stroke/CTM, the stroke tracing the *merged* outline. A scoped **block form** (`smoothUnion(k:){ drawCircle…; drawRect… }`, plus `union`/`subtract`/`intersect`/their smooth forms/`mirrored`/`repeated`/`repeatedRadially`) is sugar: bare SDF *region* draws inside are captured at `Drawer.appendSDF` (the chokepoint) as leaves instead of drawn, and the block reaches **every** fillable region shape (not just the value type's named set). **Rendering is an "SDF VM":** the value-type tree flattens (CPU) to a flat `SDFNode` program — a new `SDFGroupInstance` + node buffer + `GeometryKind.sdfGroup` + `.sdfGroup` pipeline, *beside* the per-instance `SDFInstance` path (which it can't ride: that struct is full at 144) — that `ollin_sdfgroup_fragment` walks per pixel with two fixed-depth stacks (cap 16): a **value** stack of (distance, color) for the combine/modify ops, a **point** stack for the transform/domain scopes (an XFORM pushes+transforms the point; the matching RESTORE_P pops it and, for a scale scope, multiplies the child distance back). The smooth ops use iq's polynomial smin whose blend factor **also lerps the two operands' colors** (the "melt two colors" look); hard ops pick by min/max. **Leaves carry no transform** — all positioning (the shape's intrinsic anchor, `.at`/`.rotated`/`.scaled`, domain repeat/mirror) is XFORM nodes, so method-chain order is exact (`a.at(p).repeated()` tiles the moved shape; `a.repeated().at(p)` shifts the tiling). The leaf distance is **`ollin_sdf_distance`** — the per-shape region-SDF decode (Y-flips/recentering/insets) factored out of `ollin_sdf_fragment`'s switch; the two are **kept in sync by hand** (a new region shape goes in both — the fragment switch was left untouched, so the single-shape snapshots stay byte-identical). 2D AA reuses the single-shape coverage tail (`regionCoverage` + `fwidth` + `perceptualCoverage`); the covering quad is the whole-tree conservative AABB the flattener computes. **Gradient paint** (2D) is shipped: a `fill`/`stroke` is a solid color *or* a **linear/radial gradient**, sampled in **field space** at `in.field` (cleaner than the 3D path's screen projection — a 2D field already lives in canvas space), the whole merged region/outline painted by one ramp (leaf colors bypassed). `SDFGroupInstance` widened 96→128 with `fillGradientGeo` + `fillGradient{Kind,Row}` + `strokeGradient{Kind,Row}` (the *stroke* geometry reuses the existing `strokeColor` slot, exactly as `SDFInstance` reinterprets its color slots — so it lands at 128 with no pad); the fragment binds the same baked LUT strip (`gradients` @texture 0) the per-shape `.sdf` path uses and calls the shared `resolvePaint` (in scope since ShaderShapes concatenates *before* ShaderCombinator). Along-path has no single path on a merged field, so it falls back to solid; a solid-leaf field keeps kind 0 and is byte-identical (`sdf-combinators` unmoved). **Per-axis sizing** (2D + 3D) is shipped: `stretched(x:y:[z:])` (iq `opElongate`, a pure point-domain warp `p − clamp(p, −h, h)` that stays an **exact** SDF — a circle/sphere → stadium/capsule, so smin/round/onion don't distort) and `scaled(x:y:[z:])` (a true non-uniform scale, only a **conservative bound**: evaluate in unscaled local space, then RESTORE_P rescales the distance by the **min** scale component — the Lipschitz bound that keeps the march safe — so the surface is right but blends distort under strong anisotropy; `stretched` is the preferred per-axis tool). Two new XFORM **sels** — 6 (non-uniform scale, `p /= geo0`) and 7 (stretch) — in *both* `ollin_sdf_xform` (2D) and `ollin_sdf3d_xform` (3D); adding them moved **polar from `default` to `case 5u`** (byte-identical, all combinator snapshots unmoved). Uniform `.scaled(s)` (sel 2) is untouched. **Limits/gotchas:** closed **region** shapes only (lines/open-arcs/Béziers have no interior, skipped in a block with a one-time log); a field past the stack/node caps (value/point depth 16, ~256 nodes) is logged + skipped, never mis-drawn; the buffers thread through all 9 `encode` call sites (live/accumulation/export/effect-targets), so combinators work in every path. The **raymarched 3D sibling** is shipped too: **`SDF3D`** + **`drawSDF3D(_:)`** (`Sources/Ollin/Drawing/SDF3D.swift` + `Renderer/ShaderRaymarch.metal`) compose 3D fields (sphere/box/roundBox/torus/capsule/cylinder/cone/octahedron/ellipsoid/plane leaves + the same combine/modify ops + translate/rotate/scale) that **merge** the same way, **sphere-traced** as one surface through the active camera and **depth-composited with the rasterized meshes**. It's a *parallel* path beside the 2D one (its own `SDFNode3D` + `SDF3DGroupInstance` structs — the 2D `SDFGroupInstance` is `float3x3`-based — plus a new `GeometryKind.sdfGroup3D` + `.raymarch` pipeline + the `ShaderRaymarch.metal` segment, the buffers threaded through the same 9 encode sites). Load-bearing: the march runs in **world space** (each step maps the world point into the field's local frame via the per-field `inverseModel`, then scales the local distance back by the model's uniform scale), so the **4-tap gradient normal** and the written **`[[depth(any)]]` depth** (the world hit point through the *same* view·projection the meshes use, exactly the `ollin_depthscene_fragment` trick) come out world-space with no normal matrix; one **fullscreen triangle per field** bounded by its world AABB (a ray that misses bails O(1)); shading **reuses `meshLitColor` unchanged** (so the snapshot-pinned mesh shading never moved) by binding the same lighting/material/shadow resources; `Uniforms3D` gained exactly one field, `inverseViewProjection`, for ray reconstruction. The **scoped block form** reaches 3D too, and it's the *same* `smoothUnion(k:){ … }` blocks as 2D (one unified path): inside a block with a camera, the SDF-able **mesh** builders (`drawSphere`/`drawBox`/`drawCapsule`/`drawCone`/`drawTorus`/`drawCylinder`/`drawRoundedBox`/`drawOctahedron`) route through `Drawer.drawMeshPrimitive` (which captures an `SDF3D` leaf instead of tessellating), are positioned by the **relative model matrix** (`groupModel⁻¹ · drawModel` decomposed to translate+rotate+uniform-scale — the only similarity an SDF respects), per-`fill` colored, and merged; a non-primitive `Mesh` inside a block is ignored (one-time log, the 3D analogue of 2D's non-region warning). The one `CombineFrame` now carries *both* `children` (2D `SDF`) and `children3D` (`SDF3D`), so `endCombine` builds whichever the body populated — a sketch is in one dimension or the other; the **domain** blocks (`mirrored`/`repeated`) carry a 2D *and* a 3D `Transform` (`CombineFrameKind.domain(SDF.Transform, SDF3D.Transform)`) so one block serves both. **Domain operators** (`.mirrored(x:y:z:)`, `.repeated(spacing:count:)`, and `.repeatedRadially(count:around:)` — value-type and block-form) are shipped, mirroring the 2D mirror/limited-tile XFORM scopes (sel 3/4) in three dimensions via `ollin_sdf3d_xform`; method-chain order stays exact. **Polar/radial repeat is sel 5**, a shared new XFORM in *both* `ollin_sdf_xform` (2D, fold around the origin) and `ollin_sdf3d_xform` (3D, fold around an `axis` — an orthonormal fold-plane basis with wedge 0 on +X, so a wedge placed with `.at(x: r)` lands canonically), bounded by the child's bounding sphere (rotation about an axis through the origin preserves |p|). The block form `repeatedRadially(count:around:)` carries both dims (a 2D `.polar(count:)` + a 3D `.polar(axis:count:)`); the fold is the single-evaluation kind (wedge-symmetric content is exact, a seam otherwise — like `.repeated`, no neighbor-min). **Soft self-shadows** are shipped, gated on `castShadows()` (the same opt-in as meshes, so a field without it stays byte-identical): the raymarch fragment marches a penumbra ray toward the caster light (`ollin_sdf3d_softshadow`, iq's `min(k·h/t)` — the *standard* form, not the previous-step refinement, which divides by zero on a receding ray and false-shadows lit faces) and feeds it to `meshLitColor` via a new `fieldShadow` param (sentinel `-1` = a mesh, sample the maps as before → byte-identical; `≥0` = a field's own self-shadow, used in place of the maps at the caster light). One renderer tweak: `shadowLight` is no longer forced to `-1` when only a field is present (a field self-shadows analytically with no map). **Field→mesh cast shadows** are shipped too (directional/spot only): a field now *also* renders into the 2D shadow map so rasterized **meshes receive its shadow** — `encodeFieldShadowCasters` (in `encodeShadowPass`, after the mesh casters) draws one fullscreen tri per field through the new `.raymarchShadow` pipeline (`ollin_raymarch_shadow_fragment`), marching the field from the light's POV and writing the hit's light-clip depth (depth-only, z-tested against the mesh casters) via the new `OllinRaymarchShadowUniforms` (lightVP + its inverse, to rebuild the march ray); the field buffers thread through `encodeShadowPass`'s 3 call sites and are uploaded there since the shadow pass precedes the main encode. **Field *receives* mesh shadows** is shipped too (directional/spot): the raymarch fragment now also samples the 2D map at the hit (`shadowFactor`, the same path a mesh receiver uses) and takes `min` with the analytic self-shadow, so a mesh's shadow lands on a field surface just as on another mesh — folded into the existing `fieldShadow` factor `meshLitColor` already consumes, so **no renderer/encode change** (the map + lighting were already bound to the raymarch fragment). Gated on `shadowKind == 0` (a point/RT caster can't hold a field-receivable occluder in a 2D map → self-shadow only, the remaining gap). The normal-offset bias keeps the field's own front surface out of it (its self-occlusion stays the analytic march's job); the *shared* map carries the field's own cast too, so a self-shadowed edge can harden where the two overlap (a separate mesh-only receive map is the clean follow-up). A field-only scene (no meshes → the shadow pass early-returns) samples a **dummy all-lit** map → `min(self, 1) = self` → byte-identical, so `sdf-combinators-3d-shadow`/`-cast` (and all six other raymarch snapshots) are unmoved. The field is the one unbounded thing that can be a caster (the plane marches near..far in the shadow map too). **Field casts under a point/RT light** is shipped too: a point caster has no 2D map a field can render into, so the lit **mesh** fragments march the field(s) inline toward the light instead (`ollin_fields_shadow` → the same `ollin_sdf3d_softshadow` penumbra march, `min` over the field groups) and fold it into the mesh's own point-shadow (`meshLitColor` gained a `meshFieldShadow` param, default 1.0, multiplied into `lit01` in the mesh-receiver branch). The field group + node buffers bind to the **solid + textured** mesh fragments at buffers 4/5; the new `OllinLighting.fieldCasterCount` (set only for a point/RT caster with fields present) gates it, so a mesh-only or directional/spot scene marches nothing → **byte-identical** (all 57 snapshots unmoved, verified). `ollin_fields_shadow` lives in ShaderRaymarch (segment 5) but is **forward-declared** in Shader3D (segment 4) so the earlier mesh fragments can call it (one concatenated TU); the march budget is a fixed `OLLIN_MESH_FIELD_SHADOW_STEPS` (48 — the lit mesh fragments have no `Uniforms3D`/quality dial bound). Works on both RT and non-RT GPUs (it never touches the accel structure or the cube). Matcap/wireframe meshes don't run `meshLitColor`, so they don't receive a field's point-shadow (a documented nuance, like their other lighting carve-outs). **Perf (load-bearing trade-off):** the cast is *per-receiver-pixel*, so a screen-filling floor under a field is GPU-heavy (measured ~half the frame: ~7ms of a 15ms/1080² `RaymarchedPointCast`, the rest the blob's own raymarch + the sphere's RT shadow; at the live ~1620² window that's the ~40fps @eaviles saw). A conservative **AABB early-out** in `ollin_fields_shadow` skips the march for a ray that can't reach a (finite) field's world AABB — inflated by the soft-shadow penumbra reach (`dist/k`), so a grazing near-miss still marches and the result is byte-identical (a skipped ray is the 1.0 the full march returns anyway; an *unbounded* plane field always marches). It helps most when the field is small and off the light axis; an *overhead* point light funnels the receivers' shadow rays through the field, so it helps little there (the `RaymarchedPointCast` case). The bigger win is **shipped**: a **half-res field-shadow pass** (`encodeFieldShadowHalfRes`), wired to the **same `resolveRaymarchScale` dial** as the raymarch resolution. Live `.default` re-renders the receiver meshes at half-res into a single-channel target (`ollin_mesh_fieldshadow_fragment` outputs only `meshFieldShadowFactor`, depth-tested so the front surface's factor wins), and the full-res mesh fragments **sample it by screen position** (`ollin_resolve_mesh_field_shadow`, gated `fieldShadowMode == 1`) instead of marching per pixel. `OllinLighting` gained `fieldShadowMode` + `fieldShadowViewport`; the mesh fragments take a `fieldShadowTex` at **texture 3** (the gradient `strip` is the never-sampled stand-in when full-res). **`.detail`/export skip the pre-pass** (scale 1 → `nil` → the inline march), so snapshots stay **byte-identical** (all 58 pass) and exported art is never downscaled — the same live-only invariant as the raymarch half-res. Measured: the `RaymarchedPointCast` GPU dropped 15.0→9.2ms/1080² (the field-shadow march ~7.3→~1.5ms), the live ~1620² window ~40→~60fps. The AABB cull still composes (it trims the half-res march too). **Analytic silhouette AA** is shipped: the fullscreen pass gets no MSAA at the hit/miss edge, so the primary march tracks the closest the ray came to the surface relative to the pixel's own cone (`kPixel·t`, `tan(fovY/2)/height` from `projection[1][1]`); `1 − min(ratio)` is the edge coverage, a grazing near-miss shading at the closest-approach point and compositing by that coverage over what's behind (the `.normal` straight-alpha blend the path already uses). A solid hit is coverage 1 (the mesh path unchanged), so it's *sub-tolerance* on the snapshots (a ~1px edge change) — verified by native-res crop instead. **Gradient paint** is shipped, **screen-space**: a gradient `fill` paints the whole merged surface by each hit's *projected screen position* in canvas points (the canvas-space `Gradient`/`Paint` reused unchanged, sampled from the same baked 256-texel LUT strip via `resolvePaint`), bypassing the per-leaf colors — `SDF3DGroupInstance` widened 112→144 with `fillGradientGeo`/`fillGradientKind`/`fillGradientRow` (the geometry encoded `center: .zero` = absolute canvas coords; the strip bound to the raymarch fragment at texture 0), and a solid-leaf field keeps `fillGradientKind 0` and is byte-identical (so the existing 3D snapshots are unmoved). The 2D combinator path (`drawSDF`) carries its own gradient now too, in **field space** (fill + stroke; see the 2D *Gradient paint* note above). **Quality dial — `raymarchQuality(_:)` / `raymarchResolution(_:)` (load-bearing model).** A field is a fullscreen sphere-tracer whose cost is **bound to pixel count, not step count** (the `Scripts/benchmark.sh raymarch` sweep is ~flat 65→77ms across 32→256 steps at 1620²), so the dial scales the field's **internal resolution** — `.detail` full / `.default` half / `.performance` quarter, or `raymarchResolution(0.75)` for a custom fraction — and a half-res pre-pass (`encodeRaymarchHalfRes`, single-sample `.raymarchHalfRes` pipeline) marches each `.normal`-blend field into one pooled half-res color+depth, which the main pass composites once via `ollin_raymarch_upsample_fragment` (bilinear color, **point-sampled depth so the silhouette stays crisp**, re-emitted as the fragment depth so meshes still z-test/interpenetrate). **Resolution scaling is live-preview only:** `render()` + `benchmarkGPUMilliseconds` + `image(of:)` run the pre-pass, but a `.detail` export (scale 1.0) skips it, so `--export`/headless always march full-res and the default-tier snapshots are byte-identical (snapshots render at `.detail`, within the mean-2.0 tolerance). The dial rides the shared **`RenderQuality` model**: `.default` doubles as "automatic" — `effectiveQuality` maps it to `MetalRenderer.automaticQuality` (`.default` live, `.detail` for export via `OllinApp.image(of:…,quality:)` / `renderFrames`, overridable by the **`--render-quality`** CLI flag, distinct from `--quality` = video encoding) — while a *non-default* tier (or an absolute `raymarchSteps`/`shadowSamples`) is explicit and honoured on every path. All four `RenderQuality` knobs (shadows, `.defocus`, `.ambientOcclusion`, raymarch resolution) now target frame-rate bands (`.default` 60–90fps, `.detail` 15–30, `.performance` 120), tuned from `Scripts/benchmark.sh {shadows,dof,ssao,raymarch}` (SSAO is too cheap to hit `.detail`'s band, capped at 256). **v1 limit** (follow-up): the **remaining shadow sliver** — a field *receives* a mesh's shadow under a directional/spot caster but **not yet under a point/RT** one (the symmetric gap to casting: the field would sample the cube/RT for the mesh occluder. Field *casting* now covers all light types — directional/spot via the 2D map, point/RT via the inline mesh march). (Per-axis scale/stretch is shipped, above; uniform scale is no longer the only option.) The **infinite plane** (`SDF3D.plane(normal:offset:)`, `sdPlane = dot(p,n)−h`) is the one *unbounded* leaf: it has no finite AABB, so the flattener marks the whole field `unbounded` (the renamed `SDF3DGroupInstance.unbounded` flag, ex-`_pad0`; propagated through combine — union spreads it, subtract keeps lhs, intersect needs both) and the raymarch fragment marches the near..far span instead of the AABB slab (sphere tracing keeps open sky cheap — the distance grows so the steps do). Its `leafHalfExtent` is a finite ±64 used *only* to seed the self-shadow march budget (the camera path ignores it). It's **value-type-only** (no mesh primitive, so the scoped block form can't capture it); merged with shapes as one field under `castShadows()` it grounds them with soft self-shadows (a true infinite floor). The ten leaves are iq's 3D distance functions (ellipsoid is a *bound*, not exact, so it leans on the global `STEP_SCALE`); `ollin_sdf3d_eval`'s switch must stay in sync with `SDF3DShape` (the EVAL geo packing). - **Layered effects** (the substrate; `Sources/Ollin/Effects/`). Draw into off-screen layers, filter them on the GPU, composite back with blend modes, following the OPENRNDR `RenderTarget`/`Filter`/`compose` model. `renderTarget(scale:)` → `RenderTarget` (off-screen `rgba16Float` layer); `withTarget(_:) {}` redirects drawing into it (scoped like `withState`, fresh batch forced at each boundary; `background(_:)` inside clears *that* layer); `target.image` composites it via the textured-quad path (`Image(renderTarget:)`); `target.filtered(_:)` → a new layer; `postProcess(_:)` filters the whole frame. **`Filter`** is a broad (~44-entry) catalog: blur/glow (`.gaussianBlur` via `MPSImageGaussianBlur`, `.bloom` as bright-pass → blur → add-back, `.bilateral` edge-preserving, `.motionBlur`/`.radialBlur` directional gathers), color/tone (`.colorGrade`/`.invert`/`.posterize`/`.threshold`/`.sepia`/`.duotone`/`.gradientMap`/`.exposure`/`.levels`/`.solarize`/`.temperature`/`.vibrance`/`.colorama`/`.lumaKey`), stylize/optical (`.edges`/`.sharpen`/`.vignette`/`.chromaticAberration`/`.halftone`/`.dither`/`.grain`/`.pixelate`/`.lineScreen`/`.emboss`/`.oilPaint` (Kuwahara)/`.crosshatch`/`.toon`/`.median`/`.contour`/`.cmykHalftone`/`.normalMap`), retro (`.scanlines`/`.glitch`/`.crt`), and distortion — uv warps that re-sample the source (`.kaleidoscope`/`.swirl`/`.bulge`/`.wave`/`.ripple`/`.mirror`/`.polar`/`.tile`/`.perturb`). All are fullscreen-tri fragment passes on the `.effect` pipeline (reusing `ollin_present_vertex` + an `ollin_fx_*` fragment), reading/writing premultiplied-linear — most single-sample, a handful (`bilateral`/`motionBlur`/`radialBlur`/`oilPaint`/`median`/the halftones) gather several taps; only `gaussianBlur` and bloom's internal blur use MPS. `gradientMap` binds a baked 256-step LUT (`rgba32Float`) as a second texture. New filter built-ins are written from the published technique (credited in the README's Techniques list, never in `.swift`); the warps don't touch a texel's value (premultiplied passes through), the color/stylize ones un/re-premultiply around a straight-color op. The per-pass uniform is a **packed `[SIMD4<Float>]`** (`constant float4 *params`, widened from a single `float4`) so a filter can carry several params + colors. **`Generator`** + `generate(_:)` is the input-less sibling: a procedural pattern (`.checkers`/`.gridLines`/`.bars`/`.noise`) filled into a `RenderTarget` you then filter/composite, a `.generator` `RenderTarget.Origin` resolved by a no-input `ollin_gen_*` fragment pass, ahead of geometry/filter passes (the seed of the live-coding / shader-mix direction). One nuance: a fine 1px pattern (`dither`) averages away when the layer is drawn smaller, so `dither` takes a `pixelSize`. **Previous-frame feedback** — `feedback(scale:)` → a *persistent* `Feedback` layer (made once in `setup()` and held, *unlike* the per-frame `RenderTarget` — its identity carries state across frames); `withFeedback(_:) { prev in … }` redirects drawing into it and hands in last frame as `prev` (the `withTarget(Feedback)` form reads `feedback.previous` by name instead), and `feedback.image` composites this frame's result. It's a two-texture ping-pong the renderer keeps in a persistent map keyed by the layer's identity (`MetalRenderer.feedbackSlots`, *separate* from the per-frame pools), rendering into the *back* while the block reads the *front*, then flipping after the frame — relying on Metal's automatic GPU↔GPU hazard tracking (feedback is inherently serial, so no extra semaphore), with slots pruned by a weak owner ref on reload. **Gotcha:** the headless `image(of:frame:)` must render *every* warmup frame when `drawer.usesFeedback` (exactly like accumulation), not just `stepCompute`, or the ping-pong never evolves — the built-up state is what the single-frame export and the `effects-feedback` snapshot depend on. (`Feedback` is the per-frame `RenderTarget`'s persistent sibling; the `RenderTarget.Origin.feedback(Feedback)` case routes its write layer to the ping-pong storage.) **Simulation fields** — `simField(_:scale:)` → a *persistent* `SimField` (`Effects/SimField.swift`) that runs a built-in **`Sim`** (a `Sendable` value catalog like `Filter`: `.reactionDiffusion(feed:kill:)` Gray-Scott, `.gameOfLife` Conway, `.fluid(...)` a real-time fluid) on its state each frame, the *stateful* sibling of the stateless `Filter`. You **draw into it to seed/force it** (`withField(_:_:)`, scoped like `withTarget`); the renderer renders the drawn marks into a transient seed texture, runs `ollin_sim_inject` (compositing the seeds onto the front state), then steps the sim's `ollin_sim_*` fragment N sub-steps (RD 14, GoL 1) ping-ponging pooled scratch into the back buffer — `runSimulation` in `MetalRenderer`. It **reuses the feedback path**: the `RenderTarget.Origin.simField(SimField)` case routes to the same persistent ping-pong storage (`FeedbackSlot`, now `owner: AnyObject`; `feedbackSlot(for:restState:)` clears a fresh pair to the sim's rest state — RD rests at A=1,B=0, GoL dead — not transparent), and `usesFeedback` counts sim fields so the headless warmup steps every frame. The field is raw state (data): `SimField.image` shows it, `SimField.filtered(_:)` recolors it through the `Filter` catalog (the substrate payoff — RD output `gradientMap`'d). The two single-field sims fit "draw to seed" cleanly; **`.fluid(...)`** is the *multi-field* one (a real-time incompressible flow carrying colour) and so runs a **dedicated `runFluid` pipeline** (~30 passes/frame) instead of the single-state step path: velocity+dye **splat** (the mark's colour → dye, `withField`'s `force:` → velocity, converted to a velocity by `/dt`), **curl** + **vorticity confinement**, a divergence-free projection via a **Jacobi pressure solve** (default 20 iters) + gradient subtract, then **semi-Lagrangian advection** of velocity then dye (Stam stable fluids / GPU-Gems / Pavel's splat recipe, written from the technique — README Techniques; boundaries are the clamp-to-edge sampler, `dt` a fixed constant for determinism). Its persistent state is *two* ping-pong pairs (velocity + dye) in a separate `MetalRenderer.fluidSlots` map keyed by the `SimField`'s identity (pressure/divergence/curl are per-frame pooled scratch — `acquireFilterTexture` hands out a distinct texture per call, so the ~8 passes never alias), kept beside `FeedbackSlot` so the single-field path stays **byte-identical** (no `effects-simfield`/`effects-feedback` re-record — verified); `usesFeedback` counts it for the headless warmup. One global `force` per field per frame (the brush model). The `SimField.image` is the dye, recolourable/bloomable like any layer. Beside it: the shipped `Compute/ReactionDiffusion` (compute-path Gray-Scott) and the `FlowTracker` Vision optical flow. **Deferred render-graph (load-bearing):** the `Drawer` is a pure recorder, so it just *tags* each `GeometryBatch` with its `target: RenderTarget?` and records `renderTargets`/`filterOps`/`frameFilters`; the renderer resolves the graph at `render()`/`image(of:)` time: each geometry target's tagged batches render into its own MSAA→resolve pass, then filter ops run (MPS/fragment) into pooled textures, all *before* the main pass (which samples them) and `postProcess` filters run on the resolved frame before present. **Stays entirely GPU-resident**: layers are render-pass attachments, filter inputs are sampler binds, never a CPU round-trip (the p5 `createGraphics`-as-uniform upload that made a prior project unusably slow). Layers are **premultiplied linear** (blur/bloom physically correct; tone-map+dither still once at present); `scale` renders a layer at fraction-res (fill-rate-bound effects); textures are pooled per frame-ring slot. **Depth-capturing targets** — a render target a 3D scene is drawn into carries a `depth32Float` MSAA attachment resolving (`.min`) to a sampleable buffer, so its meshes/points z-test correctly *and* the depth becomes a layer: `target.depth` exposes it as a gray layer (0 near … 1 far) via an `ollin_fx_depth_normalize` fullscreen pass that linearizes the clip-space depth over the camera's `near`/`far`, **sRGB-encoded so the existing perceptual `.defocus` decode reads it back exactly — the DoF shader is unchanged**; fed straight to `.defocus` (`scene.combined(with: scene.depth, .defocus(...))`) it's 3D depth-of-field, so set the camera `near`/`far` to bracket the scene. Two-tier opt-in keeps *2D never pays*: the depth attachment turns on only when 3D is recorded into the target (`Drawer` marks the `RenderTarget.needsDepth` flag from `drawMesh`/`drawPointCloud`/`drawDepthScene`), and the extra resolve+normalize only when `.depth` is read; a pure-2D target carries neither and is byte-identical to before. (Particles in a target still skip.) **Load-bearing batch invariant the depth path exposed:** every `GeometryBatch` must record *all* the `*Start` offsets — a batch's vertex count is `next.<kind>Start − this.<kind>Start`, so a creator that omits `meshStart` (the image/glyph/particle/depthScene begins did) zeroes the count of a *preceding* mesh batch (its `next` reads `meshStart 0`); harmless until a 3D mesh in a target is followed by `drawImage`/`drawCaption` (the `SceneDefocus` case), now fixed by all begins snapshotting `meshStart`. The no-targets path is byte-identical (gated on empty `renderTargets`/`filterOps`/`frameFilters`). **Compose DSL** (`Effects/Compose.swift`) — the declarative layer-stack surface over the substrate: `compose { layer { … }.post(_:).blend(_:).scale(_:) … }` makes a `renderTarget` per `layer`, draws into it via `withTarget`, chains its `.post` filters, and composites under its `.blend` (bottom-to-top in declared order). Pure sugar (a user can hand-write the same `renderTarget`/`withTarget`/`filtered`/`drawImage`); `ComposeLayer` is the public value type, `@ComposeBuilder` the result builder (so `if`/`for` build layers). One load-bearing detail: `layer(_:)`'s draw closure is `@escaping @_implicitSelfCapture` (it runs synchronously inside `compose` but is stored in the builder), so bare draw calls inside a `layer { }` need no `self.` — without the attribute the p5-style feel breaks (verified: the attribute propagates across module boundaries to example/test targets). **Multi-input combine** (`Effects/Combine.swift`) — the two-input sibling of `Filter`: `base.combined(with: aux, op)` reads *two* layers, covering what one-input filters can't. `Combine` is a `Sendable` value descriptor like `Filter`, but it can't hold the reference-type `RenderTarget`, so the aux rides alongside it and the op records a new `RenderTarget.Origin.combine(base:aux:op:)` case resolved in the *same* `filterOps` list as filters (record order guarantees both inputs — which must exist to be referenced — fill first). Six ops, each an `ollin_fx_*` fragment binding `[base, aux]` (the bind path already existed — bloom binds `[input, blurred]`; AO and SSR bind a third `normals` input too): `.mask` (multiply base by aux luminance/alpha, optional invert — premultiplied luma so coverage is honoured), `.displace` (offset base UV by aux RG recentred to ±amount), `.mix` (premultiplied cross-dissolve), and `.defocus` (depth of field — a circle-of-confusion bokeh gather with **near/far field separation** (architecture from the Catlike Coding DoF tutorial; the per-field gather is Gustafsson's running-average form, Tuxedo Labs / studied via LYGIA's `sample/dof`, Prosperity → reimplemented; README Techniques). The aux is read *perceptually* as a depth map (`linearToSrgb(luma)`, matching the depth-feed read so the gray you draw is the depth). Each tap is sorted by whether it's **nearer than focus** (foreground) or not into *two* accumulators, each a Gustafsson **running average** — `acc += mix(acc/tot, s, reach); tot += 1`, where `reach = smoothstep(radius±.5, sampleSize)` tests whether a tap's own blur spans its distance; a non-reaching tap adds the *current average* so every tap counts, which both kills grain (no variance from a varying effective-sample count → no per-pixel jitter needed) **and** blends overlapping bokeh. **Near/far separation is the load-bearing idea** a plain single-pass gather can't do: the *foreground* field carries a **coverage** that composites it *over* the background field, so a defocused foreground spreads over and *hides* an in-focus subject behind it (no sharp crescent). The sharp centre is then blended toward the bokeh by `max(centreDefocus, foregroundCoverage)` — so an in-focus subject stays crisp (and *correctly* occludes blurred things behind it with a sharp edge) unless a foreground blur covers it. Two supports: an **expanding golden-angle spiral** (`radius += radScale/radius`, ~`OLLIN_DOF_TAPS` taps, `radScale ∝ maxBlur²`) packs rings denser toward the rim so the bokeh edge is smooth without jitter; and a **seam dilation** (centre blur size = max over a small neighbourhood) consumes the thin CoC≈0 in-focus ring a hard depth edge leaves where its AA boundary crosses the focal plane (the dotted-circle artifact, found via a CoC-debug viz). Works on smooth/continuous depth (gradient, feed) **and** hard-edged discrete per-object depths with overlapping objects. The full artifact journey — bleed, dotted rings, seams, grain, occlusion cuts, and which fix addressed each — is in [[ollin-depth-of-field-gather-artifacts]]. The **`quality`** param is a `RenderQuality` tier the renderer resolves to a per-GPU bokeh tap budget (`resolveDofTaps`, hardware-relative like `shadowQuality`, passed in `params`; the shader's `OLLIN_DOF_TAPS` is now the fallback default) — the tap budget, not the blur radius, so `.detail` = creamier, `.performance` = faster, `maxBlur` is the blur amount. The surface **normal** comes from a dedicated **mesh-normal G-buffer** when the AO target holds meshes (a true view-space normal, stable at concave seams), and *falls back to one reconstructed from depth* when it doesn't (a hand-drawn depth map). The G-buffer is gated by `RenderTarget.needsNormals` (set when an `.ambientOcclusion` combine reads a 3D target), so a 2D sketch never pays and a 3D scene that doesn't run AO is byte-identical. The camera near/far + FOV the reconstruction needs are stamped on the depth layer at normalize time (`RenderTarget.depthReconstruction`, a unified perspective/ortho/intrinsic form) and read back through the combine's `aux` RenderTarget — the one non-trivial wiring, since the `filterOps` loop otherwise sees only textures. It runs in **two passes** (the canonical SSAO recipe — Crytek / john-chapman / LearnOpenGL, written from the technique): `ollin_fx_ssao` decodes the gray depth via `ollin_dof_depth`, takes the surface normal from the **mesh-normal G-buffer** when present (a true view-space normal stored by a dedicated MSAA mesh pass — `encodeMeshNormals` + `ollin_mesh_normal_vertex`/`_fragment`, with a *depth-aware* resolve `ollin_mesh_normal_resolve` (see the silhouette-flicker note below), mirroring the half-res field-shadow pass, NOT a second attachment on the shared geometry pass; stored in the same view space `ollin_ssao_viewpos` works in, so no transform), else rebuilds the normal as the better-facing of paired depth neighbours sampled **a few texels out** (load-bearing: a 1-texel stencil is comparable to the 16-bit depth layer's quantization step, so its normal stair-steps and bands the flat faces — the "dirty faces" bug), then samples a **dense low-discrepancy Fibonacci hemisphere kernel** oriented to that normal, projecting each sample back to the depth layer and counting it occluding when the visible surface there sits in front of it (within `radius` — a **range-check** `smoothstep(0,1, radius/|Δdist|)` that rejects across depth discontinuities). **The kernel choice is load-bearing, and was the crux of three wrong "fixed" claims @eaviles caught** (meta-lesson: judge a per-pixel artifact at *native resolution* on the affected faces, never a downscaled thumbnail): textbook SSAO rotates the kernel *per pixel* to break the coherent-silhouette banding a fixed *sparse/random* kernel paints onto faces as "**projected squares**", then blurs the resulting noise away — but that screen-space noise **crawls and flickers** in crevices as the camera turns. A dense Fibonacci kernel is near-isotropic, so it avoids the banding **with no per-pixel rotation at all**, leaving the estimate **geometry-locked** (it moves with the surface rather than crawling) — measured ~2× less flat-face noise than the rotated form, and flicker-free. Pass 2, `ollin_fx_ssao_blur`, is then a gentle **7×7 Gaussian depth-aware blur** (depth-weighted so it doesn't bleed AO across silhouettes and re-open the haloes — a *smooth*, not a denoise; the Gaussian spatial falloff keeps it soft, and the wider reach feathers the thin contact line the depth-aware normal resolve leaves at an internal silhouette so it reads as a soft contact, not a drawn line) that multiplies the base by the AO; `radius` is world units, `intensity` scales it, a modest `bias` clips flat-face self-occlusion, `quality` → `resolveSSAOSamples` (16/32/64). As a post-effect it darkens the final image, not just the ambient term (the screen-space trade). The **mesh-normal G-buffer** is shipped (above): a mesh scene feeding AO now occludes against a true view-space normal, so the concave-seam flicker the depth-reconstructed normal showed (its ambiguity wobbling frame to frame as the camera turned) is *much reduced* — @eaviles confirmed the live demo is much more stable. The static `ssao-3d` snapshot is *sub-tolerance* (the fix is temporal stability, not a gross static change), so it didn't re-record. The buffer also feeds **screen-space reflections** (the `.screenSpaceReflections` combine, below), which reads the same true view-space normal to build each reflection ray. **The silhouette-edge flicker is now cut** by making `encodeMeshNormals` an **MSAA-resolved** pass (it was the lone single-sample buffer, so an edge pixel toggled between the mesh normal and the cleared background sub-pixel while the scene depth it reads beside was already 8×-resolved — a silhouette-AA artifact, distinct from the (fixed) concave-seam ambiguity): a silhouette pixel now resolves to a coverage-weighted mesh normal (renormalized on read; the SSAO accept threshold dropped `> 0.5` → `> 0.001` so *any* coverage uses it instead of falling back to depth reconstruction), turning the binary normal↔zero snaps into smooth sub-pixel slides. Measured on the normal buffer (frame-to-frame across a ~0.5px camera nudge): hard flips 377→230, worst-case per-pixel jump 238→197, the rest redistributed into smooth gradients; all 61 snapshots stay within tolerance (the change only AA's ~1px silhouettes, so no re-record). **One MSAA wrinkle the box-average introduced, then fixed:** a plain hardware resolve is right at a mesh-vs-*background* silhouette (the background samples are the cleared zero, so the average is the front normal scaled by coverage) but at an *internal* silhouette — a near box's edge against a farther box — it blends the **front and back surface normals** into a tilted one that varies along the edge, tilting the AO hemisphere into a faint **dashed** occlusion line (@eaviles spotted this live as the residual special-case flicker). So the resolve is a custom *depth-aware* pass (`ollin_mesh_normal_resolve`): it averages **only the front surface's samples** (nearest covered depth, then the samples within half the covered depth span), so the stored normal matches the `.min`-resolved scene depth the SSAO reconstructs position from. Stores coverage-scaled (the box-average convention, so identical at mesh-vs-bg → the flicker fix is unchanged; the per-sample normal + depth therefore both `.store` and read back in the resolve). Verified the depth-aware resolve matches the plain MSAA on the flicker metric (497 vs 506 hard flips, both ~half of single's 937) **and** removes the dashing (the B-vs-C diff is exactly the dash pattern at internal edges; B striated, C smooth). One follow-on the depth-aware resolve exposed: the now-*continuous* contact line it leaves at an internal silhouette (correct, and a touch lighter than the box-average's dashes — the signed diff showed C lighter, not darker) reads as more drawn-on than scattered dashes in some views, so the **pass-2 AO blur was widened to 7×7 Gaussian** (above) to feather it. **Ahead (deferred, @eaviles-noted [[ollin-ssao-normal-gbuffer-followup]]):** any residual sub-pixel edge shimmer (8× MSAA isn't infinite; TAA-accumulation history is the lever); and a **raymarched SDF field** feeding AO still takes its normal from depth — @eaviles deferred routing its analytic 4-tap normal into the G-buffer (marginal for a smooth field, where depth reconstruction already works; it would only help fields with sharp subtract/intersect creases). **Screen-space reflections** are the sixth combine op, `.screenSpaceReflections(intensity:maxDistance:thickness:roughness:fresnel:edgeFade:quality:)` (`ollin_fx_ssr` + `ollin_fx_ssr_resolve`): reflect the rendered scene off its own surfaces, reading the aux as depth + the base's mesh-normal G-buffer — the exact three inputs (`base`/`aux`/`normals`) SSAO already wires, so **no new render-graph plumbing** (the same `needsNormals` gate in `recordCombine` extended to SSR, the same `applyCombine` two-pass shape, **byte-identical when unused** — all 62 snapshots green). Two passes mirror SSAO: a **trace** (`ollin_fx_ssr`) rebuilds view-space position + normal from the depth (`ollin_ssao_viewpos`, mesh G-buffer normal with the same depth-reconstruction fallback), reflects the eye ray `reflect(normalize(P), N)`, and **traces the reflection ray in screen space as a one-pixel DDA** (the canonical screen-space ray trace — **LYGIA `lighting/ssr` + McGuire-Mara**, studied from the references, *not* hand-rolled; the path @eaviles forced after three guess-and-patch rounds): project the ray's view-space endpoints to uv with **`ollin_ssao_project`** (the *shipped* inverse of `ollin_ssao_viewpos`), step **one pixel along the major screen axis** (`max(|dx|,|dy|)`, so the stride never grows — **uniform sampling is load-bearing**, a budget-capped stride that grows under-samples a long ray into vertical streaks, the bug this replaced), and accept a hit on a **depth-interval crossing** (McGuire-Mara): the ray's depth interval across the one-pixel step (`[prevRayDepth, rayDepth]`, perspective-correct via 1/depth lerp) brackets the surface depth, widened behind by `thickness` (the surface's assumed solid thickness, depth-relative). A *crossing* test, not a "near the ray line" distance (the `lineSDF` first cut) and not a single-point depth compare, is what rejects a ray that merely grazes a silhouette *beside* an object: it never crosses that object's depth. The surface must also face the ray (`dot(R, sceneNormal) < 0`, so the backs of objects don't reflect). **The "cylinder" was a multi-round debugging odyssey** @eaviles drove (the DoF/SSAO loop, third time). A sphere's floor reflection rendered as a constant-width **cylinder** (the bottom band smeared straight down) instead of a foreshortened ellipse, and the decisive clue was that it was **resolution-dependent**: correct at low resolution, a cylinder at high. *Two* resolution-dependent sampling bugs hid behind it, both rooted in stepping a fixed *pixel* count: **(1)** the depth fraction was `s = i / nSteps`, but a reflection longer than the step budget caps `nSteps` while the stride still reaches part way, so `s` over-read the depth to the ray's far end; **(2)** even fixed, a fixed *pixel* budget **truncates** a reflection that spans more pixels than the budget, cutting its far end into a flat-bottomed capsule (this one only showed once @eaviles moved to a *larger screen* than the exports). Both are fixed by the canonical **McGuire-Mara adaptive stride**: cover the *whole* ray in `≤ steps` coarse steps (`nF = clamp(majorStep, 1, steps)`, `frac = i / nF`), so the screen parameterization is always honest *and* the reach is resolution-independent, with a binary search pinning the crossing within the (now coarser) stride. `thickness` is depth-relative (`thickness · sceneDepth`, default 0.025), the interval test's solid-thickness tolerance. **Lessons (reinforced): a *resolution-dependent* artifact points at the sampling/parameterization, not the hit test (I burned rounds tuning thickness and swapping the hit test first); render the same frame at several resolutions side-by-side to localize it; and reproduce the user's *actual* resolution — the truncation was invisible until the live window grew past every export I'd tested.** The hit's base colour is sampled and written **premultiplied** by strength = `intensity` × Schlick-grazing `fresnel` (blend `mix(1, schlick, fresnel)`, so 0 = flat mirror, 1 = grazing rim) × `edgeFade` (border) × a **distance fade by the world length the ray travelled to the hit** (`smoothstep` over `[0.35, 0.9]·maxDistance`, physically motivated: a longer reflection path scatters more — and the lever that turns the genuine grazing-angle *stretch* of a reflection into a natural taper instead of a hard full-strength elongated "cylinder", the artifact @eaviles caught at a 23° camera). **The screen-space march is load-bearing, and the debugging is the cautionary tale @eaviles drove:** the first cut stepped a fixed *world*-space distance and forward-projected each step, which **samples unevenly under perspective and aliases into a diagonal moiré** — the spheres' reflections sheared and "fell in diagonal." A sequence of debug vizzes isolated it: a normal viz (`return float4(N*0.5+0.5,1)`) showed the floor normal was uniform/correct, a hit-uv viz showed the march landing in swirls/arcs, and a **single-sphere minimal scene rendered a *perfect* mirror** — proving the algorithm sound and the artifact a sampling/scene-density problem, not a math bug. **The debugging is the cautionary tale (the DoF marathon again):** the first cut hand-rolled a fixed-world-step march (diagonal moiré → shear), then a budget-capped screen-space stride (vertical streaks), then a refine-before-thickness depth-crossing (box-face arcs, then sphere fans) — three "fixed" claims @eaviles rejected, each a guess-and-patch that traded one artifact for another. The fix was to **stop guessing and study the references** ([[research-before-implementing]]): reading **LYGIA's `lighting/ssr` and OPENRNDR's McGuire-Mara port** showed the three things the hand-rolled march got wrong — a *grown* stride (vs one-pixel DDA), a depth-*difference* thickness (vs `lineSDF` perpendicular distance), and no back-face rejection. Reimplementing from the canonical algorithm made the floor, box, sphere, and cube reflections clean in one pass. The remaining residual is **inherent SSR**: a strongly *curved* surface reflecting a *nearby* object at its grazing silhouette fans slightly (a curved mirror magnifies a near reflection — even AAA engines defer mirror-finish curved surfaces to cubemaps/IBL), softened by `fresnel ≈ 0.8` (reflections concentrate at grazing, fade face-on) + a touch of `roughness`, and the example/snapshot use a glossy floor (a broad flat reflector, SSR's strength) under well-separated objects. **Lesson, reinforced: for a graphics technique, study the canonical algorithm + reference implementations *first*; don't reason-from-plausibility and patch.** Lessons: judge a per-pixel rendering artifact at native res, bisect with debug vizzes, and reduce to a minimal scene to separate an algorithm bug from a scene-stress artifact before declaring "fixed" — @eaviles rejected two premature "fixed" claims here ([[verify-perceptual-temporal-fixes]], [[research-before-implementing]]). The **resolve** (`ollin_fx_ssr_resolve`) is a depth-aware, roughness-scaled blur (single tap at `roughness 0` = sharp mirror) then a premultiplied over. `quality` → `resolveSSRSteps` (128/256/512 *coarse* steps (the adaptive stride covers the whole ray in this many, so it's a **precision** knob, not a reach cap — reach is resolution-independent) — a GPU-independent fidelity tier, like the raymarch resolution, + an `ssrStepsOverride` sweep hook + a `Scripts/benchmark.sh ssr` micro-bench; the cost is near-flat in the count on M2 (~12-17ms/1080²), so the tiers sit in the frame-rate bands). **v1 model:** a post-process over colour+depth+normal, so *every* surface reflects (modulated by Fresnel/angle), no per-material channel — a user-drawn reflectivity-mask 3rd input is a deferred follow-up (the combine path is 2-input, a 3rd is heavier plumbing). **Known limits (documented, not bugs):** off-screen/hidden geometry can't reflect (the screen-space limit; `edgeFade` hides the frame-edge cutoff); a reflection beyond `maxDistance` (world units) fades out at its tail (distance-faded); raymarched SDF fields / point clouds fall back to depth-reconstructed normals (only rasterized meshes feed the G-buffer). Linear-tracing technique from Sugu Lee + 3D-Game-Shaders-for-Beginners + the perspective-correct screen-space march of McGuire & Mara, written from the technique — README Techniques. **Temporal + spatial resolve** (the stability + cleanup pass): the op now runs **four** passes — `ollin_fx_ssr` (trace) → `ollin_fx_ssr_resolve` (spatial denoise) → `ollin_fx_ssr_temporal` (reproject + accumulate) → `ollin_fx_ssr_composite`. The **temporal** pass reprojects last frame's reflection by camera motion (reconstruct the receiver's view-space point with `ollin_ssao_viewpos`, lift it to world via the scene camera's `inverseView`, project through the *previous* frame's `viewProjection` to its prior uv), **neighbourhood-clamps** the sampled history to the current reflection's premultiplied-RGBA 3×3 AABB (rejects ghosting/trailing), then **exponential-blends** (the EMA weight is `resolveSSRAlpha` — .92/.88/.80 by tier). History is a renderer-managed `SSRHistorySlot` ping-pong keyed by the SSR op's **ordinal in the frame**, *not* an owner identity: a sketch makes its `renderTarget()` fresh each frame (unlike persistent `Feedback`/`SimField`), so there's no stable object to key on. The scene camera's `inverseView`/`viewProjection` ride on the depth layer's `DepthReconstruction` (the previous VP held per slot), and `usesFeedback` counts an SSR combine so the headless/export warmup converges. Measured ~45% off the worst-case contact-flash flicker. The **spatial** denoise in `ollin_fx_ssr_resolve` is a 3×3 conservative-smoothing despeckle (clamp an outlier pixel into its neighbours' range, edge-preserving via the local depth slope) plus a variance-aware gloss blur whose kernel is **dense (contiguous-texel), never strided** — load-bearing, since a strided kernel steps over the fine grazing-contact streaks and never smooths them. The march/blur/temporal run at `resolveSSRScale` (`.performance` half-res, `.default`/`.detail` full-res — **full on export**, so the snapshots stay within tolerance) and the composite upsamples. The remaining **contact-seam streaks** (a near-mirror reflecting a curved object's grazing silhouette, undersampled into radial dashes — confirmed present in the raw march *before* any denoise) are SSR's *inherent* limit, the case ray-traced reflections will answer next. ## Live reload — edit code, see it render (shipped via `OllinLive`)

The headline creative-coding feature, and it's built. `swift run OllinLive <path/to/Sketch.swift>` opens a window, watches the file, and on save recompiles *just that sketch* into a `.dylib` and hot-swaps it into the running loop — the window never closes. This is the Olive / canvas-sketch model (a persistent host owns the window; the sketch is the swappable unit), chosen over InjectionIII because that needs an external app and is finicky on the terminal `swift run` workflow Ollin lives in. Code is in `Sources/OllinLive/` (`main`, `FileWatcher`, `LiveSession`, plus `--selftest`/`--watchtest` headless smoke tests); the reusable loader `SketchLoader` lives in the **`OllinRuntime`** library (a small target shared with the examples gallery, kept *out* of the shipping `Ollin` framework so it stays free of dev-only tooling); the runner-side swap is `SketchRunner.reload(to:)` in `SketchView.swift`.

How it works, and the load-bearing decisions (most are cheap-to-forget, expensive-to-rediscover):

- **Host + swappable sketch dylib.** OllinLive is a SwiftUI `App`: its `WindowGroup` hosts a `SketchView`, which hands back the `SketchRunner` through its `onRunner` callback; the file watcher then drives `SketchRunner.reload(to:)`. `SketchRunner.sketch` is a `var`; the loop already calls `sketch.performDraw()` through the instance, so swapping the var means the next frame runs new code.
- **`-undefined dynamic_lookup`, not a dynamic Ollin product.** The sketch dylib compiles with `-I` pointing at the dirs that hold `Ollin.swiftmodule` and the C targets' module maps (to type-check `import Ollin`) and `-undefined dynamic_lookup` with *no* `-lOllin`; the host links `-Xlinker -export_dynamic` so the dylib's Ollin symbols resolve against the host at `dlopen`. Those `-I` dirs are **discovered, not assumed** (`SketchLoader.moduleSearchPaths`): the classic SwiftPM build puts them next to the executable (`<bin>/Modules`, `<bin>/<C>.build`), but the Xcode/Swift build system puts `Ollin.swiftmodule` directly in `<bin>` and the C maps under `.build/index-build/<triple>/debug`, so a `<bin>/Modules`-only assumption fails with "no such module 'Ollin'" (it did; the `--selftest` harness exercises exactly this). One copy of `Sketch`, so the loaded object casts as `Ollin.Sketch`. **A `.dynamic` Ollin product does not fix this** — SwiftPM still links the target statically into the executable, giving two copies and a failed cast (verified the hard way). Each load uses a unique `-module-name` so repeated reloads of the same class don't collide in the objc runtime.
- **A generated factory shim.** The loader regexes the `class …: Sketch` name and compiles a sibling `@_cdecl("ollin_make_sketch")` file alongside the user's source, so the user file is untouched and its `@main` is harmless (it compiles fine under `-emit-library`).
- **FSEvents on the *directory*.** Editors save atomically (temp file + rename), which breaks fd-based watches; `FileWatcher` watches directories with `kFSEventStreamCreateFlagUseCFTypes | …FileEvents` (the UseCFTypes flag is required or the path-array cast crashes), debounced ~150ms. It dispatches by extension: `.swift` → recompile + swap; `.metal` → `MetalRenderer.reloadLibrary(source:)` (live shader reload, active only when run from the repo); image assets → re-run `setup()` (a forward hook; image *loading* isn't a feature yet).
- **Resilience + threading.** Recompile runs off the main thread (the window keeps drawing the old sketch); the swap is marshaled to the main queue. A compile error is printed and the running sketch is left alone — a typo never closes the window. `MetalRenderer.reloadLibrary` builds the new pipelines before committing, so a bad shader edit can't blank the renderer.
- **State on reload: fresh restart by default; `--keep-clock` to continue.** `reload(to:keepClock:)` re-instantiates and re-runs `setup()`; by default it resets `time`/`frameCount`, and `--keep-clock` carries them forward (offsets `startTime` so `time` continues, copies `frameCount`) so an animation's phase doesn't jump. Either way instance state resets (fresh instance). `Sketch.onReload()` (lifecycle hook) fires once after the post-reload setup (never on first launch). Matches Olive/canvas-sketch.
- **Keep `Sketch`/`draw()` `open`** (already true) — the dylib subclass must override them; never `final`.

Window title: `"Ollin - <SketchName>"` (plain hyphen, not a middot). @eaviles ruled out FPS-in-the-title (the oF idiom); live FPS lives in the inspector panel beside the canvas (and, in the panel-less run modes, a click-toggled on-canvas stats overlay), not the title bar.

**GUI / parameter knobs — shipped.** A typed `@Param` wrapper/registry in the `Ollin` core (`Param.swift`, à la OPENRNDR `@DoubleParameter`) drives a SwiftUI `InspectorPanel` in the OllinLive host — a `NavigationSplitView` sidebar (`LiveRootView`) showing live performance stats plus a slider per knob. Because the host owns the panel, knob values *persist across reloads*: `LiveSession` records user-tuned values by name and re-applies them to each freshly loaded sketch (`syncParams`), so a knob doesn't snap back. Ties to the extension/lifecycle seam.

**Performance stats — a shared `FrameStats` feeding two surfaces.** The runner (`SketchRunner`) fills one `FrameStats` (`@Observable`: fps, CPU frame time, vertex/SDF draw counts, clock, canvas size) a few times a second — `statsSink`. The OllinLive inspector reads it (FPS / CPU / Geometry rows), and the same instance drives a click-toggled, draggable on-canvas overlay (`StatsOverlay` + the `OllinHUDCommands` `View ▸ Show FPS` command, bound via `@AppStorage(OllinHUD.showStatsKey)` so menu and overlay stay in sync and the choice persists). The overlay is *debug chrome, not in-canvas drawing*: a SwiftUI sibling of the Metal view, so it never lands in exports and needs no text rendering of our own — which is why it ships without the after-draw seam, text, or keyboard input the in-canvas version would have required. It's enabled in the panel-less run modes (standalone `swift run`, gallery) and **off in OllinLive** (the inspector already shows the same numbers — `SketchView(showsStatsOverlay:)` opts it out, and the live host omits the menu command). Two gotchas the build proved: the CPU-ms must time `performDraw()` *alone* — timing across `renderer.render()` includes the triple-buffer semaphore (vsync) wait and pins it to ~1/fps, telling you nothing; and the overlay's corner inset must be `.padding` *before* the canvas-filling `.frame`, or the padded box overflows and clips. This made `SketchView` a SwiftUI `View` that `ZStack`s the overlay over a private `MetalCanvas` — the `NSViewRepresentable` MTKView is now `MetalCanvas`, still the AppKit/UIKit-portability seam, with the public `SketchView` the composed view.

## Roadmap & design notes

Planned, in-progress, and eventual work is documented outside this file so the always-loaded guidance stays small:

- [`ROADMAP.md`](ROADMAP.md) — the public, contributor-facing roadmap: what's planned and how to help.
- [`DESIGN-NOTES.md`](DESIGN-NOTES.md) — the engineering design intent behind each planned item (the approach, the APIs involved, the reasoning).

**When work ships, it leaves these two files.** Drop it from `ROADMAP.md` (the roadmap stays forward-looking — what's *planned*, not a changelog) and record it instead under *Current state* above. Remove it from `DESIGN-NOTES.md` too, unless its design rationale still guides future maintenance or evolution (e.g. the conventions for extending the examples set), in which case keep only that part, not the status narration. Anything fully done and self-contained belongs in its own `Docs/` page or this file — not the roadmap, not the design notes.

**No status words in `ROADMAP.md` / `DESIGN-NOTES.md`.** They describe only what's *ahead*: never write "X landed / shipped / done" or a changelog aside into either file — a reader shouldn't be able to tell from them what shipped yesterday versus a year ago. When the shipped thing is one entry in a still-open *umbrella* item (the SDF shape catalog, a family of helpers), **drop just that entry and keep the umbrella** — don't annotate it as landed. (The `drawTriangle` commit got this wrong: it rewrote the catalog bullet to announce the triangle "has landed" instead of silently dropping it — the exact narration this rule forbids.) The ship checklist, every time something lands: **(1)** add it to *Current state* in this file; **(2)** remove it from `ROADMAP.md` (drop the entry; for an umbrella, the sub-entry only) with no "landed" note — and the README's Roadmap section is a short pointer with a one-line "what's ahead" list, so drop the item there too if it's named; **(3)** strip it from `DESIGN-NOTES.md`, keeping only rationale that still guides future work; **(4)** if it adds user-facing API, give it a `Docs/` page *and* wire it into both indexes (`Docs/README.md` and the README docs list) in the *same* commit — a commit that introduces a public concept but leaves `Docs/` untouched is missing its page; purely internal changes (a refactor, a renderer tweak) skip this and live only in *Current state*. Do all of this only once the work is actually verified (built and run) — don't pre-narrate unbuilt work as shipped.

Both live at the repo root, alongside `README.md`. The convention: the root holds project meta and contributor docs (`README.md`, `ROADMAP.md`, `DESIGN-NOTES.md`, this file, `LICENSE`, `THIRD-PARTY-NOTICES.md`), while [`Docs/`](Docs/) is the user-facing API reference (`Sketch`, `Drawing`, `Color`, …) — and nothing else.
