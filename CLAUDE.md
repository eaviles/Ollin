# Ollin — guidance for development

Ollin is a creative-coding framework for Swift + Metal (macOS). This file captures the design intent so work here stays coherent across sessions.

## Vision

**p5.js ergonomics on an OPENRNDR-grade core, with motion as the default.**

- The API people *type* should feel like p5: `setup()`/`draw()`, bare calls like `background(.white)`, `stroke(.black)`, `drawCircle(x, y, radius)`. That familiarity is the point — don't sacrifice it.
- The architecture they *grow into* should feel like OPENRNDR: typed value objects, an explicit `Drawer`, and composable geometry.
- `draw()` runs continuously at the display refresh rate. Animation is not opt-in — `radius: 120 + sin(time) * 40` just moves. `noLoop()` is the rare still-image escape hatch.

## Platform scope

Apple platforms only, by design. macOS is the focus today; iOS, tvOS, and visionOS are in scope as *future* targets (see the Swift Playgrounds / iOS follow-up and the 3D & visionOS follow-up). Linux and Windows are explicitly out of scope — not now, not later — so don't add cross-platform abstractions for them: lean on Metal, AppKit/UIKit, and SwiftUI freely. "No Linux/Windows" is not "macOS-only"; keep Apple-platform portability in mind (the `#if canImport(AppKit)`/`#if canImport(UIKit)` seams) so the iOS/visionOS work later isn't a retrofit.

## The architecture rule (load-bearing)

**The bare p5-style API is sugar over a public, typed core. Never make the facade the only path to a feature.**

- `Sketch`'s bare methods forward to an internal `Drawer` (see `Sources/Ollin/Sketch.swift`). Keep that split. Anything `drawCircle(...)` can do, the `Drawer` should also do — with more control.
- The day a capability is reachable *only* through the bare API, the ceiling is capped. Build the feature on the core first, then add the sugar.

## Conventions

- **Typed value objects early.** Geometry and color are data you pass around, transform, and compose — not just immediate draw calls. Prefer adding `Vector2`, `Rectangle`, and a vector `Shape`/`Contour` type *before* the call sites multiply; retrofitting `x:y:` doubles into `Vector2` later is expensive.
- **Swift-idiomatic, not a literal p5 port.** Enums for modes (not `"CENTER"` strings), trailing-closure scoping (`withState { }`) over leaky global state, value types, overloads. Borrow p5's feel, not its warts.
- **Build on the extension seam.** OPENRNDR's `extend(...)` is shipped: register a `SketchExtension` (`Sketch.extend`) for `setup`/`beforeDraw`/`afterDraw` (in-frame, before the render — can draw into the canvas), `afterFrame` (post-render, with `FrameInfo` timing), and `frameRendered` (post-render, with the rendered `CGImage`) hooks. New cross-cutting features — overlays, guides, recorders, the FPS stats (already the seam's first customer) — bolt on as extensions instead of bloating the core. Extensions are per-instance, so the runner re-attaches built-ins like the stats observer across live-reload swaps. The **frame-grab** hook is the seam's latest customer: `frameRendered(_:_:)` hands an extension the rendered frame, *opt-in* via `wantsRenderedFrame` (read live each frame, so a recorder can arm/disarm) so only something recording pays the GPU→CPU readback; on the live path it's served by an off-screen re-render (pixel-identical to export, keeps it off the present path — an async drawable readback is a later optimization). The same capture without a window is the public headless `OllinApp.image(of:frame:)` (returns a `CGImage`; `OllinApp.export` is the PNG wrapper over it), which is what the render-correctness snapshot tests diff against committed references.
- Drawing methods live on `Sketch` (scoped to the instance), not true globals — keep it that way.
- **Draw verbs, not nouns.** Geometry-emitting calls are imperative verb phrases with a `draw` prefix — `drawCircle`, `drawRect`, `drawLine`, `drawPolygon`, `drawPolyline`, never bare nouns (`circle`). They read as the side-effecting immediate-mode commands they are (what the Swift API Design Guidelines want), and the prefix gives a clean rule: `draw*` emits geometry; state (`fill`/`stroke`/`background`) and transforms (`translate`/`rotate`/`scale`) keep their own names. "Feels like p5" is the *shape* of the API — bare top-level calls, terse positional args, motion by default — not p5's literal spelling, so the prefix keeps the feel and stays a good Swift citizen. New primitives take it too (`drawEllipse`, `drawTriangle`, …). (oF landed here too: `ofCircle` → `ofDrawCircle`.)
- **Consistent point arguments.** A primitive that takes a point offers a *positional* scalar form and a *role-labeled* `Vector2` form: `drawCircle(x, y, radius)` beside `drawCircle(center:radius:)`, `drawRect(x, y, width, height)` beside `drawRect(corner:…)`/`drawRect(center:…)`, `drawLine(x1, y1, x2, y2)` beside `drawLine(_:_:)`, `translate(x, y)` beside `translate(_ offset: Vector2)`. The rule: bare scalars go positional — everyone knows the `x, y, radius` order, and labels on them are pure stutter once call sites pass `x`/`y` variables (`drawCircle(x: x, y: y, …)`). The label is reserved for the value-object overload, where it names the *anchor* (`center:` vs `corner:`) and carries real information. New point-taking primitives (`drawEllipse`, `drawPoint`, `drawTriangle`, …) follow the same split. (Unlike Kotlin/OPENRNDR, Swift can't make one declaration callable both ways, so don't double the overloads to fake "both" — pick positional for the scalar form.)
- **State stack reads as Swift.** The drawing-state stack is `pushState()` / `popState()` — the combined transform+style snapshot, mirroring Core Graphics' `saveGState`/`restoreGState` — with `withState { }` as the scoped, exception-safe primary form (the `with…{ }` idiom of `withAnimation`/`withTaskGroup`). Reach for `withState { }`; the bare pair is the escape hatch. Combined (not split into transform vs style) by design; a split push/pop can come later as `Drawer`-level methods.
- **Deprecation path is a 1.0 gate.** Pre-1.0 the public API churns freely with no shims (the README disclaims stability) — no external sketches to protect yet, so renames like the noun→verb (`circle`→`drawCircle`) and `push`/`pop`/`isolated`→`pushState`/`popState`/`withState` ship unshimmed. *Before* 1.0, stand up the migration discipline that holds from 1.0 on: every public rename/removal ships an `@available(*, deprecated, renamed: "…")` shim that forwards to the new API, so Xcode offers a one-click fix-it. Gotchas: use the *full selector* in `renamed:` when labels or arity differ (`@available(*, deprecated, renamed: "drawCircle(_:_:_:)")`, not just `"drawCircle"`); keep deprecated members together (a `Deprecations.swift`) so they're easy to audit and drop after a grace cycle; have the shim *forward* to the new API, not duplicate it. A must-do gate, not a nice-to-have — the 1.0 stabilization pass is where the pre-1.0 renames get their shims.

## Sourcing & attribution (load-bearing — it's the public face)

This project is built with AI and says so openly (README's "Built with AI" and "Influences & attribution" sections). Getting attribution and license-compatibility right earns the creative-coding community's trust — treat it as first priority, not a side chore.

The framework is *inspired by* p5.js (LGPL-2.1), OPENRNDR (BSD-2-Clause), and openFrameworks (MIT): borrow their ideas and API vocabulary, write the implementation independently. **Never translate their source line-by-line** — a port of source is a derivative work that carries the original's license, and p5.js's LGPL is incompatible with Ollin shipping wholesale as MIT. "Inspired by" keeps Ollin MIT-clean; "ported from source" does not.

**One sanctioned exception: bundled third-party source (a distinct tier).** A library may be *vendored* — shipped as actual source — when it's a self-contained, permissively-licensed component wasteful to reimplement, wrapped behind Ollin's own API so it stays swappable and off the public surface. This is the opposite of inspired-by (it *is* their code), so it carries license obligations: keep the upstream LICENSE + per-file headers **intact** in the vendored dir (the one exception to "no framework names in code" — they're the library's own headers, and stripping them breaks the license); record provenance (upstream URL, commit, date); list it in the repo-root `THIRD-PARTY-NOTICES.md`; add a *Bundled third-party code* line to the README's Influences section; keep the root `LICENSE` pure MIT so GitHub's root-only license detection holds the "MIT" badge. Vendor under `External/`, not `Sources/`. The first and only instance is **libtess2** (`External/CLibtess2`, SGI-B), the triangulator behind `Shape`/`Contour`. This tier is *not* a license to vendor copyleft (LGPL/AGPL/GPL) code, which stays inspired-by-only.

For ported *example sketches* (the iterate-by-porting workflow), provenance is per-sketch and must be honored:

- **Only port sketches whose license permits redistribution under MIT** — MIT, BSD, Apache-2.0, CC0/public domain, or CC-BY (with credit). For GPL/LGPL, CC-BY-NC, or CC-BY-SA sources, either get permission or rewrite the sketch as original work using the source only as inspiration (credit it as "inspired by").
- **Name the source in the file header** — the specific sketch, its author, a URL, and its license. Template lives in `Examples/README.md`.
- When unsure of a sketch's origin or license, **ask before committing it.** A trivial sketch (a plain dot grid) may fall below the copyright-originality bar, but crediting the inspiration is still the default.
- **Recreations** (`Examples/Recreations/`, organized by artist) credit the artist, framed as a homage *after* them (not a reproduction, not endorsed), plus the SFPC "Recreating the Past" class that inspired the section. Some are *ported* from a source sketch, so they also carry the code-lineage header (e.g. the Molnár ones, via the p5 repo); others are *original* Ollin interpretations built directly from the artwork, with no code lineage (e.g. the Riley one). Either way, name the artist and work and keep the homage framing. See `Examples/Recreations/README.md`.
- **Keep framework names — and product/lineage comparisons — out of code.** The influence story (p5.js / OPENRNDR / openFrameworks) lives in this file, the README, and commit messages — *not* in `.swift` comments. This is not limited to those three: it covers any *external product* reference (e.g. **Record3D** the capture app, SinkCam, Hydra) **and** *lineage/marketing comparison framing*. Don't write `// p5 default`, `/// like oF's ofNoise`, `// the own-app successor to borrowing Record3D's feed`, `// Ollin's own-app answer to X`, `// the way X does, but ours` — keep the information, drop the name *and* the comparison. (Ollin's *own* type/example names — `Record3DDevice`, `Camera`, `PhoneBodyPose` — are fine as plain internal cross-references, and Apple-framework API names actually in use — ARKit, Vision, usbmuxd — are fine; the prohibition is *external* product/framework names and *comparison framing*, not internal documentation.) Apply this *at authoring time*, not as a later cleanup, and when sweeping a file check *pre-existing* comments too — these have slipped into committed code before. The one *exception* is the per-example attribution header, which credits the actual source lineage. Source littered with running comparisons reads like a port and undercuts the "independent implementation, inspired-by not copied" stance.

There's a second tier of influence worth distinguishing from the conceptual one. Where p5.js / OPENRNDR / openFrameworks shaped the *API and ideas*, two peer Swift+Metal frameworks were read for *engineering approach* on the same platform: **swifty-creatives** (Apache-2.0, Processing-style immediate-mode) and **AsyncGraphics** (MIT, GPU image/video compositing). They were studied, not ported — specific lessons are noted inline through this file (shader build, pipeline cache, SDF circle, iOS seam, easing, snapshot testing). Same rules apply: credit them in the README and commits, never in `.swift` comments, and write our own implementation. The public credit lives in the README's Influences & attribution. (PixelKit is AsyncGraphics's older node-graph predecessor; cite AsyncGraphics instead.)

A third tier names influences for *capabilities still ahead* — shader-function collections, shader-composition / livecoding APIs, and AR. **These are inspirations, not dependencies:** *study how they work and reimplement our own*, never vendor or depend on them. It's especially clean for the shader-function collections — mostly implementations of *known, published techniques* (SDFs, noise, blends, color-space math, domain repetition): peek at the approach, then write Ollin's own, preferring the canonical source of a technique over any one collection's expression. Licenses still drive the no-line-by-line-copy rule:

- **LYGIA** (github.com/patriciogonzalezvivo/lygia, Patricio Gonzalez Vivo, who also created The Book of Shaders) — a large, multi-language catalog of shader functions (GLSL/HLSL/WGSL/CUDA plus an *experimental, partial* MSL/Metal port: `sdf`, `sampler`, `blend`, parts of `distort`/`generative`/`math` done; `lighting`/`geometry`/`palette` not yet). The best *map* of which techniques exist and how they're commonly approached. Licensed **Prosperity Public License 3.0.0** (noncommercial) — since we reimplement rather than ship its code, that's not a bundling problem; it's the reason to never translate a LYGIA file line-by-line and to implement from the underlying technique instead.
- **Hydra** (github.com/ojack/hydra, Olivia Jack) — a web livecoding environment with a chainable, analog-video-synth shader API (`osc().rotate().modulate(noise())…`). The thing to mine is *how it makes combining and mixing visuals so fluid* — borrow that ergonomic direction. Licensed **AGPL-3.0** (strong network copyleft) → **inspiration only**, never ported or vendored, exactly like p5.js's LGPL.
- **ShaderPark** (github.com/shader-park — `shader-park-core`, `shader-park-examples`, `shader-park-live-coding`, all **MIT**) — a JS→shader SDF "sculpting" library with composable combine/blend functions and its own livecoding environment; another reference for *how to compose and mix* shader-driven shapes. MIT, so it can be studied freely — still: write our own, credit it.
- **ofxFX** (github.com/patriciogonzalezvivo/ofxFX, Patricio Gonzalez Vivo again, **MIT**) — the openFrameworks effects addon behind his *Efecto Mariposa*: each effect is a ping-pong-FBO object chained/mixed with a `<<` operator, organized as composers (blend/mask/multi-texture), filters (blur, gaussian, bloom, glow, bokeh, **LUT color grading**, chroma aberration, old-TV), generative (noise, FBM, fire, Gray-Scott), and operations (ripples, flow, edge detect, normals). The reference for the [layered-effects](DESIGN-NOTES.md#layered-effects-and-compositing-not-started) *effect-object architecture and catalog* — blending fx shaders and LUTs — from the GL/oF generation, beside AsyncGraphics' Metal-native take. MIT, study freely — still: write our own, credit it.
- **Meta Spark** (Meta's discontinued AR studio, shut down Jan 2025 — no public source) — the *product* reference for an AR direction: its template-driven AR-effect authoring is the void @eaviles wants Ollin to fill on Apple platforms. Conceptual/product influence only; there's nothing to port. (Used in Zach Lieberman's AR class — keep that personal detail out of public files, see the AR follow-up.)

Same rules as every tier: credit in the README's Influences & attribution and in commits, never in `.swift` comments, own implementation.

## Shaders & the Metal back end

The shader set is one `.metal` file today; it will grow. Decisions that are cheap now and expensive to retrofit:

- **One source of truth for CPU↔GPU structs — defined once in a shared C header.** The three structs shared between Swift and MSL (`OllinVertex`, `Uniforms`, and `SDFInstance` — the last a stride-144 *tagged union* that keeps growing) live in `Sources/Ollin/Renderer/OllinShaderTypes.h`, so a field can't drift between the two sides and silently corrupt memory. Swift imports them through the thin `COllinShaders` C target (whose umbrella header re-includes the canonical file by relative path, since SwiftPM won't let a resource escape its target or two targets' dirs overlap); `Shaders.metal` `#include`s the same header. The one wrinkle the header note predicted: runtime `makeLibrary(source:)` has no include path, so `MetalRenderer.composeShaderSource` splices the header's text in for the `#include` directive before compiling — which is why the header ships *beside* the `.metal` as a `.copy` resource. The fields are spelled in the `simd_*` names the Swift importer maps to `SIMD2<Float>`/etc.; a `__METAL_VERSION__` guard aliases those onto Metal's `float2`/`float3x3`. **A new shared struct (or a wider `SDFInstance`) goes in that header — never re-declared in two places.**
- **Runtime source compilation is a feature, keep it.** `loadLibrary` compiles `Shaders.metal` from source at runtime (`makeLibrary(source:)`). For a creative-coding framework that's the seam for shader hot-reload and user-supplied shaders later — don't rip it out. Its costs are startup time and *no build-time error checking*.
- **Add a precompiled `default.metallib` when those costs bite, don't replace.** Build-time validation and zero startup cost need the built-in shaders compiled ahead of time. `loadLibrary` already prefers a precompiled `Bundle.module` metallib *before* the source path, so a precompiled lib slots in with no API change; runtime compilation stays for dynamic shaders. Two facts settle *how* to produce it (both verified on this toolchain — Swift 6.3, macOS):
    - **`swift run` does not compile loose `.metal`.** Dropping a `.metal` in the target as plain undeclared source only earns a `found 1 file(s) which are unhandled` warning; no metallib is produced and `makeDefaultLibrary(bundle: .module)` throws "no default library." That auto-compile is an *Xcode*-build-system behavior — how peer frameworks ship 100+ loose `.metal` files with no plugin — and it does not carry over to Ollin's `swift run` workflow. (And `.process(...)`/`.copy` on a `.metal` just copies it as *source*, never compiles it.)
    - **A precompiled `default.metallib` shipped as a `.copy` resource loads fine.** `xcrun metal` + `xcrun metallib` produce a `default.metallib`; `.copy`-listed in the target, it's found by `makeDefaultLibrary(bundle: .module)`. So under `swift run` the path is a SwiftPM build-tool plugin that runs that compile and emits the metallib as a resource. (Playgrounds plugin support is unreliable — see the iOS follow-up — so keep runtime source compilation too; never go plugin-*only*.)
- **A user-supplied shader-library seam is cheap.** Resolve the active library as `customMetalLibrary ?? defaultMetalLibrary` so a user can drop in their own compiled library without touching the built-ins; pairs with the runtime-source loader for hot-reload. (Both peer Swift+Metal frameworks expose exactly this.)
- **Built-in shader functions are our own, written from the technique — not a vendored library.** As the shader set grows past drawing (noise, SDF primitives, blends, color-space conversions, domain repetition), implement each from the *published technique*, then credit that source in the README's Techniques list (as the cosine `CosinePalette` and `curlNoise` already do). The canonical sources to reach for, baked in here so we go straight to them: **Inigo Quilez** for signed-distance functions (2D `iquilezles.org/articles/distfunctions2d`, 3D `/distfunctions`) and smooth-minimum, and the cosine palette (already used); **hg_sdf** (`mercury.sexy/hg_sdf`) for domain operators — axis rotation, mirror, and linear/polar repetition; **The Book of Shaders** for hashing and value noise. LYGIA is a broad *catalog/map* of which techniques exist and how they're approached — read it to discover, implement from the underlying technique, never translate its files (Prosperity; see [Sourcing & attribution](#sourcing--attribution-load-bearing--its-the-public-face)). (Distinct from the user-supplied seam above, which is for a *user's* own shaders, not for vendoring someone else's library into Ollin.)
- **Cache pipelines; don't grow `init`.** `MetalRenderer.init` builds one `MTLRenderPipelineState` inline. A new pipeline (textured quads, a new blend mode, compute) should be a cache lookup, not more code in the constructor. Key the cache on a `Hashable` descriptor struct (shader, blend mode, MSAA sample count, pixel format), not a flat enum: pipeline variants are *combinations* of those axes, and a struct key captures the product without an enum case per combination. Folding blend mode into that descriptor also keeps it a pipeline *parameter* — one pipeline factory — rather than a whole renderer subclass per blend mode (the trap a peer framework fell into).
- **Don't hard-code the single-file assumption.** `loadLibrary` looks up `Shaders.metal` by name. As shaders multiply, keep one umbrella file that `#include`s the rest, or enumerate the `.metal` resources — decide before the second file lands.

## Rendering performance (roadmap)

The drawing model is *immediate-mode GPU*: every frame `Drawer` tessellates each primitive into one flat triangle array on the CPU, the renderer uploads it to a **triple-buffered, semaphore-gated vertex-buffer ring**, and issues a single `drawPrimitives`. (That ring is load-bearing — never collapse it back to one shared buffer: writing a buffer the GPU is still reading for an in-flight frame tears the geometry on screen, e.g. gaps in a stroked ring. That was a real bug, fixed by the `maxFramesInFlight` ring + `frameBoundary` semaphore in `MetalRenderer`.) This is the right shape — it's what NanoVG, Dear ImGui, and Processing's GL renderer do — so the "low-level" look is the cost of a Metal core, not accidental complexity. Don't trade it for Core Graphics / SwiftUI `Canvas` / SpriteKit: those are CPU rasterizers or retained-mode scene graphs, and adopting one as the substrate throws away the GPU + shader ceiling the whole vision rests on.

Where it caps out, and the levers — in priority order, all *iterations on this pipeline, not rewrites*:

- **CPU tessellation is the first bottleneck, not the GPU.** Re-tessellating thousands of primitives every frame on the draw thread stalls long before the GPU breaks a sweat. Everything below attacks that cost.
- **Instancing is the biggest lever.** Upload one unit-circle mesh once and draw it N times with a per-instance buffer (center, radius, color) via `drawPrimitives(instanceCount:)`. CPU work per circle drops to a struct write; this is the "10,000 circles at 60fps" path. It's a new `Pipeline` case (`.instancedCircle`) plus a per-instance buffer — the cache seam already exists for exactly this.
- **SDF analytic primitives (point, circle, ellipse, rect, oriented box, line, circular arc, triangle, general 3-point triangle, quadratic Bézier, regular polygon, star, rhombus, vesica, oriented vesica, moon, cross, ring, trapezoid, parallelogram, egg, heart, cut disk, uneven capsule, horseshoe, parabola, rounded X, blobby cross, tunnel, stairs, cool S) — *shipped*.** `drawPoint`/`drawCircle`/`drawEllipse`/`drawRect`/`drawLine`, circular `drawArc`, `drawTriangle` (equilateral + isosceles), and `drawNgon`/`drawStar` are no longer tessellated: each is one instanced quad (`SDFInstance`, the `.sdf` `Pipeline` case). `SDFInstance` is a *tagged union* — a `shape` tag plus generic `size`/`param0`/`param1`/`param2`/`extra` slots — and `ollin_sdf_fragment` switches on it to evaluate the matching SDF, then runs a shared fill + stroke + anti-aliasing tail (iq's 2D distance functions, written from the technique). Per-shape CPU cost is one struct write — `Myriad` draws 8,100 circles at ~1,100 fps CPU ceiling. Each instance carries its own CTM (`float3x3`), so the fragment evaluates the SDF in local space and AA stays ~1px under any transform (`fwidth`); the quad covers `size` + ½ stroke + a small margin. (Circle approach studied from AsyncGraphics's circle shader, MIT — written independently.) The per-shape encodings — which param slot carries what and the `sd*` each calls (`drawPoint`'s round/square/diamond/cross/x markers, `drawNgon`/`drawStar` sharing one `sdStar`, the egg/heart/tunnel/stairs Y-flips, the three-point `drawTriangle` and `drawBezier` reading their free points from `param0`/`param1`/`param2`, and the rest) — live in `SDFShape` + `Shaders.metal`; all evaluate iq's distance functions and all region shapes use `regionCoverage`. One rule there is *not* safely discoverable from the code, so it stays: the four roundable shapes (rhombus/vesica/moon/cross) take a footprint-preserving `cornerRadius`, and vesica/moon must `opRound` off a *full-footprint* SDF — insetting the vesica's waist toward zero sends its derived circle radius/offset to ~1e7 and the shader's `sqrt(r²−d²)` loses all precision (a real glitch, fixed by the full-footprint form). **Coverage is split by whether a shape tiles, and it's load-bearing.** `box`, `pie`, `chord`, `triangle`, `star`/n-gon, and the non-round point `marker`s use an **inside-biased** ramp (`regionCoverage`: full to the geometric edge, AA halo only outside) so abutting fills — tiled grids, gradient bands, the rotated wedges that tile a cell in `LifeQuilt` — leave no seam; never move them onto the centered ramp or the seams return. The **disk (ellipse/circle/round point)** and **capsule/line** instead use **area-conserving** coverage (`diskCoverage` and the capsule case): a centered AA ramp, but any mark smaller than ~½px on screen keeps a ~1px footprint while its alpha scales by the true/clamped **area** (disk) or **width** (line). That makes sizes run from 0…n — tiny dots, small circles, and thin lines fade by area instead of popping in, snapping to a 1px floor, or flickering as they move — and it's safe because disks and lines never tile edge-to-edge, so they don't need the inside bias. (These area-conserving paths and every stroke band then run their coverage through `perceptualCoverage`, and the capsule/bézier footprint is the L2 gradient length rather than `fwidth` — both detailed in the linear-light bullet below.) **The other load-bearing piece is draw-order preservation:** `Drawer` records geometry into call-ordered `GeometryBatch`es (a run is `.triangles` or `.sdf`), so SDF shapes and tessellated triangles composite front-to-back as the sketch drew them — never collapse that into two unordered passes (it breaks occlusion, e.g. EllipseField's black-fill ropes). Still on the triangle path by nature: arbitrary `drawPolygon`/`drawPolyline`, and *elliptical* + full-turn arcs (`drawArc` runtime-branches `rx == ry` and sweep `< τ` to SDF, else tessellates). **Hollow/band mode** generalizes the ring's `opOnion` to every region shape: `hollow(_:)` / `solid()` set a per-instance `bandWidth`, and `regionFill` onions the shape's SDF (`abs(d) − bandWidth/2`) before `regionCoverage`, so the `fill` paints a constant-width band hugging the outline and an active `stroke` borders *both* edges (the framed-ring look stroke alone can't make). The band straddles the edge, so the covering quad grows by `bandWidth/2`; the `bandWidth` field fit the `SDFInstance` *tail padding*, so it forced no widening (the struct only grew later, to 144, for the three-point shapes' `param2`). Region shapes opt in via `SDFShape.honorsHollow`; points, lines, and the ring (already a band) opt out, and the round-dot point opts out by hand since it shares the `.ellipse` tag (a solid disk's area-conserving `diskCoverage` is bypassed for `regionFill` only when banding). **Stroke alignment** (`strokeAlign(_:)` → `.center`/`.inside`/`.outside`) rides the same coverage tail: `regionCoverage`/`diskCoverage` take a `strokeBias` (`0` / `−hw` / `+hw`) that shifts the stroke band off the edge (`abs(d − strokeBias) < hw`) while the fill still stops at `d = 0`, so the inset/outset is an exact SDF offset; `.center` (bias 0) is byte-identical to before. The 3-state align rides in **bits 8-9 of the `shape` tag** (the tag is < 256), so the vertex shader masks (`shape & 0xFF`) before the switch and align costs the instance no room; `.outside` grows the covering quad by another ½ stroke. Hollow forces the bias to 0 (a band already has two edges); lines/points/open-arc never compute a stroke band, so they stay centered.
- **More SDF primitives — the cheap catalog expansion (roadmap).** The tagged union has a *scalar budget* — `size`(2) + `param0`(2) + `param1`(2) + `param2`(2) + `extra`(1) on top of the per-instance CTM/center/colors/stroke — so any shape that's a *canonical form parameterized by a size + a ratio or two* drops in as the same four touch-points (an `SDFShape` case, a `Drawer.draw*` builder, an `sd*` function, a fragment `case`) with **no renderer/pipeline change**; position/rotation/scale come free from the CTM. One constraint: `size` is *not* a free slot — the vertex shader uses it as the covering quad's AABB half-extent, so it carries the bounding extent and can't double as a geometry point. All from iq's 2D distance functions, implemented from the technique and credited in the README's Techniques list (canonical-source and no-copy rules under *Built-in shader functions* above; **hg_sdf** is the source for the *operator* track below). More canonical iq forms drop in the same four touch-points whenever one's wanted. The two shapes that need **three free points** beside `size`-as-AABB — the **general 3-point triangle** and the **quadratic Bézier** stroke (`sdBezier`, the *fast* path for curved contours, exact AA, no tessellation) — forced the one widening so far: a `param2` (2) slot added to `SDFInstance` in the shared C header (one definition for both sides — see *One source of truth for CPU↔GPU structs* below), taking the stride 128 → 144; the 8 bytes of tail padding that left have since been claimed by the gradient-paint row fields, so the struct is *full* at 144 — the next field is a real widening. Two things stay *off* this list by nature: arbitrary polygon/polyline (variable vertex count — they stay on the triangle path / libtess2), and SDF *operators* (smooth-min, union/subtract, hg_sdf domain repetition) which *combine* fields and so belong to [shader-composition & layered effects](DESIGN-NOTES.md#shader-composition-and-live-coding-not-started), not the one-shape-per-instance primitive path.
- **MSAA is 8× where the device supports it** (else 4×), and only for the *triangle* path. The SDF primitives already bypass it (analytic coverage); the remaining triangle-path shapes (polygon/polyline, elliptical/full arcs) are where thin strokes or large zoom can still reveal that limit. The sample count is chosen once via `ollinPreferredSampleCount(_:)` (`SketchView.swift`) and shared by the live view and the export paths.
- **Rendering is gamma-correct (linear-light).** Geometry composites into a **linear `rgba16Float` intermediate** (`linearFormat`; the sRGB `.bgra8Unorm_srgb` `ollinColorPixelFormat` is now the *drawable*/present-target format, not the geometry target — see *HDR / float pipeline* under *Current state*), so the hardware blends and resolves MSAA in linear space — anti-aliased edges and translucent stacks composite physically, not with the too-dark fringes of a gamma-space blend, and the float precision means many overlapping translucent layers don't band as an 8-bit intermediate would. Three load-bearing pieces keep tones from shifting: (1) the shaders **linearize** their sRGB `Color` inputs before compositing and output linear into the float target (the *present pass* re-encodes to sRGB, not the geometry store); (2) the **background/clear color** is *also* linearized (`Color.srgbToLinear` in `mtlClearColor`) so the clear value lands in the float target as linear, matching the shaded geometry — miss this and the background washes out lighter (the clear bypasses the shader); (3) image textures load `.SRGB: true` so each sample decodes to linear, matching the linearized solid colors beside them. A triangular-PDF **dither** (a pure function of pixel position, so renders stay reproducible) is applied in `finalizeColor` — which now runs **in the present pass** (the single 8-bit quantization point, after tone-mapping the resolved float frame) — just before the 8-bit quantization to break the banding smooth gradients otherwise show. The image fragment still skips the dither (its source pixels are premultiplied; it outputs premultiplied linear straight into the float target). **One deliberate carve-out from pure linear light: stroke and disk/dot AA *coverage* is remapped to perceptual alpha** (`perceptualCoverage`, `1 − srgbToLinear(1 − c)`) before compositing. Linear blending makes a partially-covered dark mark read lighter than its coverage (a 50%-covered black pixel → sRGB ~0.74), so a thin diagonal line's correctly-conserved ink splits across the pixel staircase and reads faint/"beaded" — the bug that made the Molnár *Interruptions* field look chopped after the linear-light switch. The remap lands each covered pixel at the gamma-space darkness its coverage implies, so a 1px stroke is evenly dark at *any* angle and a sub-pixel mark still fades 0…n. It touches **only partial coverage** (`perceptualCoverage(1)=1`, `(0)=0`) and never a shape's own fill/stroke *alpha*, so solid interiors and translucent/overlap blending stay linear-light (solids still merge correctly). It's applied to the capsule/`drawBezier` strokes, `diskCoverage` (fill + outline), and `regionCoverage`'s **stroke** band — but **not** the region *fill* ramp, which stays plain linear so abutting fills tile seamlessly. Paired with this, the capsule/bézier footprint uses the **L2 gradient length**, not `fwidth`: a unit-gradient distance field's L1 norm overshoots √2× at 45°, which had been fading diagonal 1px lines as if sub-pixel. (Verified near-optimal for the raster path: 4× SSAA barely beats it — a 1px diagonal's residual softness is fundamental to native-resolution rasterization, see [`DESIGN-NOTES.md`](DESIGN-NOTES.md).)

Seam in place and now exercised: `MetalRenderer` builds pipelines through an enum-keyed cache (`Pipeline` + `makePipeline(_:)`) — `.solid` and `.sdf` today — so further pipelines slot in as new cases instead of more `init` code. Once variants multiply across blend mode × MSAA × pixel format, migrate that enum key to a `Hashable` descriptor struct (see *Cache pipelines* above) rather than enumerating the product by hand. (The CPU↔GPU structs feeding these pipelines live in the shared C header — see *One source of truth for CPU↔GPU structs* under *Shaders & the Metal back end*.)

Triangulator — *shipped, not hand-rolled.* The vector `Shape`/`Contour` type (concave polygons, holes) fills via **vendored libtess2** (the GLU tessellator lineage Processing/p5 descend from), wrapped in `Shape.triangulatedFill()` (`ShapeTriangulator.swift`, `import CLibtess2`) and drawn by `drawShape` on the triangle path. The fill rule is a per-`Shape` `winding: FillWinding` (`.evenOdd` default — nested contours become holes, a contour's direction doesn't matter — or `.nonZero`); `triangulatedFill()` maps it to `TESS_WINDING_ODD`/`TESS_WINDING_NONZERO`. **Font glyphs must be `.nonZero`** (the rule outlines are authored for): even-odd drops the region where a glyph's outline self-overlaps — e.g. the terminal of an `e`/`a`/`g`/`s` rendered as a flat *cut* (a real bug, fixed by giving glyph `Shape`s `.nonZero`), while simple glyphs (`o`, `l`) look the same either way. So `OutlineFont` builds glyph shapes `.nonZero`, and `Shape.mapPoints(_:)` (the point-transform helper used to place/warp glyphs — in `drawText(along:)`, `shifted`, the `OutlineText` warp) *preserves* `winding`; rebuilding a glyph via `Shape(contours:)` would silently reset it to even-odd and re-break the `e`. **A second glyph gotcha, distinct from winding: some system faces (San Francisco) build a glyph from *overlapping* sub-contours.** Even with `.nonZero`, the overlaps leave a faint hairline seam in the triangulated *fill* (visible inside the counters of `a`/`e`/`g`) and doubled edges in the *outline* (so a stroke, or dots sampled along the outline, double up where sub-contours cross). `OutlineFont.geometry(for:)` cleans each glyph with a Clipper2 union (`Shape.union` with an empty shape, normalizing it under nonzero) before triangulating, and feeds the **cleaned contours to both the fill and the returned outline** (so stroke/`textToShapes`/dots are clean too). Two load-bearing details: the union only merges cleanly when the curves are finely flattened, and **flatten density tracks the render size** (`CurveSampling`), so at small sizes the overlap stays coarse and the seam survives — so clean at a large **reference scale (1024)**, then scale the result to the render size; and that reference-scale flatten leaves the contours ~40× denser than the render size needs, which the per-frame stroke tessellation + fill bake then pay for *every frame* (a real 12→ fps regression), so **simplify** the cleaned contours back to a sub-pixel tolerance (Ramer–Douglas–Peucker, `OutlineFont.simplifyClosed`) before returning. All cached per `(glyph, size)`. (The niche `glyphRun` text-on-path/per-glyph path still flattens raw — a known follow-up.) libtess2 is bundled, not reimplemented — see the bundled-third-party-source tier in [Sourcing & attribution](#sourcing--attribution-load-bearing--its-the-public-face) (`External/CLibtess2`, SGI-B). Convex shapes (circle, rect, ellipse) and convex `drawPolygon` stay on the current fan/strip math; don't route them through the triangulator. Polyline-family strokes (`drawPolyline`, `drawPolygon` outline, `drawShape` contours) draw through `appendStrokedPath` (segment quads plus a per-vertex join filler), with a **configurable join and cap style**: `strokeJoin(_:)` → `.miter` (sharp, beveling past the miter limit — what keeps a star's tips clean) / `.bevel` (always flat) / `.round` (an arc fan over the outer gap), and `strokeCap(_:)` → `.butt` / `.round` (a half-disk fan) / `.square` (a flat ½-weight extension) on the *open* ends only (closed outlines have no ends). Round joins and round caps share one `appendArcFan` triangle-fan helper; the defaults (`.miter`/`.butt`) are byte-identical to before, so don't reach for `appendSegment` directly for multi-segment strokes. These are tessellated-path state, like `strokeAlign`'s tessellated exclusion: SDF shapes draw their own outlines and `drawLine`/`drawBezier` are round-capped capsules, so none of them honor join/cap. Curved outlines (quadratic/cubic Bézier + Catmull-Rom `curve`) **sample to points** via the public `Path` builder (`Path.swift` — `move`/`line`/`curve`/`quadCurve`/`cubicCurve`/`close`, plus `Contour`/`Shape(curveThrough:)`), surfaced as the closure sugar `drawShape { p in … }` and the top-level `drawCurve(_:closed:)`. They feed the same triangulated fill + stroked path, so a curve never touches the SDF/renderer side — the `Contour`/`Shape` data stays polygonal, the `Path` just flattens curves into it.

## Build, run, verify

```sh
swift run Example-HelloCircle   # opens a window running an example
```

The canvas is `1080×1080` by default (`canvasSize`, the typed `CanvasSize` enum — `.square(n)` / `.size(w, h)` + named presets, integer pixels); the preview window is sized from the sketch's `windowMode` (`.auto` fits the screen, `.fixed`, or `.resizable`) — the window is a scaled view of the canvas, not the canvas itself.

- **Requires macOS 26+ and a Metal-capable GPU.**
- **`swift build --target Example-X` does not relink the executable.** It compiles the module and reports success, but `.build/debug/Example-X` stays the *old* binary — a tuning loop against it silently re-runs stale code (a real hour lost: three "tuning" rounds of VideoTrace all ran the first build). Rebuild runnable examples with `swift build --product Example-X` or just `swift run Example-X`; reserve `--target` for compile-checking libraries.
- **Check the environment before claiming you can't build.** Ollin needs the Swift toolchain and Metal, which exist on a Mac but *not* in the Linux web/iPhone container. These two run on different machines, so don't assume: if `swift --version` and `xcrun --find metal` succeed, you're on a Mac with the toolchain — **build, run, and verify directly** (`swift build`, `swift run <Example>`), and don't add caveats about being unable to compile. Only when that toolchain is genuinely absent (the Linux container) are changes unverifiable on this machine — say so then, and not before. Either way, the things that truly need a simulator or device (iOS/visionOS/AR) stay unverifiable here regardless.

## Current state & roadmap

- **Today** (the shipped surface; per-feature design detail is in the relevant section above or in `Docs/`):
    - **Lifecycle & input.** `Sketch` base class; temporal state (`frameCount`, `time`, `deltaTime`, `frameRate`); mouse (`mouseX`/`mouseY`, `mouseIsPressed` for the held state, `mousePressed()`/`mouseReleased()` hooks — the held flag + release hook mirror the keyboard's, so drag-to-paint is a `draw()` poll, the way `DigitReader` stamps strokes) and keyboard (`key`/`keyCode`/`keyIsPressed`, `keyPressed()`/`keyReleased()` hooks, `isKeyDown(_:)` for held keys, named keys via the typed `KeyCode` enum).
    - **Rendering.** `Drawer` + Metal renderer (solid fills, stroked outlines, gamma-correct linear-light blending in a 16-bit-float intermediate that a final present pass tone-maps to the sRGB drawable — see *HDR / float pipeline* below, 8× MSAA where supported, output dithering) over two pipelines — a tessellated-triangle path and an instanced-SDF path — recorded into call-ordered batches so the two composite in draw order. **Blend mode** is drawing state on the stack (`blendMode(_:)`, saved by `withState`): `.normal` (default source-over) plus the fixed-function combining set `.add`/`.subtract`/`.multiply`/`.screen`/`.lightest`/`.darkest` (additive sums colors as *light*, the accumulation/sandpainting mode — best on a dark background). It rides as a parameter in the `Pipeline` cache key (`BlendMode` is part of the `Hashable` enum key, *not* a renderer path per mode — the trap the design notes warn against): a batch breaks when the blend mode changes and selects the matching pipeline, so it composes across all four pipelines (SDF, triangles, image, glyph) and the `.add` variant builds lazily on first use. Two load-bearing pieces: the factors are resolved per the fragment's **alpha convention** (`BlendMode.blendState(premultiplied:)` — straight-alpha for solid/SDF/glyph following the GL set, additive = `srcAlpha, one`; premultiplied for the image path, additive = `one, one`), and `.normal` reproduces the renderer's **original** factors exactly for both conventions, so existing renders stay byte-identical (pinned by the unchanged snapshots; the new `additive-blend` snapshot pins `.add`). Because the targets blend in linear light, `.add` sums physically. **HDR / float pipeline** (the compositing substrate): every frame's geometry composites into a **linear `rgba16Float` intermediate**, not the sRGB drawable. The geometry MSAA target is `.memoryless` (tile-only — the frame clears each time, so its samples needn't be backed by DRAM; the accumulation MSAA target stays `.private` since it persists), resolving to a single-sample float texture that a **final present pass** maps down: `Pipeline.present` (rasterSampleCount **1**, blending off, targets the display format) draws a fullscreen triangle (`ollin_present_vertex`/`ollin_present_fragment`) that scales by exposure, tone-maps, then `finalizeColor`s (sRGB-encode + the de-banding dither) into the drawable. So colors above 1.0 survive compositing (additive light) and many translucent blends don't band as 8-bit would. **Load-bearing consequence: the geometry fragments now output raw linear** — `finalizeColor` was *removed* from `ollin_fragment`/`ollin_sdf_fragment`/`ollin_glyph_fragment` (the image fragment was already premultiplied-linear) and moved to the present pass, the single 8-bit quantization point; the dither is a function of pixel coordinate, so it lands on the same pixels as before and an in-range SDR frame stays within snapshot tolerance. **`toneMap(_:exposure:)`** is a frame-wide `Drawer` mode (`Sketch.toneMap`, persists across frames like `accumulates`, *not* stack state — one mapping over the finished frame, so `withState` doesn't save it; `ToneMap` = `.clamp` default / `.reinhard` / `.aces`, mapped to the present shader via `shaderIndex`; `exposure` is a pre-scale, default 1). `.clamp` clips to [0,1] so the default look is unchanged; `.reinhard`/`.aces` roll highlights off (the glow/bloom + sandpainting look). The uniform rides the shared C header (`OllinPresentUniforms`). The drawable is now **single-sample** (`view.sampleCount = 1`) — MSAA lives in the float intermediate, so the renderer takes the MSAA sample count separately from the view's (the `init(sampleCount:)` is the MSAA count, fed `ollinPreferredSampleCount` directly). `Docs/HDR.md`; example `Basic/ToneMapping`; snapshot `tone-mapped-bloom`. **Accumulation surface** (`noClear()`/`clearEachFrame()` on `Sketch` → `Drawer.accumulates`, a *mode* that persists across frames, not stack state): when on, the renderer routes through a **persistent MSAA accumulation target** (float, kept `.private` so its samples survive — never memoryless — `loadAction = .load` unless the frame resets) resolved (`storeAndMultisampleResolve`) into a single-sample float texture, which the **present/tone-map pass** maps to the drawable (an ordinary render-into-drawable like the main path now — no byte-blit, no `framebufferOnly = false`; the float pile stays in linear so faint samples keep summing next frame). A frame *resets* (`loadAction = .clear` to the background color) only when the target is first allocated / resized or the sketch called `background(_:)` this frame (`Drawer.backgroundSetThisFrame`, the long-exposure reset) — so omitting `background()` accumulates without bound and calling it every frame mimics clear-each-frame. The present pipeline is shared (no new pipeline-key variant for accumulation), and the non-accum paths render through the same float substrate, so existing renders stay within snapshot tolerance (the `accumulation` snapshot pins the don't-clear build-up at frame 12). Headless export accumulates too: `MetalRenderer.accumulatedImage(...)` renders one frame into the persistent target, tone-maps into an sRGB display texture, + reads back, and the export drivers (`renderFrames`, `image(of:sketch:frame:)` looping frames 0…N) call it per frame; the **live frame-grab/texture hooks hand over the tone-mapped accumulation** (`accumulatedFrameImage(_:)`/`accumulatedTexture(_:)` — they take the drawer and run the present pass over the existing float pile rather than re-rendering, which would double-accumulate) so a consumer gets display-ready bytes, never the raw HDR float. It's now a **float surface** (faint <1/255 samples sum correctly, the precision the look needs), the **sandpainting track's foundation**: additive samples → don't-clear float accumulation → `toneMap` makes the playable DoF-particle prototype (examples `Basic/Accumulation` + `Basic/ToneMapping`, and `Basic/DepthOfField` — the dedicated sandpainting depth-of-field sketch: 3D Lissajous ribbons sampled **GPU-side** (a compute kernel regenerating ~10⁶ samples/frame — see *Compute & GPU particles* above) into accumulated bokeh, with energy-conserving area-uniform disc scatter, perspective-scaled foreground bokeh, drag-to-rack focus, and a per-channel colour-shift toggle for chromatic-aberration fringes; `Docs/Accumulation.md`, `Docs/HDR.md`). GPU texture is built **lazily on first draw and cached on the `Image`** (so loading needs no device, and the renderer owns no texture cache — the texture lives with the image); blends **premultiplied** (its own pipeline blend, source factor `.one`) since MTKTextureLoader keeps the CGImage's premultiplied alpha, loaded `.SRGB:true` so each sample decodes to linear for the gamma-correct (linear-light) blend. **Load-bearing texture-upload gotcha: `MTKTextureLoader` honors `.SRGB` only for ImageIO-backed CGImages.** A bitmap-context-made CGImage — a `CIContext`-converted camera frame, any user CG drawing — silently comes back as a *non-sRGB* texture holding the same sRGB bytes, so sampling skips the decode and the picture washes out lighter (linear→sRGB re-encode; found via the TrajectoryTracking example's synthetic feed, and it had been subtly washing the camera examples too). `Image.texture(for:)` self-heals: when the loaded texture's format isn't sRGB it rebuilds by hand (`sRGBTexture(from:on:)` — premultiplied-BGRA sRGB context draw + `replace(region:)` into `.bgra8Unorm_srgb`); pinned by `ImageTests.contextMadeImageRendersAtFaceValue`, and the `tinted-image` snapshot reference was re-recorded for the corrected (saturated, no longer pastel) render. Each `drawImage` is its own batch (one texture per draw). `resource:in:` can't default `in:` to `.module` (same bundle gotcha as fonts). **`tint(_:)`/`noTint()`** is drawing state on the stack: it sets the per-vertex tint the image vertex/fragment already carry (RGB recolors, alpha fades; nil = unchanged), so it needed no shader change. **Pixel get/set** is an `Image[x, y]` subscript over a CPU RGBA8 buffer (premultiplied, top-left origin) materialized lazily from the `cgImage` (the no-flip `CGContext` draw is already top-down — *don't* add a y-flip, it inverts it; pinned by `ImageTests`); a write flips `pixelsModified` so `texture(for:)` re-uploads — **straight from the pixel buffer into an `.rgba8Unorm_srgb` texture** (`sRGBTexture(premultipliedRGBA:…)`: no loader, no context redraw, no self-heal — ~5× faster per upload; read-only images keep the unchanged decode path, and the self-heal still covers context-made `CGImage`s without a buffer). Out-of-range reads return `.clear`, writes are ignored. The blank **`Image(width:height:color:)`** authors from scratch (fills the buffer, marks it modified), and **`Image(width:height:premultipliedRGBA:)`** wraps bulk-produced RGBA8 bytes directly as the image's own pixels — the fast lane per-frame publishers use (segmentation mattes/cutouts), since the texture uploads straight from the buffer. Still not yet: pixel-buffer batch ops, an *in-place* `replaceRegion` re-upload (each change allocates a fresh texture on purpose — an in-flight frame may still read the old one, the never-replace-in-place rule).

On top sits the reactive-ergonomics layer that most audio-visual sketches actually use: **`bands(_:)`** (the spectrum *shaped for drawing* — `count` log-spaced bars, adaptively normalized to ~0…1, with a fast-attack/slow-release envelope, so a bar height is a plain map to pixels with no hand-tuned gain) and **beat/onset detection** via spectral flux (a running-average threshold gated by a sample-counted refractory) surfaced as `beatCount` / `timeSinceBeat` / `beat` (a 0…1 decaying pulse) / `beatSensitivity`.     - **OSC** (the satellite `OllinOSC` library — `import OllinOSC`, kept out of the drawing core so `Ollin` stays free of `Network.framework`; the first of the *integration* tier). The typed core is the OSC 1.0 **wire format written from the spec** (no vendored library): an `OSCArgument` tagged enum (`i`/`f`/`s`/`b` + `d`/`h`/`T`/`F`/`N`/`I`, with literal conformances so `OSCMessage("/x", 0.5, 1, "go")` reads terse and a variable wraps by its case, `.float(x)`), `OSCMessage` (address + args), `OSCBundle`/`OSCTimeTag` (NTP), and `OSCPacket` with `encode()`/failable `init?(data:)` — **decode is total**: any malformed/truncated datagram returns `nil`, never traps (fuzz-tested), since the bytes come off the network. Transport is UDP over `Network.framework`: `OSCSender` (`send(_:)`/`send("/addr", args…)`, fire-and-forget) and `OSCReceiver` (`@unchecked Sendable`, mirrors the audio analyzer's serial-producer/locked-handoff model — datagrams decode on a private `DispatchQueue`, results cross to the main-thread reader through an `OSAllocatedUnfairLock`). The receiver offers **three read surfaces**: a *latest-value cache* (`float("/x")`/`int`/`string`/`bool`, `+default:`) for continuous controls polled in `draw()`; an *event drain* (`messages()` returns + clears everything since the last call, in order) for discrete triggers; and **`@Param` binding** (`bind("/radius", to: $radius, from: 0...1)` maps an incoming value into the param's range and assigns it) so an OSC address drives the same knob the inspector slider does. **`NWConnection`/`NWListener` are non-`Sendable`** but thread-safe, so they ride behind a private `@unchecked Sendable ConnectionBox` to satisfy strict concurrency in the `@Sendable` network callbacks. The binding required making core **`Param` thread-safe + `Sendable`** (its stored value moved behind an `OSAllocatedUnfairLock`) since it now has two writers (inspector on main, OSC on the network queue) — a legit core hardening, not OSC leaking into core. Tests are GPU-free (CI): wire-format round-trips + an in-process UDP loopback self-test. Example: `Examples/Integration/OSCLoopback` (self-contained — sends an animated position to itself on `127.0.0.1` and draws the dot from what it *receives*, so the picture is the round-trip; needs no second app, à la the audio `Spectrum`).

The typed core is the **MIDI 1.0 message format written from the spec** (no vendored library): a `MIDIMessage` value type — a `Kind` enum (`noteOn`/`noteOff`/`controlChange`/`programChange`/`channelPressure`/`polyPressure`/`pitchBend` plus the channel-less system real-time `clock`/`start`/`stop`/`continue`) plus a 1–16 `channel`, with convenience reads (`note`/`velocity`/`controller`/`value`/`isNoteOn`) and **total parsers** `init?(status:data1:data2:)` / `init?(umpWord:)` that return `nil` for anything unmodeled (a bare data byte, SysEx/MTC/song-position, MIDI-2.0/utility/data UMP word types) rather than trapping, since the bytes come off the wire (parser unit-tested exhaustively). A note-on with velocity 0 is normalized to `noteOff`; the reverse `bytes`/`umpWord` encoders round-trip and clamp out-of-range channel/data. Transport is the **modern Core MIDI UMP API** (`MIDIInputPortCreateWithProtocol` `._1_0`, event lists walked via `MIDIEventList.packet` offset + `MIDIEventPacketNext`; `MIDISendEventList`/`MIDIReceivedEventList` out): `MIDIInput` (`@unchecked Sendable`, mirrors `OSCReceiver`'s serial-producer/locked-handoff — parses on the Core MIDI thread, hands off through an `OSAllocatedUnfairLock`; connects every source at `start()` and reconnects hot-plugged ones on `msgSetupChanged`) and `MIDIOutput` (`open(to:)` to a hardware destination matched by name, or `openVirtual(named:)` to *publish* a virtual source). The input offers **four read surfaces**: a *latest control-value cache* (`controlValue(_:channel:)`, `+default:`), *held-note state* (`isNoteOn(_:channel:)`), an *event drain* (`messages()`), and **`@Param` binding** (`bind(controlChange:to:channel:from:)`, default input `0...127`). Same **render-thread SIGILL gotcha as audio**: the receive/notify blocks are formed in the non-`@MainActor` `MIDIInput` so the Core MIDI thread can call them without tripping the executor assertion. **New core feature this milestone: optional `@Param` smoothing** — `@Param(range, smoothing: .eased(duration:curve:) | .smoothed(minCutoff:beta:))` makes a knob *glide* into new values instead of snapping. `Param` now holds glide state and conforms to the internal `FrameAdvancing`, so it rides the **same per-frame advance pass as `@Eased`/`@Smoothed`** (found by the same reflection that already collects them — `@Param`s are sketch-level stored properties); `wrappedValue =` retargets (a no-op if unchanged, so it's safe to drive every frame) while `set(_:)` jumps (the live host's reload-restore uses `set(_:)` so a knob doesn't glide in from its default). Because softening lives **on the param**, it applies uniformly to MIDI, OSC, and inspector-drag — not just MIDI. Tests are GPU-free (CI): MIDI 1.0/UMP parse+encode round-trips, a guarded virtual-source→input loopback (soft-skips if the Core MIDI server is unavailable, runs for real on a Mac), and core `Param`-smoothing tests. Examples: `Examples/Integration/MIDILoopback` (self-contained — a virtual source sends stepped CC to itself and the bound smoothed `@Param` glides toward each step, so it runs with no hardware, à la `OSCLoopback`) and `MIDIMonitor` (lists every source and prints/draws each message — the tool for discovering what a controller sends; verified against a connected **Intech Grid EN16**).

The frame path is the GPU seam working as designed: `AVPlayerItemVideoOutput` (BGRA, Metal-compatible) → `CVMetalTextureCache` → `Image(texture:)` → `drawImage`, zero CPU copies; `frame` returns the previous image between decodes (a sketch draws faster than the video's fps) so there's never a gap. **Load-bearing details:** (1) the texture is created as **`.bgra8Unorm_srgb`** so sampling decodes to linear — the Syphon color lesson applied; verified live (no washout); (2) **no y-flip** — video pixel buffers are top-down, already matching Ollin's top-left image space; (3) a short ring (`inFlightTextures`, last 4) keeps each `CVMetalTexture` alive while in-flight frames may still read it — don't collapse it to a single retained texture; (4) Swift 6 wrinkles: the end-of-item observer token is `nonisolated(unsafe)` (read in nonisolated `deinit`), and the `[String: Any]` output attributes build in a `nonisolated` factory (`[String: any Sendable]`) to satisfy strict concurrency. **`snapshot()`** is the CPU companion (CVPixelBuffer → CIContext → `Image(cgImage:)`): pixel reads and vision `detect(in:)` work on it (a texture-backed `Image`'s CPU paths are inert), at a GPU→CPU copy per call. Tests are CI-safe (write a tiny clip with `AVAssetWriter`, then metadata/snapshot/Metal-gated-frame checks, each soft-skipping where the environment can't encode/decode). **The player is a `FrameSource`** (the core frame-source seam, below under *Computer vision*): a vision tracker attaches to a `VideoPlayer` the way it attaches to a `Camera` and analyzes the footage as it plays. The conformance attaches a **second `AVPlayerItemVideoOutput`** to the item plus a GCD-timer pump on a background queue (verified: two outputs on one item each receive every frame, so the tap never steals a decoded frame from the display path), converting via its own `CIContext` and delivering at the footage's cadence (`hasNewPixelBuffer` gates the ticks, so a paused video delivers nothing). Example: `Examples/Video/VideoPlayback`, looping a bundled CC BY-SA clip of the *Danza de los Voladores* (José Millán, via Wikimedia Commons — chosen for clean figure/sky separation, which is exactly what `Vision/VideoTrace` now exploits; trimmed + re-encoded to 1.5 MB; provenance in `THIRD-PARTY-NOTICES.md`, the El Fandanguito asset tier). Still ahead (deliberately not in this cut): routing the file's audio into `AudioAnalyzer` (an `MTAudioProcessingTap`); deterministic frame *pull* for the export paths (`copyPixelBuffer` by timestamp, so a sketch drawing a video exports the same frames every run).
    - **Physics** (the satellite `OllinPhysics` library — `import OllinPhysics`, kept out of the drawing core like the others, but for a *different* reason: it needs **no heavy framework** (no AVFoundation/Network/Core MIDI), just Ollin's `Vector2`/`Rectangle`, so the satellite split is purely to keep simulation *opt-in* as a capability tier — matching the prior art where physics is an add-on, not core, p5↔matter.js and oF↔`ofxBox2d`. Fold it into core later if wanted; nothing forces the split). The model is **Verlet with relaxation** (position-projection, Jakobsen-style), tuned for "a few hundred bodies that feel right", not exactness. Three types: **`Particle`** (a point mass — *no stored velocity*; it keeps `previous` and the velocity is `position - previous`, so `place(at:)` teleports without imparting velocity while `push(_:)` *adds* velocity by nudging `previous`; plus `applyForce`, `radius` for disk collision, `mass`/`inverseMass`, `pin()`/`pinned` = infinite mass, `userData`). **`Particle` is a `final class` — the one place Ollin reaches for reference semantics**, because springs and collisions hold and mutate the *same* particles by identity, not copies. **`Spring`** is a *positional distance constraint, not a force*: `length` (defaults to the pair's current spacing), `stiffness` 0…1 (`1` = rigid stick, less gives), `strain`; solved by a mass-weighted position nudge so the bounce comes through the implicit Verlet velocity for free. **`World`** (`final class`) holds `particles`/`springs` and the rules — `gravity` (points/s²), `drag` (velocity damping), `bounds` (optional `Rectangle` container) + `bounce` (wall restitution), `collisions` (opt-in disk separation, **broad-phased through a uniform spatial hash** — cell = 2·maxRadius, test the same + 8 neighbour cells with a `j>i` dedup, so it scales to thousands of bodies, *not* O(n²); **off by default**: a cloth doesn't want its own points colliding and it's a per-frame pass; radius-0 points never collide), `iterations` (relaxation passes), `maxTimestep` (dt clamp). `step(dt:)` integrates everything (**time-corrected Verlet** — scales the velocity term by `dt/lastDt` so a variable frame rate doesn't change speeds; `dt<=0` is a no-op, a large `dt` is clamped), then runs `iterations` passes of springs → collisions → bounds; every constraint edits *positions* and the velocity follows. Bounds/collision reflections nudge `previous` (the Verlet way); near-coincident disks separate along `unitX` to avoid a NaN normal. **Load-bearing gotcha: `drag` compounds per step**, so any non-zero drag freezes a *weightless* (gravity-`.zero`) field within seconds — perpetual-drift fields use `drag = 0` + elastic `bounce = 1` (this bit the Packing example: 0.004 looked motionless live within ~10s). **The same `World` also owns a rigid-body side, backed by vendored Box2D** (Erin Catto's v3.1.1, MIT — the bundled-third-party tier like libtess2: `External/CBox2D`, the `CBox2D` C target with a hand-written `include/module.modulemap` exposing the `box2d/box2d.h` umbrella; the upstream `src/`+`include/` layout is preserved so `#include "box2d/…"` resolves, and it compiles clean on Intel/SSE2 with C atomics needing no extra `-std` flag). It's a **hybrid by design** — the read of "Box2D under one World" that *doesn't* throw away the soft side: the Verlet `Particle`/`Spring` solver above is **untouched** (every existing example and test unchanged), and a Box2D world is added *inside* the same `World`, created **lazily on first `addBody`** so a pure particle/spring sketch never spins one up. `addBody(_:at:kind:density:friction:restitution:)` returns a **`Body`** (`final class` wrapping a `b2BodyId`): `position`/`angle`/`velocity`/`angularVelocity`, `mass`, `kind` (`.dynamic`/`.static`/`.kinematic`), `applyForce`/`applyImpulse`/`applyTorque`, `userData`. **`Collider`** is `.circle`/`.box`/`.capsule`/`.polygon` (the last hulled convex via `b2ComputeHull`, ≤8 verts). `connect(_:_:_:)` makes a **`Joint`** from a **`JointKind`** (`.revolute`/`.distance` (springy below stiffness 1)/`.weld`/`.prismatic`), and `grab(_:at:)` is the cursor-drag **mouse joint** (steer `Joint.target` each frame, `remove()` to release). The rigid side **shares** the world's `gravity`, `bounds` (rebuilt as static wall segments), `bounce` (wall + default contact restitution), and `drag` (body damping), and rides the same `step(dt:)` (4 sub-steps). **`pixelsPerMeter`** (default 100) bridges Ollin points ↔ Box2D meters (a 100-pt shape = 1 m, Box2D's sweet spot); the Verlet side ignores it. **Load-bearing gotchas:** (1) **Box2D's world pool is a non-thread-safe global**, so two `b2CreateWorld` calls racing across *parallel tests* corrupt it (a SIGILL) — every Box2D-touching test lives in one **`@Suite(.serialized)`** suite (the Verlet `PhysicsTests` never creates a rigid world, so it stays parallel); (2) a `Body` spawned *above* `bounds` is trapped against the ceiling wall — spawn it *inside* the box (this bit the `Tumble` drizzle). Tests are GPU-free (CI): the Verlet ones (gravity's ½·g·t², spring rest-length restoration, pinned-stays-put, disk separation + mass-weighted split, wall bounce, drag bleed) plus the rigid ones (a body falls/floors/settles, a stack holds, polygon+capsule mass, revolute holds its pivot, distance holds length, grab pulls to target, the raw-b2-API smoke test). Examples: `Examples/Physics/Packing` (256 colliding crosshair tokens drifting weightlessly and bouncing — scene composition *after @eaviles's sketch 2025.037*, but the physics is Ollin's own Verlet world, **not** a port of that sketch's elastic-collision math) and `Blobs` (soft bodies — a hub + spokes + rim ring of springs with colliding rim particles, drawn as a smooth filled `drawCurve` outline, under a slowly tilting gravity so the pile keeps sloshing). (The broad-phase is what makes Packing's 256 colliding tokens smooth in the live `swift run` *debug* path — the first cut was O(n²)×iterations and froze under load; `-c release` still helps batch export / very high counts.) Rigid examples: `Stack` (a pyramid of boxes that topples when you click to fire a ball), `Tumble` (a pile of mixed colliders — boxes/disks/capsules/random convex polygons — raining into a heap), and `Chain` (revolute-hinged capsule chains with weighted ends, grab-and-fling via the mouse joint).
    - **Computer vision** (the satellite `OllinVision` library — `import OllinVision`, kept out of the drawing core so `Ollin` stays free of `AVFoundation`/`Vision`; the perception capability tier, built out tracker by tracker). The substrate is the **modern Swift `Vision` API** (`DetectFaceLandmarksRequest().perform(on:)` → `[FaceObservation]`, async/typed — Ollin targets macOS 26 so it's used unguarded), wrapped behind Ollin's own types so the engine stays swappable. The modern API also covers the **stateful across-frames** trackers (object/trajectory tracking, image registration) as `StatefulRequest`s, so they *don't* need the classic `VNSequenceRequestHandler` after all — `ObjectTracker` re-`perform`s one `TrackObjectRequest` instance per frame and it carries tracking state internally (verified on the Intel Mac; classical, no Neural Engine). Three pieces: **`Camera`** (`@MainActor`, an `AVCaptureSession` frame source — `.video` permission *deferred until granted* like `AudioInput`, device selection `.default`/`.builtIn`/`.continuity`/`.external`/`.deskView`, publishes the latest frame as a drawable Ollin `Image` via a per-frame `CVPixelBuffer`→`CGImage` `CIContext` convert) feeding **`VisionAnalyzer`** (internal `@unchecked Sendable` engine that runs the registered trackers' requests on a detached background task and **drops frames it can't keep up with** — analysis is gated by an idle flag while the *display* frame is never dropped; the locked-handoff/`OSAllocatedUnfairLock` model from the audio analyzer) and the composable **trackers** (sixteen so far): **`FaceTracker`** (`FaceTracker(camera)`, read `.faces`) producing **`Face`** (bbox + 76-pt landmark regions + `roll`/`yaw`/`pitch` + capture `quality`), **`ContourDetector`** (read `.shapes(in:)` / `.contours(in:)`) producing **`DetectedContours`** (a tree of nested closed contours decoded into Ollin `Contour`/even-odd `Shape` — so a camera frame becomes *vector* geometry that flows straight into `drawShape`/SVG/hatching, the plotter pipeline `ofxCv` can't reach), and **`HandTracker`** (`HandTracker(camera, maximumHandCount:)`, read `.hands`) producing **`Hand`** (`chirality` + the 21 `HandJoint`s above a confidence floor, with `point(_:in:)`/`points(in:)`/`finger(_:in:)`/`bones(in:)` skeleton helpers and a `Finger` enum — gestures fall out of joint math, e.g. thumb-tip↔index-tip = pinch), and **`BodyTracker`** (read `.bodies`) producing **`Body`** (19 joints head-to-ankle above a confidence floor, with the same `point`/`points`/`bones(in:)` helpers over a hand-defined `Body.skeleton` joint-pair list), and **`RectangleDetector`** (read `.rectangles`) producing **`DetectedRectangle`** (four perspective corners → `corners(in:)` quad — *classical* CV, no ML model, so it runs on any Mac and was verified here numerically), and **`BarcodeScanner`** (read `.barcodes`) producing **`DetectedBarcode`** (decoded `payload` + `symbology` + `corners(in:)` — classical too, verified here by a CoreImage-generated-QR round-trip), and **`TextRecognizer`** (read `.lines`/`.text`) producing **`DetectedText`** (the OCR `transcript` + `corners(in:)`/`bounds(in:)`, `.fast`/`.accurate` levels — Apple's Live Text engine; it's an ML model but has a CPU path, so it *does* run on the Intel Mac and was verified here by a CoreText-rendered-text round-trip). The eighth is the first that **tracks** rather than detects: **`ObjectTracker`** (`ObjectTracker(camera)`, seed via `track(_:in:)`/`track(centeredAt:size:in:)`/`track(normalized:)`, read `.trackedObject`) producing **`TrackedObject`** (a followed box + `confidence`, `bounds(in:)`/`center(in:)`) — *classical*, runs here (verified by a synthetic moving-patch sequence test); it re-`perform`s one stateful `TrackObjectRequest` so it carries state across frames, and seeding from canvas space added the inverse map `VisionSpace.normalizedPoint`/`normalizedRectangle` (the existing forward `point`/`rectangle`'s reverse). The ninth *detects motion over time*: **`TrajectoryTracker`** (`TrajectoryTracker(source, trajectoryLength:minimumObjectRadius:maximumObjectRadius:)`, read `.trajectories`, `reset()` after a scene jump, offline `detect(across:frameRate:)`) producing **`DetectedTrajectory`** (a parabolic arc of small-object motion — a throw, a bounce — with `detectedPoints(in:)`/`projectedPoints(in:)`, the fitted `equationCoefficients` (sample past the last point to *predict* where it lands), `confidence`, and a stable `id` per arc for accumulating trails) — *classical*, runs here (verified by a synthetic thrown-ball sequence test *and* live). **Its load-bearing gotcha: `DetectTrajectoriesRequest` only detects through timestamped `CMSampleBuffer`s** — performing on a `CGImage`/`CVPixelBuffer` (even with `targetFrameTime` set) silently returns nothing, ever (probed both ways) — so the tracker wraps each frame in a sample buffer (`TrajectoryTracker.sampleBuffer(from:at:)`, BGRA `CVPixelBuffer` + `CMSampleTimingInfo`), timestamping live frames by arrival uptime (kept strictly increasing) and offline frames by index over `frameRate`. The tenth and eleventh are the first **per-pixel** trackers — segmentation, the people/subject *pixels* rather than boxes or joints: **`PersonSegmenter`** (`PersonSegmenter(camera, quality:)`, read `.matte`/`.cutout`; quality `.fast`/`.balanced` (live default)/`.accurate` (still default — it's also *Vision's own request default*, too heavy for live)) and **`SubjectSegmenter`** (read `.matte`/`.cutout`/`.count` — the salient-foreground "subject lift", objects as well as people; nothing lifted → `nil`/0, and the still `detect(in:)` returns `nil`), both *neural* (run on the M2; the tests run the real models — a synthetic bright disk genuinely lifts as a subject). Both publish the same pair, built by shared, **vImage-vectorized** CPU byte work (`SegmentationImages` in `Segmentation.swift`, deterministic + unit-tested — vectorization is load-bearing: the conversions run per analyzed frame and `swift run` is a *debug* build, where the hand-rolled per-pixel loops cost ~150 ms/frame at 720p and capped live segmentation at ~6 matte updates/s while the model itself takes ~11 ms; the vImage passes hold the low milliseconds, so analysis tracks the camera's ~30 fps cadence): **`matte`** — a premultiplied *white-alpha* `Image` (bytes `(m,m,m,m)`) so `tint()` recolors it into silhouettes/shadows/glows — and **`cutout`** — the frame × matte (matte rescaled to the frame), the background gone; the still path returns them as the `Segmentation` pair. **Two load-bearing gotchas:** (1) **`InstanceMaskObservation.allInstancesMask` holds instance *labels*** (0 background, 1, 2, …), **not a soft matte** — read as gray, a one-subject mask is 1/255 alpha, i.e. invisible (a real bug, caught by the disk test; the probe's `pixel(at:)` returning `1.0` was the raw label masquerading as full confidence). The soft mask is **`generateMask(for: allInstances)`** (OneComponent32Float, converted by `SegmentationImages.grayCGImage(from:)`); the person request's `observation.cgImage` *is* the soft matte directly. (2) **Publishing is the fast path, and its two pieces are deliberate.** Each analyzed frame builds the pair as **bytes-backed `Image`s on the analyzer thread** (`Image(width:height:premultipliedRGBA:)` — the texture uploads straight from the buffer, no CGImage round-trip, no main-thread sRGB self-heal; the getters hand back the *stored instance*, so repeated reads reuse the cached texture with no wrap cache needed), and each conversion is **gated by a wants-flag armed by that surface's first read** — a sketch reading only the matte never pays for the cutout, and an arming read can return `nil` once until the next analyzed frame publishes (the `wantsRenderedFrame` opt-in pattern; the live-wiring test must read *both* surfaces in its poll loop for exactly this reason). Draw matte/cutout into the *same rect* as the frame (no `VisionSpace` mapping — they're images, and rescaling lands the model-res matte on the picture). Matte-as-GPU-texture publishing remains the layered-effects-era upgrade. The twelfth measures *motion everywhere at once* — optical flow: **`FlowTracker`** (`FlowTracker(camera, accuracy:)` — `.low`/`.medium` (live default)/`.high`/`.veryHigh`, read `.field`, `reset()` after a scene jump; offline `flow(from:to:)` measures a still pair via `TargetedImageRequestHandler` and `flow(across:)` runs a sequence through the same stateful path the live tracker uses) producing **`FlowField`** (the dense motion field between consecutive analyzed frames, *queried rather than converted*: `vector(at:in:mirrored:)` answers "how is the picture moving under this canvas point" in canvas points, `samples(in:every:)` lays an arrow-ready grid, `averageFlow(in:)` is the global drift, `flowNormalized(at:)` the raw normalized surface) — *classical*, runs anywhere (verified by synthetic shifted-texture tests). **Its load-bearing facts, all pinned empirically:** the raw map stores the **backward** displacement in flow-map pixels with image y *down* (where each pixel of the newer frame came from), so `FlowField` negates and y-flips to expose forward motion in normalized (y-up) space — both components come out of `-dx, dy`; the map comes back at the input's own resolution; the stateful `TrackOpticalFlowRequest`, re-`perform`ed per frame like `ObjectTracker`'s, **does** produce flow on plain `CGImage`s (no sample-buffer requirement, unlike trajectories) with the first perform returning `nil` (flow needs a pair); **`flow(at:)` does no bounds clamping and traps** (EXC_BREAKPOINT inside Vision) when the scaled coordinate rounds past the last pixel — it's nearest-neighbor with `lround` semantics, so *any* x ≥ `(w − 0.5)/w` crashes, including 0.999999 and a particle sitting on the frame's right/bottom edge (a real crash, live within seconds; the tests missed it because none queried the far edge) — so `flowNormalized` clamps queries to the last pixel's exact coordinate `(w − 1)/w`, pinned by the edge-query regression test; and magnitudes are **conservative, accuracy-dependent estimates** (~⅔ of a known shift at `.high`, ~½ at `.medium` on synthetic texture) while *direction* is reliable — the docs steer sketches to scale by a gain of their own. Because every read goes straight to the observation's `flow(at:)`, publishing costs nothing per frame and needs no arming flags (`averageFlowNormalized` is a coarse 12×12 grid read at init). The thirteenth is the first with **no geometry at all** — image classification, *what's in the picture* rather than where: **`ImageClassifier`** (`ImageClassifier(camera, minimumConfidence:)`, default floor 0.1; read `.labels` (strongest first), `.top`, or by name — `confidence(of: "dog")` answers 0…1 for *any* vocabulary label, unfiltered, with spaces mapping to underscores — so a concept's confidence drives a knob; still `detect(in:)`, the vocabulary via static `supportedLabels()`) producing **`Classification`** (the underscored `label` identifier + `confidence` + display `name`) — *neural*, verified live here (the SceneLabels bars correctly named the living room: people/adult/art/frame/pillow). **Its empirical facts, pinned by probe:** `ClassifyImageRequest().perform` scores the **entire ~1,300-label vocabulary every time** (most near zero), so the tracker stores the full sorted list and applies the floor on read (`labels` prefixes the sorted list; `confidence(of:)` bypasses the floor); the taxonomy is **hierarchical** — one clear subject lights its whole lineage at *equal* confidence (blue_sky/sky/outdoor all 0.9062 on the voladores frame), so never de-dup by confidence value; `supportedIdentifiers` is sync and non-throwing; ~8–110 ms per classify on the M2, comfortably inside the live cadence. The fourteenth maps *what draws the eye* — saliency, "which parts of the picture matter" where segmentation answers "which pixels are the subject": **`SaliencyTracker`** (`SaliencyTracker(camera, mode:)` — `.attention` (default, trained on human gaze) / `.objectness` (where discrete objects are), the mode fixed at init so a sketch makes one tracker per mode; read `.heatMap` (a tintable white-alpha `Image`, the segmentation matte machinery reused) or `.regions` (`[DetectedRectangle]` — upright boxes here, read via the new `bounds(in:)` AABB helper added to the shared type), or query **`salience(at:in:mirrored:)`** — the salience under any canvas point, `0…1`, straight off the stored observation (the `FlowField` query model); still `detect(in:mode:)` returns the **`Saliency`** triple of the same surfaces) — *neural*, verified by real model runs in the tests (the attention heat genuinely centers on the synthetic disk; objectness boxes it). **Its empirical facts, pinned by probe:** the heat map is **always 68×68 OneComponent32Float**, whatever the input's size or aspect (the square map stretches over the frame — exactly what drawing it into the frame's rect does); `observation.heatMap.cgImage` *is* the soft map (the person-matte pattern, so `SegmentationImages.matteImage` consumes it unchanged); and **`PixelBufferObservation.pixel(at:)` is the same clamp-less nearest-neighbor family as `flow(at:)`**, so `salienceNormalized` clamps queries to the last pixel's exact coordinate (the optical-flow lesson re-applied preemptively, pinned by the edge-query test). Publishing follows the established split: the heat-map image conversion is armed by its first read (the segmentation pattern), while the observation and regions always publish (storing them is free and every query reads the observation directly, the flow pattern). The fifteenth puts the skeleton **in space** — 3D body pose from the same single 2D camera: **`BodyTracker3D`** (`BodyTracker3D(camera)`, read the singular **`.body`** — the model follows *one* person, the most prominent (probed: a group photo the 2D request finds 4 people in returns 1 observation); still `detect(in:)`) producing **`Body3D`** (`confidence` + `height`/`heightEstimation` (`.reference` = assumed-scale on depth-less frames — a webcam always reads 1.8 m; `.measured` only when the capture carried depth) + `distance` (meters to the pelvis root), with all 17 `BodyJoint3D` joints readable in **three spaces**: canvas `point`/`points`/`bones(in:)` exactly like `Body`'s, model-space `position(_:)`/`positions`/`bones()` (meters, root at the origin, x picture-right, y up, z away from the camera — project `(z, y)` and you've drawn the person from the side), and `cameraRelativePosition(_:)` (meters from the camera, z out the lens)) — *neural*, verified by a real-photo decode through the package API (a standing figure: head +0.79 m, ankles −0.93 m, 1.67 m from the camera). **Its load-bearing facts, all pinned by probe:** a fresh `DetectHumanBodyPose3DRequest` costs **~300–400 ms per perform** (its setup isn't cached process-wide) while re-performing one held instance runs ~21 ms on the M2, so the tracker builds **one request on the analysis task and re-performs it** (the `ObjectTracker` pattern — the 2D `BodyTracker`'s fresh-per-frame would cap live tracking at ~3 fps); `perform(on: CGImage)` detects directly (no sample-buffer requirement, unlike trajectories); **all 17 joints always report and there is no per-joint confidence** — joints out of view are the model's extrapolation and their `pointInImage` projections land *outside* 0…1 (an upper-body crop still yields full legs, projected below the frame), so the canvas helpers can return points outside the rect (documented, not clamped — the opposite of the 2D tracker's drop-what-it-can't-see); `pointInImage` is normalized lower-left origin (straight through `VisionSpace`); and positions come off the matrices' translation columns (`Joint3D.position` / `cameraRelativePosition(for:)` — the rotations stay off the public surface until something needs them). It also brought **`Vector3` into the `Ollin` core** (`Vector3.swift`: `Vector2`'s arithmetic surface generalized, plus `cross` returning a vector, `unitZ`, and `xy` dropping back to `Vector2`; no angle/rotation helpers — those wait for the 3D-mode transform work — so the first piece of 3D-mode groundwork landed early because a result type needed it). The sixteenth opens the catalog's far end — **any custom Core ML model**: **`ModelTracker`** (`ModelTracker(camera, modelAt:)` for an `.mlpackage`/`.mlmodel`/compiled `.mlmodelc`, `(camera, model:)` for a self-configured `MLModel`, `(modelAt:)` alone for stills) holds one `CoreMLRequest` (the modern `CoreMLModelContainer` wrapper) and re-performs it per frame, decoding **by observation kind** into whichever surfaces the model's outputs match: `ClassificationObservation`s → `labels`/`top`/`confidence(of:)` (the classifier shape over the model's own vocabulary — decode pinned live with MobileNetV2), `RecognizedObjectObservation`s → `objects` as the new **`DetectedObject`** (top label + confidence + `bounds(in:)`/`center(in:)` — pinned live with YOLOv3Tiny), and a `PixelBufferObservation` → the white-alpha `map` `Image` plus the clamped point queries `value(at:in:mirrored:)`/`valueNormalized(at:)`, **both built from one gray plane Ollin extracts itself** from the observation's stride-aware `cgImage` (internal `MapBytes`; value queries arm the plane, a `map` read also arms the drawable image; **`outputImage`** is the same observation decoded *at face value* — full color through the shared `SegmentationImages.colorRGBABytes` premultiplied context draw, armed by its own first read — the surface a style-transfer model's painted frame arrives through) — **never from `pixel(at:)`, which misindexes multi-channel (BGRA) buffers**, exactly what image-to-image models output (pinned by probe: 13/100 grid points agree with the observation's own `cgImage`, the rest scatter with no consistent offset — read live as diagonal banding over the picture, caught by a hand held up to the camera; still-photo scans had looked plausible because depth-map rows are self-similar). Queries and the drawable map therefore agree *by construction* — regression-pinned by an exact cell-for-cell test — at 8-bit resolution; the still path is the *instance* `detect(in:)` (the model is per-instance state, unlike the other trackers' static detects), returning **`ModelOutput`** — same surfaces, one value. The fourth decode kind is the **semantic-segmentation surface**: a `CoreMLFeatureValueObservation` whose multiarray is a 2D **class-index plane** (Int32, the DeepLabV3 form — `[H, W]` or with 1-sized dims squeezed; a Float plane rounds in; logits/embeddings reject) → `classMask` as **`ClassMask`** — presence (`presentClasses`/`presentLabels`, largest first) + `coverage(of:)`, clamped point queries (`classIndex`/`label(at:in:)`), and per-class white-alpha `mask(of:)` images (one vImage table-lookup each, memoized per result; class indices > 255 unrepresentable). The plane decodes in one fused unsafe pass (UInt8 plane + histogram) on the analyzer thread, armed by the surface's first read like the other conversions; the model's own vocabulary rides along, parsed at load from the `com.apple.coreml.model.preview.params` creator-metadata JSON (DeepLab's 21 PASCAL VOC classes, `labels[15]` = "person"). Two facts pinned by probe: the plane's **rows are top-down** (the voladores flyers land in the top rows — the regression shape that caught the mirrored queries elsewhere), and the modern `CoreMLRequest`'s default crop/scale action is **`scaleToFill`**, so the plane covers the **full frame** and stretching a mask into the frame's rect is geometrically right (the depth-map treatment). **Load-bearing empirical facts:** (1) **the compiled model must live at a stable path** — `compiledModelURL(for:)` compiles once into `Caches/Ollin/CompiledModels/<name>-<fnv1a of path|mtime|size>.mlmodelc` (FNV because `Hasher` is per-process-seeded) — since Core ML *specializes* a model for the compute device keyed to the compiled artifact *and the loading executable*: the first launch of a (re)built binary pays ~10 s for the small depth model (M2) while every later launch of the same build loads in ~50 ms, and compiling to a fresh temp path re-specializes every time (`swift test` stays warm across rebuilds because the stable `xctest` host binary does the loading — which is why the example, not the tests, exposed this); per-frame perform is ~25 ms. (2) **Loading runs on its own detached task**, kicked off by the first analyzed frame — `analyze` never awaits it, so frames pass by while it loads and co-registered trackers on the same source aren't stalled behind the load (the analyzer walks its trackers serially); `isLoaded` is the public signal, and a missing or unloadable file surfaces through `markUnavailable(_:)`, the direct-reason path added to `VisionStatus`. ## Live reload — edit code, see it render (shipped via `OllinLive`)

The headline creative-coding feature, and it's built. `swift run OllinLive <path/to/Sketch.swift>` opens a window, watches the file, and on save recompiles *just that sketch* into a `.dylib` and hot-swaps it into the running loop — the window never closes. This is the Olive / canvas-sketch model (a persistent host owns the window; the sketch is the swappable unit), chosen over InjectionIII because that needs an external app and is finicky on the terminal `swift run` workflow Ollin lives in. Code is in `Sources/OllinLive/` (`main`, `FileWatcher`, `LiveSession`, plus `--selftest`/`--watchtest` headless smoke tests); the reusable loader `SketchLoader` lives in the **`OllinRuntime`** library (a small target shared with the examples gallery, kept *out* of the shipping `Ollin` framework so it stays free of dev-only tooling); the runner-side swap is `SketchRunner.reload(to:)` in `SketchView.swift`.

How it works, and the load-bearing decisions (most are cheap-to-forget, expensive-to-rediscover):

- **Host + swappable sketch dylib.** OllinLive is a SwiftUI `App`: its `WindowGroup` hosts a `SketchView`, which hands back the `SketchRunner` through its `onRunner` callback; the file watcher then drives `SketchRunner.reload(to:)`. `SketchRunner.sketch` is a `var`; the loop already calls `sketch.performDraw()` through the instance, so swapping the var means the next frame runs new code.
- **`-undefined dynamic_lookup`, not a dynamic Ollin product.** The sketch dylib compiles with `-I <bin>/Modules` (to type-check `import Ollin`) and `-undefined dynamic_lookup` with *no* `-lOllin`; the host links `-Xlinker -export_dynamic` so the dylib's Ollin symbols resolve against the host at `dlopen`. One copy of `Sketch`, so the loaded object casts as `Ollin.Sketch`. **A `.dynamic` Ollin product does not fix this** — SwiftPM still links the target statically into the executable, giving two copies and a failed cast (verified the hard way). Each load uses a unique `-module-name` so repeated reloads of the same class don't collide in the objc runtime.
- **A generated factory shim.** The loader regexes the `class …: Sketch` name and compiles a sibling `@_cdecl("ollin_make_sketch")` file alongside the user's source, so the user file is untouched and its `@main` is harmless (it compiles fine under `-emit-library`).
- **FSEvents on the *directory*.** Editors save atomically (temp file + rename), which breaks fd-based watches; `FileWatcher` watches directories with `kFSEventStreamCreateFlagUseCFTypes | …FileEvents` (the UseCFTypes flag is required or the path-array cast crashes), debounced ~150ms. It dispatches by extension: `.swift` → recompile + swap; `.metal` → `MetalRenderer.reloadLibrary(source:)` (live shader reload, active only when run from the repo); image assets → re-run `setup()` (a forward hook; image *loading* isn't a feature yet).
- **Resilience + threading.** Recompile runs off the main thread (the window keeps drawing the old sketch); the swap is marshaled to the main queue. A compile error is printed and the running sketch is left alone — a typo never closes the window. `MetalRenderer.reloadLibrary` builds the new pipelines before committing, so a bad shader edit can't blank the renderer.
- **State on reload: fresh restart by default; `--keep-clock` to continue.** `reload(to:keepClock:)` re-instantiates and re-runs `setup()`; by default it resets `time`/`frameCount`, and `--keep-clock` carries them forward (offsets `startTime` so `time` continues, copies `frameCount`) so an animation's phase doesn't jump. Either way instance state resets (fresh instance). `Sketch.onReload()` (lifecycle hook) fires once after the post-reload setup (never on first launch). Matches Olive/canvas-sketch.
- **Keep `Sketch`/`draw()` `open`** (already true) — the dylib subclass must override them; never `final`.

Window title: `"Ollin - <SketchName>"` (plain hyphen, not a middot). @eaviles ruled out FPS-in-the-title (the oF idiom); live FPS lives in the inspector panel beside the canvas (and, in the panel-less run modes, a click-toggled on-canvas stats overlay), not the title bar.

**GUI / parameter knobs — shipped.** A typed `@Param` wrapper/registry in the `Ollin` core (`Param.swift`, à la OPENRNDR `@DoubleParameter`) drives a SwiftUI `InspectorPanel` in the OllinLive host — a `NavigationSplitView` sidebar (`LiveRootView`) showing live performance stats plus a slider per knob. Because the host owns the panel, knob values *persist across reloads*: `LiveSession` records user-tuned values by name and re-applies them to each freshly loaded sketch (`syncParams`), so a knob doesn't snap back. Ties to the extension/lifecycle seam.

**Performance stats — a shared `FrameStats` feeding two surfaces.** The runner (`SketchRunner`) fills one `FrameStats` (`@Observable`: fps, CPU frame time, vertex/SDF draw counts, clock, canvas size) a few times a second — `statsSink`. The OllinLive inspector reads it (FPS / CPU / Geometry rows), and the same instance drives a click-toggled, draggable on-canvas overlay (`StatsOverlay` + the `OllinHUDCommands` `View ▸ Show FPS` command, bound via `@AppStorage(OllinHUD.showStatsKey)` so menu and overlay stay in sync and the choice persists). The overlay is *debug chrome, not in-canvas drawing*: a SwiftUI sibling of the Metal view, so it never lands in exports and needs no text rendering of our own — which is why it ships without the after-draw seam, text, or keyboard input the in-canvas version would have required. It's enabled in the panel-less run modes (standalone `swift run`, gallery) and **off in OllinLive** (the inspector already shows the same numbers — `SketchView(showsStatsOverlay:)` opts it out, and the live host omits the menu command). Two gotchas the build proved: the CPU-ms must time `performDraw()` *alone* — timing across `renderer.render()` includes the triple-buffer semaphore (vsync) wait and pins it to ~1/fps, telling you nothing; and the overlay's corner inset must be `.padding` *before* the canvas-filling `.frame`, or the padded box overflows and clips. This made `SketchView` a SwiftUI `View` that `ZStack`s the overlay over a private `MetalCanvas` — the `NSViewRepresentable` MTKView is now `MetalCanvas`, still the AppKit/UIKit-portability seam, with the public `SketchView` the composed view.

- [`DESIGN-NOTES.md`](DESIGN-NOTES.md) — the engineering design intent behind each planned item (the approach, the APIs involved, the reasoning).

**When work ships, it leaves these two files.** Drop it from `ROADMAP.md` (the roadmap stays forward-looking — what's *planned*, not a changelog) and record it instead under *Current state* above. Remove it from `DESIGN-NOTES.md` too, unless its design rationale still guides future maintenance or evolution (e.g. the conventions for extending the examples set), in which case keep only that part, not the status narration. Anything fully done and self-contained belongs in its own `Docs/` page or this file — not the roadmap, not the design notes.

**No status words in `ROADMAP.md` / `DESIGN-NOTES.md`.** They describe only what's *ahead*: never write "X landed / shipped / done" or a changelog aside into either file — a reader shouldn't be able to tell from them what shipped yesterday versus a year ago. When the shipped thing is one entry in a still-open *umbrella* item (the SDF shape catalog, a family of helpers), **drop just that entry and keep the umbrella** — don't annotate it as landed. (The `drawTriangle` commit got this wrong: it rewrote the catalog bullet to announce the triangle "has landed" instead of silently dropping it — the exact narration this rule forbids.) The ship checklist, every time something lands: **(1)** add it to *Current state* in this file; **(2)** remove it from `ROADMAP.md` (drop the entry; for an umbrella, the sub-entry only) with no "landed" note — and the README's Roadmap section is a short pointer with a one-line "what's ahead" list, so drop the item there too if it's named; **(3)** strip it from `DESIGN-NOTES.md`, keeping only rationale that still guides future work; **(4)** if it adds user-facing API, give it a `Docs/` page *and* wire it into both indexes (`Docs/README.md` and the README docs list) in the *same* commit — a commit that introduces a public concept but leaves `Docs/` untouched is missing its page; purely internal changes (a refactor, a renderer tweak) skip this and live only in *Current state*. Do all of this only once the work is actually verified (built and run) — don't pre-narrate unbuilt work as shipped.

Both live at the repo root, alongside `README.md`. The convention: the root holds project meta and contributor docs (`README.md`, `ROADMAP.md`, `DESIGN-NOTES.md`, this file, `LICENSE`, `THIRD-PARTY-NOTICES.md`), while [`Docs/`](Docs/) is the user-facing API reference (`Sketch`, `Drawing`, `Color`, …) — and nothing else.
