# Ollin — guidance for development

Ollin is a creative-coding framework for Swift + Metal (macOS). This file captures the design intent so work here stays coherent across sessions.

## Vision

**p5.js ergonomics on an OPENRNDR-grade core, with motion as the default.**

- The API people *type* should feel like p5: `setup()`/`draw()`, bare calls like `background(.white)`, `stroke(.black)`, `drawCircle(x, y, radius)`. That familiarity is the point — don't sacrifice it.
- The architecture they *grow into* should feel like OPENRNDR: typed value objects, an explicit `Drawer`, and composable geometry.
- `draw()` runs continuously at the display refresh rate. Animation is not opt-in — `radius: 120 + sin(time) * 40` just moves. `noLoop()` is the rare still-image escape hatch.

## Scope — a framework, not an editor (load-bearing)

Ollin is a *framework* — a library of creative-coding techniques you call from `draw()` — not an *application* you open instead of writing a sketch. The framing that keeps this honest: Ollin is a curated **collection of creative-coding recipes/techniques exposed as a coherent Swift API**, so depth is always welcome *as more recipes a sketch can call*, never as application surfaces that replace writing the sketch. The test for a feature: is it a *capability a sketch calls*, or an *application surface that owns the workflow*? The first grows without bound and Ollin stays a framework; the second is the drift to resist — a full 3D editor, a DAW, a video NLE, a node-graph studio.

**Richer experiences live in host apps built *on top of* the framework, not in the core.** `OllinLive` (dev hot-reload), `OllinExamples` (the gallery), and `OllinLiveCoding` (the live-coding / live-performance instrument) are apps that *consume* Ollin — the same tier, and the right home for performance- or editor-*shaped* features. **Live coding and live performance are first-class use cases** Ollin aims to serve, through that app layer. Three rules keep the apps from dragging the core out of lane: the framework stays fully usable on its own; the `.swift` **sketch is always the artifact and the source of truth**; and any tool is a *lens on that source* (round-trips to `.swift`), never a proprietary document only the GUI can open. A **code editor is the in-lane kind of editor** — `OllinLiveCoding` live-codes the Ollin **Swift sketch itself** (not just the shader part) and *shows* that code to the audience (the Hydra model, where the code is the performance), which keeps code canonical; a GUI document editor that makes the sketch incidental is the out-of-lane kind. (The live-coding loop builds on the shipped dylib hot-reload engine — `SketchLoader` / `SketchRunner.reload`, the `--keep-clock` phase-carry — driven from an in-app editor with evaluate-on-command, since Swift compiles rather than `eval`s.)

**Where Ollin meets the pro tools, it interoperates rather than replaces.** The integration tier — Syphon, OSC, MIDI, virtual camera, tempo sync (sync *to* Ableton, never *be* Ableton), USDZ export — is "play in someone's existing rig," not "be the rig." That interop posture is the framework lane expressed in code.

## Platform scope

Apple platforms only, by design. macOS is the focus today; iOS, tvOS, and visionOS are in scope as *future* targets (see the Swift Playgrounds / iOS follow-up and the 3D & visionOS follow-up). Linux and Windows are explicitly out of scope — not now, not later — so don't add cross-platform abstractions for them: lean on Metal, AppKit/UIKit, and SwiftUI freely. "No Linux/Windows" is not "macOS-only"; keep Apple-platform portability in mind (the `#if canImport(AppKit)`/`#if canImport(UIKit)` seams) so the iOS/visionOS work later isn't a retrofit.

**Web / WebAssembly was considered and declined, on purpose.** WASM (via SwiftWasm) is the one path to p5's "share a sketch by URL" web reach — the incumbents' biggest on-ramp advantage Ollin structurally lacks — so it's worth recording *why* it stays out rather than re-litigating it. The browser has no Metal: a web build needs a *second renderer* on WebGPU, exactly the cross-platform renderer abstraction this stance refuses, and the web version would be a reduced subset anyway (WebGPU has no hardware ray tracing or MetalFX, so the photorealism/RT tier wouldn't port, and the Apple-framework satellites — Vision, audio, MIDI, video, ARKit, the iPhone sensor link — have no browser equivalent). The Metal-native bet and a browser runtime are mutually exclusive, and the bet wins. Web *reach*, when wanted, is served by *exporting the artifact* (video / GIF / USDZ / SVG) and the OS-surface outputs, not a live web runtime; the only WASM use that wouldn't betray the bet is compiling the non-rendering geometry/SVG core for a web *tool* that emits vectors. The bar that would reopen it: WebGPU reaching feature parity (ray tracing included) *and* strong, specific demand for in-browser sketches — until both, it stays out.

## The architecture rule (load-bearing)

**The bare p5-style API is sugar over a typed core. Never make the facade the only path to a feature.**

- `Sketch`'s bare methods forward to an internal `Drawer` (see `Sources/Ollin/Core/Sketch.swift`). Keep that split. Anything `drawCircle(...)` can do, the `Drawer` should also do — with more control.
- **What's public today is the typed *value* layer, not the `Drawer`.** The value objects (`Color`, `Vector2`, `Rectangle`, `Shape`/`Contour`/`Path`), plus `Shader`, `Filter`, and `Batch`, are public; `Drawer` is `internal`. So an outside extension composes those and reaches the GPU through `Shader` (`Docs/Tools/Extensions.md`); it cannot drive the drawer. Opening it is an unmade, 1.0-shaped call: direct immediate-mode control, against a large surface to keep stable afterwards. Don't describe the drawer as public until that call is made.
- The day a capability is reachable *only* through the bare API, the ceiling is capped. Build the feature on the core first, then add the sugar.

## Conventions

- **Typed value objects early.** Geometry and color are data you pass around, transform, and compose — not just immediate draw calls. Prefer adding `Vector2`, `Rectangle`, and a vector `Shape`/`Contour` type *before* the call sites multiply; retrofitting `x:y:` doubles into `Vector2` later is expensive.
- **Swift-idiomatic, not a literal p5 port.** Enums for modes (not `"CENTER"` strings), trailing-closure scoping (`withState { }`) over leaky global state, value types, overloads. Borrow p5's feel, not its warts.
- **Build on the extension seam.** OPENRNDR's `extend(...)` is shipped: register a `SketchExtension` (`Sketch.extend`) for `setup`/`beforeDraw`/`afterDraw` (in-frame, before the render — can draw into the canvas), `afterFrame` (post-render, with `FrameInfo` timing), and `frameRendered` (post-render, with the rendered `CGImage`) hooks. New cross-cutting features — overlays, guides, recorders, the FPS stats (already the seam's first customer) — bolt on as extensions instead of bloating the core. Extensions are per-instance, so the runner re-attaches built-ins like the stats observer across live-reload swaps. The **frame-grab** hook is the seam's latest customer: `frameRendered(_:_:)` hands an extension the rendered frame, *opt-in* via `wantsRenderedFrame` (read live each frame, so a recorder can arm/disarm) so only something recording pays the GPU→CPU readback; on the live path it's served by an off-screen re-render (pixel-identical to export, keeps it off the present path — an async drawable readback is a later optimization). The same capture without a window is the public headless `OllinApp.image(of:frame:)` (returns a `CGImage`; `OllinApp.export` is the PNG wrapper over it), which is what the render-correctness snapshot tests diff against committed references.
- Drawing methods live on `Sketch` (scoped to the instance), not true globals — keep it that way.
- **Draw verbs, not nouns.** Geometry-emitting calls are imperative verb phrases with a `draw` prefix — `drawCircle`, `drawRect`, `drawLine`, `drawPolygon`, `drawPolyline`, never bare nouns (`circle`). They read as the side-effecting immediate-mode commands they are (what the Swift API Design Guidelines want), and the prefix gives a clean rule: `draw*` emits geometry; state (`fill`/`stroke`/`background`) and transforms (`translate`/`rotate`/`scale`) keep their own names. "Feels like p5" is the *shape* of the API — bare top-level calls, terse positional args, motion by default — not p5's literal spelling, so the prefix keeps the feel and stays a good Swift citizen. New primitives take it too (`drawEllipse`, `drawTriangle`, …). (oF landed here too: `ofCircle` → `ofDrawCircle`.)
- **Consistent point arguments.** A primitive that takes a point offers a *positional* scalar form and a *role-labeled* `Vector2` form: `drawCircle(x, y, radius)` beside `drawCircle(center:radius:)`, `drawRect(x, y, width, height)` beside `drawRect(corner:…)`/`drawRect(center:…)`, `drawLine(x1, y1, x2, y2)` beside `drawLine(_:_:)`, `translate(x, y)` beside `translate(_ offset: Vector2)`. The rule: bare scalars go positional — everyone knows the `x, y, radius` order, and labels on them are pure stutter once call sites pass `x`/`y` variables (`drawCircle(x: x, y: y, …)`). The label is reserved for the value-object overload, where it names the *anchor* (`center:` vs `corner:`) and carries real information. New point-taking primitives (`drawEllipse`, `drawPoint`, `drawTriangle`, …) follow the same split. (Unlike Kotlin/OPENRNDR, Swift can't make one declaration callable both ways, so don't double the overloads to fake "both" — pick positional for the scalar form.)
- **State stack reads as Swift.** The drawing-state stack is `pushState()` / `popState()` — the combined transform+style snapshot, mirroring Core Graphics' `saveGState`/`restoreGState` — with `withState { }` as the scoped, exception-safe primary form (the `with…{ }` idiom of `withAnimation`/`withTaskGroup`). Reach for `withState { }`; the bare pair is the escape hatch. Combined (not split into transform vs style) by design; a split push/pop can come later as `Drawer`-level methods.
- **Deprecation path is a 1.0 gate.** Pre-1.0 the public API churns freely with no shims (the README disclaims stability) — no external sketches to protect yet, so renames like the noun→verb (`circle`→`drawCircle`) and `push`/`pop`/`isolated`→`pushState`/`popState`/`withState` ship unshimmed. *Before* 1.0, stand up the migration discipline that holds from 1.0 on: every public rename/removal ships an `@available(*, deprecated, renamed: "…")` shim that forwards to the new API, so Xcode offers a one-click fix-it. Gotchas: use the *full selector* in `renamed:` when labels or arity differ (`@available(*, deprecated, renamed: "drawCircle(_:_:_:)")`, not just `"drawCircle"`); keep deprecated members together (a `Deprecations.swift`) so they're easy to audit and drop after a grace cycle; have the shim *forward* to the new API, not duplicate it. A must-do gate, not a nice-to-have — the 1.0 stabilization pass is where the pre-1.0 renames get their shims.

## Sourcing & attribution (load-bearing — it's the public face)

This project is built with AI and says so openly (the README's "Built with AI" and "Influences & attribution" sections; the latter is a summary of the full credit record in the repo-root `ATTRIBUTION.md`). Getting attribution and license-compatibility right earns the creative-coding community's trust — treat it as first priority, not a side chore.

The framework is *inspired by* p5.js (LGPL-2.1), OPENRNDR (BSD-2-Clause), and openFrameworks (MIT): borrow their ideas and API vocabulary, write the implementation independently. **Never translate their source line-by-line** — a port of source is a derivative work that carries the original's license, and p5.js's LGPL is incompatible with Ollin shipping wholesale as MIT. "Inspired by" keeps Ollin MIT-clean; "ported from source" does not.

**One sanctioned exception: bundled third-party source (a distinct tier).** A library may be *vendored* — shipped as actual source — when it's a self-contained, permissively-licensed component wasteful to reimplement, wrapped behind Ollin's own API so it stays swappable and off the public surface. This is the opposite of inspired-by (it *is* their code), so it carries license obligations: keep the upstream LICENSE + per-file headers **intact** in the vendored dir (the one exception to "no framework names in code" — they're the library's own headers, and stripping them breaks the license); record provenance (upstream URL, commit, date); list it in the repo-root `THIRD-PARTY-NOTICES.md`; add a *Bundled third-party code* entry to `ATTRIBUTION.md` (the credits file the README links); keep the root `LICENSE` pure MIT so GitHub's root-only license detection holds the "MIT" badge. Vendor under `External/`, not `Sources/`. The first instance was **libtess2** (`External/CLibtess2`, SGI-B), the triangulator behind `Shape`/`Contour`; the current inventory (Box2D, Jolt, Clipper2, Syphon, Hosek-Wilkie, …) lives in `THIRD-PARTY-NOTICES.md`. A C++ library is reached through a hand-written `extern "C"` shim whose header is the target's `publicHeadersPath` (the CClipper2/CJolt pattern), never Swift C++ interop, so Swift only ever imports a C module. This tier is *not* a license to vendor copyleft (LGPL/AGPL/GPL) code, which stays inspired-by-only.

For ported *example sketches* (the iterate-by-porting workflow), provenance is per-sketch and must be honored:

- **Only port sketches whose license permits redistribution under MIT** — MIT, BSD, Apache-2.0, CC0/public domain, or CC-BY (with credit). For GPL/LGPL, CC-BY-NC, or CC-BY-SA sources, either get permission or rewrite the sketch as original work using the source only as inspiration (credit it as "inspired by").
- **Name the source in the file header** — the specific sketch, its author, a URL, and its license. Template lives in `Examples/README.md`.
- When unsure of a sketch's origin or license, **ask before committing it.** A trivial sketch (a plain dot grid) may fall below the copyright-originality bar, but crediting the inspiration is still the default.
- **Recreations** (`Examples/Recreations/`, organized by artist) credit the artist, framed as a homage *after* them (not a reproduction, not endorsed), plus the SFPC "Recreating the Past" class that inspired the section. Some are *ported* from a source sketch, so they also carry the code-lineage header (e.g. the Molnár ones, via the p5 repo); others are *original* Ollin interpretations built directly from the artwork, with no code lineage (e.g. the Riley one). Either way, name the artist and work and keep the homage framing. See `Examples/Recreations/README.md`.
- **Keep framework names — and product/lineage comparisons — out of code.** The influence story (p5.js / OPENRNDR / openFrameworks) lives in this file, the README, `ATTRIBUTION.md`, and commit messages — *not* in `.swift` comments. This is not limited to those three: it covers any *external product* reference (e.g. **Record3D** the capture app, SinkCam, Hydra) **and** *lineage/marketing comparison framing*. Don't write `// p5 default`, `/// like oF's ofNoise`, `// the own-app successor to borrowing Record3D's feed`, `// Ollin's own-app answer to X`, `// the way X does, but ours` — keep the information, drop the name *and* the comparison. (Ollin's *own* type/example names — `Record3DDevice`, `Camera`, `PhoneBodyPose` — are fine as plain internal cross-references, and Apple-framework API names actually in use — ARKit, Vision, usbmuxd — are fine; the prohibition is *external* product/framework names and *comparison framing*, not internal documentation.) Apply this *at authoring time*, not as a later cleanup, and when sweeping a file check *pre-existing* comments too — these have slipped into committed code before. The one *exception* is the per-example attribution header, which credits the actual source lineage. Source littered with running comparisons reads like a port and undercuts the "independent implementation, inspired-by not copied" stance.

There's a second tier of influence worth distinguishing from the conceptual one. Where p5.js / OPENRNDR / openFrameworks shaped the *API and ideas*, two peer Swift+Metal frameworks were read for *engineering approach* on the same platform: **swifty-creatives** (Apache-2.0, Processing-style immediate-mode) and **AsyncGraphics** (MIT, GPU image/video compositing). They were studied, not ported — specific lessons are noted inline through this file (shader build, pipeline cache, SDF circle, iOS seam, easing, snapshot testing). Same rules apply: credit them in `ATTRIBUTION.md` and commits, never in `.swift` comments, and write our own implementation. The public credit lives in `ATTRIBUTION.md` (linked from the README). (PixelKit is AsyncGraphics's older node-graph predecessor; cite AsyncGraphics instead.)

A third tier names influences for *capabilities still ahead* — shader-function collections, shader-composition / livecoding APIs, and AR. **These are inspirations, not dependencies:** *study how they work and reimplement our own*, never vendor or depend on them. It's especially clean for the shader-function collections — mostly implementations of *known, published techniques* (SDFs, noise, blends, color-space math, domain repetition): peek at the approach, then write Ollin's own, preferring the canonical source of a technique over any one collection's expression. Licenses still drive the no-line-by-line-copy rule:

- **LYGIA** (github.com/patriciogonzalezvivo/lygia, Patricio Gonzalez Vivo, who also created The Book of Shaders) — a large, multi-language catalog of shader functions (GLSL/HLSL/WGSL/CUDA plus an *experimental, partial* MSL/Metal port: `sdf`, `sampler`, `blend`, parts of `distort`/`generative`/`math` done; `lighting`/`geometry`/`palette` not yet). The best *map* of which techniques exist and how they're commonly approached. Licensed **Prosperity Public License 3.0.0** (noncommercial) — since we reimplement rather than ship its code, that's not a bundling problem; it's the reason to never translate a LYGIA file line-by-line and to implement from the underlying technique instead.
- **Hydra** (github.com/ojack/hydra, Olivia Jack) — a web livecoding environment with a chainable, analog-video-synth shader API (`osc().rotate().modulate(noise())…`). The thing to mine is *how it makes combining and mixing visuals so fluid* — borrow that ergonomic direction. Licensed **AGPL-3.0** (strong network copyleft) → **inspiration only**, never ported or vendored, exactly like p5.js's LGPL.
- **ShaderPark** (github.com/shader-park — `shader-park-core`, `shader-park-examples`, `shader-park-live-coding`, all **MIT**) — a JS→shader SDF "sculpting" library with composable combine/blend functions and its own livecoding environment; another reference for *how to compose and mix* shader-driven shapes. MIT, so it can be studied freely — still: write our own, credit it.
- **ofxFX** (github.com/patriciogonzalezvivo/ofxFX, Patricio Gonzalez Vivo again, **MIT**) — the openFrameworks effects addon behind his *Efecto Mariposa*: each effect is a ping-pong-FBO object chained/mixed with a `<<` operator, organized as composers (blend/mask/multi-texture), filters (blur, gaussian, bloom, glow, bokeh, **LUT color grading**, chroma aberration, old-TV), generative (noise, FBM, fire, Gray-Scott), and operations (ripples, flow, edge detect, normals). The reference for the [layered-effects](DESIGN-NOTES.md#layered-effects-and-compositing) *effect-object architecture and catalog* — blending fx shaders and LUTs — from the GL/oF generation, beside AsyncGraphics' Metal-native take. MIT, study freely — still: write our own, credit it.
- **Paper Shaders** (github.com/paper-design/shaders, paper.design, **Apache-2.0**, shaders by Ksenia Kondrashova) — production design-shader effects for the web: mesh gradients, liquid metal, fluted glass, god rays, water, heatmap, paper texture, dithering/halftone. The map of which *designer-facing* effects exist and their parameter feel — the design-pattern `Generator` set was cross-read against it (written from the canonical techniques, credited per-technique in `ATTRIBUTION.md`), and the design-filter set (fluted glass, water, paper texture, liquid metal, heatmap, gem smoke) was cross-read the same way. Permissive, so study freely — still: write our own, credit it.
- **Meta Spark** (Meta's discontinued AR studio, shut down Jan 2025 — no public source) — the *product* reference for an AR direction: its template-driven AR-effect authoring is the void @eaviles wants Ollin to fill on Apple platforms. Conceptual/product influence only; there's nothing to port. (Used in Zach Lieberman's AR class — keep that personal detail out of public files, see the AR follow-up.)

Same rules as every tier: credit in `ATTRIBUTION.md` and in commits, never in `.swift` comments, own implementation.

## Shaders & the Metal back end

The shader set is split across several `.metal` segments (`Renderer/Shader*.metal`), concatenated and compiled as one library at runtime (see *The shader set is multiple segments* below). Decisions that are cheap now and expensive to retrofit:

- **One source of truth for CPU↔GPU structs — defined once in a shared C header.** The three structs shared between Swift and MSL (`OllinVertex`, `Uniforms`, and `SDFInstance` — the last a stride-144 *tagged union* that keeps growing) live in `Sources/Ollin/Renderer/OllinShaderTypes.h`, so a field can't drift between the two sides and silently corrupt memory. Swift imports them through the thin `COllinShaders` C target (whose umbrella header re-includes the canonical file by relative path, since SwiftPM won't let a resource escape its target or two targets' dirs overlap); `ShaderCore.metal` (the first segment) `#include`s the same header. The one wrinkle the header note predicted: runtime `makeLibrary(source:)` has no include path, so `MetalRenderer.composeShaderSource` splices the header's text in for the `#include` directive before compiling — which is why the header ships *beside* the segments as a `.copy` resource. The fields are spelled in the `simd_*` names the Swift importer maps to `SIMD2<Float>`/etc.; a `__METAL_VERSION__` guard aliases those onto Metal's `float2`/`float3x3`. **A new shared struct (or a wider `SDFInstance`) goes in that header — never re-declared in two places.**
- **Runtime source compilation is a feature, keep it.** `loadLibrary` concatenates the `.metal` segments and compiles them from source at runtime (`makeLibrary(source:)`). For a creative-coding framework that's the seam for shader hot-reload and user-supplied shaders later — don't rip it out. Its costs are startup time and *no build-time error checking*.
- **Add a precompiled `default.metallib` when those costs bite, don't replace.** Build-time validation and zero startup cost need the built-in shaders compiled ahead of time. `loadLibrary` prefers a precompiled `Bundle.module` metallib *before* the source path **on a non-ray-tracing device** (an RT device source-compiles, to splice in the device-conditional `OLLIN_RT_SHADOWS` define), so a precompiled lib slots in with no API change; runtime compilation stays for dynamic shaders. Two facts settle *how* to produce it (both verified on this toolchain — Swift 6.3, macOS):
    - **Ship `.metal` as `.copy` (raw source) — `.process` now precompiles a metallib.** Ollin compiles its shaders from source at runtime, the seam the shader hot-reload, user shaders, *and the device-conditional `OLLIN_RT_SHADOWS` ray-traced-shadow path* all rely on — so the raw `.metal` must reach `Bundle.module`. **On current SwiftPM toolchains, `.process` on a `.metal` precompiles a single `default.metallib`** (and stops copying the raw source), so `makeDefaultLibrary(bundle: .module)` then succeeds — convenient for a fixed shader set, but a metallib holds only one compile, so it *can't* carry a device-conditional variant. That's why the `Shader*.metal` segments are **`.copy`** resources and `loadLibrary` source-compiles on a ray-tracing device (preferring the metallib only on non-RT GPUs). (Historically `swift run` did *not* auto-compile loose `.metal` — that was Xcode-build-system-only — but the toolchain caught up; don't assume `.process` leaves the source uncompiled.)
    - **A precompiled `default.metallib` shipped as a `.copy` resource loads fine.** `xcrun metal` + `xcrun metallib` produce a `default.metallib`; `.copy`-listed in the target, it's found by `makeDefaultLibrary(bundle: .module)`. So under `swift run` the path is a SwiftPM build-tool plugin that runs that compile and emits the metallib as a resource. (Playgrounds plugin support is unreliable — see the iOS follow-up — so keep runtime source compilation too; never go plugin-*only*.)
- **A user-supplied shader-library seam is cheap.** Resolve the active library as `customMetalLibrary ?? defaultMetalLibrary` so a user can drop in their own compiled library without touching the built-ins; pairs with the runtime-source loader for hot-reload. (Both peer Swift+Metal frameworks expose exactly this.)
- **Two texture samplers, and the split is load-bearing.** `imageSampler` (the effect chain, the image quads, the glyph atlas, the gradient strip) stays at `maxAnisotropy` 1: a screen-space pass reads one texel per pixel, so there is no footprint to resolve, and asking for one makes the sampler derive a level from a quad that a *per-pixel* early `return` has already broken. That read is undefined, and it made a plain lit box render *differently on every run* (~450 bytes at up to 12/255) on a scene with no picture in it at all. `surfaceSampler` (16x) is bound only by the textured-mesh draws, where the footprint is real; the `constexpr` tile/mirror wrap samplers in `ollin_sample_wrapped` carry the same settings or a *tiled* floor misses what a clamped one gets. Two rules follow: a pass that samples after a per-pixel `return`/`discard` names `level(0)`, and a uv the fragment marched for itself (parallax) reads through `gradient2d` of the *geometric* uv, never its own (or the silhouette moves).
- **Built-in shader functions are our own, written from the technique — not a vendored library.** As the shader set grows past drawing (noise, SDF primitives, blends, color-space conversions, domain repetition), implement each from the *published technique*, then credit that source in the `ATTRIBUTION.md` Techniques list (as the cosine `CosinePalette` and `curlNoise` already do). The canonical sources to reach for, baked in here so we go straight to them: **Inigo Quilez** for signed-distance functions (2D `iquilezles.org/articles/distfunctions2d`, 3D `/distfunctions`) and smooth-minimum, and the cosine palette (already used); **hg_sdf** (`mercury.sexy/hg_sdf`) for domain operators — axis rotation, mirror, and linear/polar repetition; **The Book of Shaders** for hashing and value noise. LYGIA is a broad *catalog/map* of which techniques exist and how they're approached — read it to discover, implement from the underlying technique, never translate its files (Prosperity; see [Sourcing & attribution](#sourcing--attribution-load-bearing--its-the-public-face)). (Distinct from the user-supplied seam above, which is for a *user's* own shaders, not for vendoring someone else's library into Ollin.)
- **Cache pipelines; don't grow `init`.** `MetalRenderer.init` builds one `MTLRenderPipelineState` inline. A new pipeline (textured quads, a new blend mode, compute) should be a cache lookup, not more code in the constructor. Key the cache on a `Hashable` descriptor struct (shader, blend mode, MSAA sample count, pixel format), not a flat enum: pipeline variants are *combinations* of those axes, and a struct key captures the product without an enum case per combination. Folding blend mode into that descriptor also keeps it a pipeline *parameter* — one pipeline factory — rather than a whole renderer subclass per blend mode (the trap a peer framework fell into).
- **The shader set is multiple `.metal` segments, concatenated at load.** It outgrew a single file at ~2,000 lines and split into `Renderer/Shader*.metal`: `OllinShaderLib` (the shared helper library — see *User-supplied shaders*), `ShaderCore` (preamble + shared color/dither/hash helpers), `ShaderShapes` (SDF primitives + the shared `ollin_sdf_distance`), `ShaderCombinator` (the SDF-combinator node VM — must follow `ShaderShapes`, it reuses `ollin_sdf_distance` + the coverage tail), `Shader3D` (particles/cloud/mesh/matcap/wireframe), `ShaderRaymarch` (the 3D SDF sphere-marcher — must follow `Shader3D`), `ShaderEffects` (present + the single-input filters + basic generators; `PresentOut` lives here for every later segment), `ShaderCombine` (two-input combines + the screen-space depth ops + the deferred RT-reflection passes), `ShaderSim` (the stateful ping-pong sims + fluid), `ShaderPatterns` (the design-pattern generators + design filters), `ShaderIBL` (the environment bake). `loadLibrary` reads them from `Bundle.module` in the fixed order `MetalRenderer.shaderSourceNames` and concatenates into one compile unit, because runtime `makeLibrary(source:)` has no include path (so an `#include` umbrella can't work). **Order is load-bearing:** `ShaderCore` is first because Metal needs a declaration before use and the later segments rely on its helpers; no segment is compilable alone, and the header `#include` lives once in `ShaderCore` for `composeShaderSource` to splice. Live shader reload (`SketchRunner.reloadShaderLibrary(fromDirectory:)`, used by OllinLive) concatenates the same segments from the repo filesystem via `MetalRenderer.concatenatedShaderSource(fromDirectory:)`. Adding a segment: create the file, add it to `shaderSourceNames` (in dependency order) and to the `Package.swift` `.copy` resources.

## Rendering performance

The drawing model is *immediate-mode GPU*: every frame `Drawer` records each primitive into call-ordered batches, the renderer uploads them through a **triple-buffered, semaphore-gated vertex-buffer ring**, and encodes one draw per batch run. (The ring is load-bearing — never collapse it back to one shared buffer: writing a buffer the GPU is still reading for an in-flight frame tears the geometry on screen, e.g. gaps in a stroked ring; a real bug, fixed by the `maxFramesInFlight` ring + `frameBoundary` semaphore in `MetalRenderer`.) This is the right shape — it's what NanoVG, Dear ImGui, and Processing's GL renderer do — so the "low-level" look is the cost of a Metal core, not accidental complexity. Don't trade it for Core Graphics / SwiftUI `Canvas` / SpriteKit: those are CPU rasterizers or retained-mode scene graphs, and adopting one as the substrate throws away the GPU + shader ceiling the whole vision rests on. **CPU tessellation is the first bottleneck, not the GPU** — and **instancing is the shipped answer** (the SDF quads, the point-cloud splats), with **retained batches** (`Batch`, its `CAPABILITIES.md` bullet) the shipped answer for static heavy content, and **GPU-driven culling** above them (`MeshField`, its own bullet). The two tiers past that were explored and answered rather than deferred: **indirect command buffers** are unusable for the lit mesh fragment on a ray-tracing device ("Fragment shader cannot be used with indirect command buffers" — the RT intersector in the fragment is the blocker), so GPU-written `MTLDrawPrimitivesIndirectArguments` carry the identical GPU-driven payload instead, and any future ICB use must run RT-free shaders (a depth-only pass is the natural fit); **mesh shaders** compile and build pipelines here, but Apple's guidance is to prefer draws wherever draws are faster, so a mesh-shader slice needs an A/B against instancing before it ships.

Mechanism and history live in [`ARCHITECTURE.md`](ARCHITECTURE.md) § *The 2D drawing paths*; the regression-preventing rules stay here:

- **SDF analytic primitives — shipped.** The closed 2D primitives (~30 shapes: point markers / circle / ellipse / rect / oriented box / circular arc / triangle / ngon / star / ring + the novelty catalog) each render as one instanced quad (`SDFInstance`, the `.sdf` pipeline) — per-shape CPU cost is one struct write, and each instance carries its own CTM so AA stays ~1px under any transform. `drawLine`/`drawBezier` moved to the **fringe stroke path** (their shader cases retained-but-unemitted); arbitrary `drawPolygon`/`drawPolyline` and elliptical/full-turn arcs stay on the triangle path (`drawArc` runtime-branches; its *stroke* goes to the fringe path either way). **Coverage is split by whether a shape tiles, and it's load-bearing:** box/pie/chord/triangle/star/ngon + the non-round markers use the **inside-biased** ramp (`regionCoverage` — full to the geometric edge, AA halo only outside) so abutting fills leave no seam — never move them onto the centered ramp; disks and capsules/lines use **area-conserving** coverage (`diskCoverage` — a sub-pixel mark keeps a ~1px footprint while its alpha scales by true area/width, so sizes run 0…n without popping or flicker); stroke **bands** conserve ink the same way (`strokeBandCoverage`; a band ≥~1px reduces to the plain smoothstep, byte-identical). **Draw order is preserved:** call-ordered `GeometryBatch`es (`.triangles`/`.sdf` runs) composite as drawn — never collapse into unordered passes (breaks occlusion, e.g. EllipseField's black-fill ropes). One non-discoverable rule: vesica/moon `cornerRadius` must `opRound` off a *full-footprint* SDF (the inset form loses all float precision — a real glitch). **Hollow/band mode** (`hollow(_:)` / `solid()`) onions every region shape's SDF (`SDFShape.honorsHollow` opts in); **stroke alignment** (`strokeAlign(_:)`) shifts the stroke band by an exact SDF offset riding bits 8-9 of the `shape` tag; `.center` is byte-identical. New shapes drop in as four touch-points under a fixed scalar budget — **`SDFInstance` is full at 144 bytes** (the next field is a real widening) and `size` doubles as the covering-quad AABB half-extent, never a free geometry slot; the forward shape list lives in `ROADMAP.md`, and SDF *operators* live on the combinator path.
- **MSAA is 8× where the device supports it** (else 4×), and only for the *triangle* path (the SDF and fringe paths carry analytic coverage). The sample count is chosen once via `ollinPreferredSampleCount(_:)` (`SketchView.swift`) and shared by the live view and the export paths.
- **Rendering is gamma-correct (linear-light).** Geometry composites into a **linear `rgba16Float` intermediate**; the present pass tone-maps, dithers (TPDF, a pure function of pixel position — reproducible), and re-encodes to the sRGB drawable — the single 8-bit quantization point. Three rules keep tones from shifting: shaders **linearize** their sRGB `Color` inputs; the **clear color is linearized too** (`Color.srgbToLinear` in `mtlClearColor` — miss it and the background washes out lighter, since the clear bypasses the shader); image textures load `.SRGB: true`. **One deliberate carve-out: stroke and disk/dot AA *coverage* is remapped to perceptual alpha** (`perceptualCoverage`) — pure linear blending reads a thin dark mark faint/"beaded" (the Molnár *Interruptions* bug) — touching **only partial coverage**, never a shape's own fill/stroke alpha, and **not** the region *fill* ramp (abutting fills must keep tiling seamlessly). The capsule/bézier AA footprint is the **L2 gradient length**, not `fwidth` (the L1 norm overshoots √2× at 45°, fading diagonals). Verified near-optimal for the raster path (4× SSAA barely beats it).
- **Fills triangulate, strokes fringe.** Concave/holed fills go through **vendored libtess2** (`Shape.triangulatedFill()`, per-`Shape` `winding` — `.evenOdd` default, font glyphs `.nonZero`; the glyph clean/simplify gotchas live under *Text* in `CAPABILITIES.md`) + MSAA; convex shapes keep the direct fan/strip math — don't route them through the triangulator. **Every stroke renders through the AGG/NanoVG-style fringe expander** (`appendFringeStroke`): CPU edge-expansion plus a ~1px screen-space AA fringe, honoring `strokeJoin`/`strokeCap` (`drawLine`'s default cap is now **butt**), the coverage riding an `aa` field in `OllinVertex`'s alignment padding (stride stays 32, the triangle path byte-identical), the fringe straddling the true edge so perceived width = `strokeWidth`. **The fringe is strokes-only — fills stay libtess2 + MSAA, byte-identical** (a fill fringe reintroduces abutting-fill seams or fattens; settled by a native-res A/B). A cross-section is **five points (outer/core/center/core/outer), and the centerline one is load-bearing**: every join fans from the path vertex, so without it that apex T-junctions into the middle of the core band's end edge and the sub-pixel-snapping hairline eats MSAA samples (isolated 6/8-coverage pixels inside solid ink; `FringeStrokeTests` pins it, no snapshot can — a few pixels in a million average away). Coverage is equal across the two core bands, so the split draws nothing new, and building each cross-section as a fixed `Cross` value rather than the old per-call `offsets(_:).map` arrays makes it a net **~10% faster** than before. **Consecutive segments end on their shared inner crossing** (the inner miter point, NanoVG's `chooseBevel` model, `innerMiter[v]` scaled so an offset stays the true distance to *both* centerlines): ending each on its own perpendicular makes both quads cover the wedge between them, and non-opaque ink composites it twice — a hard second-coat diamond at every corner (224 → 197 at alpha 0.25), a graded band down a curve's inner half, dark radial spokes combing a spiral. **Only the inner side moves** (the outer side keeps its perpendicular, so the join filler and the centerline seam are untouched), the covered region is *unchanged* for opaque strokes (the union already ended at that crossing → whole snapshot suite passed unrecorded), collinear vertices are skipped (a straight polyline is byte-identical), and a crossing outside either neighboring segment falls back to square ends (the inner-bevel case — an overlap beats a crack when the corner folds anyway). Triangle count and speed are unchanged. `FringeStrokeTests` pins it (a snapshot's mean diff averages it away). **Measure coverage in linear light** before reasoning about gap widths (the same pixel reads 46% in sRGB, 75% linear — the sRGB figure made the seam look impossible). `appendStrokedPath` is retained for **outline-glyph stroking only** and shares the rule via `Drawer.innerCrossings`, but its segments are plain quads with no centerline point, so bending the inner end moves the end edge off the path vertex and a filler fanning from there T-junctions (a **pale** comb, the mirror of the dark one): its filler fans from **the crossing itself** instead (free — the gap is bounded by both end edges, which run to that point; pixel-identical to splitting each segment at the centerline, which costs two triangles). `GlyphStrokeTests` pins both symptoms with AA-immune predicates (darker-than-coat / lighter-than-coat-with-ink-all-around, `InkProbe` in the test support; note the present pass **dithers**, so one coat straddles two 8-bit levels). The **elliptical/full-turn `drawArc` stroke** joined the fringe path too (it used to lay bare `appendSegment` quads with no joins or caps at all, so it carried *both* defects: inner overlap **and** outer gaps, together a fine faceting) — it hands the expander the same shapes `svgRecord` writes (`.open` polyline / `.chord` closed / `.pie` closed through the center), so raster and vector trace one outline, and it now honors `strokeCap`/`strokeJoin` (default `.butt` keeps the old ends). Curved outlines flatten through the public `Path` builder (`drawShape { }`, `drawCurve(_:closed:)`) into the same fill + stroke paths — a curve never touches the SDF side.

Pipelines build through the `PipelineKey`-keyed cache (`makePipeline(_:)`; the enum→`Hashable`-struct key migration shipped with the 3D work), so a new pipeline is a new cache key, not more `init` code — blend mode, MSAA count, and pixel format ride the key as parameters (see *Cache pipelines* above).

## Build, run, verify

```sh
swift run --package-path Examples Example-Basic-HelloCircle   # opens a window running an example
```

The canvas is `1080×1080` by default (`canvasSize`, the typed `CanvasSize` enum — `.square(n)` / `.size(w, h)` + named presets, integer pixels); the preview window is sized from the sketch's `windowMode` (`.auto` fits the screen, `.fixed`, or `.resizable`) — the window is a scaled view of the canvas, not the canvas itself.

- **Requires macOS 26+ and a Metal-capable GPU.**
- **Run tests through `Scripts/test.sh`.** `Scripts/test.sh <Suite>` for the area touched (seconds), `quick` for the sub-minute pass, bare for the whole suite — which runs many minutes, so background it with a long timeout, never as a plain foreground call. The full run is phased: the suites that want a device to themselves (`DataFeedTests` counts polls per elapsed second, `ListeningTests` waits on the speech stack, `SpatialVideoTests` on the hardware decoder — its readback has wedged rather than failed under load) go first on a quiet machine, and everything else runs after. Rerun a failure there alone before investigating, and report *which tests* failed rather than calling the suite red. **Never read the phasing as "a failure here is load"** — measured 2026-08-26, `OllinVisionTests` starved to 113 s *with the target running alone*, and `PushFeedTests` was frozen by its own helper parking all eight cooperative-pool threads. Phase 1 helps only a suite competing with *other targets* for a device; one that fails while running alone has a defect, and moving it here hides it. A timeout while the process burns 2% CPU is a parked thread pool, not a busy machine, and `sample <pid>` names the culprit in one shot. Two rules follow, both free: never park a concurrency worker on a semaphore (the pool is one thread per core), and poll `>=` on a counter rather than `==`, since a full run can hand a task back long after the thing it watches happened. Skip patterns are unanchored regexes over the full test ID: write `OllinTests.SnapshotTests`, never bare `SnapshotTests` (which also matches `PhysicsSnapshotTests` and silently drops 46 real tests). **`ScreenCaptureTests` needs the screen unlocked** — ScreenCaptureKit lists no displays and delivers no frames behind the lock screen, so the suite fails 5 tests there and passes in under a second when someone is logged in and awake (proven both ways in one session on 2026-08-26). That, not a stale permission grant, is what the long-standing "screen capture fails on this Mac" report was.
- **`Scripts/preflight.sh` before every commit.** It reads the diff and runs exactly the gates that apply (the figure probe on framework changes, `check-links` + `guide-coverage` on prose, `prose-lint` on touched Guide/Docs pages, the em-dash net), saying what it skipped and why. `--milestone` runs everything: the full test suite, the full `--no-probe` figure render, and `swift build --package-path Examples` — the examples anti-rot guard, since CI runs on pull requests only and mainline work goes straight to `main`.
- **Two sessions, one repo.** A second Claude/agent session works in a git worktree (its own checkout and `.build`), never the same checkout: a second SwiftPM invocation in one checkout *blocks* on the `.build` lock, which reads as a hang. While the other session is mid-build, don't run the full test suite (the load fires the wall-clock failures above) and never `OLLIN_RECORD_SNAPSHOTS` (it rewrites 242 tracked reference PNGs under them). Known cross-process collisions if two test runs overlap anyway: the Core MIDI loopback endpoints have fixed machine-global names, and `VideoExportTests`/`ExportMetadataTests`/`DataFeedTests` use fixed `$TMPDIR` paths.
- **The examples are their own package, in `Examples/`.** SwiftPM builds every target of a package and offers no way to scope a build to the tests and their dependencies (`--target` and `--product` are both refused alongside `--build-tests`), so 350 sketch executables in the root package would make every `swift test` link all of them: a cold run measures 7m23s / 13 GB that way against 1m30s / 1.7 GB split out. Add an example with a folder plus one `example(...)` line in `Examples/Package.swift`; run it with `cd Examples && swift run Example-X` or `swift run --package-path Examples Example-X`. Nothing reaches an example through its *target* — the gallery and the live hosts compile a sketch from its source file, finding modules from their own binary's location and resolving `Bundle.module` to the sketch's folder — so the targets serve only `swift run` and the compile-check build. A sketch needing the shared CPU↔GPU structs imports `COllinShaders`, now a product for exactly that reason.
- **`swift build --target Example-X` does not relink the executable.** It compiles the module and reports success, but the built binary stays the *old* one — a tuning loop against it silently re-runs stale code (a real hour lost: three "tuning" rounds of VideoTrace all ran the first build). Rebuild runnable examples with `swift build --package-path Examples --product Example-X` or just `swift run --package-path Examples Example-X`; reserve `--target` for compile-checking libraries.
- **Check the environment before claiming you can't build.** Ollin needs the Swift toolchain and Metal, which exist on a Mac but *not* in the Linux web/iPhone container. These two run on different machines, so don't assume: if `swift --version` and `xcrun --find metal` succeed, you're on a Mac with the toolchain — **build, run, and verify directly** (`swift build`, `swift run <Example>`), and don't add caveats about being unable to compile. Only when that toolchain is genuinely absent (the Linux container) are changes unverifiable on this machine — say so then, and not before. Either way, the things that truly need a simulator or device (iOS/visionOS/AR) stay unverifiable here regardless.

## Live reload — edit code, see it render (shipped via `OllinLive`)

The headline creative-coding feature, and it's built. `swift run OllinLive <path/to/Sketch.swift>` opens a window, watches the file, and on save recompiles *just that sketch* into a `.dylib` and hot-swaps it into the running loop — the window never closes. This is the Olive / canvas-sketch model (a persistent host owns the window; the sketch is the swappable unit), chosen over InjectionIII (needs an external app, finicky on the terminal `swift run` workflow Ollin lives in). Code in `Sources/OllinLive/` (`main`, `FileWatcher`, `LiveSession`, plus `--selftest`/`--watchtest` headless smoke tests); the reusable loader `SketchLoader` lives in the **`OllinRuntime`** library (shared with the examples gallery, kept *out* of the shipping `Ollin` framework); the runner-side swap is `SketchRunner.reload(to:)` in `SketchView.swift`.

The mechanism (module-path discovery, the factory shim, FSEvents flags, threading, the `@Param` plumbing) is in [`ARCHITECTURE.md`](ARCHITECTURE.md) § *Live reload and the live-coding hosts*; the rules that must survive:

- **`-undefined dynamic_lookup` against the host, not a dynamic Ollin product.** **A `.dynamic` product does not fix the two-copies problem** — SwiftPM still links the target statically into the executable, giving two `Sketch` copies and a failed cast (verified the hard way). The `-I` module dirs are **discovered, not assumed** (the classic and Xcode build layouts differ), vendored C targets' checked-in module maps under `External/` are collected too (else a loose sketch can't `import OllinPhysics`), and each load uses a unique `-module-name` so repeated reloads don't collide in the objc runtime.
- **FSEvents on the *directory*, never an fd watch** (editors save atomically — temp file + rename; the `UseCFTypes` flag is required or the path-array cast crashes), debounced ~150ms, dispatched by extension: `.swift` → recompile + swap; `.metal` → shader reload; image assets → re-run `setup()`.
- **A broken edit never kills the session:** recompiles run off the main thread (the window keeps drawing the old sketch), a compile error leaves the running sketch alone, and shader reloads build the new pipelines before committing.
- **State on reload: fresh restart by default; `--keep-clock` carries `time`/`frameCount` forward** so an animation's phase doesn't jump (instance state resets either way). `Sketch.onReload()` fires once after the post-reload setup, never on first launch. `reload(to:)` honors the *new* sketch's declared `canvasSize` for non-`.resizable` modes.
- **Keep `Sketch`/`draw()` `open`** (already true) — the dylib subclass must override them; never `final`.

Window title: `"Ollin - <SketchName>"` (plain hyphen, not a middot). @eaviles ruled out FPS-in-the-title (the oF idiom); live FPS lives in the hosts' inspector surfaces (the OllinLive and gallery sidebars; standalone, the detached ⌘/ panel), not the title bar.

**Single-file sketches — the `ollin` command (`Scripts/ollin`), shipped.** One loose `.swift` file is a whole sketch, run from any directory: `ollin <file.swift>` opens it in the live host (all flags pass through, so every export flag works on the loose file; `--installation` / `--calibrate` route instead to **`OllinRun`**, which compiles the file once and hands the sketch to `OllinApp.run` — the only path that reads a declared `Installation`, so it is how a loose file goes on a wall, and it reloads nothing by design), `ollin new [name]` writes an executable starter file (class named from the file name), `ollin install [dir]` symlinks the script onto PATH. **Load-bearing:** the script resolves the repo from its own symlink-resolved location and execs `swift run --package-path`, so a PATH symlink is the whole install and `git pull` self-heals on the next run — capture `${0:A}` at **top level** (inside a zsh function `$0` is the *function name*, a real bug) — and sketch paths are absolutized before handoff (the host process runs with the repo as its package, not the caller's cwd). **Hashbang:** `#!/usr/bin/env ollin` + `chmod +x` makes a sketch directly executable; `SketchLoader` neutralizes a leading `#!` to `//` **in place** (same length, so diagnostics keep exact line/column) and compiles from the work-dir copy, since swiftc allows a hashbang only in a main file — applies to `.file` *and* `.source` inputs (the live-coding editor buffer carries the line too). Pinned by two `--selftest` phases (hashbang renders; a broken hashbang sketch reports `Sketch.swift:5:`). `Docs/Tools/SingleFile.md`; the Guide's Ch 1 points at it.

**Project generator — `ollin new` + `ollin generate`, shipped.** A ready-to-run project from a few questions, over three targets: **`OllinProjects`** (the model and emitters, `Sources/OllinProjects/`), **`OllinNew`** (the CLI behind `ollin new`), and **`OllinProjectGenerator`** (the SwiftUI window). Three catalogs are the extensible axes: **`ProjectKind`** (`.singleFile` / `.macSketch` available; `.iOSApp` / `.visionOSApp` / `.screenSaver` / `.arEffect` **declared-but-gated**, each carrying the platform leg it waits on), **`ProjectTemplate`** (10 ready-made starting points, each a whole small sketch), and **`Capability`** (asset folders + satellite links, contributing an import, a manifest entry, a folder, and one commented starter line in `setup()`). **Load-bearing:** `OllinProjects` depends on **nothing, not even `Ollin`** (it only produces text), so it builds in ~1s and its tests are pure; the **plan/write split** (`ProjectGenerator.plan` is pure, `write` only puts planned files down) is what lets the window preview the exact file list and the tests assert without disk; `write` **refuses any file that already exists** rather than overwriting; a generated manifest points at the **framework's own path** (the CLI/window walk up from their binary to find it) since the framework is unpublished, with `--remote`/`--framework-path` the overrides; asset folders are **`.process`** (SwiftPM *flattens* a processed folder into the bundle root, which is what puts a dropped file within reach of `url(forResource:withExtension:)`, since Ollin's loaders pass no `subdirectory:`) while a `.metal` is a **flat `.copy`** file (a processed `.metal` compiles to a metallib, and a copied *folder* keeps its nesting) — so the per-folder placeholder note is named **after its folder, never README.md**, or two folders collide on one bundle name; `@main` is inserted **on the class**, under the template's doc comment; a template that declares its own `canvasSize` never gets a second one. The window is **three resizable columns** (stage takes the slack) built to the design review: **one sectioned source list** (Templates group + the examples' own two-level catalog, one filter matching group names too, selection scrolled into view), the **kind menu in the title bar** with the gated kinds under a divider (a roadmap in a menu reads as a roadmap; in the main flow it reads as a broken control), a **status line under the stage** (built-in-Ns vs from-cache), the **3D chain as a strip under the stage** laid along the constraint's own direction (Geometry → Finish → Extras, arrows, chips; a blocked chip names its cause and the blocker reports `blocks N` via `ThreeDRecipe.blocker(of:)`/`blocks(_:)`; the reason line sits **outside any scroll view**, which is how the old clipped-hover-text gap disappears), everything else behind one **Wire in** disclosure that still reports what the starting point brought, the **file list above the fold** with the no-overwrite guarantee under it, and the dated serial as the field's **placeholder rather than a value**. `OllinInspector.accent` (purple) is applied **where it means something** (list selection, chips, Create), never as a root `.tint`, which would color every neutral native control. It **previews a starting point by compiling and running it** through `SketchLoader` (the gallery's path, hence the satellite links + `-export_dynamic`), so one that stopped compiling shows up there. **Starting from an example** (`--from Group/Name`, the Examples tab) copies a maintained sketch instead of a template: the type is renamed by **whole-word** replacement (a sketch may name its own type inside itself), its `import`s decide the linked satellites, its sibling files are **copied** (`GeneratedFile.copiedFrom`) and declared `.copy`, and **the header comment travels verbatim** (for a ported or homage sketch that is where the credit lives). `ExampleSource.discover` compares **path components after resolving symlinks** (a `/var` temp dir walks out as `/private/var`, and a string-prefix test then matches nothing). **Dated serial names** (`ProjectNaming.nextSerial`) are the default when none is given: `Sketch<year><nnn>`, one past the highest already in the destination counting **both folders and `.swift` files**, the year passed in rather than read from a clock so it is testable. The window remembers the destination (`@AppStorage`) and re-suggests the next serial after each Create. **The 3D options surface `Docs/3D/Combining.md` as data** (`ThreeDOption`/`ThreeDRecipe`): each piece carries `requires`/`conflicts` plus the one-sentence `rule`, and the rules are a **hierarchy, not a flat set** (geometry is never blocked and `settle()` fixes the finish and extras under it; a finish is blocked by its geometry; an extra by either) which is what keeps the panel navigable rather than refusing the first click; `ThreeDSource` writes the sketch from the recipe, and **`everyValidThreeDRecipeCompiles` compiles every combination the rules permit** (a rule that allows something uncompilable is the worst failure here, since the window would offer it). **The build test is the load-bearing one** (`GeneratedProjectBuildTests`): all 10 templates compile as targets of one generated package (one framework build), plus one full generated project built end to end; it caught three real template defects on its first run (`Insets` takes a literal not a computed `Double`, `Rectangle` has no `maxX`/`maxY`). `Scripts/ollin new` routes to `OllinNew` (a `.swift` name still writes one loose file, unchanged), `ollin generate` opens the window. **Joining an existing package** (`ProjectKind.inPackage` + `PackageHost`) is the one path that *changes* a file rather than only creating them, so it is deliberately timid: it refuses a host that does not already depend on Ollin (a target added there could not import the framework), inserts one target by **matching the `targets:` array's own brackets** (never the first `]`, which would land inside a target's `dependencies:`), preserves the closing line's indentation by inserting after the last entry rather than before the bracket, and when it cannot read the list confidently it **writes the sketch and hands the stanza over to be pasted** instead of guessing. `GeneratedEdit` carries the whole new text (worked out at plan time so the window shows it first) and edits apply **after** the new files. The CLI and the window both default to it whenever the destination sits inside such a package, since a folder of sketches is one package with a target each (the framework then builds once for all of them). **Gotcha:** `relativePath(of:)` compares twice, because symlink resolution only applies to path components that *exist*, so a folder about to be created keeps a `/private` prefix its own parent has already lost and a single comparison silently yields an empty `path:`. **Two catalogs grow by different rules, and the difference is load-bearing:** the **examples list is discovered** (`ExampleSource.discover` walks `Examples/` for `Sketch.swift` at launch), so a new example appears with no generator change, and an example's `import` lines are read as the **union** with the capability catalog, never filtered by it (a filter drops a satellite that has no `Capability` entry yet, and since the `import` is copied verbatim the new project then fails to build; `unknownSatellitesSurvive` pins it). The **3D catalog is hand-kept** (`ThreeDOption.all` + `ThreeDSource`'s fragments), mirroring `Docs/3D/Combining.md`: **a 3D capability that changes what combines updates that page AND this catalog**, the same hand-sync rule `ollin_sdf_distance` carries, and `everyValidThreeDRecipeCompiles` then covers the new combinations automatically. `ProjectGeneratorTests` (19) + `ExampleAndNamingTests` (12) + `ThreeDRecipeTests` (7) + `PackageHostTests` (8) + `GeneratedProjectBuildTests` (3); no pixel snapshot (the output is files). `Docs/Tools/ProjectGenerator.md`; Guide Ch 1 § *When one file isn't enough*.

**Bringing a GLSL shader over — `ollin new --from-shader`, shipped.** A pasted fragment shader translated to Metal and handed over as a project (`Sources/OllinProjects/GLSL/`: `GLSLLexer` / `GLSLFunctions` / `GLSLTranslator` / `GLSLCompat` / `ShaderImport` / `ImportedShaderSource`, plus `ShaderSourceReader` on the CLI side). The shape read is the common web one — `mainImage(out vec4, in vec2)` over the `iTime`/`iResolution`/`iMouse`/`iFrame`/`iChannel0-3` values a site supplies — mapped onto Ollin's shipped `shade(uv, info)`; **how many channels it reads decides the routing** (0 generator / 1 filter / 2 combine, the user-shader path's own rule), so no new render plumbing exists. **Load-bearing:** it is a **lexer plus token rewriter, never a parser and never regex** (a full grammar is far more to keep right than the rules need; blind substitution is the thrash trap), and **every edit replaces the text of a token already there — nothing is inserted or removed** — which is what keeps a pass's indices valid for the next one *and* preserves the author's spacing, blank lines, and comments (the property that makes the output editable source rather than machine output; `theAuthorsLayoutAndCommentsSurvive` pins it); a token carries its **original bracket in a field beside its text** (`GLSLToken.bracket`) so a rule may hang a whole argument off a `)` or turn a `(` into a `{` and every later structural walk still reads the shape the author wrote — matching on text broke exactly this and cost two defects; an emptied token stops counting (`hasText`), or a blanked `precision …;` swallows the statement after it and mis-attributes its line. **`mod` is the one rule that silently changes a picture rather than failing to build** (GLSL floors the quotient, Metal's `fmod` truncates, so they disagree for negative operands — the ordinary case when tiling a plane reaching left of the origin): the flooring form is written out as `ollin_glsl_mod`, never the built-in, **measured at max 255 / mean 63.65 over 576k pixels on a tiled ramp** — and note a `sin`/`cos` tile spanning exactly one period **cannot see the difference**, so a counterfactual probe must not go through one (the first one did and read inert). A **layer read turns the coordinate over** (a texture is measured from its bottom edge, an Ollin layer from its top) or every imported filter arrives upside down; **`info` travels as a parameter only as far as it is needed** (a supplied value is a global in GLSL and cannot be one in Metal, so a call-graph closure adds it to the functions that read one and the functions that call those, leaving pure sdf/noise helpers untouched); alpha is **held at 1** (the source site shows every pixel opaque, so that is what reproduces the look). **Nothing is dropped in silence** — what cannot be carried lands in the file as `NOTE(ollin)` / `TODO(ollin)` and prints before anything is written (several passes, >2 channels, a self-declared texture, a *written* file-scope global (a `const` one becomes `constant`), `texelFetch`, `iDate`/`iSampleRate`, the mouse button, a 4x4 inverse). A plain `main` with `gl_FragCoord`/`gl_FragColor` or a declared `out` is reshaped into the same form. **License hygiene is the point, not a footnote:** nothing is bundled, the emitted header carries title/author/URL and says the terms travel with it, and a URL is fetched only through the site's own API with the user's own `SHADERTOY_API_KEY`. A `.macSketch`/`.inPackage` project keeps the shader as a **flat `.copy` `imported.metal`** (a processed `.metal` compiles to a metallib — the shipped rule) so it hot-reloads with no swiftc pass; **a single loose file carries it inline in a raw `#"""` literal** (no target to declare a resource on, and a raw literal keeps a backslash a backslash). `ShaderImportTests` (17) + `ImportedShaderProjectTests` (4) in `OllinProjectsTests` (pure), and **`ShaderImportRenderTests` (11) in `OllinTests` compiles every claimed shape through `composeUserShaderSource` + `makeLibrary` on the real device** — a rewrite that merely looks right is worth nothing (this is why `OllinTests` now depends on `OllinProjects`). No pixel snapshot (the output is files). `Docs/Tools/ShaderImport.md`; Guide Ch 17 § *Somebody else's shader*.

**Bringing a 3D scene over — `ollin new --from-scene`, shipped.** A glTF or USD scene written out as the sketch that draws it (`Sources/OllinProjects/Scene/`: `ImportedScene` + `ImportedSceneSource`; the reader in the new `OllinSceneImport` target; `ScenePlacement.swift` in the core). **The split is the design: structure becomes source, geometry stays in the file.** The camera prints as a `Camera3D` with its own numbers, each light as its own factory, and each node as a `withState` block of the moves that put it where the file put it, **nested as the file nests** (so a group still turns as one thing) — while the sketch reads the file once for its meshes and places them itself through a generated `drawPart(_:)`, because a mesh is not something a person edits as text. **Load-bearing:** `OllinProjects` still **depends on nothing**, so the reader is its own tiny target (`Ollin` + `OllinProjects`) that both faces of the generator share, and `ImportedScene` carries plain numbers, never framework types; the placement split is `SceneNode.placement` (**package**, `Sources/Ollin/3D/ScenePlacement.swift`) reusing the shipped **`Scene.decomposeTRS`** rather than a second decomposition, and it **reports `isExact == false`** by recomposing and comparing, so a shear is said rather than silently mis-drawn; the **emitted walk and the generator's naming walk must agree** (each node before its children), which is why the part names are **written into the sketch as a literal list** rather than re-derived at runtime (a repeated or blank name still gets its own key); a move under 0.00005 is **not printed** (it would print as a call that does nothing), an **axis-aligned turn reads as `rotateX/Y/Z`** (with the negative axis flipping the angle), and `scale` always takes the **three-argument form** (the one-argument one is the 2D call and would leave z alone). **`withState` saves `modelMatrix`**, which is what makes the nested blocks reproduce `drawScene`'s own composition exactly. What cannot come over is **noted per node where it happens** (a mesh wearing several materials draws in the first; a shear) and per scene in the header (animation, skins, blend shapes, and that **materials ride their meshes**, which is why no `fill` is emitted). A scene with no geometry needs **no file at all**. Verified against `drawScene` on the bundled `LoadedScene`: identical but for the one multi-material slab, which is the documented loss. `SceneSourceTests` (13, pure) + `SceneImportTests` (11, against the loader; the placement probe **verified red by sabotage**, naming the node it moved) + a `GeneratedProjectBuildTests` case compiling every light kind and both projections (which caught three wrong argument labels). No pixel snapshot (the output is files). `Docs/Tools/SceneImport.md`; Guide Ch 22 § *A scene you can take apart* + the SceneAsSource figure.

**Writing an extension — `ollin new --kind extension`, shipped.** The third-party tier's *convention* half: a library other sketches import, named `ollinx-<thing>` with the module `Ollinx<Thing>` (`ExtensionNaming`, a capital run staying one word — `SVGTools` → `ollinx-svg-tools`), written by `planExtension` over the new **`ExtensionSeam`** catalog (`Sources/OllinProjects/ExtensionSeam.swift`, the data-not-a-code-path shape the kinds and templates already use). Four `--seam` starters, each a worked file plus real tests plus a publishing checklist: a drawing call on `Sketch`, a `Shader` wrapped as a `Filter`, a `FrameSource`, a `SketchExtension`. **Two surface facts run the other way from what the design note assumed, and they are why the Docs page exists rather than a one-liner:** `Drawer` is **internal** (so an extension extends `Sketch` and the public value types, and reaches the GPU through a `Shader` — this file's own architecture rule says "public, typed core" and names the `Drawer`, which is looser than the code; **@eaviles has not ruled on opening it or rewording the rule**), and `Filter`/`Generator`/`Sim`/`Combine` are structs with **no public initializer**, so the effect catalogs take no new cases and `.shader(_:)` is the one way into the render graph (`Filter.Kind` and `Shader.params` are internal too, so an extension can *build* a filter and never *read one back*, which is what its tests can and cannot check). **Load-bearing:** the kind **bypasses `template.fits(_:)` before the switch** (a template's fit is about sketches, and asking would refuse a good library) and the CLI **refuses every sketch-shaped flag** (`--template`/`--from`/`--3d`/`--canvas`/`--with`) rather than writing a package where they went nowhere; a seam's shader constant is emitted **internal, never `private`** (`@testable import` reaches internal and never private, so a `private let` makes the generated test fail to compile); the **generator window filters the kind out** (`offeredKinds`) because it previews a starting point by compiling and *running* it, and a library has nothing to run (a stage that shows source is the follow-up, in ROADMAP). Discovery — a curated index, DocC, a Swift Package Index listing — **waits on the repository being public** and stays in ROADMAP naming what it waits on. `everyExtensionSeamCompiles` builds all four seams **and their tests** in one package, `aGeneratedExtensionPackageBuilds` runs `swift test` on a real emitted package, plus `ExtensionProjectTests` (10 pure, the manifest-shape and placeholder-survival sabotages verified red); no pixel snapshot (the output is files). `Docs/Tools/Extensions.md`; Guide Ch 31 § *Giving it to somebody else* + the ExtensionShape figure.

**GUI / parameter knobs — shipped, typed.** The generic `@Param` wrapper/registry in the core (`Param.swift`) drives the shared inspector (`Inspector.swift`) in all three hosts; **the control follows the property's type** — `Double` slider / `Int` stepper / `Bool` toggle / `ParamOption` enum menu / `Color` well / `Vector2` fields (+ `style: .pad`) / `Vector3` / `Rectangle` / `Insets` / `ClosedRange<Double>` two-thumb slider / `String` field / `style: .segmented` / the **`ParamChoices`** named-catalog menu — through the type-erased `AnyParam` / `ParamControl` surface, so hosts never touch `Param<Value>`; `ParamValue` is public, so a user type can conform by mapping onto an existing control kind (no custom rows). `icon:` / `group:` decorate rows into titled group cards; numeric value boxes scrub (Option fine, Shift coarse, click to type). Rules: `ParamChoices` needs `Equatable` to find the current selection (why `Easing`, a closure wrapper, stays out; `LightingPreset` and `Material` conform — the latter puts the whole curated finish library on the menu, while the parameterized `Material` helpers (`.glass(...)`, `.metal(...)`, `.skin(radius:)`) stay off it, since a menu needs fixed values); knob values persist across reloads as `ParamStored` payloads (`syncParams`; a property that changed *type* drops its stale value so the new default wins); OSC/MIDI bind to `Param<Double>`, and smoothing stays Double-only. The SwiftUI layout gotchas (the scrub-pill `.fixedSize()`, the segmented ViewThatFits wrap) are in ARCHITECTURE.md. Headless gates: `OllinLive --paramtest` + `ParamTests`.

**Performance stats — a shared `FrameStats` feeding every host surface.** The runner fills one `FrameStats` (`@Observable`: fps, CPU frame time, draw counts, clock, canvas size) via the built-in `StatsExtension` on the extend seam; the OllinLive sidebar, the gallery's right sidebar, and — standalone — a detached frosted `NSPanel` (⌘/ via `OllinHUDCommands`) read it. A host with its own inspector sidebar opts the panel off (`SketchView(showsInspectorPanel: false)`) and omits `OllinHUDCommands`. Stats are *debug chrome, not in-canvas drawing* — SwiftUI siblings of the Metal view, so they never land in exports. Gotcha: the CPU-ms must time `performDraw()` *alone* — timing across `renderer.render()` includes the triple-buffer semaphore (vsync) wait and pins to ~1/fps, telling you nothing. `SketchView` `ZStack`s host chrome over a private `MetalCanvas` — the `NSViewRepresentable` MTKView, still the AppKit/UIKit-portability seam.

**Live coding — the performance host (shipped via `OllinLiveCoding`).** `swift run OllinLiveCoding [Sketch.swift]` (release wrapper `Scripts/OllinLiveCoding`) is the on-stage instrument: one window, the sketch letterboxed on a black stage, the code over it as translucent text (per-glyph backdrop strips, not a panel), ⌘↩ compiles the editor buffer and hot-swaps mid-motion (`keepClock` **on by default**; ⌘⇧↩ evaluates fresh), ⌘S is the only thing that writes the `.swift` (evaluate never saves; a crash-recovery autosave rides every evaluation). Load-bearing invariants, cheap to forget:

- **The shared engine lives in `OllinRuntime.SketchSession`** (supersede-cancel compile scheduling, `syncParams` re-applied *before* the swap so knobs never snap, the two-channel Swift-vs-shader error model where neither clears the other); `LiveSession` and `PerformanceSession` are thin wrappers over it — orchestration changes go in `SketchSession`, never re-forked per host.
- **Buffer compiles** write the editor text into the per-compile work dir *under the sketch's own file name* (diagnostics carry exact buffer lines and match by `fileName` — never by path, it's the temp copy), while the factory shim's `Bundle.module` keeps pointing at the sketch's *real* folder so co-located assets resolve. An untitled buffer compiles as a stand-in path under Application Support; save first if the sketch needs assets.
- **Letterbox at the SwiftUI layer only** (`.aspectRatio(_, contentMode: .fit)` around `SketchView`): the canvas view stretches to its frame and maps the mouse by bounds, so the aspect-fit frame is what keeps rendering *and* mouse coordinates exact.
- **No `.windowResizability(.contentSize)` here** (unlike the sibling hosts): fullscreen is the projection mode (`.fullScreenPrimary` via `WindowCustomizer`), the stage flexes, and status/error UI are *stage overlays* (chip, evaluated toast, diagnostics strip) because fullscreen hides the title bar. The error strip never dims the stage — the last good sketch keeps playing through a typo.
- **Editor rules:** the `NSTextView` owns the buffer (never mirror it into SwiftUI state); hide-code (⌃⇧H) is `.opacity` + hit-testing, never a structural `if` (that destroys the buffer and undo stack); every automatic substitution is off (a smart quote is a silent compile break); `keyboardFocus: .onClick` so the editor keeps the keys, and a canvas click intentionally hands them to the sketch.
- **Recovery is scoped to its document** (`recovery-origin` beside `recovery.swift`): an untitled buffer's net must never offer itself over an opened file (a real early miss — restoring replaced an opened sketch with old untitled work).
- Headless gates: `--selftest` (buffer compile → render → edit → differ, plus line-accurate diagnostic parsing; asserts the buffer path never writes the file) and `--sessiontest` (param carry, edited defaults, supersede semantics — the extraction's regression net for both hosts).

## Roadmap & design notes

Planned, in-progress, and eventual work is documented outside this file so the always-loaded guidance stays small:

- [`ROADMAP.md`](ROADMAP.md) — the public, contributor-facing roadmap: what's planned and how to help.
- [`DESIGN-NOTES.md`](DESIGN-NOTES.md) — the engineering design intent behind each planned item (the approach, the APIs involved, the reasoning).

**When work ships, it leaves these two files.** Drop it from `ROADMAP.md` (the roadmap stays forward-looking — what's *planned*, not a changelog) and record it instead in [`CAPABILITIES.md`](CAPABILITIES.md). Remove it from `DESIGN-NOTES.md` too, unless its design rationale still guides future maintenance or evolution (e.g. the conventions for extending the examples set), in which case keep only that part, not the status narration. Anything fully done and self-contained belongs in its own `Docs/` page or this file — not the roadmap, not the design notes.

**No status words in `ROADMAP.md` / `DESIGN-NOTES.md`.** They describe only what's *ahead*: never write "X landed / shipped / done" or a changelog aside into either file — a reader shouldn't be able to tell from them what shipped yesterday versus a year ago. When the shipped thing is one entry in a still-open *umbrella* item (the SDF shape catalog, a family of helpers), **drop just that entry and keep the umbrella** — don't annotate it as landed. (The `drawTriangle` commit got this wrong: it rewrote the catalog bullet to announce the triangle "has landed" instead of silently dropping it — the exact narration this rule forbids.) The ship checklist, every time something lands: **(1)** add it to [`CAPABILITIES.md`](CAPABILITIES.md) — a terse bullet under the area it belongs to, never a per-feature paragraph in this file; **(2)** remove it from `ROADMAP.md` (drop the entry; for an umbrella, the sub-entry only) with no "landed" note — and the README's Roadmap section is a short pointer with a one-line "what's ahead" list, so drop the item there too if it's named; **(3)** strip it from `DESIGN-NOTES.md`, keeping only rationale that still guides future work; **(4)** if it adds user-facing API, give it a `Docs/` page *and* wire it into both indexes in the *same* commit — `Docs/README.md` (the flat annotated index, one grouped entry per page) and the README, which links **by capability** through its *What's in it* catalog table, so a new page joins the table row it belongs to (or the short "good places to start" list) rather than a flat enumeration. **The invariant is that every `Docs/` page stays reachable from the README** — it broke once when that flat list was slimmed and orphaned 21 pages; `Scripts/check-links.sh` now enforces it (both indexes, plus every Docs link and anchor), so run that rather than eyeballing. A commit that introduces a public concept but leaves `Docs/` untouched is missing its page; purely internal changes (a refactor, a renderer tweak) skip this and live only in `CAPABILITIES.md`; **(5)** if it adds a user-facing capability, **teach it in the Guide, don't just list it** — give it a row in the feature-coverage matrix (`Guide/PLAN.md`) naming its chapter home, clear its parking-lot entry, and get the row to at least **`shown`** (a chapter mention plus a worked example) *in this commit*, with `taught` (a section plus a figure) the goal. A row left at `pointed` is Guide debt and needs an entry in the ledger in `Guide/PLAN.md` naming the chapter that owes it, called out in the commit message. **`Scripts/guide-coverage.sh` is the gate** (it fails on a `pointed` row with no debt entry, a Docs page with no row, and a page unreachable from a numbered chapter); the rationale and the authoring workflow live in `Guide/AUTHORING.md` § *Coverage*. Its sibling **`Scripts/check-links.sh`** (formerly guide-links.sh) gates *navigation repo-wide* — the Guide, every `Docs/` page, the root README, and the `Examples/` lists (links, anchors, images and their orphans, the footer chain, the contents and status listings, Docs reachability from both indexes, every example listed in the README that covers it, and every chapter pointer — including the `Guide Ch N § *Heading*` form in this file and `CAPABILITIES.md`, where a heading that no longer exists is the failure mode a renumber leaves behind); `Scripts/guide-renumber.sh` moves chapters and rewrites all of that in one pass. A row marked `pointed` used to satisfy this step outright, which is how seven slices shipped un-taught while audits stayed green. **A renderer change moves Guide figures even when the diff never touches `Guide/`** — run `Scripts/guide-figures.sh` after any change to the drawing paths and commit the re-renders with it, or the next Guide-touching commit inherits unexplained churn (the stroke-join work moved 79 figures by a sub-perceptual ~2/255 at their joins, invisible to the snapshot suite's mean-diff tolerance but real pixel movement, which is exactly what the gate compares — encoder-byte differences with identical pixels no longer count as movement and no longer rewrite images). Do all of this only once the work is actually verified (built and run) — don't pre-narrate unbuilt work as shipped.

Both live at the repo root, alongside `README.md`. The convention: the root holds project meta and contributor docs (`README.md`, [`CAPABILITIES.md`](CAPABILITIES.md), `ROADMAP.md`, `DESIGN-NOTES.md`, [`ARCHITECTURE.md`](ARCHITECTURE.md), `AGENTS.md`, this file, `LICENSE`, `ATTRIBUTION.md`, `THIRD-PARTY-NOTICES.md`), while [`Docs/`](Docs/) is the user-facing API reference (`Sketch`, `Drawing`, `Color`, …) plus `Docs/Tools/` for the user-facing host-app guides (live coding) — and nothing else. The third doc tree is [`Guide/`](Guide/), the narrative book: a practical creative-coding guide taught through Ollin, written chapter-by-chapter across sessions. Its authoring charter is `Guide/AUTHORING.md`, its chapter queue + briefs + feature-coverage matrix `Guide/PLAN.md`, its figures rendered/verified by `Scripts/guide-figures.sh` — guide facts route there, not here. `CAPABILITIES.md` is the shipped-capability inventory (*what* exists and each capability's load-bearing invariants — the one place per-feature status belongs, and the reason this file stays small enough to load every turn); `ARCHITECTURE.md` is the contributor-facing engineering-internals doc (the *how* and *why* of shipped systems, the home for depth that would otherwise bloat either); `DESIGN-NOTES.md`/`ROADMAP.md` stay forward-looking, `Docs/` stays user-facing, so `ARCHITECTURE.md` is the one place shipped internals belong. Keep these at the root (don't fold them into a `Notes/`-style folder): several are auto-discovered or front-page (`README`/`LICENSE`/`CLAUDE.md`/`AGENTS.md`), and `ARCHITECTURE.md` wants root-level discoverability by convention.
